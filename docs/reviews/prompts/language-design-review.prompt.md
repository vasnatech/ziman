## What to evaluate (be specific, cite file:line or doc section, and give concrete code examples that show the problem)
1. Language design coherence: the type system (static types, generics with explicit type arguments, Option/Result as builtin-with-autowrap, enums and `switch`, the `?` operator and its restrictions, named arguments and Option-parameter omission, variadics, lambdas/closures capturing immutably, `with` expressions, the `unit` type, no methods / free functions only, the module system with flat names, `use` forms, global `val`, derive(Json/Row/Properties/Ord), pattern-binding `if Some(x) = e && ...`). Which choices are principled and consistent, which are surprising, inconsistent, or will hurt as programs grow? Look for special cases, cliffs, and restrictions that feel accidental.
2. Semantics and safety: value semantics, immutability, the concurrency model (spawn/channels), the memory model (Boehm GC), the error-handling story, integer overflow behaviour, the string/byte model, equality/hash/ordering rules. Any soundness holes or gotchas you can demonstrate by experiment? Try deep recursion, threaded use of every mutable-looking type, numeric edge cases, a runtime error inside a spawned thread.
3. Standard library design: API consistency across modules (naming, argument order, Result/Option usage, error types, `Ok(unit)` vs values), layering (prelude vs core vs db vs http), what is missing that a real backend language needs, what is over-engineered. Look at lib/core/json.zm, collections.zm, fs.zm, net.zm, log.zm, jwt.zm, crypto.zm, otp.zm, lib/db/datasource.zm, migrate.zm, lib/http/server.zm and client.zm, lib/time/time.zm. Note duplication, leaky abstractions, footguns, and performance traps (O(n) operations hidden behind simple names, immutable arrays copying).
4. Implementation quality: interpreter architecture, typechecker structure, error messages (try several deliberately wrong programs and judge the messages), tooling (formatter, LSP, lint, test conventions), documentation quality and whether docs match behaviour (find doc/behaviour mismatches by experiment).
5. Comparison and positioning: how does Ziman compare with the languages it resembles for its target use (a small typed language for writing backends)? What are its best ideas worth keeping and its biggest risks? What would you change first if you owned it? Give a prioritised list (P0/P1/P2) of concrete recommendations, each with rationale and rough effort (S = a day or less, M = a few days, L = a week or more).
