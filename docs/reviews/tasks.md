# Tasks from the 2026-09-26 reviews

The two reviews merged and de-duplicated: [language-design-review.md](language-design-review.md) (**L**) and [developer-experience-code-review.md](developer-experience-code-review.md) (**D**). Items refer to the reports' own numbering (`L P0-1` is the language review's recommendation P0-1, `D B4` the developer review's bug B4, `D item 9` its action-list item 9, `D S1` its security issue S1).

Effort: **S** = a day or less, **M** = a few days, **L** = a week or more. Tick a box when the task is done; note the commit beside it.

Suggested order: A and B first (B1, B2, B4 and B5 are each about a day or less, and the web client depends on some of them), then C1, C2 and D1, which remove the most everyday friction, then E.

## A. Ziman runtime and safety (P0)

- [x] **A1** Stack-depth guard: a clean "stack depth exceeded" error instead of a segfault, from a per-thread limit read at run time (`src/stack.c`); the main interpreter thread and each `spawn` run on stacks sized from usable memory, thread count and `--stack-mb`/`--thread-stack-mb`/`--threads` (or the `ZIMAN_*` variables); parser, checker and deep values are guarded too. (L P0-1, D B4; S-M)
- [x] **A2** Fatal-error boundary per thread and per request: a runtime error in a spawned thread ends that thread (logged to stderr, its defers run) and the process stays up; `spawn f(x) on_error handler` chooses another response per spawn (`os.fatal` keeps the old exit); `server.serve` answers 500 and releases the connection. (L P0-4, D B5; M)
- [x] **A3** Builders stay in their thread (chosen over locking): `#[thread_bound]` marks the type; compile errors for a `Channel` element, a `spawn` argument and a module-level `val`; a runtime owner check on every builder operation; docs corrected. `Iter<T>` is thread-bound too. (L P0-2; S)
- [x] **A4** Numeric holes: range-check int literals (including the negated minimum), saturate `float as int`, convert `float as bigint` exactly, reject `%` on floats in the checker. (L P0-3, D B6; S)
- [x] **A5** Fix the prelude namespace leak: a user struct named `T`, `K`, `V`, `R` or `U` fails to compile and the error names no file. (L P0-5; S-M)
- [x] **A6** Make `arr = push(arr, x)` amortised O(1) (200,000 pushes: 8.5 s, against 0.23 s with `ArrayBuilder`). (L P0-6, D; M). `push` shares spare capacity through a tip check (`ArrayStore`, CAS on `used`); 200,000 pushes: 0.2 s. `--lint` flags the still-quadratic `x = concat(x, ..)` and `x = concat_arrays(x, ..)` in a loop.

## C. Ziman language ergonomics (P1)

- [x] **C3** Infer generic type arguments from arguments (591 explicit generic calls in the backend). (L P1-3; M-L). Part 1 done: infer from plain arguments and named function references (`identity(5)`); part 2 (an unannotated lambda argument) still to do.

- [x] **C7** Better errors: source excerpt and caret, always the file name, stack frames, sorted by position, no cascades. (L P1-12, D item 15; M). ## F. Longer term and documentation (P2)

- [x] **F1** Decide the traits stance (a function-typed bound would unify `_compare`, `_to_json` and `_from_row`). (L P2-2; L) Decided 2026-09-28, no code change: still no general trait/interface system (coherence/orphan rules, supertraits and dynamic dispatch it would need are exactly the class-hierarchy complexity Principle 1 already rejected, and no concrete program needs one). `Eq`/`Hash`/`Ord` are named for what they already are -- a closed, compiler-known "function-typed bound," a fixed signature resolved by the type's own name -- and the list grows by one, `Row`, on the strength of a concrete pain point E9 hit: `Crud<E, Req, Res>` has to plumb `from_row`/`to_params` through every literal as explicit function-value fields because `E: Row` cannot be expressed as a bound. `Json` deliberately stays out (no generic-over-Json function exists anywhere in the library or the reference backend to justify it). `?`'s error conversion (P1-2) needed no part of this: `#[from]` (C2, done) already solved it a different way. See DESIGN.md "The traits/interfaces stance"; the `Row` bound's actual implementation is deferred and tracked in ROADMAP.md's "Larger, needs its own design pass".
- [ ] **F2** Interpreter speed: resolve identifiers to slots or compile to closures (a loop is about 28 times slower than CPython; 500-650 requests per second that does not scale with clients). (L P2-1, D; L) Diagnosed 2026-09-28, not fixed: this is two separate problems, not one. The "does not scale with clients" half is the Boehm collector, not the connection pool the developer review also suspected -- `tests/bench/server_concurrency.sh` (new) shows the collector build flat-to-declining across concurrency (347/584/429/361 req/s at c=1/4/8/16) while a `make nogc` build of the same code climbs the whole way (500/1319/1711/2552), 7x faster at c=16; a real multi-connection pool (file-backed SQLite instead of `:memory:`) made no difference, ruling that suspect out. See DESIGN.md "The collector, not the connection pool...". The raw-speed half (28x slower than CPython, `strcmp` identifier lookup) is untouched by this finding and still needs slot resolution or closures/bytecode, independently of whatever the collector ends up costing under concurrency. A tuning pass (same day): a bigger initial heap is a free 30-80% win at every concurrency level with no rebuild (`GC_INITIAL_HEAP_SIZE=512M`), more marker threads add nothing on top of it, and incremental mode is not just slower but catastrophic under concurrent load (~8x, reject it) -- but no configuration closes the gap to `ziman-nogc` (still 4.8x at c=16 even with the best config found), so this needs either less per-request allocation or the deeper memory-reclamation redesign already on the roadmap, not more tuning.
