# F360 — flattening the curves in C, and why it was reverted

2026-11-27. `tests/stdlib/shape_test.zm` is what shipped; the implementation is not here.

Asked for directly: *"flatten the curves in C."* It was built, it was exact, and it was **reverted
because the measurement that motivated it was wrong.** This file is the record of that, because a
reverted change that is not written down is a change somebody makes again.

## Why it looked like the right target

A per-phase clock inside `fill_shape` put `edges_of` — which turns a path into the edge list a
scanline fill walks, and runs for every filled shape of every frame — at **43-128 ms of a 262 ms
paint**, over about a hundred fills. That was the largest single item in painting, and the
mechanism was plain: flattening allocates a `Point` per vertex and six more per subdivision step,
plus a `[Point]` per polyline, and then `edges_of` walks all of it again to turn it back into pairs
of numbers.

## What was built

`src/native_shape.c`: the adaptive subdivider transcribed to C — the six midpoints in their order,
both branches of the flatness test, `abs_of`'s `v < 0 ? -v : v` rather than `fabs`, and the run
rules. The path crossed as a flat `[float]`, a tag and its coordinates per segment, as every other
native here takes structured input. `shape.flat_outline` returned runs of bare numbers;
`shape.flattened` was rebuilt on it so there was still one subdivider; `raster.edges_of` read the
numbers directly.

It was **byte-identical on all six graphics fixtures**, including `graphics_stroke.zm`, which
prints the actual polylines a rectangle and a circle flatten to.

## Why it went

`tests/bench/ui_frame.zm`, eight alternating rounds:

| case | Ziman | C | |
|---|---|---|---|
| 1280x800 fills only | 27 ms (min 24) | 36 ms (min 35) | **0.74x** |
| empty 1280x800 | 15 ms (min 13) | 32 ms (min 30) | **0.47x** |
| 1920x1080 | 147 ms | 136 ms | 1.08x |
| 1280x800 samples=1 | 100 ms | 93 ms | 1.07x |
| 1280x800 | 135 ms | 132 ms | 1.02x |

A wash at best, and a consistent regression on the two cases with the fewest curves. A control on
a benchmark with no shapes in it showed the two binaries equivalent, so this was the graphics path
and not the build.

Then `ziman --profile` on the same benchmark said why, and contradicted the premise outright:

```
   21.0      113  mutable_array_filled
   12.4       67  (garbage collection)
   10.9       59  raster::to_bytes_premul
    8.3       45  raster::blit
    ...
    1.9       10  shape::cubic_is_flat
    1.5        8  shape::flattened
```

**Flattening is about 2% of the time, not 16-50%.** The same is true in the application's own
profile, where `with_point`, `cubic_is_flat`, `flatten_cubic_into`, `midpoint` and `point_of`
together come to roughly 10%, and `edges_of`'s own self time is 1.6%.

## The mistake, which is the point of this file

**A wall clock around a span inside a frame measures that span plus whatever garbage collection
happened to land in it.** `edges_of` allocates heavily, so collections land there — and the clock
reported them as the cost of flattening. The same measurement had already produced a 162 ms outlier
for `transform_path` against its usual 15-22, which is a collection in plain sight, and I noted it
and used the numbers anyway.

**A sampling profiler and a wall-clock split disagree about an allocating span, and the profiler is
right.** Use the clock to find *which phase*; use the profiler to find *which function*.

See [[feedback_perf_effect_size]]'s companion rule: a method is fit for an effect size, and it is
also fit for a question. This one answered a question it was not fit for.

## What shipped: the tests

`tests/stdlib/shape_test.zm`, thirteen of them, which `shape` had none of. They were written to
hold the C to the Ziman it replaced, and they outlived it — they now hold the Ziman to itself.

The curve half is light, because `graphics_stroke.zm` already prints what a rectangle and a circle
flatten to: endpoints preserved, more than two vertices, a tighter tolerance never asking for
fewer, zero meaning the default, and a cusp bounded by the depth cap rather than subdividing for
ever.

The **run rules** are the half that had nothing. Where a run starts, when it is kept, when it is
discarded — fiddly, asymmetric, and reached by every path the library draws. Three breaks, and two
of them are caught by **these tests alone** while every graphics fixture stays byte-identical:

| break | reddens | fixtures |
|---|---|---|
| a `MoveTo` emits a run no `MoveTo` began | `a_run_begun_without_a_move_is_not_kept` | unchanged |
| a one-point run is kept when closed | `a_close_after_a_single_point_leaves_no_stray_vertex` | unchanged |
| a `Close` does not start the next run clean | three tests | **both differ** |

Those two tests exist because breaking the C in exactly those places left everything else green.
A rule only a malformed path can see is still a rule the renderer follows, and now something says
so.

## What the profile does point at

`mutable_array_filled` at 21-25% and garbage collection at 12-14% — the canvas allocated per
`raster.render`, which a *window* does not pay because `surface_fitting` keeps its canvas across
frames. So the bench's biggest item is not the application's. The application's own profile has no
cliff left in it: collection at 26%, and nothing else above 6%.
