# F322 to F329 — the controls health-record's front end needs

Opened 2026-11-19 from [the port's design document](../../design/health-record-port.md), which
holds the measurement these come from and the four decisions the programme owes.

**Only what is ready to start is here.** Charts, message catalogues, navigation, a virtualised
list, a file chooser and animation are all real gaps and all need a design pass first — this file's
own README says why that split exists, and the roadmap's larger entries are kept out for the same
reason: an item with no checkable done condition becomes a headline that flattens the reasoning
behind it.

**Each of these ends with a gallery demo.** The gallery is how this toolkit has found every defect
it has — the stepper's dead width, the calendar's twenty-two points, Save and Share drawn as the
same disc — so a control without one is a control nobody has looked at.

Effort: **S** = a day or less, **M** = a few days, **L** = a week.

---

- [x] **F322** **An autocomplete.** (L; `lib/ui/controls.zm`, a demo, tests.) Done 2026-11-19.

  The largest gap and the most used thing in the target: twelve bespoke autocompletes over one
  generic dropdown. Every piece already existed here -- the entry, the filtered list, the popup
  layer -- and none of the assembly did, which is where the behaviour lives.

  **The five decisions, taken and written into the code:**

  1. **Case-insensitive substring, not prefix.** The part of a long drug name a user remembers is
     often in the middle: `amox` has to find Co-amoxiclav as well as Amoxicillin.
  2. **The arrows do not write into the field.** Filling the entry as the highlight moves reads
     well and destroys the typing of anyone who arrows past their answer. Moving the highlight is
     looking and Enter is choosing, which is the calendar's rule and the number field's.
  3. **The popup stays open when nothing matches**, and says so. One that vanished would be
     indistinguishable from one that broke.
  4. **Enter with nothing highlighted never takes the first match.** That is how a form ends up
     holding a diagnosis nobody chose. It commits the typed text where the field allows free text
     and gives it up where it does not -- which is the one decision the control cannot take for a
     caller, so `free_text` is a field.
  5. **Escape shuts the popup and keeps the typing; a second Escape gives it up.** One key, one
     step, as the calendar's Escape is between its views.

  **The whole candidate set is held rather than a filtered one**, so the control can say "two of
  five" -- the half of an autocomplete that every hand-rolled one leaves out. A list that silently
  goes from a hundred rows to three has told a sighted user something and a blind user nothing.

  **The case fold is deliberately the locale-free one.** `to_lower(s, locale)` is more correct for
  display and wrong here: under `tr_TR` it maps `I` to `ı`, so a Turkish user typing an ASCII `i`
  would stop matching `Ibuprofen`. Matching wants one fold for everybody. It is **ASCII-only**,
  which is a real limit rather than a simplification -- `Ärztin` does not match `ärztin` -- and
  full case folding is already a roadmap item.

  **A render found the last defect, as usual.** A press in the field placed the caret and did not
  open the suggestions, so a field holding a browsable set showed nothing when clicked. That is the
  calendar header's defect again: it works, and nothing on screen says so.

  **One done condition was not fully met and is recorded rather than quietly dropped.** It said "a
  reader announces the count as it changes". The count exists and rides on the control's
  description, so a reader hears "combo box, Medication, amox, expanded, 2 of 5 suggestions" --
  but **`a11y` has no live region**, so there is no way to say anything *as it changes*, only when
  a reader next reaches the control. That gap is now in the port's design document.

- [x] **F323** **A card.** (S or M; `lib/ui/controls.zm`, a demo, tests.) Done 2026-11-20.

  62 files. **P3 is decided and recorded in the design document: a card is a function**, returning
  a named group with no role of its own.

  **The question turned out not to be control-or-function.** It is *focusable or not*. A `Control`
  is a tab stop, and sixty-two cards on a dashboard would be sixty-two extra presses between a
  user and what they came for -- which the watched fail shows directly: making it a control
  reddens the tab-stop test, and reddens the waiting test too, because a control is a tab stop
  even when its body is not laid out. Everything a card wanted a control *for* it gets without
  being one: a named group gives a reader "Medications" and gives a click a name to report.

  **Waiting for F322 and F325 was right, but neither settled it.** F324 did, and F324 was not on
  this list when P3 was written. The target's own `CardShell` takes `title`, `icon`, `loading` and
  `empty` -- which is `Panel` plus a title row. So a card *holds* a panel rather than restating
  one, and all sixty-two inherit the four-state rule that "No medications recorded" and "not yet"
  are different statements.

  Three defects, all found by rendering it and none by a test:

  1. **An invisible box.** The first surface was built by hand from `style.window` and the resting
     border -- and the plain look gives a resting control no border, so it drew a page-coloured
     box edged with nothing. It wears `raised_of` now, which is where "a surface above the page"
     already lives, **plus a hairline in `style.grid`**: a popup is read against the content it
     covers and a card has only the page behind it.
  2. **A card that did not fill itself.** The panel needed `expand`, or the box was drawn full
     size with its contents huddled under the title.
  3. **A list measures as nothing**, so a caller handing one to a card has to say how tall. That
     is the list's contract and not the card's, and the list demo already says the same.

- [x] **F324** **A busy indicator, and a convention for a panel that is loading.** (M;
  `lib/ui/controls.zm`, a demo, tests.) Done 2026-11-19.

  48 files in the target. The missing shape was the smaller half: **a panel that is loading is a
  state of that panel**, not a spinner drawn on top of one, and a spinner alone would have left
  every application to invent the rest differently.

  **Four states and not a flag.** A panel that is empty and one that is still fetching look the
  same to a boolean and must not look the same to a user: "No medications recorded" while a query
  is still running is a statement that is not true yet. A failure is a third fact again, and the
  one most often drawn as an empty list.

  **What it is not showing is not laid out at all**, which is F304's rule and here it is what makes
  the keyboard behave: a Tab cannot land in a form that is still being fetched, because there is no
  form there. A panel that drew a spinner *over* its content would leave every control underneath
  reachable, focusable and editable while the records replacing them were still arriving.

  **The live region is part of the panel.** A panel that finishes while the user is looking
  elsewhere says so, and a failure interrupts where finishing waits its turn -- news a user is
  about to act without, against news they can hear when they get to it. **This is the half the task
  could not have met an hour earlier**: F329 was pulled forward precisely so that this and F327
  would not each invent their own way of not saying it.

  **The spinner is a ring segment built as one polygon**, because `shape` has no arc and a spinner
  drawn as several dots would be several paths where `drawn_of` takes one. Its phase is the
  application's, exactly as `Progress.Busy`'s is: `lib/ui` has no clock and is not going to grow
  one.

  The demo found two things, as demos do. The probe that photographs the gallery only *pressed*,
  and a button fires on the way up -- so every state rendered as the one before it until the probe
  learned to complete the gesture. And the demo asked each button twice, once for how to draw it
  and once for whether it fired: two answers to one question, which is the shape of defect this
  gallery keeps finding in its own library.

- [x] **F325** **Sorting, by value and not by text.** (M; `lib/ui/controls.zm`, tests, the demo.)
  Done 2026-11-19.

  20 files in the target sort. Nothing here did, and until F321 nothing could have done it
  correctly: a column of text sorts `"10"` before `"9"`, which makes a sorted table worse than an
  unsorted one because the user believes an order that is not there.

  **The affordance was already half-built and did nothing.** A press on a column *title* reached
  no code at all -- `edge_at` claimed the resize grips, the body claimed the rows, and the title
  between them fell through every branch. That is where the sort went.

  **Three states and not two**: up, down, and back to the order the caller gave. That order is
  meaningful -- a query already sorted by date, a list a user arranged -- and a header that could
  only toggle would have thrown it away the moment somebody touched it.

  **A `Blank` sorts to the end whichever way the column points.** A missing measurement is not
  smaller than every number and larger than none; it is absent. Flipping it with the rest would
  make reversing a column look like data moving.

  **The sort is an index projection, not a reordering**, which is `Tree.visible_rows`'s pattern and
  here it is load-bearing: `selected` is an index into `rows`, so sorting the array itself would
  silently move the selection to a different record.

  **That introduced a second index space, which is where the bug would have been.** A press and an
  arrow key answer in *positions on screen*; the selection is a *record*. `table_to` takes a
  position now and converts, and the keys move through `display_at` — unsorted the two numbers are
  identical, which is exactly why this was invisible until a column could be sorted. It is the
  calendar's twenty-two points in another costume, and the test that guards it asserts the two
  spaces round-trip through each other rather than recomputing either.

  **A reader hears the order on the header**, "column header, Name, ascending", because there is
  still no live region to announce it as it changes.

- [x] **F326** **A search field.** (S; `lib/ui/controls.zm`, a demo, tests.) Done 2026-11-19.

  15 files in the target. It is a composition -- an entry, a mark, a button -- but **the clear
  button is a control inside a control**, which is the arrangement the number field had to get
  right and the tooltip demo had to name. Fifteen applications assembling it is fifteen chances to
  make it a second tab stop, and a search box that did would make Tab out of the field take two
  presses in every form that has one.

  **The mark appears only when there is something to clear**, because a button that does nothing
  is worse than no button: the pointer changes over it and promises otherwise.

  **Escape clears it**, which is what every search box does and why the key is worth spending
  here -- and on an empty field it changes nothing, so a caller can let Escape fall through to the
  dialog around it.

  **There is no placeholder, deliberately.** A hint drawn inside an empty field has to share the
  box with the caret, which makes it `Entry`'s business rather than a composition's -- and a
  half-built one that made the caret vanish while the field was empty would be worse than none. A
  label beside the field keeps saying what the field is for after somebody has typed, which is
  what the guidance asks for anyway. If a placeholder is wanted it belongs in `Entry`.

  The magnifier and the cross are drawn paths, which is F302 for the fourth time.

- [x] **F327** **A badge.** (S; `lib/ui/controls.zm`, a demo, tests.) Done 2026-11-19.

  11 files in the target: a count on a navigation button, and a status word on a row.

  **The whole of the difficulty is accessibility, not drawing.** A badge drawn beside a label is
  two nodes a reader meets separately -- "Medications", then "3" -- where the user sees one fact.
  So it is a **field on a control** rather than a widget beside one, exactly as `Button.icon` is,
  and the control folds it into what it announces: `button, Medications, 3`. The test that matters
  is that a badged button is visited exactly as often as an unbadged one.

  **Zero is not a badge**, so `count_badge_of` returns `Option<Badge>`. A badge showing "0" is a
  dot that means "no news" in a place a user has learnt means "news".

  **The cap is in the library.** "99+" is a convention, and twelve callers each choosing where to
  cut off would give one window three different answers -- which is the only reason
  `count_badge_of` exists rather than a struct literal.

  Loud wears the accent, for a count asking to be noticed; quiet is the ordinary face, for a status
  word that is merely true. The quiet capsule is faint at 1x and reads as a chip at the density the
  gallery actually runs at -- checked by magnifying a render, because at 1x it looked like plain
  text and that would have been a real defect.

  `badge_widget` takes a `Frame` like every other builder, with a private `badge_inside` taking
  just the `Style`, because `button_inside` has no metrics and a word in a capsule needs none.

- [x] **F328** **The clipboard, which is the half of F273 that was left.** (M;
  `src/native_window.c`, `lib/ui/desktop/`, an integration test.) Done 2026-11-19.

  **X11 has no clipboard.** It has selections: a name, an owner window, and a protocol by which a
  reader asks the owner to write its text onto a property of the reader's own window. Nothing is
  stored centrally, which is why the work is entirely in the native and why F273's seam was the
  right shape -- `controls.zm` was not touched, and still does not know what a selection is.

  **Three defects, each found by a test that two processes could run and one could not.**

  1. **A livelock on the second paste.** The wait loop put unrelated events back with
     `XPutBackEvent`, which pushes onto the *head* of the queue -- so an `Expose` in front of the
     reply was read, put back, read again, and the answer behind it never reached. The first paste
     in a window works, because the queue is empty. The second does not. Events are now held in a
     buffer and given back, backwards, when the wait ends.
  2. **Pasting from ourselves would hang.** The owner's answer comes from the owner's event loop,
     so when owner and asker are one process that loop is the one blocked asking. It short-circuits
     now, and the test *measures the time* rather than asserting the text, because the text is
     right either way and only the clock shows the bug.
  3. **TARGETS has to be answered** or GTK and Qt never ask for the text at all.

  **Two of my own test's cases were wrong about the world, not about the code.** "An unowned
  selection is empty" and "a selection dies with its owner" are both true of the bare protocol and
  both failed on this GNOME desktop, because a clipboard manager takes ownership when a program
  exits -- which is the entire reason clipboard managers exist. They are gone, and the file says
  why, so nobody writes them again.

  **The real check is `xclip` at the other end, in both directions**, which is the done condition
  and the thing two ziman programs cannot stand in for: both ends agreeing on a mistake looks
  exactly like both ends being right.

  **A fourth defect, and the one the gate caught rather than the test.** The no-backend stubs were
  written inside the file's existing `#ifdef ZIMAN_X11` region, so a nested `#else` that never
  compiled: `make gui` was fine and `make ziman` stopped building. Worth saying twice -- the gate's
  `EXIT=2` is usually `lib-manual-check` and benign, and reading only the exit code would have
  called a broken default build a clean run.

  **A fifth, and the worst-shaped of them: a green gate that never ended.** `xclip -i` forks and
  stays alive to own the selection -- it must, because on X11 an owner is a live process -- and the
  copy it left behind inherited the script's stdout, which is the pipe `run_tests.sh` reads from.
  The suite printed every PASS and then waited on EOF for nineteen minutes. **A hang after a pass
  is worse than a failure**, because every line you look at says the thing worked. `-l 1` is the
  obvious fix and is the wrong one: the desktop's clipboard manager asks for the content the moment
  xclip takes it, spending the single serving before our reader asks.

  `desktop.input_in` is a second door rather than a changed one -- `input_of` stays pure, so
  everything that replays recorded events keeps working without a window. Ctrl+V only: `Key` has no
  `Insert`, and adding one means an arm in every exhaustive switch over `Key` in the library and in
  every application on it. That is a change worth making and not inside this task.

  **Not done, and not hidden: the gallery cannot copy.** Paste is wired and works. Copy needs
  `EntryStep.clipboard` threaded out through `all.input_to`, which returns a `Demo` and would have
  to return a pair -- 33 arms and 8 demo signatures, which is a gallery refactor rather than this
  task's `lib/ui/desktop/` and native. The platform half of copy *is* built and is proven by
  `clipboard_another_application_can_read_what_ziman_copied`.

- [x] **F329** **A live region.** (M; `lib/ui/widget.zm`, `lib/ui/a11y.zm`,
  `lib/ui/desktop/atspi.zm`, `src/native_a11y.c`, a gate, tests.) Done 2026-11-19.

  **Not on this list when it was written**, and pulled forward because three of the remaining
  tasks each route around it: F322 had to put its suggestion count on a `description` so it is
  heard on arrival, F325 did the same for the sort order, and F324 and F327 would each have
  invented a third and fourth shape. Four conventions for one thing, and the port would be built
  on them.

  **A reader is a cursor.** Everything else this library publishes is read when the user arrives
  at it, which covers what a user does deliberately and nothing the application does on its own: a
  list narrowing under their typing, two hundred rows reordering, a panel finishing, a save
  failing.

  **The politeness is the role**: `Status` waits for the reader to finish its sentence, `Alert`
  interrupts. That is ARIA's own answer -- `role="status"` *is* polite -- so there is no second
  field to disagree with the role.

  **The change is a pure diff of two trees**, threaded by the application exactly as `hovered`,
  `pressed` and `focused` already are. Hidden state inside the bridge could not be tested by
  handing it two values. Only a change counts, because the tree is republished every frame and a
  reader repeating itself sixty times a second is the worst thing this could ship; a region that
  *appears* counts as changed, which is what makes an error banner speak when it opens.

  **`notification` and not `announcement`.** ATK registers both at runtime and declares neither in
  its public header -- so this was probed rather than assumed -- and only `notification` carries
  the politeness.

  **Gated from outside the process**, which `atspi_dump.c` already argued for: the publishing side
  marking its own homework proves nothing. `tests/tools/atspi_listen.c` is its companion and tests
  the other half -- that one walks the tree a reader *pulls*, this one waits for what an
  application *pushes*. Two assertions: the words arrive with the politeness they were sent with,
  and an unchanged region stays silent.

  **A wrong diagnosis, recorded because the watched fail is what caught it.** The first listener
  heard nothing, and that was read as the bridge never implementing
  `AtkUtilClass.add_global_event_listener` -- so it was implemented, and the listener then worked.
  Removing it again to watch the gate fail is what showed the vfunc had never been the cause: the
  real fault was the listener's own filter, which compared the top parent's name against the
  application name when an application registers on the bus as `main`. The vfunc is gone. **A
  watched fail checks the diagnosis, not only the fix**, and a result should be attributed by
  isolating it rather than by whatever change happened to be most recent.
