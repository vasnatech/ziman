# F278 to F279 — the builder half of the variadic builtins

Asked for as "a MutableArray flavour of `join`", and the question turned out to have two answers
underneath it. Written down together because the second blocks the first.

- [x] **F278** **Named-argument resolution loses its `Option` wrapping when a name is overloaded.**
  (M; fixed 2026-11-10, and a second gap found in the same place)

  A bare value given for an `Option<T>` *named* parameter auto-wraps into `Some` — that is how
  `join(separator: ",", pieces: xs)` works today, with three of its four parameters unmentioned. The
  wrapping is lost the moment the name has more than one declaration, and the call then matches
  none of them.

  Reproduced in plain Ziman with no builtin involved:

  ```
  fn label(prefix: Option<string>, items: [int]) -> string { ... }
  fn main() {
      val a: [int] = [1, 2]
      print(label(prefix: ">", items: a))   // ">arr2"
      print(label(items: a))                 // "arr2"
  }
  ```

  Both calls work. Add a second declaration differing **only** in the last parameter —
  `fn label(prefix: Option<string>, items: MutableArray<int>)` — and the *same* two calls fail with
  `no declaration of 'label' accepts its argument 1`.

  A second gap came with it, in the same experiment: **the resolver does not fall back to another
  declaration when the first it tries rejects an argument's type.** With the pair above,
  `label(items: a)` for an `[int]` reported `expects MutableArray<int>, found [int]` rather than
  trying the other declaration. One name, two declarations, and only one of them is ever attempted.

  Both are pre-existing and neither is about builtins.

  **Fixed in `overload_resolve`'s per-argument filter, and the fix needed two tiers rather than one
  more case.** The filter now retries a failed match allowing the bare-value auto-wrap — exactly
  parallel to the lone-array-spread retry already beside it, which exists for the same reason and
  whose comment explains the mechanism that hid both: the loop runs only `while (live_count > 1)`,
  so a name with one declaration never reaches the filter and `check_arg_against_param` does the
  coercion unaided.

  **The first attempt allowed the wrap in the same pass and broke 25 calls.** `validate.not_blank`
  declares both `(value: string)` and `(value: Option<string>)`, so `not_blank("")` matches the
  first exactly and the second through the wrap — and a coercion competing with an exact match is
  ambiguous. So the filter makes two passes per argument: the strict reading, and the wrap only when
  the strict one leaves nothing. The strict pass writes nothing when it keeps nothing, so the second
  re-scans the same candidates safely.

  `tests/lang/overload_option_auto_wrap.zm` covers both halves, and both are load-bearing: without
  the tier the call matches no declaration, and with the tier but no ranking `exact("x")` goes
  ambiguous between `string` and `Option<string>`.

  **And a third gap, in the same function, which is what `join` was actually hitting.**
  `ovl_arity_fits` read `argc >= n - 1` for a variadic declaration — "every fixed parameter was
  supplied", which is right positionally and wrong for a named call, where an `Option` may simply
  be left out. `join`'s declaration has four parameters with three of them optional, so
  `join(separator: ",", pieces: xs)` arrives with two arguments and was refused for needing three.
  The variadic declaration was therefore eliminated at the *arity* step, before any type was looked
  at, and the only survivor — the `MutableArray` one — was chosen unchecked and then refused on its
  argument. Hence an error naming parameter 4 for a call that two declarations accept.

  **The same mistake F239 fixed on the arm below it**, in the same function, for the same reason:
  that one read `argc == n` and broke named calls against a set the moment one existed. This arm
  kept the positional rule because no overloaded set had a variadic member with omittable
  parameters until `join` gained a second declaration. `ovl_min_named_arity` already skips a
  variadic parameter unless it demands at least one, so it needed no change.

  It also explains why the user-defined pair worked throughout: `gather` has two parameters, so
  `argc >= 1`, and the call supplied two. **The bug needs two or more optionals omitted** — which
  in the whole prelude is `join` alone.

  **And two more, which `make check` found after the entry already said "fixed".** The lang suite
  reported 13 failures where the stdlib suite and the overload gates had all been green:

  * **A named variadic argument need not be written last.** The filter that recognises a lone array
    as a spread required `pos == argc - 1` — the last *argument* — which is only true of a
    positional call. A named argument supplies exactly one value for its parameter, so `pieces:` is
    the whole tail wherever it appears. `lib/http/client/send.zm:175` writes
    `join(pieces: snapshot(out), separator: "")`, variadic first, and that call had worked for
    months. It accounted for 12 of the 13: every HTTP client test, both HTTP examples, the regex
    and error-message fixtures — everything that loads `client/send.zm`.
  * **A variadic's own at-least-one demand must not be counted at the arity gate.** The third fix
    routed named calls through `ovl_min_named_arity`, which counts a variadic parameter as required
    when it demands at least one value — so `merge()` was eliminated at arity and lost the rule that
    says *"needs at least one value for its variadic parameter 'maps'"*, becoming a generic
    no-match. Arity now counts only the required non-variadic parameters and lets that rule speak.

  Five gaps in one function, each exposed by the next thing after the last was fixed. The four
  resolver ones are in `tests/lang/overload_option_auto_wrap.zm`; `join`'s pair is in
  `tests/lang/join_basic.zm`.

  **What let four of them hide for so long is one line**: the per-argument filter runs only
  `while (live_count > 1)`, so none of it executes for a name with a single declaration. Every
  coercion the call path performs has to be modelled there, and there was no way to find out which
  were missing except to overload something and see what broke.

- [x] **F279** **The variadic builtins have no `MutableArray` partner.** (L; `join` shipped and its
  53 sites converted; the rest declined on measurement)

  `join(separator: ", ", pieces: snapshot(parts))` appears **67 times in `lib/`** and 33 more in
  tests and examples. Every one of them copies an array to satisfy a signature.

  **A variadic cannot take a builder, and that is correct.** Tested: a variadic parameter accepts a
  scalar or an immutable array and nothing else — for a user's own function as much as for `join`.
  Teaching variadics to accept a `MutableArray` would mean materialising it at the call boundary,
  because a callee receives its tail as a `[T]` value it may store, and aliasing a builder's buffer
  would let a later `push` mutate an array someone holds as immutable. `collapse_variadic_args`
  passes a lone spread array *through* with no copy today, so the general change would cost exactly
  the `snapshot` it replaced — and hide it, in a tree that comments on every allocation.

  **A builtin can do better, which is the whole case for this task.** One that walks a builder's
  buffer and returns a string retains nothing, so it needs no copy at all. That is a promise a
  general variadic cannot make and a specific native can.

  The sweep, from `--api builtins`. Two kinds of gap:

  *Element-type twins* — a variadic whose elements are collections, where the receiver forms are
  already paired and the pure-value forms are not:

  | has | missing |
  | --- | --- |
  | `concat<T>(parts: variadic [T]) -> [T]` | `variadic MutableArray<T>` |
  | `merge<K, V>(maps: variadic Map<K, V>) -> Map<K, V>` | `variadic MutableMap<K, V>` |
  | `union<T>(sets: variadic Set<T>) -> Set<T>` | `variadic MutableSet<T>` |
  | `intersect<T>(sets: variadic Set<T>) -> Set<T>` | `variadic MutableSet<T>` |

  *Spread sources* — a variadic of scalars that cannot be fed from a builder: `join`,
  `concat(pieces: variadic string)`, `append`, `append_byte`, `filter_present`, `filter_ok`,
  `filter_err`, and the `remove`/`add` families. `push` needs nothing: `concat(items, parts)`
  already appends a collection to a builder, in both worlds.

  **Declarations only, not bespoke arms.** F167 to F202 deleted 68 of the 70 hand-written
  `check_call` arms and left `concat` and `mutable`, and `tools/overload_sets.sh` checks
  `#[compiler_resolved]` *inversely* — the attribute is a defect on any set that does not need it.
  So adding a third exception to carry this is against a completed programme, and the route is
  F278 first.

  **`join` is done (2026-11-10)**, on the third attempt and only once all three of F278's gaps were
  closed. Both declarations share one native, which walks either the variadic's collapsed array or
  the builder's elements through `ziman_piece_count` and `ziman_piece_at` — one table lookup per
  element rather than a copy of the array. `tests/lang/join_basic.zm` covers the spread form, the
  builder form, both agreeing on the same content, the empty builder, and that **the answer does not
  alias**: growing the builder after a join leaves the returned string alone, which is the property
  that makes reading a buffer in place safe for a builtin and unsafe for a general variadic.

  The first two attempts were reverted, and each one found a gap rather than wasting the time: the
  bare-value auto-wrap, then the arity arm. `tools/overload_sets.sh` stayed green through all of
  them, because it asserts that *some* call can tell a set apart and not that every call that worked
  still does — worth knowing before trusting that gate.

  **`join`'s 53 call sites are converted (2026-11-10)**, which is the payoff rather than the
  capability: 53 arrays no longer copied, across 22 files, with `eql.zm` and `derive_routes.zm`
  nine each. 1460 lang tests and 701 unit tests unchanged, the library lint clean.

  **The demand was measured first and the first measurement was wrong**, which is worth recording
  because it nearly sent the next instalment at the wrong target. Counting lines where `snapshot`
  and a builtin's name both appear gave `join` 80, `concat` 52 and **`push` 46** — and `push`'s were
  all `push(out, Token { text: snapshot(text) })`, a snapshot being *stored*, which is necessary and
  not a gap at all. Most of `concat`'s were lines whose snapshot fed a nested `join`. Counting only
  a builtin's own direct argument gives the real picture: 55 for `join` (now 2, both inside
  expressions rather than bare identifiers), **13 for `concat(pieces:)`**, 16 for `concat`'s
  positional form, 4 for `append`, and **zero for the other eight** — `append_byte`, the three
  `filter_*`, `merge`, `union`, `intersect`, `add`, `remove` and `push` have no call site asking for
  this anywhere in the tree.

  **So the remaining work is smaller and more awkward than the entry first implied.** `concat` is
  29 of the 33 sites left, and `concat` is one of the two sets carrying `#[compiler_resolved]` — a
  bespoke `check_call` arm chooses among its four shapes because no argument list can. Adding a
  fifth shape means editing that arm, which is the one place in the prelude where overload choice is
  hand-written. `append`'s four sites and the eight builtins with no demand are not worth a
  declaration each on this evidence.

  **Closed 2026-11-12, with the remainder declined and measured rather than carried.** What the task
  asked for exists: a builder-taking `join`, shipped, with its 53 call sites converted. What is left
  is `concat`, and it does not pay.

  **What a converted `concat` would save, measured** -- `snapshot` of a builder whose elements are
  themselves arrays, which is the shape every one of the 29 sites has (the payloads are not copied,
  only the slots):

  | elements | per snapshot |
  | --- | --- |
  | 8 | 0.24 us |
  | 32 | 0.41 us |
  | 128 | 2.4 us |

  The sites that sit in loops are PDF object serialisation and repository code generation --
  hundreds of iterations at the very most, so **sub-millisecond in total across the tree**, and most
  of the 29 run once.

  **What it would cost is the part that decides it.** `concat` is one of two sets with
  `#[compiler_resolved]`, and `tools/overload_sets.sh` checks that attribute **inversely**: its own
  comment says the attribute "is a defect on a set that does not need it -- so the exemption cannot
  spread". F167 to F202 deleted 68 of 70 hand-written `check_call` arms. Growing one of the two
  survivors, to save microseconds, is paying in the currency a completed programme was spent
  earning.

  So the honest shape of this task was: one real capability, which shipped; one measurement, which
  found most of the demand was imaginary (`push`'s 46 were snapshots being *stored*); and one
  decline. The eight builtins with no call site asking for them get no declaration, `append`'s four
  get none, and `concat` keeps its four shapes.
