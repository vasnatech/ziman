# F345 — measuring a word cost more than drawing it

Done 2026-11-25. `lib/graphics/truetype.zm`, `lib/graphics/font.zm`,
`tests/run_pdf_tests.sh`.

Raised by the health-record port, which was simply too slow to use. A frame of its window —
**243 laid nodes**, 980×720 at two pixels a point — took **57 ms**, so the window could not
exceed about 17 frames a second and every mouse move, keystroke and scroll paid the whole price.

Measured with a per-phase trace in the application's own loop
(`HEALTH_RECORD_TRACE=1`), because which of the five phases a frame goes into is not guessable
from outside it:

| phase | before | after |
|---|---|---|
| build the widget tree | 12 ms | 12 ms |
| lay it out (two passes) | 41 ms | **16 ms** |
| build the scene | 14 ms | 14 ms |
| paint the damage | 1 ms | 1 ms |
| publish the accessibility tree | 1 ms | 1 ms |
| **a dirty frame** | **57 ms** | **31 ms** |

## What it was

`font.advance` — which is what every `widget.measure` of a label ends at — walked the whole
chain **per character**:

```ziman
for ch in chars(text) {
    val cp = charset.code_point_of(ch)
    switch try truetype.glyph_for(face, cp) {        // walk the cmap segments
        Some(g) { total = total + (try truetype.advance_of(face, g)) }   // read hmtx
        None { total = total + (try truetype.advance_of(face, notdef)) }
    }
}
```

That is a cmap segment scan and an `hmtx` read, each a handful of `u16_at` calls over a byte
array, with a `Result` built and unwrapped at every step — **about 6 µs a character**, which a
synthetic probe isolated cleanly:

| 120 labels in a column, one layout pass | per node |
|---|---|
| no text at all | 2.5 µs |
| a 4-character label | 28.9 µs |
| a 31-character label | 181.8 µs |

Text was the entire cost and it was linear in characters, at six microseconds each. And a window
measures **the same words on every frame**, because a frame is built, laid out and sceneed from
scratch.

**It is also multiplied by depth**, because each container measures its children and is then
measured by its own parent: the same 120 labels wrapped in four layers of padding cost 281 µs a
node rather than 182.

## The fix

`truetype.Face` gains `latin_advance: [int]` — the advance of every code point below 256, in font
units, worked out once in `parse`. `truetype.text_advance(f, text)` reads that table once and
indexes it per character, falling back to the walk above 255 and for a face with no `cmap`
subtable or no `hmtx`, so such a face still reports the absence in the words it always did.
`font.advance` now makes **one call for the string** instead of one per character.

**One call for the string and not one per character, which was the first attempt and left a third
of the win behind.** A `truetype.code_point_advance` called from `font.advance` per character took
the probe's flat case from 219 ms to 71; moving the loop itself into `truetype`, where the table
is read once, took it to 54. The cross-module call and the `Result` it returns are not free, and
at one per character they were a third of what was left.

**This is the same bargain `cmap_subtable` struck**, two fields above the new one, and for the
same reason: that field exists because `glyph_for` used to choose the subtable per character,
"which measured as 281 ms of a 347 ms frame on a page of text". This is the step after it.

Measured, same probe, same machine:

| 120 labels, 10 layout passes | before | after |
|---|---|---|
| flat | 219 ms | **54 ms** |
| four layers of padding | 1,658 ms | **327 ms** |

**256 entries and not more.** They cost about a millisecond to fill at parse time and cover every
string a Latin interface measures; a table over the whole of Unicode would be 1.1 million lookups
nobody asked for.

## Watched fail

`tests/run_pdf_tests.sh` gained three assertions, against the real face `fc-match` finds:

- **`table 256`** — the face carries the table. Without this one, breaking the fix leaves the
  suite green: a build with the table deleted agrees with the walk perfectly, because the walk is
  what it is compared against. Confirmed by making `latin_table` return `[]`: `table 0`, red —
  and `disagreements` stayed **0**, which is the whole point of this assertion existing.
- **`disagreements 0`** — for every code point from 0 to 399, `text_advance` of that one character
  equals `glyph_for` plus `advance_of` by hand. Confirmed by indexing the table one place off:
  `disagreements 113` of 400, red. (Not 400 of 400, because a code point the face does not cover
  and its neighbour both measure as `.notdef`.)
- **`whole minus parts 0`** — a string crossing the table's edge
  (`Blood pressure 142/91 — Привет şeker`) measures as the sum of its characters, which pins the
  boundary between the table and the walk: the bulk path and the single-character path have to
  treat code point 255 and code point 256 the same way.

  **This one did not redden for either break**, which is worth writing down rather than quietly
  keeping: both halves of the comparison read the same table, so a table that is wrong in the same
  way throughout is invisible to it. It catches a divergence between the two paths and nothing
  else, and the two assertions above are what catch a wrong table.

## What this did NOT fix

The frame is still **31 ms**, and the reason is structural rather than in the font:

- **The whole window is rebuilt, laid out and sceneed on every frame**, including a frame that a
  mouse move made dirty and that paints nothing. 342 of the health-record window's first 349
  frames painted **zero regions** — `desktop.repaint` correctly found no damage after 45 ms of
  work had already been spent finding out.
- **Building the scene now costs as much as laying out** (14 ms against 16), and no part of it is
  cached either.
- **A layer whose position is read off the laid tree costs a second full layout.**
  `lib/ui` has no way to place a laid layer over an existing `Laid`, so an application that pins a
  button to another widget's edge — the health-record frame's menu toggle, which straddles the
  sidebar — must lay the entire window out twice. That is about half of the 16 ms.

  **And the application cannot avoid it by computing the position itself**, which was tried: the
  toggle is centred on the sidebar's trailing edge and level with the name beside it, so its box
  needs the sidebar's width (a constant the frame knows) *and* the height of the header above it
  (whatever that header's contents measured to). Deriving it would be writing the frame's vertical
  arrangement a second time, in a place nothing would correct. Reading it off the laid tree is the
  right thing for the application to do; the cost belongs to the toolkit.

Each of those is a reuse question for `lib/ui`, not a measurement one, and none should be answered
by making the toolkit remember something an application could tell it.
