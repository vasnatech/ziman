# F339 — the retry on a reused connection, and the two things it got wrong

Done 2026-11-20. `lib/http/client/send.zm`, four cases in `tests/lang/httpclient_features.zm`.

Found by the health-record port: three of the five cards in its right-hand pane read **"request
timed out"** every run, against services `curl` answers in under a second.

## Measuring it, which took three wrong answers first

| suspected | ruled out by |
|---|---|
| no Happy Eyeballs — v6 tried first on one budget | the two hosts that **do** have AAAA records always succeeded |
| the `User-Agent: ziman` tripping a CDN | `curl -A ziman`, 24 of 24 |
| `Accept-Encoding: gzip, deflate` | 9 failures with compression off, 1 with it on — noise, not signal |

That third row is the lesson: two runs **disagreed**, which meant the thing being measured was
moving. I had sent about a hundred requests to open-meteo by then and could not tell my own effect
from the fix's. The answer was to stop running A and B in sequence and **alternate them in the same
minutes**:

```
ziman  3 failures / 32
curl   0 failures / 32     (same URLs, same concurrency, same headers, interleaved)
```

Four threads in one process against four processes — so: shared state. `reuse: false` made it 0 of
32, which named the keep-alive pool.

## What was wrong

`send_once` retried on `reused && ClientError.is_Network(why)`.

**`Timeout` is not a `Network`.** The pool's own comment in `native_net.c` promises the caller
"retries on a fresh connection when that shows" — and a peer that drops a parked connection
*politely* sends a FIN, which reads as EOF, which is a `Network`, which was retried and worked.
A peer that drops one **silently** shows as nothing at all until the budget runs out. Every one
of the 3 failures was a `Timeout`; not one was a `Network`.

**And there was no mention of the method**, so a `POST` on a parked connection that timed out was
quietly sent a second time. The server may have received it, acted on it, and failed to answer: a
duplicate order, a duplicate payment, a duplicate record. That one was not making anything fail,
which is why it was still there.

## The fix, and the correction the tests forced

Writing it as *"no retries for a `POST`"* broke `httpclient_basic` and `httpclient_binary` within
the minute. Both post on a parked connection the server has since closed — the **safe** case, and
the common one: the write fails with a broken pipe, no server acts on a truncated request, so
there is nothing to duplicate.

So the question is not the method alone but **how far the exchange got**:

| stage | retry? |
|---|---|
| `Sending` — the write failed, so the request never left | **any method** |
| `Awaiting` — it went out, nothing came back | **idempotent only** |
| `Replied` — the server is answering | never |

That is Go's `nothingWritten`, arrived at by being wrong first. The suite was right and I was not,
and it cost one build to find out — which is the argument for those two tests existing at all.

## Cost

**A call can now take up to twice `timeout_ms`** in the silent-drop case: the first attempt spends
the budget discovering the pool handed it a dead socket, and the second needs a budget of its own.

Splitting the budget in half instead would make every slow-but-alive endpoint fail on a reused
connection, which is the worse bargain. Bounding it properly wants a monotonic clock — and
`clock.now_raw` says in its own comment that it is the wall clock and must not be used for elapsed
time. **That is the next thing to want here.**

## Two watched fails

| removed | what reddened |
|---|---|
| `Timeout` from the retry | the `GET` on a muted connection, "request timed out" |
| the method check on `Awaiting` | the `POST`, which came back `200 mute` — sent twice, visibly |

The second is the one worth keeping: a defect that makes nothing fail is still a defect, and the
only way to see it was to write the test that asks.

`/mute` is the new case in the test server — answers once on a connection, then holds its tongue
without closing, which is a load balancer that has forgotten an idle flow. `/flaky` beside it is
the polite close, which already worked.
