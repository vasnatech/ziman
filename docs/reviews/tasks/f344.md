# F344 — a scroll bar painted over the dialog in front of it

Done 2026-11-26. Raised 2026-11-24 by the health-record port, which drew the first dialog wide
enough to see it. `lib/ui/widget.zm` (`paint_adorned`, `collect`), `lib/ui/controls.zm`
(`paint_scrolled`, `bar_ops`).

## What happens

A modal dialog is drawn over a dimmed window. Any scroll bar belonging to a control *underneath*
that dialog is then painted on top of it — not dimmed by the scrim, not clipped by the dialog, a
twelve-point grey band straight across the fields.

In the health-record front end the band falls down the middle of the lab result dialog, cutting
`LOINC code` to `LOIN| code`, `Ref. low` to `Ref. l|w` and the Save button to `Sa|e`. It is the
window's own sidebar menu that owns the bar.

## Why

`paint_scroll_bars` is **one pass over the whole laid tree, run after everything else is painted**:

```
pub fn paint_scroll_bars(l: Laid, over: scene.Scene, f: Frame) -> scene.Scene {
    …
    collect_bars(l, style, ops)       // appends to the ops already there
```

and `collect_bars` recurses into every child without ever asking which layer it is in. A layered
tree holds the base, then a dialog, then a popup; the dialog's scrim is an op in the base's own
scene, so it dims what was painted before it — and the bars are appended after all of it.

The pass is right about *why* it is a pass and not a widget: a thumb's length is the view's share
of the content, and nothing knows the view extent until the layout has run. The bug is only that
one pass over a layered tree is not one scene.

## Why it had not been seen

The condition for seeing it is narrow and both halves had to arrive:

- **A scrolling control under a modal.** The port's sidebar has scrolled since it reached fifteen
  rows — measured, not guessed: at 980×720 the menu's viewport is 637 points against 654 of rows.
- **A dialog wide enough to reach it.** Every record dialog in that application is a 560-point
  form, which comes out about 566 wide and clears the 208-point menu by a point. The lab result
  dialog was drafted at 640 — eleven fields in a six-track grid — and that is the first one that
  overlaps.

The 640 was then dropped for an unrelated reason (a width picked to fit a caption that already
fitted), so the band across the fields went away with it.

**Both halves turned out to be unnecessary.** Reported again 2026-11-26 as "scrollbar shows on top
of dialogs", from the ordinary 560-point dialog: a bar does not have to fall *across* a dialog to
be wrong. A scrim dims the window behind it, and a bar painted after the scrim is not dimmed — so
every dialog in the application showed a bright blue-grey strip down each edge where the window
behind it scrolls, at full strength beside controls the scrim had greyed. That is the same defect
without the overlap, and it was there from the first dialog the application ever drew.

## The fix

**A bar is drawn with its own node, not with its own layer** — what this report asked for, one step
shorter. A layer is only the case that was noticed; a viewport nested inside anything painted after
it has the same problem and the same answer.

`widget.collect` already walks the tree in paint order, and it already draws one ornament a widget
cannot draw for itself: the focus ring, whose box nothing knows until the layout has run. It now
takes a second from its caller:

```ziman
pub fn paint_adorned(l, m, focused, ring, width, over: fn(Laid) -> [Op]) -> scene.Scene
```

`over` is called for every node once that node's subtree has been painted, and its ops go in
there — in the order, not appended to it. `paint_focused` is now `paint_adorned` with an ornament
that draws nothing.

`controls.paint_scrolled` is the one call an application's loop makes: `paint_focused` and the bars
in a single walk, with `bar_ops` as the ornament. `paint_scroll_bars` is kept, because a caller
composing a scene a piece at a time still wants it, and its doc comment now says what it cannot do.

**Every door out of `collect` draws it.** That function leaves by three — a viewport, a fixed box
and the plain walk — and an ornament drawn on two of them is one that works until the node is put
inside a `Fixed`. The viewport's goes **outside** its own clip, because a bar is drawn over its
viewport rather than scrolled with what is in it.

**What it costs** is a function call per node that answers `[]` for all but a handful; that is the
price of the hook staying general rather than being about scroll bars.

## Watched fail

Three breaks, each reddening its own assertion:

- **`paint_scrolled` appends again**, its body replaced by the old two-call form:
  `a_bar_is_covered_by_the_layer_painted_over_it` fails.
- **The viewport door forgets its ornament**: that test fails, and so does
  `an_ornament_is_drawn_for_a_fixed_box_and_a_viewport_too`.
- **The plain door draws the ornament before its subtree instead of after**: both widget tests
  fail, on the op order itself.

`the_appending_pass_puts_the_bar_over_the_layer` asserts that the old pass still has the defect, so
the difference between the two is written down rather than left as a story.
