# F358 — a window with a back buffer

Done 2026-11-27. `src/native_window.c`, `lib/ui/desktop/window.zm`, `lib/ui/desktop/desktop.zm`,
`tests/integration/window/quadrants.zm`, `tests/run_window_test.sh`.

Asked for directly, after [F356](f356.md) and [F357](f357.md): *"implement double buffering. Check
the paint and response numbers after."*

## What there was

Offscreen rendering, yes; double buffering, no. `raster.Surface` is a canvas of premultiplied RGBA
doubles kept across frames, `present_premul_raw` packs the damaged rectangle into an `XImage` — in
a shared-memory segment when the server allows it — and `XShmPutImage` put that rectangle **straight
onto the window**, followed by an `XSync`. No `Xdbe*`, no pixmap, no `XCopyArea` anywhere.

The retained canvas is a *damage* buffer, not a flicker buffer: it exists so `raster.damage_between`
can say what changed. Nothing in the path made a frame's several rectangles arrive together.

## What there is now

A **back buffer**: a server-side pixmap the size of the window, kept between frames. Every
rectangle is packed and put into the pixmap, then the rectangles are copied to the window one after
another with nothing waiting in between, and one `XSync` ends the frame.

**A pixmap rather than the Double Buffer extension**, because DBE's swap is defined over the whole
drawable and this renderer paints damage, so it needs a back buffer whose contents survive a frame.
`XdbeCopied` promises that and is the swap action servers implement least well; a pixmap promises
it by being one.

`window.present_regions` is the new door and `desktop.repaint` now makes one call where it made one
per region. **That is where the only saving is**: a frame that changed four distant places cost
four round trips to the display and appeared a rectangle at a time; it now costs one and appears
once.

## The numbers, which are the point of the exercise

Three interleaved passes of two binaries, the health-record window at 1960x1440 under a real
record, with a clock around rasterising and around presenting:

| | no back buffer | back buffer |
|---|---|---|
| **present** | 13.0 ms median (11-17, n=30) | **12.0 ms median (11-17, n=30)** |
| rasterise, as a control | 190.5 ms median | 190.0 ms median |

**It costs nothing and saves nothing measurable.** The one-millisecond difference in the median is
the resolution of the clock; the control moving by half a millisecond over thirty frames is what
says the comparison was fair.

That is the answer to "check the paint and response numbers", and it was the expected one:
presenting is 12 ms of a 400 ms frame, and this change touches only presenting. **Painting is
rasterising, and rasterising is where the work still is.**

## And the measurement that did not happen, which is worth more than the one that did

The saving is per *frame with several rectangles*, and the application never makes one.

Driving the window for three passes produced **60 painted frames, every one of them a single
region**. Hovering down the sidebar — which should un-highlight one row and highlight the next, the
textbook two-rectangle frame — produced **no frames at all**: the move-skip of F345 discards them,
because nothing in this look changes when the pointer crosses a rail row. A click in the same run
painted, so the injection was working.

So every repaint this application makes is a screen change that damages the whole window, and the
back buffer's benefit is unexercised today. It will start to matter when painting is cheap enough
for partial repaints to be the common case — which is the other end of the same problem.

## The tests, and the break that taught something by not failing

`tests/integration/window/quadrants.zm` grows a `regions` mode and the harness screenshots it: two
40x40 squares in different quadrants, sharing neither a row nor a column, with the buffer behind
them flooded magenta so that a door pushing more than it was asked to is caught. Ten pixel checks,
including both edges of the second square.

Three breaks, each reddening its own:

| break | reddens |
|---|---|
| only the first rectangle is copied over | the second square and both its inside edges |
| the copy reads from the wrong source offset | both squares, which the first break did not test |
| a rectangle never reaches the back buffer | the second square, through the pack loop rather than the copy loop |

And one break that **did not fail, correctly**: making each copy spill past its rectangle to
320x240. With a direct present that is the classic corruption — it is exactly what the
single-region test's flooded buffer exists to catch — but **through a back buffer it is harmless,
because the back buffer always mirrors the frame the window should be showing.** Over-copying moves
correct pixels. That is a real robustness property of the design and not a hole in the test; the
thing that can still go wrong is packing the wrong area, which the gap check catches.

## The hole the first version had, found by asking which doors exist

`present_premul_raw` and `present_premul_regions_raw` each called `ensure_back` beside
`ensure_image`. **`present_raw` -- the bytes door -- calls `ensure_image` and did not call
`ensure_back`**, so a window that presented floats at one size, resized, and then presented bytes
would have drawn the new frame into a pixmap still the old size, and shown the wrong pixels with
nothing to say so.

Not caught by anything: the harness runs one present mode per process, so no test mixes the two
doors, and no application in this repository does either. It was found by reading which callers
`ensure_image` has rather than by a failure.

**The fix is where the rule lives, not another call site.** The back buffer is made inside
`ensure_image` now -- it is the same size as the image and is wanted whenever the image is -- so
the two cannot diverge, and a door added later gets it without knowing it exists. A rule kept in
two places is kept in neither.

Belt and braces beside it: `put_image` uses the back buffer only when its size matches the image's,
so a door that somehow still missed the invariant draws straight to the window, which is merely the
old behaviour, instead of into a pixmap of the wrong shape.

**This is not covered by a new test, and that is a deliberate judgement rather than an oversight.**
Reproducing it needs a program that presents floats, is resized, and then presents bytes, which no
mode of `quadrants.zm` does and no application does; the fix removes the possibility rather than
guarding it. What the change did buy in coverage is free: the `bytes` mode's pixel checks now
exercise that door **through** the back buffer, where before the bytes path never had one.

## What it cost

A pixmap the size of the window on the server — about 11 MB at 1960x1440 — freed with the window
and remade when it resizes. A new pixmap's contents are undefined, which is safe here only because
every path that makes one also forces a full repaint: `painter_fitting` drops the remembered scene
on a resize, and a new window has none. Verified by resizing the real window down and up and
screenshotting both.
