# F337 — the first charts an application drew, and the axis that read 11.5

Done 2026-11-20. `lib/graphics/chart.zm` and three tests here; the screen is
`health-record/health-record-frontend-ziman`.

`AssessmentsVisualView.tsx` — one trend chart per screening instrument — is **the first chart any
application has drawn on this toolkit**. `lib/graphics/chart.zm` and `controls.ChartView` were
built for this port (F332, F333) and until now had only the gallery demo they were written beside,
which is exactly the state `controls.Autocomplete` was in before the allergy form.

## The defect

**An axis of counts had gridlines at values its data could not take.**

A PHQ-9 score is an integer between 0 and 27. The chart drew its y axis at

    14 · 11.5 · 9 · 6.5 · 4

because the five gridlines sat at equal shares of the data's range whatever that range was, and
`axis_number` could only decide how to *print* the value it was handed. Its own doc comment said
what it was for:

> **Whole numbers without a decimal point**, because an axis of counts reading "1.0, 2.0, 3.0"
> says that something was measured to a tenth when it was counted.

It could only do half the job. A questionnaire chart labelled **11.5** is a score that does not
exist; `recharts` spells the fix `allowDecimals={false}`.

## The first fix was wrong, and the existing tests said so

Widening the span to the next multiple of four gaps makes every label whole — and turns a range of
0–5 into 0–8, a **60% overshoot that squashes every bar on the chart**. Three existing tests broke
immediately, each pinning an exact range: 83 for a weight series, 5 for a bar series, 90 for a
band. They were right.

So the **gap count moves instead**. Four, five or three, whichever stretches the axis least — and
an exact fit is simply an overshoot of zero, so one search finds both cases:

| span | gaps | axis | overshoot |
|---|---|---|---|
| 10 (4–14) | 5 | 4 · 6 · 8 · 10 · 12 · 14 | none |
| 5 (0–5) | 5 | 0 · 1 · 2 · 3 · 4 · 5 | none |
| 3 (80–83) | 3 | 80 · 81 · 82 · 83 | none |
| 9 (38–47) | 3 | 38 · 41 · 44 · 47 | none |
| 7 (0–7) | 4 | 0 · 2 · 4 · 6 · 8 | 1 |

All three original tests pass unchanged, which is the evidence that the second version is the one
the first was reaching for.

**A chart of measurements is left alone.** A weight chart has every right to a gridline at 81.75,
and rounding its axis to whole numbers would lose exactly what such a chart exists to show. The
rule applies only when every point and every band is already whole.

**`y_gaps` is public**, because the gridlines and the labels both read it: a grid drawn at quarters
beside a range divided into fifths would put every label between two lines. It was the literal `4`
in two places before this.

## A watched fail that did not fail, and the dead code it found

Two attempts were made to redden the new tests. Removing the widening failed two of them, as
expected. **Removing the explicit search for an exact divisor failed none** — because the
minimum-overshoot search already finds it, an exact fit being an overshoot of zero. The first loop
was dead code from the moment the second was written, and only the watched fail showed it. It is
gone.

## What the screen found that is not fixed here

| | |
|---|---|
| a series has one colour | the target colours **every dot** by that reading's severity band; `chart.Series.ink` is one `Color` for the whole line. The port's line wears the latest band instead, and the per-point colouring is lost. |
| `Badge.loud` is a boolean, **for the second time** | the allergy row wanted three colours; this wants **five**, and they are a *scale* -- MINIMAL to SEVERE, where telling one band from the next is the whole point. A boolean cannot carry a scale. The application wrote its own chip, which is what a `lib/ui` badge carrying a colour would be built from. |
| `Tabs.tab_width` is the caller's | documented and defensible -- one number serves the widget and the hit test, and measuring inside would need the metrics in `tabs_input` too. But every caller will write the same three lines to fit the longest label, and the default of 100 points drew the second tab over the first one's last six characters. |
| `navigate.screen_widget` is a region **and** a heading | they cannot be had separately, so an application whose navigation already names the screen gets the name twice. The port uses `navigate.screen_region` and draws no heading, which is the choice the target makes in the other direction. |

The second is now the strongest candidate for a `lib/ui` change: two screens have asked for it, and
the second asked for a scale rather than a third colour.
