- [x] **C16** **Multi-segment module references (`model.patient.X`)**, so two modules of the same file name need no alias. (C12's design half, L2 P1-10; M-L) The ergonomic half of C12: a module is referenced by its path's last segment, so the reference backend writes 351 aliases and invented a `_model` suffix convention, and its `use` lines come to 1,261 (~9% of the codebase). Worth separating from the defect C12 fixed, because this one is a language design change and not obviously the right one. Two things to settle before writing code. (a) It collides head-on with C15: `a.b.c(...)` has to decide whether `a.b` is a module path or a field access on a local, which is the same ambiguity that makes `h.run(21)` hard, so the two want designing together rather than in sequence. (b) Most of those 1,261 lines are not aliases at all -- they are the one-name-per-import rule ("no `{A, B, C}` list"), which SYNTAX.md adopts deliberately so that "a file's `use` lines account for every bare name its body could have come from". Multi-segment references would not shorten them; a grouped import form would, and that is a different decision with a documented rationale to argue against first. So the honest question is which of the two costs is actually being complained about. **Evaluated 2026-10-06 and declined as proposed, with the measurement that decided it.** No code change. The question this task was filed with -- which of the two costs is actually being complained about -- has an answer, and it is neither of the ones multi-segment references would fix. The reference backend's 1,271 `use` lines are 812 per-name imports, 459 whole-module imports, 351 of them aliased. Replacing the collision-forced whole-module aliases with dotted paths saves 3,865 characters of `use` lines and adds **14,213 at use sites**, a net +10,348 -- longer, in the places people read most. The pattern is `use controller/admin as admin` beside `use model/admin as admin_model`, and `admin_model.AdminUserResponse` is both shorter and more informative than `model.admin.AdminUserResponse`: an alias names the role, a path names the location. C12 already made the collision a loud error that writes the alias for you, which was the real defect here. Add the resolution cost -- `a.b.c(...)` would have to decide between a module path and a field access, in the same spot C15 just made subtle -- and the trade is clearly bad. Two things worth keeping fell out of the measurement, filed as C17 and noted in F9.

- [x] **C17** **A grouped per-name import, `use model/patient.{Patient, find}`.** (from C16's measurement, 2026-10-06; M, and a decision first) This is where the verbosity actually is, and C16 is where it is not: of the reference backend's 1,271 `use` lines, 812 are per-name imports covering only 424 distinct (file, module) pairs, so a grouped form would remove **388 lines, 47% of them** -- 15 names from `time` in one file, 9 from `service` in another. SYNTAX.md currently says "one name per import, no `{A, B, C}` list", so this needs that decision revisited rather than simply implemented. Worth noting what the stated rationale actually says, because it does not forbid grouping: "No wildcard import form; a per-name import always names the one thing it binds, so a file's `use` lines account for every bare name its body could have come from." A grouped import still names every bare name it binds -- it is wildcards that break that property, not grouping. So the principle survives the change intact, which makes this a question about syntax and taste rather than about the invariant the rule exists to protect. Decide first, then implement. **Decided 2026-10-07: declined, and the rule now carries its reason.** The task's framing was right -- SYNTAX.md asserted "one name per import, no `{A, B, C}` list" with no rationale, and a rule with no recorded reason is indistinguishable from an oversight. The complaint is also legitimate: the backend has **1,275 `use` lines** and `service/medication_adherence.zm` imports fifteen names from `time` alone, and the real cost is positional rather than verbosity -- adding one name to an alphabetised run means finding the slot, which an earlier session scripted rather than did by hand. Three things outweigh it. `--fmt` already sorts runs of consecutive `use` lines, so that friction was solved before it was raised and the answer is to run the formatter. One name per line is independently valid, so a mistake costs one line and the error points at it, where a malformed group breaks the whole import -- which matters more for generated code, since one-line-at-a-time is the shape that goes wrong least. And one fact per line stays greppable: `grep -rn "use service.is_email"` answers "who imports this?" exactly, which a group turns into a multi-line pattern. Then the second principle decides it: a group is a second way to import three names. Recorded in SYNTAX.md where the rule is stated and in DESIGN.md as "Grouped imports, declined", including what would change the answer -- a reader finding fifteen `use time.X` lines worse to *read* than they are to generate, which is the one side of this a human owns and nothing measured here speaks to.


- [x] **C18** **A `Row` bound, generalizing the `Eq`/`Hash`/`Ord` mechanism to a fourth case.** (R, ROADMAP.md:1615; M) `Crud<E, Req, Res>` (`health-record-backend-ziman`'s `service/crud.zm`) has to carry `from_row: fn(Row) -> Result<E, DbError>` and `to_params: fn(E) -> [SqlValue]` as explicit function-value fields on **every** literal -- nine today, growing with each migrated resource -- because there is no way to say "`E` already has a `#[derive(Row)]` pair" the way `<T: Ord>` already says "`T` already has a `_compare`". A `Row` bound would resolve `<snake_type>_from_row`/`<snake_type>_to_params` through the same `find_compare_function` path in the type checker, and both fields would drop out of every literal. Needs the bound grammar and checker extended to a fourth name, and a *two*-function resolution where the existing three resolve one. Taken first of the ten because it is the smallest and it unblocks the database follow-ups at ROADMAP.md:1596; the design pass is the task, not an afterthought to it. **Done 2026-10-09 as a design pass, and the answer is no -- with F1's decision to add `Row` withdrawn in its own entry.** Three findings, each checked against the code rather than argued. **(1)** `Ord`'s mechanism is *runtime dispatch on a value's own type* (`value_compare` reads `a.type.struct_name`, src/interpreter.c's `TY_STRUCT` arm) and generics are erased -- `call_function` takes no type arguments, so a generic body cannot know what `E` was bound to. `to_params: fn(E) -> [SqlValue]` therefore fits the mechanism exactly; **`from_row: fn(Row) -> Result<E, DbError>` cannot**, because `E` appears only in the return type and at the moment of the call no value of type `E` exists. A constructor-shaped function is not resolvable by value dispatch; it needs a per-parameter witness (dictionary passing) or monomorphisation, both of which are the general trait machinery F1's first paragraph refuses. Covering `to_params` alone would be worse than covering neither: a bound named after a derive pair, supplying one of its two functions. **(2)** "The two fields disappear from every `Crud` literal" needs a second, unrelated feature -- struct literals must set every field (`P { a: 1 }` is "missing field 'b'"), and there are no field defaults. **(3)** F1's safety argument -- "nothing stops a copy-paste mistake wiring one resource's `from_row` to another's `to_params`, since both are just function values of matching shape" -- is already covered: they are *not* of matching shape, and `Crud<Allergy> { from_row: allergy_from_row, to_params: encounter_to_params }` is rejected today with *expects fn(Allergy) -> [int], found fn(Encounter) -> [int]*. Verified directly. So what remains of the motivation is **eighteen lines of boilerplate in one file of one sibling repo**, against a new language mechanism. Reversed by, cheapest first: monomorphisation arriving for the bytecode entry's sake; struct-field defaults arriving independently; or F1's own deferral test being tripped properly by a *second* `Crud`-shaped abstraction. Full reasoning in docs/DESIGN.md "The `Row` bound, and why `from_row` cannot work the way `compare` does"; ROADMAP.md's entry struck through with the summary.

- [x] **C21** `#[from]` on `HttpError`, `ClientError` and the `pg`/`mysql` error enums, deleting four hand-written `lift` functions. The backend already proved the pattern pays, going from 158 conversions to 3. (DX3 item 21; S) Done 2026-10-14, **but not as specified, because the premise does not hold.** The report calls the four `lift`s "identical in shape, differing only in the target enum"; reading all four says otherwise. `pg`/`mysql` *flatten* a `NetError` into `DbError.Connection(net_error_message(e))` -- a string payload, not the error value -- and `server`/`client` *dispatch on the source variant* to choose a different target variant (`NetError.Timeout` -> `HttpError.Timeout`/`ClientError.Timeout`, everything else to an `Io`/`Network` message). `#[from]` wraps the error value in a variant whose payload type matches it, so it cannot express a flatten or a variant mapping. Using it here would mean `DbError`, `HttpError` and `ClientError` each growing a variant that carries a `net.NetError`: it would leak `net` into the public error type of `db` and `http` -- the whole point of these functions is that a caller never has to know `net` exists -- and add a variant to every exhaustive `switch` over them in every program. What *was* real is that `pg` and `mysql` held the same conversion twice, identical in meaning and differing only in `switch` versus `if`; that is now one `db.lift_net`. The review's other observation stands and is worth keeping: `#[from]` appears **nowhere** in `lib/`, so the feature is indeed unused there -- just not at these four sites. Verified with the real driver suites, 11 Postgres and 6 MySQL tests, since `lift` sits on every socket path; 1017 fixtures.
