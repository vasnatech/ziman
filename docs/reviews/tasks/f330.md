# F330 — a list holds a value, and the search field learns its own height

Two follow-ons to [F322 to F329](f322-f328.md), both raised by using the gallery rather than by
reading the code. They are recorded together because they landed together, not because they are
related.

## F330.1 — the search field was a padding too tall

**Found by eye, in the gallery, after 391 tests passed.** A search box stands beside ordinary
fields in every form the port has, so a field that is taller than its neighbours reads as a
mistake before anyone can say why.

Two defects stacked, and either alone would have done it:

1. **The marks were sized across the wrong axis.** `search_mark_side` added the field's
   *horizontal* padding to a *vertical* measurement, so the magnifier and the clear cross were
   taller than the line of text they sit beside.
2. **It wrapped `entry_inside`**, which brings its own padding *and its own surface*. So the
   control drew a field inside a field, and stood a whole padding taller than the plain entry next
   to it.

**Neither was visible to any test, because no test asked how tall it was.** There is one now: a
search field must measure exactly as tall as an ordinary entry, empty and with the clear mark
showing. The marks are sized from the text line, and the box is built here rather than borrowed --
one surface, one padding.

Also added, since it was the same kind of hole: the clear mark is hit where it is drawn, with a
press just outside it landing in the text. That is the invariant the calendar cost 22 points for
not having.

## F330.2 — `List` and `ComboBox` hold values

`JList` and `JComboBox` take a `ListModel` of objects and render each through a cell renderer, the
way `JTable` takes a `TableModel`. F321 answered that question for the table with `Value`; this
answers it the same way for the list and the picker, so **a list and a table holding the same
column hold it the same way**.

- `List.items` is `[Value]` and `List.locale` is its own, as the `Table`'s is. A value knows what
  it is; only a locale knows how it is spelled.
- `list_of` and `combo_box_of` each gained a `[Value]` door and a `[Value] + Locale` door, with the
  `[string]` spelling **kept as an overload** -- `table_of` already keeps the same door, and every
  caller written before `Value` existed still compiles.

  **The overload is not a free pass, and curly proved it.** Code that *constructs* a list was
  untouched; code that *reads one back* was not, because `items[i]` is a `Value` now. curly's
  builder broke in eight places -- `showing()` returning a row as a `string`, and tests comparing
  rows to string literals. The GUI was fine, which is why checking the GUI alone said "no change
  needed" and was wrong: the fix is `list_text_at`, and the lesson is that a type change at a
  library boundary is found by the *whole* downstream gate, not by the part of it that looked
  most likely.
- **`combo_box_chosen` returns the value; `combo_box_value` returns its spelling.** These stopped
  being the same thing the moment a picker could hold a decimal: an application that read the text
  back and parsed it would be undoing the formatting it had just asked for, in the locale it asked
  for it in.
- `list_text_at` spells a row in the list's own locale, so no caller has to reach for `value_text`
  and the locale separately -- the one that forgets prints a date in the root locale while the rows
  above it are in the user's.
- Type-ahead matches **what is on screen**, not the underlying digits. A German picker whose
  type-ahead matched `2.5` would be answering a question nobody asked; the row says `2,5`. Tested,
  because in English the two are the same and the bug would never show.

**The cost, paid once here rather than by every caller:** `list_of(name, label, [])` is now
ambiguous, because an empty literal carries no element type and both doors accept it.
`no_values()` is the spelling for that.

**Checked rather than assumed: dates stay ISO, and that is a decision.** `controls.date_text` says
why -- there is a source for each locale's month and weekday *names* and none for its date
*pattern*, and guessing one in a format whose whole job is to be read correctly is worse than being
unambiguous. A test now pins a list's date to the date field's own spelling, so the two cannot
drift apart and changing it is a deliberate act.

The gallery shows both: the List demo holds strings on the left and values on the right, and the
Combo box demo has a second picker of doses in German. The row reading `2026` is the one that
earns `Value.Code` its place -- held as `Whole` it would print `2.026`, because a year identifies
rather than counts.
