# F359 — a layer should not cost a second layout of the window

Done 2026-11-27. `lib/ui/widget.zm`, `tests/stdlib/widget_test.zm`, and the health-record port's
`screen/frame.zm`.

Asked for as *"cache the laid tree and scene across frames"*. The measurement sent it somewhere
better: the expensive reuse was not between frames but **inside one**.

## What it was

An overlay is positioned from the laid bounds of what it hangs off — a menu from its button, a
tooltip from the control under the pointer, a pinned button from the edge of the pane it straddles.
So an application lays the window out, reads the anchor, builds the layer, and then has to lay the
whole window **again**, because `widget.layout` takes widgets and a widget tree knows nothing of
what it measured to. [F345](f345.md) named this and could not price it.

Priced now, per frame of the health-record window at 1960x1440 under a real record:

| | |
|---|---|
| build the widget tree | 5-7 ms |
| **lay it out, pass 1** | **21-47 ms** |
| **lay it out again, pass 2** | **22-40 ms** |
| a dialog, a popup | a further pass each |

**The second pass is the same work as the first**, for one pinned button. A screen with a dialog
and a popup open laid the window four times.

## What it is now

`widget.layered_over(laid, extra, within, m)` lays `extra` over a tree that has already been laid.
A tree that is already layered gains its layers at the end of its list and keeps the children it
has; anything else *is* the base layer and becomes layer zero. It chains, which is how an
application uses it: the window, then the pinned button read off it, then the dialog, then the
popup hanging off a field inside the dialog, then the tooltip — each call laying only what it was
handed.

**The result is the same tree, not a close one.** `place` gives a layered node one child per layer,
each laid into its own box, so a base layer's subtree is exactly what laying that widget alone
produces — down to every field but the root's `index`, which is its position among the layers.

Measured, three interleaved passes of the same binary with only the application file swapped, so
the one thing that differs is whether it lays twice:

| screen | layout before | layout after | |
|---|---|---|---|
| 267 ops | 74 ms | **36 ms** | 2.06x |
| 189 ops | 51 ms | **24 ms** | 2.12x |

Halved on both, n=15 each. The frame totals move 340 → 326 ms and 428 → 304 ms, but painting's
noise swamps that; the layout column is the measurement of the thing that changed.

## The tests

`Laid` cannot be compared with `==` — one of its fields is not a comparable type — so the equality
being asserted is spelled as a dump of every node's box, index and name, which catches a field
nobody thought to look at. Four tests: one layer over a laid tree, four layers added one at a time
against all at once, several at once against one at a time, and a dialog that must still take the
keyboard.

Four breaks, each reddening its own:

| break | reddens |
|---|---|
| the base keeps its standalone index of -1 | the two equality tests |
| every added layer is indexed 0 | the two equality tests |
| a positioned layer is laid at the whole box | the two equality tests |
| **the layer list forgets the layers it added** | **only the keyboard test** |

The last is why that fourth test exists. `keyboard_children` reads the layer list off the laid node,
so a reuse path that rebuilt the children and forgot the layers leaves a modal that traps nothing —
and is green under every assertion about boxes.

## What this did NOT do, and the number that decided it

**Caching the laid tree and scene *across* frames is not here, because the frames this application
paints cannot use it.** Reuse between frames needs the new tree to equal the old one, and:

- building the tree is 5-7 ms, so caching the tree itself saves nothing worth having;
- during interaction every painted frame is a screen change, where the tree is entirely different —
  across three driving passes, **60 of 60 painted frames damaged the whole window**;
- the frames that *would* have been saved are the startup burst, where data arrives and the view
  does not change: about 19 of the first 22 frames painted **zero regions** after costing a full
  layout and scene.

So a whole-tree cross-frame cache would pay a comparison on every interactive frame to save time
only at startup. Reusing *subtrees* — which is what would help a caret moving or a row's text
changing — needs stable identity or keys for nodes, and this toolkit is deliberately a tree of
values rebuilt from nothing each frame. That is a design question about the toolkit, not a cache,
and it is still open.

The 31 other `widget.layout(widget.layered_of(..))` sites in the port, the gallery and curly are
all in unit tests and the screenshot tool rather than in a frame loop, so they are left alone.
