# F280 — the tab strip

Raised 2026-11-12 by the application rather than by a review. `curly gui` wanted a Response/History
switch under its request editor and `lib/ui` had no control for one, so it shipped two buttons with
a comment admitting what they were standing in for. `widget.Role` has had `Tab` and `TabList` since
F275 -- accessibility anticipated the control -- and nothing built them, which is the one shape of
gap an application finds and a fixture never does: the roles were there, so no test was missing.

- [x] **F280** **A tab strip: `controls.Tabs`.** (S; `lib/ui/controls.zm`, 10 tests)

  **Selection follows the focus.** Arrowing along the strip changes what is shown with no second
  keystroke -- the automatic-activation model, which is the one to use unless revealing a panel is
  expensive. So `TabStep` reports only `moved` and has no `activated` beside it; a tab that has to
  be opened as well as reached is the manual model, and nothing has asked for it.

  **One tab stop, one node per tab**, which is `List`'s bargain and taken for the same reason: Tab
  reaches the strip, the arrows move within it, and each tab is a `widget.part_of` that a click and
  a reader can reach and Tab cannot. A window with four tabs does not spend four stops on them.

  **Not a `List` with another role, though a menu is one.** `List.role` is a field precisely so
  that a menu's popup can be a list, because a menu differs from a list only in what a reader calls
  it. A tab strip differs in three ways -- it runs along a row, its arrows are Left and Right, and
  it does not scroll -- and three differences is a control rather than a field.

  **`tab_width` is one number used by both the widget and the hit test**, and that is the design
  decision worth keeping. Tabs measured to fit their own labels would need the font metrics inside
  `tabs_input` as well, which means laying the strip out twice -- and two computations of one
  layout is how a click lands on the tab beside the one it looks like it hit. The test that pins
  this sweeps a point across the strip and asserts, at every step, that the part `focus.control_at`
  finds is the tab `tabs_input` chose. Stepped by 7 against tabs of 50 so the walk crosses both
  boundaries instead of sampling the middle of one tab three times.

  Verified by mutation, since a gate is worth what breaking the code proves. Widening the widget's
  tab by four points while leaving the hit test alone is caught by the agreement test **and by
  nothing else**; making `moved` always true is caught by two tests; dropping the upper bound of
  the press range is caught by one. The clamp is clamped rather than wrapped, as the list's arrows
  are: the end of a strip is a place a user can feel.

  A wheel over the strip does nothing. Some toolkits cycle the tabs with it, and the result is a
  user scrolling a page and changing what the page is.

  `curly gui` uses it (curly, same day), which closed the comment that raised this: the strip is
  announced over AT-SPI as `page tab list: "Panes"` with `page tab: "Response" [selected]`, so the
  ATK mapping F275 wrote needed nothing added.
