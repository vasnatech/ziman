# F298 to F301 — four more controls

Opened 2026-11-19. The control set covers eighteen controls and the four below are the ones two real
applications wanted and could not have. Nothing in the look-and-feel programme is needed first: D5's
state rows, D6's space scale and D8's accent are what these are built out of, which is the test of
whether that programme produced a vocabulary or a pile of names.

**Each of these is one control, and the gates say what one control costs here**: a `widget.Role` and
its three mappings, a demo and its design file, an arm in each of `demos/all.zm`'s seven switches, a
line in `docs/lib` that is generated rather than written, and tests that assert what a user would
hear and see rather than what the code does.

The set was chosen for what applications ask for, not for completeness. A toolbar and a status bar
are a row of icon buttons and a label; a breadcrumb is a row of links. Those are arrangements, and
arrangements belong in an application until two of them agree.

Effort: **S** = a day or less, **M** = a few days.

- [x] **F298** **A switch**, which is not a check box. (S; `lib/ui/controls.zm`,
  `lib/ui/{widget,a11y}.zm`, `lib/ui/desktop/atspi.zm`, `src/native_a11y.c`, a demo, 6 tests.)

  **The distinction is the user's, not the drawing's.** A check box is a choice committed with the
  rest of a form; a switch takes effect the moment it moves. That is why it is its own
  `widget.Role` rather than a check box with a different shape: every reader on every platform says
  "on" for one and "checked" for the other, and a switch announced as "check box, Dark mode,
  checked" is the announcement describing the drawing.

  So `toggle_word` now takes the role, and `Role.Switch` maps to `ATK_ROLE_TOGGLE_BUTTON` — ATK has
  no switch of its own, and a toggle button is what GTK's own `GtkSwitch` reports.

  **An on switch is `style.accent`, not `states.selected.face`.** Being on is the control's *value*,
  not its *state*; the five rows govern hovered, pressed and disabled. F295 derives the selection
  tint from `a[3]` of the accent ramp, so the principled-looking choice would have drawn a solid
  control in a pale wash. The knob is `on_accent`, the one paint guaranteed to read on it.

  **Two keyword collisions, both of which cost a compile.** `switch` cannot be a field name, so
  `SwitchStep` carries `control` where every sibling step names the field after its control; and it
  cannot be a module name either, so the demo is `demos/switches.zm` titled "Switch".

  **The knob is placed by a flexible gap, not by arithmetic** — `Along.Start` or `Along.End` inside
  the track — so it stays inside a track of any width at any density, and the test asserts both ends
  rather than one.

- [x] **F299** **A progress bar**, determinate and indeterminate. (S; `lib/ui/controls.zm`, the
  role's four places, a demo, the gallery's first animation, 6 tests.)

  curly runs HTTP requests and a response in flight has nothing to show for it, which is the gap
  this closes.

  **The fill is a hard-stopped gradient, and that is not cleverness — it is the only thing the
  model can say.** A progress fill is a *proportion* of whatever width the bar is given, and the
  widget tree has no proportional container: `Flex` is empty space and `Sized` is absolute, so a
  nested box cannot be 40% of its parent. Gradient endpoints have been fractions of the painted box
  since F294, so two stops at one offset put the edge at exactly 40% of any width at any density,
  with no arithmetic and no second node. Checked against the rasteriser before being relied on:
  pure colour either side of the stop, no blend.

  Two things fall out of it. The fraction ends up **literally in the paint**, so the test reads the
  number back out instead of counting pixels or asserting a width that depends on the window. And
  the capsule clips its own fill, which is the other thing a nested box would have had to round for
  itself.

  **`Progress` is two cases, not a number with a sentinel.** A bar whose value is `-1.0` for "I do
  not know" is a bar every caller must remember to check, and the one that forgets draws a finished
  job as one that has not started. They are announced differently too — a percentage against
  "busy" — so the difference has to survive as far as the reader, which a sentinel does not.

  **The phase comes from the application, and the gallery grew a tick for it.** `lib/ui` has no
  clock and is not going to get one: a library that reads the time cannot be tested by handing it a
  value. So `all.tick_of` answers `Option<Demo>` — nothing, for the twenty-one demos that do not
  move — and the loop marks the frame dirty only when it answers, because otherwise the gallery
  would repaint twenty still pictures sixty times a second to animate one bar.

  **It is the second demo with nothing Tab can reach, and for a different reason than the first.**
  A scroll bar is not a tab stop because the content it scrolls is what a keyboard user moves
  through; a progress bar is not one because there is nothing to operate at all. The gallery's
  smoke test names both rather than deriving a pattern, so a third has to be argued for.

- [x] **F300** **A number field with steppers.** (M; `lib/ui/controls.zm`, the role's four places,
  a demo, 12 tests.)

  **It carries text and answers a number, which is the decision the control exists to get right.**
  `-` is not a number and is on the way to one; so is `1.`; so is an empty field. A field holding a
  `float` cannot represent any of them, which is what makes a spin button infuriating on every
  platform that ships one: it rewrites `-` to `0`, or refuses the keystroke, and either way the
  field cannot be typed into backwards.

  **Nothing is clamped until it is committed**, and the test that pins it is the one that would
  have been impossible otherwise: into a field bounded 10 to 20, typing `15`. A field clamping each
  keystroke turns the `1` into `10` and the `5` after it into `105`, clamped again to `20` — so the
  value is unreachable and the field untypable. Steppers, Enter and losing the focus clamp, because
  pressing a stepper is not being in the middle of anything.

  **One rule governs every edit: could this text still become a number?** A character whitelist was
  the obvious alternative and is wrong in both directions — it lets `--` and `1.2.3` through and
  still has to special-case the sign and the point. Asking whether the text could still parse also
  makes `inf` and `nan` unreachable by typing, because `i` and `n` are not on the way to anything.

  And rather than *predict* the text a keystroke would produce — a second copy of `edit`, wrong in
  a different way per input — the field lets the editor do the edit and **vetoes a result that
  could never be a number**. One rule covers typing, pasting, deleting and replacing a selection.

  `number_in` answers `Option<float>`, because "no number yet" is a real state and zero is a lie: a
  caller handed `0.0` for a field showing `-` writes a port of zero into a config. The demo's
  caption prints "(no number yet)" to show it.

  **`entry_widget` was split so a field can be something other than a text field.** The number
  field needed the entry's text box — caret, selection, preedit — under `Role.SpinButton` rather
  than a second copy of it, which is the argument `masked` and `rows` already make. Two nested
  controls would have been two tab stops and two things for a reader to announce.

  **The tenth victim of `fixed_of(w, 0.0, child)`.** It means a height of *zero*, not "no opinion",
  and survives only while a parent stretches it back out — a row does, a column does not. The
  design file put the field in a column and it vanished, caret measuring −8 points. `wide_of` is
  the spelling; `widget.Fixed.constrains` carries the other nine. What caught it was the gallery's
  `no_demo_paints_into_no_space`, and it had to be: the trap is contextual, so a library test can
  only reproduce it by wrapping the control the way the careless caller did.

- [x] **F301** **A tooltip.** (M; `lib/ui/controls.zm`, `widget.tip_in`/`text_of`, a demo, the
  gallery's tick and layer signatures, 6 tests.)

  **Newly possible**: F294's `Frame` carries the pointer's name, so a control can know it is
  hovered — before 2026-11-18 that information did not reach a paint function at all.

  **Its words are derived, and that is the whole design.** Every platform's tooltip advice is the
  same warning: a tip that says something other than the accessible name is a control that reads
  one way to a sighted user and another to a reader, and the user who needs the name most gets the
  one nobody proofread. `widget.tip_in` takes the words from what the control already declares —
  its description, or its label when it has none — which makes that disagreement
  *unrepresentable*. There is one string, and a tip is a second way of showing it.

  That is also why no control grew a `tip` field. An icon button is the control a tooltip exists
  for, because its label is the thing the tip reveals, and it already declares one through
  `announced_name`.

  **A tip says nothing when the words are already on screen.** `widget.text_of` walks the control's
  own subtree, so a labelled button gets no tip and an icon-only button does — without anything
  being switched off per control. The emergent case is the nicest: the number field's tip is its
  range, because the value is drawn and the bounds are not.

  **The pause is a value threaded through the loop, like the focus.** `Hover` carries the name and
  the milliseconds; the window says how much time passed and `hovering` says what it means.
  Arriving counts zero — the pointer got there at some unknown point inside that frame — and moving
  to another control starts the wait again, so a pointer crossing a toolbar of eight buttons leaves
  no tips behind it.

  **It takes no keys, and it is static text rather than a control.** A layer that claimed the
  keyboard would let a tip steal the focus by appearing, which is the one thing it must never do:
  it is a consequence of the pointer resting and the user never asked for it. There is deliberately
  **no `Role.Tooltip`** — the words are the control's own, announced when the control is reached, so
  a role would put a second thing in the tree saying the same sentence.

  Two gallery signatures changed to make the demo possible, and both changes are honest: `tick_of`
  takes the frame, because a tip is driven by time passing and needs to know where the pointer is;
  `layer_of` takes the laid tree, because a layer whose content comes from the hovered control has
  to ask the tree what that control declares.

- [x] **F302** **The disclosure arrows become paths**, and two fields leave `Style`. (S;
  `lib/ui/controls.zm`, `lib/ui/theme/theme.zm`, the gallery, three files in curly, 2 tests
  rewritten.)

  **Found by looking at a rendered picture, not by a test.** Every combo box in the theme designer
  drew a hollow box where its arrow should be. `Style.collapsed_mark` and `Style.expanded_mark`
  were strings holding `▸` and `▾`, and **Liberation Sans has neither** — it is the first font the
  gallery's candidate list finds on this machine, so the real window drew `.notdef` in every combo
  box and every expandable tree row.

  The library already knew. `controls.zm` carried the sentence *"The tree's arrows are still
  strings, and this is the argument that they should not be"*, written when the check box's mark
  became a path for exactly this reason — and both applications had worked around it rather than
  fixing it: **five `with style { collapsed_mark: ">", expanded_mark: "v" }` across two
  repositories**, each one a thing somebody had to know.

  A path needs no font, so there is nothing to know and nothing to replace. The two fields are
  gone, the five overrides with them, and `controls.chevron` is one shape used by both the tree and
  the combo box — which is also one fewer pair of things that can drift apart.

  **Both tests kept their claim and changed their mechanism.** "A collapsed combo box says it
  opens" and "a tree's mark is clear of its own focus ring" are still the assertions; they look for
  a small fill at the trailing edge, or the leftmost of text *and* fills, instead of a glyph. The
  second mattered: the arrow is the leftmost thing in a row, so a test that still looked only at
  text would have quietly stopped covering the thing it was written for.
