- [x] **A7** **`NaN` breaks `Map`/`Set`.** Canonicalise it in `hash` and wherever the collections use equality, so `compare` and key lookup agree; document that `==` and `compare` deliberately disagree on `NaN`. (L2 P0-3; S) A `Set<float>` holds two copies of a value `contains` denies, and `Map<float, _>` grows without bound on repeated `set` of one key while `map_get` returns `None` -- because `compare(nan,nan)==0` while `nan==nan` is false. Worse than Rust (no `Eq` on floats) and Java (normalises NaN). Done 2026-10-06: the trie hashed both NaNs to the same slot already (value_hash normalises -0.0 and now canonicalises every NaN encoding to one quiet NaN), so the defect was entirely in `keys_equal` calling `value_equals`, whose IEEE `a == b` is false for NaN -- the leaf reached its own slot and then compared unequal to itself, so the trie filed a second copy nothing could reach. `value_equals` is also the `==` operator, so it could not simply change: split into a shared `equals_inner(a, b, nan_reflexive)` with `value_equals` (IEEE, for `==`/`!=`) and `value_key_equals` (reflexive on NaN) over it, threading the flag through the recursion so a NaN nested in a struct or array key behaves the same. `contains` uses the key form too, since one builtin serves arrays, maps and sets and must answer "is this present" the same way for each. Verified that `==` stays IEEE at float, array and struct depth. Reachable from untrusted input: `parse_float("nan")` succeeds, and `0.0/0.0` is a runtime error so this was the way in. tests/lang/nan_map_set_key.zm; documented in SYNTAX.md's Map/Set bullets.
- [x] **A8** **Invalid UTF-8 escapes through the JSON and HTTP output boundaries.** Validate, or substitute U+FFFD, in the JSON string encoder. (L2 P0-2; S-M) A `substring` that splits a code point flows through `#[derive(Json)]` into a document Python's `json` rejects and Ziman's own `parse_json` accepts -- so it passes every in-language test and fails at the client. The asymmetry is the defect: no fixture can catch this by construction. Done 2026-10-06: reproduced both halves first, including the one that made it invisible -- `{"text":"caf\xc3"}` was refused by Python's `json` with an explicit decode error and accepted by this project's own `parse_json`, so a Ziman round-trip test could not see it. `put_json_string` (src/native_json.c) copied every byte above 0x20 through; it now decodes each sequence and substitutes U+FFFD for an invalid one, resynchronising a byte at a time the way decoders do. Substituting rather than returning a Result was deliberate: the alternative changes the signature of every encoder and of every derived `*_to_json`, for an input the caller usually cannot do anything about, and lossy-but-well-formed is what encoders and browsers already do. No second validator was written -- prelude.c's `utf8_decode_strict` (strict about overlongs, surrogates and out-of-range) moved to a header-only `src/utf8.h` so both ends of the pipe share one judgement about what counts as text. Note the source of the bad text is not `bytes_to_string`, which already refuses: it is `substring`/`char_at`/`index_of`, which work on byte positions by design. tests/lang/json_invalid_utf8_output.zm covers valid text of every width passing through untouched, a 3- and a 4-byte character truncated at each point, a derived encoder, and that control characters still escape rather than being replaced; every JSON line it emits was checked to decode in Python. json.zm's own doc comment promised the old behaviour and was corrected. Not changed: `parse_json` still accepts invalid UTF-8 on input, which is lenient-in-what-you-accept rather than a defect that reaches a client, and the HTTP body path, where bytes may legitimately not be text.
- [x] **A9** **`float_from_json` saturates a large JSON integer through `int64`.** (D2 item 2, D2 B2; S) A 30-digit JSON integer comes back saturated rather than as an error or a correct float -- silent data corruption, found on a medical measurement in the reference backend. - [x] **A12** **A dead `spawn`ed thread leaves a blocked `receive` hanging forever.** Close a channel whose only remaining peer has ended so the `receive` fails with a diagnostic; document the supervision pattern `server.serve`'s `on_error` already demonstrates. (L2 P1-7; M) `tests/lang/error_stack_trace_spawned_thread.zm` relies on the harness timeout for exactly this reason and its own comment says so. Independently corroborated during the review itself: a scratch program was still hung 55 minutes later. The actor pitch needs its third leg. The cheap interim mitigation is the `--lint` rule in F9. Done 2026-10-06, by detection rather than by closing channels. Reference-counting senders per channel was the suggested route and is the fragile one: get it wrong and you either invent a deadlock or restore the hang. Instead the test Go uses -- if every live thread is blocked on a channel then nothing can ever send, so no blocked thread can ever wake. Each indefinite wait (`channel_receive`, and `channel_send` on a full bounded channel) uses a 100ms timed wait and re-asks that global question; two atomics count live threads and blocked ones, and the condition must hold across two consecutive polls, so a transient mid-update read cannot fire it. Threads are counted from the parent *before* pthread_create, since counting from inside the new thread leaves a window where it is live but invisible. Deliberately conservative: a thread computing, sleeping or in a syscall is live and not blocked, and `receive_timeout` does not count, so it fires only when every thread really is waiting on a channel. Raising an error rather than closing the channel matters because `receive_option` answers None on a closed channel and would have turned the hang into a silent wrong answer. - [x] **A16** **`add_thread` recurses unbounded with a VLA frame, and allocates quadratically beside it.** Bound it (`src/regex.c:747`): a stack check now, a worklist properly, and a documented cap on `n_inst x ncap`. A capacity check at `:759` would fix neither half. **Done 2026-10-08, both halves, and the two limits already in the file are why neither was caught.** `MAX_INSTRUCTIONS` (20,000) bounds the program and the nesting limit (200) bounds depth, but the capture buffers are `n_inst x 2 x (n_groups + 1)` ints and **nothing bounded that product** -- 6,000 groups is 12,003 instructions, inside the instruction limit, and wide, so the nesting limit never sees it.
