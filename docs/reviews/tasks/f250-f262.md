- [x] **F250** **`FIELD_ATTRS` is gone: a generator declares the field attributes it owns.**
  (user-raised 2026-10-30, listing the eight validation constraints: "let finish all"; L. §5a of
  docs/design/user-generators.md, built for the bundled generators.)

  F249 took the *meanings* out of the compiler. This takes the **names**. `src/parser.c` held
  eleven of them with their argument grammars, so a constraint was a line in the compiler as well
  as in its generator -- and a project could not have an attribute of its own at all, which is the
  gap the user found by asking what happens to someone with no access to the C.

  `derive_validate.zm` declares its nine and `derive_entity.zm` its two, as
  `pub fn attributes() -> [meta.AttrSpec]`. **A function rather than a `pub val`**: C already calls
  a generator by qualified name, so this reuses `ziman_call_in_module` instead of adding val
  lookup. A generator owning none does not export it.

  Three pieces: `meta.AttrSpec`/`attr_spec`; `ziman_generator_attr_specs` in `src/generators.c`,
  which calls `attributes()` on every loaded generator and caches the union; and
  `ziman_check_field_attributes` in `src/derive.c`, the pass itself, run once per module from
  `generate_derived_functions` -- which the loader already calls for every module. The checking
  helpers moved out of the parser with it; `field_attr_list_push` stayed, which is the parsing half.

  **The check could not stay at parse time**, because no generator has loaded while a file is being
  parsed. It is a pass of its own now, and `FieldAttr` has carried `line`/`col` all along, so a
  refusal still lands on the attribute itself. Two properties were worth keeping and both are kept:

  * **The pass walks the module's structs, not its derives**, so a misspelling on a struct that
    derives nothing is still refused. That is the entire reason the table was in C -- a generator
    only ever sees declarations it is asked to generate for.
  * **A module with no field attribute never asks**, because collecting the specs loads five
    thousand lines of Ziman. Nearly every module has none; one that carries an attribute is
    deriving something in practice and would load the generators anyway.

  What is not built is the per-*module* part: the union is global, and a project's own generator,
  found through the importing module's `use` list, needs it keyed per module plus a rule for two
  generators claiming one name. Both wait on the bridge (§12.2).

  **A grep for any of the eleven names in `src/` now finds nothing** but three unrelated hits
  (`math.min`, `len`/`size` in two did-you-mean suggestions). The compiler knows `derive`, `from`
  and ten language attributes; it knows no annotation that is a fact about a library.

  1,333 fixtures, and the North Star's derived output byte-identical at 34,800 lines.

- [x] **F251** **`#[pattern(regex:)]`, and the proof that adding an attribute no longer touches the
  compiler.** (user-raised 2026-10-30; XS.)

  Jakarta's `@Pattern`, the one constraint `docs/design/validation.md` designed and deferred as
  "the ninth, when something needs it". **The interesting part is the diff.** By the time something
  needed it, `FIELD_ATTRS` was gone (F250), so it was:

  * one line in `lib/core/derive_validate.zm`'s own `attributes()`
    (`meta.attr_spec("pattern", "regex:string,message:string?")`),
  * one case in its `rule_for`, and its entry in the `accepted` shape table,

  and **nothing in `src/` at all**. The compiler's "a struct field takes one of: pk, column, …"
  listing grew by itself, which is the first end-to-end evidence that a project could add an
  attribute of its own -- what user-generators.md §5a was written for. The rule itself
  (`validate.matches`) had been there since F246.

  **Named `regex:`, not positional**, for `#[column(name:)]`'s reason: a lone value reads fine
  until a second argument exists, and `message:` is that second argument already.

  **The pattern is quoted on the way out**, like a `message:`, and that is not cosmetic -- a regex
  is mostly backslashes. `"^\\d{3}$"` in source is `^\d{3}$` after the lexer, is re-escaped into
  the generated literal, and reaches `regex.compile` as `^\d{3}$` again. Getting it wrong would
  have been invisible until a pattern with a `\d` in it stopped matching, so
  `tests/lang/derive_validate_pattern` carries one on purpose.

  Four fixtures: the generated text, it run (including that `#[not_blank]` failing first means the
  pattern's message is not the one reported), and the refusal for a missing `regex:` -- whose
  message comes from the *generator's* spec rather than from the compiler.

- [x] **F253** **A derive target and a field attribute are one parser; `Decl.arg` becomes
  `args`.** (user-raised 2026-10-30: "2" -- the first half of docs/design/user-generators.md §5b;
  M.)

  A target took **one bare string** and nothing else -- `#[derive(Entity("patients"))]`, the only
  use in existence -- so `#[derive(Endpoint(method: POST, path: "/orders"))]`, the shape the user
  asked §5b for, could not be written at all. Field attributes had carried named arguments with
  kinds since F245.

  `parse_attr_args` is now the one reader for both, and `meta.Decl.arg: Option<string>` is
  `args: [AttrArg]`:

      #[derive(Reflect(method: POST, path: "/orders", retries: 3))]
      //   args=[method=POST:name, path=/orders:string, retries=3:int]

  **The kind is the part that matters.** The lexer takes the quotes off a string, so
  `Entity("patients")` and `Entity(patients)` arrive with the same text and only `kind` tells them
  apart -- which is why `meta.decl_attr_arg` answers the whole argument and not just its value.
  `meta.decl_arg(d)` is the convenience for the lone `value` argument, which is where a bare one
  lands (`#[min(8)]`'s convention).

  **A refusal had to be re-homed rather than kept.** The parser rejected `#[derive(Entity(patients))]`
  -- a bare word reads like a type name -- and the generic reader accepts it as kind `name`. That
  check is `derive_entity.zm`'s now, which is where §5b says it belongs, and the message names both
  spellings. `derive_entity_table_not_a_string` failing is what caught it.

  **`Target.label` is not a derive argument**, and conflating the two broke 24 fixtures before
  `no_label`/`some_label` were separated from `no_args`: a label is one optional string a *module*
  attribute carries, which is what an `Option` is for.

  §12's own ordering was wrong about this step, and the entry now says so: it claimed the grammar
  "needs (2)'s `use`-list walk and nothing else", which is true of a *user* generator declaring its
  target's spec and not of the grammar, so this shipped before (2). §12.1 was stale too -- the
  bridge it listed as outstanding shipped in F225-F229.

  1,336 fixtures; the North Star's derived output byte-identical at 34,800 lines.

  **What is left of §5b** is the larger half: `use`-list discovery, so a target name resolves
  through the importing module's `use` list instead of a `strcmp` over seven, and then
  `#![repository(E)]`/`#[repository]` migrating onto `derive`.

- [x] **F254** **A project can write its own derive: `use`-list discovery.** (user-raised
  2026-10-30: "do 2" -- docs/design/user-generators.md §12.2; M.)

      // tests/lang/derive_user_generator/
      #![generator(Csv)]            // derive_csv.zm -- a project's module, not the compiler's
      use derive_csv                // main.zm
      #[derive(Csv)]
      struct Customer { id: int  name: string  balance: float }
      // -> pub fn customer_csv_header() -> string { return "id,name,balance" }

  **Nothing in `src/` knows the name `Csv`.** `#[derive(X)]` walks the deriving module's own `use`
  list for a module carrying `#![generator(X)]` and falls back to the bundled set -- §3's rule, no
  manifest and no search path. `UseDecl` gained a `resolved` module the loader fills in
  (`link_uses`), so discovery needs no `Loader`; the lookup really was `resolve_repository`'s walk
  with a different attribute, as §12.2 predicted.

  **What §12.2 did not predict is the ordering, and it was the whole of the work.** `typecheck`
  runs in `main.c` after `load_module_graph` returns, and generation runs *during* loading. So a
  generator module sitting in the user's graph has resolved names and **no resolved slots**, and
  calling it segfaults -- the interpreter reads `resolved_depth`/`resolved_slot`. Type-checking
  that one module in place does not fix it: `typecheck` wants its dependencies' declarations
  merged, so `meta::Decl` comes back "unknown struct or enum type".

  A user generator is therefore loaded as **its own program** -- a synthetic `use <path>` entry
  against the project root, type-checked in full, initialised, cached by path. Which is what
  `load_generators` has always done for the bundled set, so there is one mechanism and not two.
  The root comes from the use path and `Module.source_file`, both new.

  **§6 called initialisation "the real cost" and it was three lines**, because F247 had already
  built every piece: `ziman_init_module_globals` records the env on `Module.globals`,
  `ziman_keep_globals` keeps it rooted past the program that follows, and `ziman_call_in_module`
  swaps to it. Fixing a two-file `ziman test` bug this morning is what made this afternoon's
  feature small.

  None of the compiler's per-target behaviour applies to a discovered target: no imports it did
  not ask for, no struct-or-enum rule of the compiler's, just its text spliced where the author
  wrote the attribute. The unknown-target refusal now names the seven the compiler knows *and*
  says how to add one of your own.

  1,337 fixtures; the North Star byte-identical at 34,800 lines.

  Left of §12: step 4 (`#![repository(E)]`/`#[repository]` onto `derive`) and step 5 (measure
  `--lsp`), plus §5a's per-module keying and the collision rule.

- [x] **F255** **The identifier-case conversions are native, in the prelude, and there is now one
  of each.** (user-raised 2026-10-30: "lets move snake_case/camel_case ... to string.zm and make
  them native", then "add upper_kebab_case too"; S.)

  Six: `snake_case`, `camel_case`, `pascal_case`, `kebab_case`, `upper_snake_case`,
  `upper_kebab_case`, in `lib/prelude/string.zm`, called bare with nothing imported.

  **Three implementations collapsed into one, which is why native rather than merely moved.**

  * `meta.snake_case` (Ziman) and `src/derive.c`'s `pascal_to_snake` were **the same algorithm
    written twice** -- the same `prev_lower_or_digit` and `prev_upper_next_lower` conditions, in two
    languages, agreeing by inspection and nothing else. The compiler needs `snake_case` before any
    Ziman has run (`Decl.snake_name`, a generator module's name) and a generator needs the same one
    afterwards, which is exactly what a native is for: C calls `ziman_snake_case`, Ziman calls
    `snake_case`.
  * `derive_properties.zm` had a third, `replace(name, Map { "_": "-" })`, which is `kebab_case`.

  **`string` cannot be a module**: it is a reserved type keyword, so `use string` does not parse.
  The user's answer was better than any of the alternatives offered -- the prelude is already split
  into parts and `lib/prelude/string.zm` is one of them, so the file has the name without a module
  needing it, and every caller loses a qualifier instead of gaining one.

  **`camel_case` is deliberately not `snake_case`'s inverse** and was kept that way:
  `camel_case("userID")` is `userID`, where a word-splitting version would answer `userId`. A
  `#[derive(Json)]` key is `camel_case` over a snake_case field name, and `json.snake_keys`
  documents itself as the inverse of *exactly what `camel_case` produces* -- a narrower rule, under
  which `userID` becomes `user_i_d` on purpose. So `snake_keys` keeps its own rule and is not a
  fourth copy of this one.

  **ASCII, and that settled a disagreement rather than introducing one.** `meta.snake_case` used
  the Unicode-aware `to_lower` while the C used `tolower`, so the two differed for a non-ASCII
  identifier and agreed for every one that exists. It is the C behaviour now -- the one that
  already governed `Decl.snake_name` -- and `tests/lang/prelude_identifier_case` pins
  `ünïcode_näme` through all six so the rule is visible rather than implied.

  Evidence the move preserved behaviour rather than my reading of two algorithms: the North Star's
  derived output is **byte-identical at 34,800 lines**, and `json_snake_keys`' own output is
  unchanged. 1,338 fixtures.

- [x] **F257** **The sample backend moves onto `#![derive(Repository(E))]`.** (user-raised
  2026-10-30: "keep goint" -- step 2 of three for docs/design/user-generators.md §12.4; S.)

  24 module attributes and 80 function attributes across 24 files, and **the derived output is
  byte-identical at 34,800 lines** with the application's own suite green (64 suites, 2,670
  checks). That is the proof the two spellings are one feature rather than two.

  **The migration found a hole in the attribute grammar**, which is the thing worth keeping.
  `crud: false` would not parse:

      an attribute argument is a string, a whole number or a name

  `true` and `false` are **keywords, not identifiers**, so `parse_attr_args` had no arm for them.
  The hand-written `#![repository]` parser matched `TOK_FALSE` directly, so nothing had ever needed
  the generic reader to. There is a `bool` kind now -- through `check_field_attribute`, the
  `as_written`/`needed` wording and `field_attr_spec_text`, so a generator can declare
  `cache:bool?` and a wrong kind reads as *"'#[min]'s 'value' is true or false and has to be a
  whole number"*.

  **Why it surfaced here and not in F253**, which is the general lesson: F253 replaced two parsers
  with one and the survivor was the *field-attribute* reader, which had never needed a bool because
  no field attribute takes one. Unifying two grammars does not reveal what only one of them
  handled -- migrating real call sites onto the survivor is what does.

  This repository's own 55 fixtures stay on the old spelling on purpose: it still works, and they
  are the only coverage of it left until step 3, when they all have to move anyway. 1,340 fixtures.

  the generators declare, a module attribute against its four, a variant attribute against

- [x] **F261** **A project's generator can have field attributes of its own.** (user-raised
  2026-10-30, item 3 of six; §5a's per-module half; M.)

      use derive_csv                    // #![generator(Csv)]; attributes() declares csv_column
      #[derive(Csv)]
      struct Customer {
          #[csv_column(name: "ID")]     // this project's attribute, not the language's
          id: int
          name: string
      }
      // -> pub fn customer_csv_header() -> string { return "ID,name" }

  **This is the gap §5a was written about** -- "a derive that cannot read `#[csv_column(name:)]`
  can only ever see a field's own name" -- and F250 built only half of it: the spec union was
  global, collected from the *bundled* generators, so a user generator's `attributes()` was never
  asked and `#[csv_column]` came back "unknown field attribute". Verified before building, which is
  what made it worth building.

  `ziman_module_attr_specs(module, ..)` is the bundled union plus every generator in **this
  module's** `use` list. So the attribute means something exactly where its generator is imported
  and is refused everywhere else, with the list of what a field there may carry -- the rule
  discovery already follows for the target itself (§3), and what keeps a project's attribute from
  becoming vocabulary.

  **A name two imported generators both claim is refused at the second import**, naming the
  attribute and one claimant: a generator cannot qualify its own attributes (`#[csv.column]` is not
  a shape the grammar has), so the collision belongs to whoever imported both and the only
  resolution is to stop.

  Reading needed nothing new -- `meta.Field.attrs` has always carried every attribute generically,
  so once the check accepts the name, `meta.attr_value(f, "csv_column", "name")` reads it. The
  spec list is built per call rather than cached, since the answer depends on the module and the
  check asks once per module and only when one carries a field attribute at all.

  1,344 fixtures; the North Star byte-identical at 34,800 lines.

- [x] **F262** **Module-generator discovery: the refusal says the real reason, and §5c says what
  would settle it.** (user-raised 2026-10-30, item 4 of six; XS, and deliberately not the feature.)

  `#[derive(Csv)]` on a struct can be a project's own (F254). `#![derive(Csv(..))]` on a module
  cannot, and **the reason is not discovery** -- which is what my own first wording implied:

      '#![derive(Csv)]' is not a module generator this compiler can seat -- the only one is 'Repository'

  That reads as an allowlist the compiler keeps by design. The truth is that there is **nothing
  decided for a module generator to receive**: `meta.Target` is `{ entity: Decl, label, crud,
  defined }` -- the repository idea reified. A project's module generator has no entity, and
  handing it one would bake `Repository`'s shape into the mechanism, which is the same mistake as a
  domain name in the compiler wearing a different hat. F258 took `repository` out of the parser's
  vocabulary; seating every module generator on an entity would put the *idea* back where the name
  used to be.

  So the message now says that, and §5c of user-generators.md carries the shape that would settle
  it -- `ModuleTarget { args, functions, defined }`, with the two existing entry points generalised
  -- **and the asymmetry worth knowing before starting**: `Repository` needs its entity *resolved*,
  which only the loader can do, so either `ModuleTarget` keeps an `Option<Decl>` that one generator
  fills and the rest ignore (a field nobody reads, which meta.md argues against) or `Repository`
  keeps a specialised input and there are two kinds of module generator after all.

  **Not built, and the reason is the same one that stopped item 2**: nothing is asking. No module
  generator but `Repository` exists or has been requested, and designing `ModuleTarget` for a
  hypothetical one is the speculative plumbing this codebase's own comments argue against -- "a
  field nobody reads is a promise that cannot be taken back". The decision is written down so it is
  available rather than re-derived.

  The document's status line is accurate now: built, except this.

- [x] **F263** **`read_text` over spans rather than a character at a time, to pay back the cursor's
  2x.** (raised 2026-11-02 while converting the XML scanner to `io.Cursor`; S. **Done 2026-11-03:
  1.65x, and the prediction below about beating the array scanner was wrong** -- the resolution is at

  `xml.events` needs -- and it cost **2x on a tree parse**, measured on a 235 KB document with some
  accented text: 223 ms as an array, 463 ms as a cursor. Accepted deliberately (the alternative was
  two copies of seven access helpers and 23 function signatures, which is how two copies drift), and
  this is the entry for earning it back.

  **The overhead is the number of accessor calls per character, not one hot line**, which was
  checked rather than assumed: inlining `at_is` -- several calls per character, the hottest line in
  the parser -- changed nothing (472 ms against 463). `read_text` is where the calls are: per
  character it asks `at_end`, `at_is`, `illegal_char(char_of(..))` and `append(out, char_of(..))`,
  four cursor calls where the array did inline indexing.

  **So read a span, not a character.** `io.find(cs, ["<"], p)` gives the end of the text run in one
  call and `io.span(cs, p, end)` gives the whole run as a string; the per-character work left is the
  illegal-character check and entity expansion, over a string that is already in hand. That is
  fewer calls than the *array* version did, so this should come out ahead of both -- the original
  was character-at-a-time too.

  **Two things to keep while doing it**: an `&` inside the run still has to be expanded by
  `read_reference`, so the span is split on `&` rather than copied whole; and the illegal-character
  refusal must still name the position it found, which means counting within the span rather than
  losing the position to a bulk copy.

  Worth doing when something cares about parse speed -- nothing does today, which is why this is
  filed rather than done. The 2x is on a path that was never the bottleneck in either the sample
  backend's exports or its imports.

  **Done, with one new primitive and one prediction refuted.**

  `io.run_until(c, stops, from)` answers where a run of characters that are none of `stops` ends --
  the first stop, or the **end of the document**, never -1, which is the difference from `find` and
  the reason it sits beside it. Two things fell out of writing it that the entry did not foresee.
  The first is that `find` was the wrong primitive for this at all: a text run with no `&` after it
  would have had `find` read to the end of the document to answer "absent", which would have
  destroyed the streaming property this parser was converted for. The second is where the real win
  came from: `at` has to re-read `base` and `window` on every call because anything may have moved
  between calls, while a run cannot move under itself -- so `run_until` hoists both out of the loop
  and indexes the window directly, doing two cell reads and a call per *chunk* rather than per
  character.

  `read_text` and `read_attr_value` both read runs now. The entry named only the first, and the
  second is half of a document shaped `<entry id="7" kind="note">text</entry>`: stopping at one
  would have paid back half the cost and called it done. `read_text` alone took the bench's 261 KB
  document from 634 ms to 435 ms; the pair took it to 380 ms.

  Both things the entry said to keep are kept and are now pinned by `xml_run_scanning`: an `&` stops
  a run so `read_reference` still expands it, and both refusals still name their position. The
  control-character check scans *bytes* -- a byte below 0x20 is always a standalone ASCII control,
  since every byte of a multi-byte sequence is 0x80 or above -- so its position is converted back to
  characters by `offending_at`, and the fixture's non-ASCII case says line 3 where the unconverted
  index would say line 6. (Checked by breaking it on purpose: a fixture that cannot fail is not
  evidence.)

  **And the prediction was wrong.** The entry reasoned that spans would come out ahead of the
  *array* scanner too, that one having been character-at-a-time as well. Measured on one machine by
  checking out the pre-cursor `lib/core/xml.zm` and building it:

      the array scanner, before io.Cursor      265 ms    515 ms
      the cursor, a character at a time        634 ms   1332 ms
      the cursor, a run at a time              380 ms    838 ms

  So the cursor still costs **1.45x over indexing an array, down from 2.4x**. The runs are no longer
  where the time goes; what is left is the rest of the scan -- names, spaces, delimiters -- still
  asking one character at a time, and the window bookkeeping (`compact`, `line`, and `at`'s two cell
  reads) that an array has no equivalent of. `Frame.line` is computed per start tag rather than
  lazily and that is deliberate, not an oversight: a position can only be turned into a line while
  it is still inside the window.

  Not pursued further, and the reason is the entry's own: nothing cares about parse speed today.
  The numbers are in `tests/bench/xml_scan.zm`'s header so the next person can re-judge rather than
  rediscover.

- [x] **F264** **A request body that streams: three layers, and the one the design document did not
  see.** (raised 2026-11-02 while building `docs/design/byte-streams.md`; M. **Steps 1 and 2 built
  2026-11-03**; step 3 is judged unnecessary and the reasoning is at the end of this entry.)

  `xml.events` and `xml.elements` exist, so a document can be read without being held -- measured in
  the North Star at **1,913 MB to 897 MB** peak resident for a 14.7 MB Apple Health export. What is
  left of that parity gap is the **transport**, and it is a chain rather than a step:

  1. **The server spills a large body.** `ServeOptions.spill_body_bytes` (0 = never, the default),
     and `read_request` writes past the threshold to a file in `os.temp_dir()` instead of
     accumulating. `Request.body` becomes `Body.Bytes([byte]) | Body.Spilled(string)` -- an enum
     rather than a second field, so every reader confronts the two cases instead of silently seeing
     an empty body -- with `server.body_bytes(req)` and `server.body_source(req)` over it. Two read
     paths to touch (`Content-Length` and chunked), and the file's life belongs to `serve`'s
     per-request loop, which is where it must be deleted including when a handler fails.
  2. **`multipart` reads a source.** This is the layer the design document missed, and it is the one
     that decides whether any of this reaches a user: the Apple Health and FHIR bulk uploads are
     `multipart/form-data`, and `server/multipart.zm` parses from `req.body` **in memory**. A spilled
     body therefore gets read straight back in, and the 413 does not move. The part boundaries are
     exactly the kind of scanning `io.Cursor` is for.
  3. **A `rest` handler family that hands a part's source to the handler**, and `#[part]` able to
     bind one -- today it binds a `server.Part` whose bytes are in hand.

  **Step 1 is worth having on its own** -- a 100 MB upload stops sitting in RAM, and `body_source`
  is what anything streaming will want -- but it does not move the North Star's ceiling by itself,
  which is why this is filed as one task with the order in it rather than three that look
  independent.

  **`http.request` (daf86c67) was the prerequisite** and is done: `Request` had no literal left in
  the repository, so adding `Body` to it is a change to one function rather than to every caller.

- [x] **F265** **The admin database endpoint segfaults the server, about one request in six, on
  PostgreSQL.** (found 2026-11-02 by the diagnostic added for it; P0. **Fixed the same day**: a
  guard's message is a crossing copy now and `src/gc_guard_roots.{c,h}` are deleted -- the
  resolution is at the end of this entry, and the full account is "2026-11-02 -- the root source
  whose key was the bug" in docs/design/journal/part-09.md.)

  **`server: exited with -11`.** The server dies of SIGSEGV handling
  `POST /api/admin/database/query`, and it has been doing so all day disguised as a flaky test: four
  occurrences of `admin_database_test.py` failing with `[Errno 104] Connection reset by peer`, each
  dismissed as a connection error because **the file captured the server's output and then discarded
  it unless *starting* it failed**. Closing that gap was the only fix that commit claimed, and it
  reported the real cause on the next occurrence.

  **The reproduction**, on a throwaway `postgres:17`, is about **1 run in 6**:

      TEST_POSTGRES=<container>:<port> python3 -I src/test/other/admin_database_test.py

  **It crashes on the first write-refusal.** The log ends with
  `ADMIN_RAW_SQL_QUERY WITH x AS (SELECT email FROM users) SELECT * FROM x` succeeding, and the next
  request -- `{"sql": "DELETE FROM users"}`, the first statement the endpoint must *refuse* -- never
  answers. Both of the original tracebacks landed on that same loop (line 173), which was the clue
  that it was not noise: a random flake does not pick the same request twice.

  So the suspect path is the refusal rather than the query: `service/admin_database.zm` parses the
  statement with `sql.parse` and rejects a write before touching the database. It has run thousands
  of times on SQLite without crashing, and the crash needs PostgreSQL -- which suggests the
  connection, the driver's own state, or something the two engines do differently around a statement
  that is never executed.

  **Rarity points at the collector**, not at bad arithmetic: a deterministic out-of-bounds would fail
  every time. `--gc-stress` is what found the two mark-phase segfaults fixed in e31d59e5 (a missing
  GC root) and 5468e8e3 (missing handle validation), and is the first thing to try here -- the server
  takes minutes to migrate under it, so run it against an already-migrated database and send the one
  request by hand. `make valgrind` is the second.

  **Not a regression from the streaming work**: first seen before any of it, on 2026-11-02's earlier
  suite runs, and the sqlite pass of every run since has been clean.

  **Resolved: a root source keyed on a recycled address.** The core dump named the site in one read
  -- `gc_mark_enum` <- `gc_mark_live_guards` <- `mark_this_threads_roots`, on a freshly spawned
  request thread, marking an enum at an address gdb could not even read. Walking `g_roots` in the
  core finished it: three live guard records claimed the crashing thread's own `GcHeap *` and all
  three pointed into one unmapped region, while that thread's arena was a single fresh block none of
  them was inside.

  `gc_guard_roots.c` keyed each guard on the `ziman_thread_heap()` pointer of its creating thread.
  That is a `malloc`'d address: `ziman_thread_heap_release`, at a request thread's exit, `munmap`s
  the arena the guard's `message` lives in and frees the struct, and the next thread's
  `gc_heap_create` is handed the same address back -- after which that thread's every collection
  marked a dead thread's guard messages. `open_rows` (lib/db/db.zm) makes a guard per cursor, so the
  crashing request was the one *after* a request that had opened a cursor and exited, and the
  refusal path's innocence was the clue rather than a contradiction.

  The fix is `g->message = value_copy_send(args[1])` in `native_guard_new`: a crossing copy on
  Boehm's shared heap, tied to no thread, traced through the `GuardBuf` itself rather than rooted,
  with the finalizer sending it `needs_receive 1`. That also closes the window no key could have --
  the finalizer sending a message whose arena its creating thread had already unmapped. The registry,
  its global list and the lock every Phase 3 collection took to walk it are gone.

  **Three of this entry's own guesses were wrong, and are left above as written.** It was not the
  refusal path, not `sql.parse`, and not anything PostgreSQL does differently with a statement it
  never runs -- Postgres only made it reproducible, by making requests slow enough that a thread
  exited between two of them. `--gc-stress` was the suggested first move and would not have found
  this: the stale records only matter once a heap address is recycled, which needs a thread to die,
  not more collections.

  **Done, and three things came out differently than written above.**

  **Step 1** is `ServeOptions.spill_body_bytes` (0 is never, and is the default), with `Request.body`
  an enum -- `http.Body` of `Bytes([byte])` or `Spilled(Spill)` -- exactly as the entry wanted, and
  for the reason it gave: the compiler then named all five readers in the library instead of letting
  them see an empty body. The two read paths differ because they have to. `Content-Length` says how
  large the body is before any of it arrives, so that path decides up front and never holds it;
  a chunked body says nothing, so `read_chunked` holds it until it passes the threshold and writes it
  out from there, the alternative being to put every short chunked POST on disk. Both hold at most
  256 KiB at a time, since `fs.append_bytes` opens, writes and closes.

  **Step 2 did not need `io.Cursor`, which this entry expected, and using it would have been wrong.**
  The cursor is a *character* window: it decodes, its spans are strings, its positions count
  characters. A multipart body is bytes -- a part is a JPEG as often as text, and a boundary is
  matched byte for byte -- so the scan is a byte-level one private to `multipart`, with
  `scan_find_discarding` (passes a part's body without holding it) and `scan_find_keeping` (reads a
  header block under an 8 KiB bound). Same shape, different alphabet; it moves into `io` if a second
  byte-level caller appears.

  **And a part is a range of the body's own file, not a copy of one.** `Spill` carries an `offset`,
  so a part of a spilled body is `Spilled { path: <the body's file>, offset, size }` -- the server
  writes the upload once and each part is a window onto it, which is better than the entry's own plan
  (it would have had the multipart layer write every part out again). `io.taking` and `io.skipping`
  are what make a range readable, and `taking` is deliberately not `limited`: one cuts a source to a
  length its caller knows, the other refuses a source that is too large.

  **Step 3 is not needed, which is the one judgement here rather than a measurement.** It asked for
  a `rest` family that hands a part's source to the handler and a `#[part]` that binds one. But
  `Part.body` is a `Body` now, so `#[part(name: "file")] file: server.Part` already *is* a binding
  of a streamable part: the North Star's Apple Health controller reads
  `val export = try uploaded_source(file)` and hands that to a service whose parameter is an
  `Iter<Result<[byte], io.IoError>>`, with nothing on the path from the socket to `xml.elements`
  holding the document. Binding the `Iter` directly would save those two lines and cost a lifetime
  contract hidden in a parameter type -- the source is only valid until the handler returns, because
  the file is deleted then -- plus a rule about which part gets streamed when several are bound. Left
  undone deliberately; reopen it if a handler turns up that reads badly this way.

  **What it bought, stated honestly.** The North Star's 14.7 MB export still peaks at the same
  897 MB, because the document was never the dominant term there -- the records written in one
  transaction are. What changed is that the ceiling is no longer memory: `server.max-body-bytes`
  bounds an upload, and raising it now costs disk. The backend sets `server.spill-body-bytes` to
  1 MiB and leaves the cap at the 16 MiB the attachment endpoint chose, because raising it lets every
  caller write that much to disk -- a judgement about the machine rather than about the API.

- [ ] **F266** **`sql` reads index DDL but not a per-column `ASC`/`DESC`.** (found 2026-11-04 by
  `sql_round_trip`, which is the fixture's whole job; XS.)

  `CREATE INDEX idx ON t (job, started_at DESC)` is refused with *expected ',', found 'DESC'*.
  `parse_create` reads an index "properly rather than swallowed" -- its own comment argues that a
  formatter may not ignore one even though an engine may -- and then takes only bare names:

      while !sees_punct(c, ")") {
          ...
          push(columns, try expect_name(c))
      }

  **Found by a gate doing exactly what it exists for.** The fixture's corpus is the North Star's
  migrations directory, so a migration using a shape the module cannot read turns it red; this is
  the third time that corpus has caught something (V042 and V043 caught a different thing -- a
  recorded file *count*, fixed at ba05f080 by asserting the property with a floor instead). The
  migration in question dropped the `DESC`, which costs nothing because every engine here reads an
  ascending index backwards for a descending order -- so this is a gap in the module rather than a
  blocked caller.

  **What it needs, and why it is not two lines.** `Statement`'s index arm holds `columns: [string]`,
  so keeping a direction means that field becoming a pair -- a name and an optional direction -- and
  the writer emitting it. Both are small; the ripple through `Statement`'s consumers is what makes
  this worth a task rather than an edit in passing. `COLLATE`, a partial index's `WHERE`, and an
  expression instead of a column are the neighbouring gaps to decide on at the same time, since all
  four live in that one loop.

- [ ] **F267** **A call evaluated in argument position runs with the collector switched off for its
  whole duration.** (found 2026-11-04 while measuring the North Star's Apple Health import; P0 for
  any long-running server work, L for the fix.)

  `tests/bench/gc_argument_position.zm` is the whole case in forty lines. The same work twice,
  differing only in where the result is bound:

      hoisted into a val       41620 -> 41660 KB   (grew 40 KB)
      evaluated as an argument 41664 -> 68120 KB   (grew 26,456 KB)

  **661x, for the same function called with the same argument.** That bench fails today and is the
  regression test for this task; benches are run directly rather than by `make check`.

  **Why.** A `Value` held only by C -- in a local, or in a buffer C is part-way through filling --
  is not a root, because the per-thread heap's mark phase is precise and has no conservative scan of
  the C stack. `gc_unsafe_enter`/`gc_unsafe_leave` is how a caller says "not yet", and
  `maybe_collect` skips **entirely** whenever that depth is nonzero. Five sites hold it:
  `src/interpreter.c`'s EXPR_CALL argument array (1403), array literal (1686), struct literal
  (1721) and `with` (1749), plus `call_closure_value` (635), which guards an **entire call** because
  the caller's own `args` array stays live across it. So the guard is held while the later elements
  are *evaluated*, and across a whole closure body -- and whatever those do, however long they take,
  cannot be collected.

  **What it cost in the North Star.** The Apple Health import reaches its handler through several
  nested closure calls, so the whole import is one uncollectable region. Measured against the
  identical per-record work -- same streaming parse, same `parse_instant`, same duplicate check,
  same derived insert -- run from a `main` instead:

      20,000 records, in the server        54.6 s   2,054 MB
      20,000 records, from a main           9.3 s      72 MB

  One 5,000-record import skipped **26 million due collections** (unsafe depth 3-6 throughout),
  the thread's heap reaching 215 MB while its live set never passed 2.4 MB. Boehm's heap is pinned
  with it, because `ziman_arena_push_scanned_roots` pushes every byte the arena has ever handed out
  as a conservative root: Boehm reported `In-use heap: 97%` of 336 MB and its mark time climbed
  88 -> 97 ms over one import, which is where the **superlinearity** comes from. It is not the work.

  **Three things ruled out by measurement, not to be re-tested.** `datasource.execute` in a
  transaction retains nothing (40,000 inserts: 128 bytes a row of SQLite's own pages, exactly
  linear). The derived repository's write path retains nothing (20,000 records: flat at 60 MB,
  252 us each). Making the trigger eight times more eager (`ZIMAN_GC_TRIGGER_DIVISOR` 2 -> 16)
  barely moved it -- 35.1 s / 1,902 MB against 54.6 s / 2,054 MB -- because `maybe_collect` never
  reaches the threshold test.

  **What the fix is.** The guard has to become a root source rather than an off switch: the
  part-built buffer registered the way `t_active_iters` already is -- walked by
  `mark_this_threads_roots` and handed to Boehm through `ziman_interp_root_ranges` -- so a collection
  partway through building one is safe instead of forbidden. `call_closure_value` then guards
  nothing: its `args`/`all` array is a registered range, and the callee's body collects normally.
  The alternative is to give the per-thread mark phase a conservative scan of the C stack, which
  `gc_lookup`'s address-to-block binary search already provides the primitive for; that subsumes
  every C local as well, and is the larger change. Either way `--gc-stress` over the whole suite is
  the gate, since this is precisely the class of bug that flag exists to surface.
