- [x] **F250** **`FIELD_ATTRS` is gone: a generator declares the field attributes it owns.**
  (user-raised 2026-10-30, listing the eight validation constraints: "let finish all"; L. §5a of
  docs/design/user-generators.md, built for the bundled generators.)

  F249 took the *meanings* out of the compiler. This takes the **names**. `src/parser.c` held
  eleven of them with their argument grammars, so a constraint was a line in the compiler as well
  as in its generator -- and a project could not have an attribute of its own at all, which is the
  gap the user found by asking what happens to someone with no access to the C.

  `derive_validate.zm` declares its nine and `derive_entity.zm` its two, as
  `pub fn attributes() -> [meta.AttrSpec]`. **A function rather than a `pub val`**: C already calls
  a generator by qualified name, so this reuses `ziman_call_in_module` instead of adding val
  lookup. A generator owning none does not export it.

  Three pieces: `meta.AttrSpec`/`attr_spec`; `ziman_generator_attr_specs` in `src/generators.c`,
  which calls `attributes()` on every loaded generator and caches the union; and
  `ziman_check_field_attributes` in `src/derive.c`, the pass itself, run once per module from
  `generate_derived_functions` -- which the loader already calls for every module. The checking
  helpers moved out of the parser with it; `field_attr_list_push` stayed, which is the parsing half.

  **The check could not stay at parse time**, because no generator has loaded while a file is being
  parsed. It is a pass of its own now, and `FieldAttr` has carried `line`/`col` all along, so a
  refusal still lands on the attribute itself. Two properties were worth keeping and both are kept:

  * **The pass walks the module's structs, not its derives**, so a misspelling on a struct that
    derives nothing is still refused. That is the entire reason the table was in C -- a generator
    only ever sees declarations it is asked to generate for.
  * **A module with no field attribute never asks**, because collecting the specs loads five
    thousand lines of Ziman. Nearly every module has none; one that carries an attribute is
    deriving something in practice and would load the generators anyway.

  What is not built is the per-*module* part: the union is global, and a project's own generator,
  found through the importing module's `use` list, needs it keyed per module plus a rule for two
  generators claiming one name. Both wait on the bridge (§12.2).

  **A grep for any of the eleven names in `src/` now finds nothing** but three unrelated hits
  (`math.min`, `len`/`size` in two did-you-mean suggestions). The compiler knows `derive`, `from`
  and ten language attributes; it knows no annotation that is a fact about a library.

  1,333 fixtures, and the North Star's derived output byte-identical at 34,800 lines.

- [x] **F251** **`#[pattern(regex:)]`, and the proof that adding an attribute no longer touches the
  compiler.** (user-raised 2026-10-30; XS.)

  Jakarta's `@Pattern`, the one constraint `docs/design/validation.md` designed and deferred as
  "the ninth, when something needs it". **The interesting part is the diff.** By the time something
  needed it, `FIELD_ATTRS` was gone (F250), so it was:

  * one line in `lib/core/derive_validate.zm`'s own `attributes()`
    (`meta.attr_spec("pattern", "regex:string,message:string?")`),
  * one case in its `rule_for`, and its entry in the `accepted` shape table,

  and **nothing in `src/` at all**. The compiler's "a struct field takes one of: pk, column, …"
  listing grew by itself, which is the first end-to-end evidence that a project could add an
  attribute of its own -- what user-generators.md §5a was written for. The rule itself
  (`validate.matches`) had been there since F246.

  **Named `regex:`, not positional**, for `#[column(name:)]`'s reason: a lone value reads fine
  until a second argument exists, and `message:` is that second argument already.

  **The pattern is quoted on the way out**, like a `message:`, and that is not cosmetic -- a regex
  is mostly backslashes. `"^\\d{3}$"` in source is `^\d{3}$` after the lexer, is re-escaped into
  the generated literal, and reaches `regex.compile` as `^\d{3}$` again. Getting it wrong would
  have been invisible until a pattern with a `\d` in it stopped matching, so
  `tests/lang/derive_validate_pattern` carries one on purpose.

  Four fixtures: the generated text, it run (including that `#[not_blank]` failing first means the
  pattern's message is not the one reported), and the refusal for a missing `regex:` -- whose
  message comes from the *generator's* spec rather than from the compiler.

- [x] **F253** **A derive target and a field attribute are one parser; `Decl.arg` becomes
  `args`.** (user-raised 2026-10-30: "2" -- the first half of docs/design/user-generators.md §5b;
  M.)

  A target took **one bare string** and nothing else -- `#[derive(Entity("patients"))]`, the only
  use in existence -- so `#[derive(Endpoint(method: POST, path: "/orders"))]`, the shape the user
  asked §5b for, could not be written at all. Field attributes had carried named arguments with
  kinds since F245.

  `parse_attr_args` is now the one reader for both, and `meta.Decl.arg: Option<string>` is
  `args: [AttrArg]`:

      #[derive(Reflect(method: POST, path: "/orders", retries: 3))]
      //   args=[method=POST:name, path=/orders:string, retries=3:int]

  **The kind is the part that matters.** The lexer takes the quotes off a string, so
  `Entity("patients")` and `Entity(patients)` arrive with the same text and only `kind` tells them
  apart -- which is why `meta.decl_attr_arg` answers the whole argument and not just its value.
  `meta.decl_arg(d)` is the convenience for the lone `value` argument, which is where a bare one
  lands (`#[min(8)]`'s convention).

  **A refusal had to be re-homed rather than kept.** The parser rejected `#[derive(Entity(patients))]`
  -- a bare word reads like a type name -- and the generic reader accepts it as kind `name`. That
  check is `derive_entity.zm`'s now, which is where §5b says it belongs, and the message names both
  spellings. `derive_entity_table_not_a_string` failing is what caught it.

  **`Target.label` is not a derive argument**, and conflating the two broke 24 fixtures before
  `no_label`/`some_label` were separated from `no_args`: a label is one optional string a *module*
  attribute carries, which is what an `Option` is for.

  §12's own ordering was wrong about this step, and the entry now says so: it claimed the grammar
  "needs (2)'s `use`-list walk and nothing else", which is true of a *user* generator declaring its
  target's spec and not of the grammar, so this shipped before (2). §12.1 was stale too -- the
  bridge it listed as outstanding shipped in F225-F229.

  1,336 fixtures; the North Star's derived output byte-identical at 34,800 lines.

  **What is left of §5b** is the larger half: `use`-list discovery, so a target name resolves
  through the importing module's `use` list instead of a `strcmp` over seven, and then
  `#![repository(E)]`/`#[repository]` migrating onto `derive`.

- [x] **F254** **A project can write its own derive: `use`-list discovery.** (user-raised
  2026-10-30: "do 2" -- docs/design/user-generators.md §12.2; M.)

      // tests/lang/derive_user_generator/
      #![generator(Csv)]            // derive_csv.zm -- a project's module, not the compiler's
      use derive_csv                // main.zm
      #[derive(Csv)]
      struct Customer { id: int  name: string  balance: float }
      // -> pub fn customer_csv_header() -> string { return "id,name,balance" }

  **Nothing in `src/` knows the name `Csv`.** `#[derive(X)]` walks the deriving module's own `use`
  list for a module carrying `#![generator(X)]` and falls back to the bundled set -- §3's rule, no
  manifest and no search path. `UseDecl` gained a `resolved` module the loader fills in
  (`link_uses`), so discovery needs no `Loader`; the lookup really was `resolve_repository`'s walk
  with a different attribute, as §12.2 predicted.

  **What §12.2 did not predict is the ordering, and it was the whole of the work.** `typecheck`
  runs in `main.c` after `load_module_graph` returns, and generation runs *during* loading. So a
  generator module sitting in the user's graph has resolved names and **no resolved slots**, and
  calling it segfaults -- the interpreter reads `resolved_depth`/`resolved_slot`. Type-checking
  that one module in place does not fix it: `typecheck` wants its dependencies' declarations
  merged, so `meta::Decl` comes back "unknown struct or enum type".

  A user generator is therefore loaded as **its own program** -- a synthetic `use <path>` entry
  against the project root, type-checked in full, initialised, cached by path. Which is what
  `load_generators` has always done for the bundled set, so there is one mechanism and not two.
  The root comes from the use path and `Module.source_file`, both new.

  **§6 called initialisation "the real cost" and it was three lines**, because F247 had already
  built every piece: `ziman_init_module_globals` records the env on `Module.globals`,
  `ziman_keep_globals` keeps it rooted past the program that follows, and `ziman_call_in_module`
  swaps to it. Fixing a two-file `ziman test` bug this morning is what made this afternoon's
  feature small.

  None of the compiler's per-target behaviour applies to a discovered target: no imports it did
  not ask for, no struct-or-enum rule of the compiler's, just its text spliced where the author
  wrote the attribute. The unknown-target refusal now names the seven the compiler knows *and*
  says how to add one of your own.

  1,337 fixtures; the North Star byte-identical at 34,800 lines.

  Left of §12: step 4 (`#![repository(E)]`/`#[repository]` onto `derive`) and step 5 (measure
  `--lsp`), plus §5a's per-module keying and the collision rule.

- [x] **F255** **The identifier-case conversions are native, in the prelude, and there is now one
  of each.** (user-raised 2026-10-30: "lets move snake_case/camel_case ... to string.zm and make
  them native", then "add upper_kebab_case too"; S.)

  Six: `snake_case`, `camel_case`, `pascal_case`, `kebab_case`, `upper_snake_case`,
  `upper_kebab_case`, in `lib/prelude/string.zm`, called bare with nothing imported.

  **Three implementations collapsed into one, which is why native rather than merely moved.**

  * `meta.snake_case` (Ziman) and `src/derive.c`'s `pascal_to_snake` were **the same algorithm
    written twice** -- the same `prev_lower_or_digit` and `prev_upper_next_lower` conditions, in two
    languages, agreeing by inspection and nothing else. The compiler needs `snake_case` before any
    Ziman has run (`Decl.snake_name`, a generator module's name) and a generator needs the same one
    afterwards, which is exactly what a native is for: C calls `ziman_snake_case`, Ziman calls
    `snake_case`.
  * `derive_properties.zm` had a third, `replace(name, Map { "_": "-" })`, which is `kebab_case`.

  **`string` cannot be a module**: it is a reserved type keyword, so `use string` does not parse.
  The user's answer was better than any of the alternatives offered -- the prelude is already split
  into parts and `lib/prelude/string.zm` is one of them, so the file has the name without a module
  needing it, and every caller loses a qualifier instead of gaining one.

  **`camel_case` is deliberately not `snake_case`'s inverse** and was kept that way:
  `camel_case("userID")` is `userID`, where a word-splitting version would answer `userId`. A
  `#[derive(Json)]` key is `camel_case` over a snake_case field name, and `json.snake_keys`
  documents itself as the inverse of *exactly what `camel_case` produces* -- a narrower rule, under
  which `userID` becomes `user_i_d` on purpose. So `snake_keys` keeps its own rule and is not a
  fourth copy of this one.

  **ASCII, and that settled a disagreement rather than introducing one.** `meta.snake_case` used
  the Unicode-aware `to_lower` while the C used `tolower`, so the two differed for a non-ASCII
  identifier and agreed for every one that exists. It is the C behaviour now -- the one that
  already governed `Decl.snake_name` -- and `tests/lang/prelude_identifier_case` pins
  `ünïcode_näme` through all six so the rule is visible rather than implied.

  Evidence the move preserved behaviour rather than my reading of two algorithms: the North Star's
  derived output is **byte-identical at 34,800 lines**, and `json_snake_keys`' own output is
  unchanged. 1,338 fixtures.

- [x] **F257** **The sample backend moves onto `#![derive(Repository(E))]`.** (user-raised
  2026-10-30: "keep goint" -- step 2 of three for docs/design/user-generators.md §12.4; S.)

  24 module attributes and 80 function attributes across 24 files, and **the derived output is
  byte-identical at 34,800 lines** with the application's own suite green (64 suites, 2,670
  checks). That is the proof the two spellings are one feature rather than two.

  **The migration found a hole in the attribute grammar**, which is the thing worth keeping.
  `crud: false` would not parse:

      an attribute argument is a string, a whole number or a name

  `true` and `false` are **keywords, not identifiers**, so `parse_attr_args` had no arm for them.
  The hand-written `#![repository]` parser matched `TOK_FALSE` directly, so nothing had ever needed
  the generic reader to. There is a `bool` kind now -- through `check_field_attribute`, the
  `as_written`/`needed` wording and `field_attr_spec_text`, so a generator can declare
  `cache:bool?` and a wrong kind reads as *"'#[min]'s 'value' is true or false and has to be a
  whole number"*.

  **Why it surfaced here and not in F253**, which is the general lesson: F253 replaced two parsers
  with one and the survivor was the *field-attribute* reader, which had never needed a bool because
  no field attribute takes one. Unifying two grammars does not reveal what only one of them
  handled -- migrating real call sites onto the survivor is what does.

  This repository's own 55 fixtures stay on the old spelling on purpose: it still works, and they
  are the only coverage of it left until step 3, when they all have to move anyway. 1,340 fixtures.

- [x] **F259** **The declaration-attribute set is closed -- and two things were silent, not one.**
  (user-raised 2026-10-30: "do 1" -- ROADMAP.md's entry, option (1); XS.)

  Every other attribute position refuses a name it does not know: a field attribute against what
  the generators declare, a module attribute against its four, a variant attribute against
  `#[from]`. **The declaration chain had no `else`**, which is `#[deprecated]`'s own history -- an
  attribute the compiler accepts while nothing reads it is indistinguishable from one that works.

  **The worse half is the one I did not know about going in.** A bare `#[foo_bar]` fell off the end
  of the `if`/`else if` chain. But `#[drive(Json)]` reached the branch that reads a **derive target

  the language parsed a derive list, threw it away, and said nothing: a struct that derived
  nothing, quietly. Found by testing the realistic typo rather than the synthetic `#[foo_bar]` I
  had started from. The branch is gated on `is_derive` now and both halves reach one refusal.

  **The migration cost was verified, not asserted**: every `#[..]` name in this repository and the
  sample backend, 29 distinct, and the only ones outside the known sets were `#[into]` (a variant
  attribute, already refused), `#[key]`/`#[not_blak]` (fixtures *of* refusals) and `#[name(..)]`

- [x] **F261** **A project's generator can have field attributes of its own.** (user-raised
  2026-10-30, item 3 of six; §5a's per-module half; M.)

      use derive_csv                    // #![generator(Csv)]; attributes() declares csv_column
      #[derive(Csv)]
      struct Customer {
          #[csv_column(name: "ID")]     // this project's attribute, not the language's
          id: int
          name: string
      }
      // -> pub fn customer_csv_header() -> string { return "ID,name" }

  **This is the gap §5a was written about** -- "a derive that cannot read `#[csv_column(name:)]`
  can only ever see a field's own name" -- and F250 built only half of it: the spec union was
  global, collected from the *bundled* generators, so a user generator's `attributes()` was never
  asked and `#[csv_column]` came back "unknown field attribute". Verified before building, which is
  what made it worth building.

  `ziman_module_attr_specs(module, ..)` is the bundled union plus every generator in **this
  module's** `use` list. So the attribute means something exactly where its generator is imported
  and is refused everywhere else, with the list of what a field there may carry -- the rule
  discovery already follows for the target itself (§3), and what keeps a project's attribute from
  becoming vocabulary.

  **A name two imported generators both claim is refused at the second import**, naming the
  attribute and one claimant: a generator cannot qualify its own attributes (`#[csv.column]` is not
  a shape the grammar has), so the collision belongs to whoever imported both and the only
  resolution is to stop.

  Reading needed nothing new -- `meta.Field.attrs` has always carried every attribute generically,
  so once the check accepts the name, `meta.attr_value(f, "csv_column", "name")` reads it. The
  spec list is built per call rather than cached, since the answer depends on the module and the
  check asks once per module and only when one carries a field attribute at all.

  1,344 fixtures; the North Star byte-identical at 34,800 lines.

- [x] **F262** **Module-generator discovery: the refusal says the real reason, and §5c says what
  would settle it.** (user-raised 2026-10-30, item 4 of six; XS, and deliberately not the feature.)

  `#[derive(Csv)]` on a struct can be a project's own (F254). `#![derive(Csv(..))]` on a module
  cannot, and **the reason is not discovery** -- which is what my own first wording implied:

      '#![derive(Csv)]' is not a module generator this compiler can seat -- the only one is 'Repository'

  That reads as an allowlist the compiler keeps by design. The truth is that there is **nothing
  decided for a module generator to receive**: `meta.Target` is `{ entity: Decl, label, crud,
  defined }` -- the repository idea reified. A project's module generator has no entity, and
  handing it one would bake `Repository`'s shape into the mechanism, which is the same mistake as a
  domain name in the compiler wearing a different hat. F258 took `repository` out of the parser's
  vocabulary; seating every module generator on an entity would put the *idea* back where the name
  used to be.

  So the message now says that, and §5c of user-generators.md carries the shape that would settle
  it -- `ModuleTarget { args, functions, defined }`, with the two existing entry points generalised
  -- **and the asymmetry worth knowing before starting**: `Repository` needs its entity *resolved*,
  which only the loader can do, so either `ModuleTarget` keeps an `Option<Decl>` that one generator
  fills and the rest ignore (a field nobody reads, which meta.md argues against) or `Repository`
  keeps a specialised input and there are two kinds of module generator after all.

  **Not built, and the reason is the same one that stopped item 2**: nothing is asking. No module
  generator but `Repository` exists or has been requested, and designing `ModuleTarget` for a
  hypothetical one is the speculative plumbing this codebase's own comments argue against -- "a
  field nobody reads is a promise that cannot be taken back". The decision is written down so it is
  available rather than re-derived.

  The document's status line is accurate now: built, except this.
