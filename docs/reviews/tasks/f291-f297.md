# F291 to F297 — the look and feel decisions, built

Opened 2026-11-17 out of [docs/design/look-and-feel.md](../../design/look-and-feel.md), which
surveyed Swing's look and feels, the third-party ones, and the CSS and CSS-adjacent approaches, then
measured what `controls.Style` cannot say. Its §13.3 carries **thirteen decisions, D1 to D13**, all
taken the same day; its §13.4 carries the build order these seven tasks are. **Read the decision
before starting its task** — these entries say what to do and what will bite, not why.

The three ideas everything converged on, because each task is an instance of one of them:

- **A theme sets a scale and the library indexes it** — shape (D1), space (D6), type (D9), the state
  rows (D5) and two twelve-step colour ramps (D8). A theme never names a control type, which is what
  closed the CSS-cascade option outright: there is nothing for a selector to select.
- **An axis is a function from `Style` to `Style`** — density (D4), scheme (D8), emphasis (D5) — not
  another entry in the register.
- **A look is two seeds plus a short override list**, and the length of that list measures whether
  the derivation is right.

CSS was taken as values only (D2, D3: OKLab/OKLCH, and `parse` learning two notations) and declined
as a cascade. There is no file format: a live editor in the gallery instead (D12).

Effort: **S** = a day or less, **M** = a few days, **L** = a week or more.

- [x] **F291** **`lib/ui/looknfeel` becomes `lib/ui/theme`, and `Theme` becomes `Look`.** (S;
  28 files across two repositories. Implements D13.)

  **First, because it is cheapest first.** The module was created on 2026-11-17 with four looks; every
  diff in F292 to F297 is written once if this lands before them and rewritten if it does not. The
  name describes something the module does not do and is not going to do — key bindings belong with
  the controls that read them, and choosing "Modern dark" from a menu must not change what Home does,
  which is exactly what Swing shipped and why one Swing application answers keys differently per
  platform.

  **`Theme` becomes `Look`**, because `theme.Theme` stutters and D8 made *look* the word that carries
  meaning: the register is two looks across two schemes. `all()` returns `[Look]`.

  The five edits a multi-part bundled module takes, all of them here: `LOOKNFEEL_PARTS` and
  `CORELIB_HEADERS` in the Makefile (lines 131, 151, 156, 171), the header rule in `make/c.mk` (110),
  three `#include`s and four registry rows in `src/corelib.c` (91-93, 207, 292-294), and `GROUPS` in
  `tools/gen_lib_manual.py` (83). Then `tests/stdlib/looknfeel_test.zm`, `tests/bench/look_and_feel.zm`,
  `tests/integration/a11y/tree.zm`, `tests/stdlib/{controls,desktop}_test.zm`, five files under
  `gallery/`, `docs/lib/examples/ui/controls_example.zm`, and six files in curly.

  **Three traps, each of which has already cost a turn here.**

  **A comment-only mention must not become a `use`.** `lib/ui/controls.zm`, `lib/ui/widget.zm` and

  `controls` defines `Style` and must never import the module that builds one.

  **Editing a `lib/` example forces a regeneration and a commit.** `controls_example.zm` is one, so
  `make corelib-reference` must run and be **committed** before `make check`, because
  `lib-manual-check` is `git diff --exit-code -- docs/lib` and so fails on an uncommitted
  regeneration.

  **Delete the stale generated headers.** `rm -f build/looknfeel_*_source.h`. A generated header with
  no findable source builds anyway while the stale file exists, which is the open `charset` problem
  recorded in §6 of the design doc's companion notes — and it would hide a missed registry row until
  a clean build.

  Format only the files touched: `make fmt-check` covers `lib gallery docs/lib/examples` and four
  integration directories, and `./ziman --fmt --write $(git ls-files '*.zm')` reformats

  ## What the rename found

  **`theme` was already this tree's word for something else.** `lib/ui/icons.zm` has `pub struct
  Theme` and `pub fn theme(name, path)` — freedesktop's *icon* themes, a different concept from a
  look and feel. Nothing breaks: no file needs both modules, and every use site is module-qualified,
  so `icons.theme(...)` and `theme.plain()` do not collide. But two files have locals named `theme`
  (`docs/lib/examples/ui/icons_example.zm:68` and curly's `gui/state.zm:606`), and **the first file
  that needs `icons.theme()` and this module together will have to rename its local** — the
  shadowing trap, deferred rather than avoided. Recorded here because the next person to meet it
  should know it was seen and accepted, not missed.

  **No caller ever named the `Theme` type.** Every one of them iterates `all()`, so `Theme` → `Look`
  was contained to the module and the public rename cost three lines rather than a sweep. `all()`
  now reads `fn all() -> [Look]`, which is what D13's attached recommendation asked for.

  **Shortening an identifier is a formatting change, and it cost two gates.** `looknfeel` is nine
  characters and `theme` is five, so wrapping decisions moved in **eleven** files. `make fmt-check`
  named five — `gallery/ui/desktop/{demos/look_and_feel,gallery,highlight_test,state_test}.zm` and
  `tests/bench/look_and_feel.zm` — and curly's own formatting phase named six more, **one per run**,
  because it stops at the first unformatted file: `gui/app.zm`, `gui_test.zm`, `builder.zm`,
  `builder_state_test.zm`, `pick_design.zm`, `render_design.zm`. Format the whole touched set at
  once rather than chasing a gate that reports one file at a time. **A pure rename is not a
  formatting no-op.**

  **The text-only substitution was the safeguard.** The rename never inserts a `use` line, so the
  three files that name the module in prose alone — `lib/graphics/paint.zm`, `lib/ui/widget.zm`,
  `lib/ui/controls.zm` — kept their comments and gained no import, which is how the circular
  dependency this trap records was avoided rather than re-created.

  `docs/lib/looknfeel.md` is deleted and `docs/lib/theme.md` generated in its place.


- [x] **F292** **`paint` learns OKLab, a colour algebra, and four more notations.** (M;
  `lib/graphics/paint.zm`, `tests/stdlib/paint_test.zm`. 16 new tests, 28 in the file. Implements
  D2 and D3.)

  `to_oklab`, `oklab`, `oklch`, and over them `lighten`, `darken`, `saturate`, `desaturate`, `fade`,
  `mix`, `tint`, `shade`, `change_hue` and `contrast(c, dark, light)`. **One working space, not two** —
  the functions keep plain names and their doc says which space they work in, because two
  vocabularies for one operation is what `Style.corner`'s comment argues against for shape and is no
  better for colour.

  **Cheaper than it looks: `relative_luminance` already contains `linear_channel`**, the
  sRGB-to-linear step. What is missing is a matrix and a cube root.

  **Why not HSL.** D8 makes colour a tonal scale, and "even steps of lightness at constant hue and
  chroma" is OKLCH's definition and something HSL cannot do. FlatLaf's `autoInverse` option — "inverts
  the amount if lightness is above 65% (lighten) or below 35% (darken)" — is a workaround for HSL's
  non-uniformity and has nothing to correct in OKLab. GTK deprecated its own `shade()` and `mix()` in
  favour of standard `oklch()` and `color-mix()`.

  **`parse` gains `hsl()`, `hsla()`, `oklch()` and `oklab()` and nothing else.** Those are ways of
  writing one colour, which is `parse`'s existing contract and what turns up in real SVG files and
  design-tool exports. It does **not** gain `color-mix()`, relative colours or `light-dark()`: those
  are expressions, and they belong in the typed algebra where a mistake is a compile error. **parse
  denotes; functions compute.** `parse` accepting `hsl()` does not reintroduce HSL as a working space.

  **Derivation is computed once, when a look is built — never at paint time.** FlatLaf's `derived`
  mode recomputes against a component's actual background; we already answer that case by
  compositing, since `hover_tint` is a translucent overlay in `widget.paint_hovered` and adapts to
  whatever face it lands on without computing anything. A look that computes at paint time stops
  being data, which is the one property not to trade.

  Self-contained, with no callers to break. Everything below needs it, so it goes second.

  ## What building it found

  **The gamut strategy was wrong, and a test said so.** The first draft clipped each sRGB channel
  into range, and `an_equal_step_is_an_equal_step_whatever_the_hue` failed on pure blue: asked to
  lighten by 0.100 it moved 0.060, because the channel that overflowed was pinned while the others
  kept going. That is the claim in `Oklab`'s own comment refuted by the implementation directly
  underneath it — and **the reasoning that let it through is worth keeping because it is plausible
  and wrong**: *a ramp starts from a colour sRGB already holds, so clipping cannot bite.* The start
  is in gamut; the steps need not be, and a ramp is made of steps. `fitted` now holds the lightness
  and the hue and **reduces the chroma until the colour fits** — eighteen halvings of a binary
  search — which is what CSS Color 4 does and for the same reason. D8's ramps would have inherited
  the distortion.

  The cost is stated rather than hidden: a saturated colour pays for a lighten in chroma and does
  not get it back on the way down. `a_saturated_colour_pays_for_a_lighten_in_chroma` pins that as
  intended behaviour, and the alternative — keeping the chroma and losing the lightness — is what
  makes a tenth stop being a tenth.

  **A test pinned the behaviour D3 reverses.** `the_keywords_that_are_not_colours_are_refused`
  asserted `refused("hsl(0, 100%, 50%)")`, which was true and deliberate before today. It now pins
  the new line instead: **notations in, expressions out.** `hsl()`, `hsla()`, `oklab()` and
  `oklch()` parse; `color-mix()`, relative colours (`oklch(from ...)`) and `light-dark()` are
  refused because they compute. `lab()` and `color()` are also refused, and that is a **gap rather
  than a decision** — they denote one colour and belong in later.

  **Two linearisations in one file, on purpose.** `relative_luminance` keeps WCAG's threshold of
  0.03928 because a contrast ratio is a claim measured against that document; OKLab uses sRGB's
  0.04045 because that is what Ottosson fitted the matrices to. They differ only below about 4%
  brightness. Using each where it belongs beats picking a favourite, and the comment says so at
  both sites.

  **`paint.Linear` was already the gradient**, so the private three-channel type is `Channels`. The
  compiler caught it — "struct 'paint::Linear' is already defined" — which is the cheapest possible
  way to find a name collision.

  **"grad" ends with "rad".** An angle reader that tests `rad` first reads `400grad` as 400 radians
  and lands 57 turns from where it meant to. `an_angle_carries_its_unit_and_grad_is_not_rad` pins
  the ordering, since the bug is invisible in every test that only uses degrees.

  **Lightness saturates, and the test says so rather than avoiding it.** The contract is *exactly
  the step, or white, whichever comes first*: yellow sits at 0.968 and has no tenth left. A test
  written only over colours with headroom would pass while a step silently became 0.03.

  Delivered: `Oklab`, `Oklch`, `to_oklab`, `to_oklch`, `oklab`/`oklch` (three and four arguments),
  `lighten`, `darken`, `saturate`, `desaturate`, `change_lightness`, `change_chroma`, `change_hue`,
  `fade`, `mix`, `tint`, `shade`, `contrast`. `mix` interpolates on the opponent axes rather than
  through hue, because a grey has no hue to interpolate and the short way round two saturated
  colours passes through hues in neither.


- [x] **F293** **The scales: shape, space with its two sibling groups, and type.** (L;
  `lib/ui/controls.zm`, `lib/ui/widget.zm`, `lib/ui/theme/`. Implements D1, D6 and D9.)

  **This is where §6.1's nineteen numbers go.** Fifteen module-level constants — `mark_weight`,
  `min_thumb`, `bar_thickness`, `divider_thickness`, `divider_step`, `divider_line`, `min_column`,
  `grid_width`, `column_grip`, `radio_height`, `track_thickness`, `thumb_width`, `thumb_height`,
  `underline_width`, `underline_gap` — plus `row_height` on three controls, `header_height`,
  `tab_width` and `indent`. They are the reason a theme can recolour the gallery but not tighten it.

  They do **not** all go to one place. Four groups:

  - **`Space { none, xs, s, m, l, xl }`** at 0/2/4/8/12/16, with `controls.zm` saying once which step
    each control uses. Today's stray 6s (table padding, radio insets) normalise to `s` or `m`;
    **pixels move, and that is what removing the 6 costs.**
  - **`Minimum { target: 24.0, thumb: 20.0 }`**, which `at_density` does **not** touch. Two of the
    three were already exactly 24, which is also WCAG 2.2's minimum target size (SC 2.5.8) — a
    Compact density that scaled them would make the densest mode the one that fails an accessibility
    criterion and the gate would have to be told to permit it.
  - **Stroke widths**, their own small group: `grid_width`, `divider_line`, `underline_width`. A
    hairline is a hairline at every density. `mark_weight` is a **ratio**, not a length, and stays one.
  - **`Shape { none, small, medium, large, full }`** and
    **`TypeScale { heading, body, label, caption, code }`** where each role is a
    `Type { face, size, line }`.

  **The face index clamps.** `gallery.zm` records that the renderer "refuses a run naming a face the
  options do not hold", and loads the text face twice so index 1 is always real. Clamp an
  out-of-range index to face 0 and a single-face application renders a look that wants bold — just
  regular. **That retires the load-it-twice workaround**, and a `code` role retires
  `gallery/ui/desktop/state.zm:211`'s `with style { text_font: code_face }`, which is the only
  per-call style override in the tree and the one apparent counterexample to D1.

  **Two things attached to this task and not yet decided.**

  **`Type.line` is new and `widget.Metrics` already carries a line-height function per face**, which
  the caret arithmetic reads. Two sources of line height is one too many, and the caret is exactly
  where that goes wrong: `Style.text_font` already caused a defect of that shape, positioning a
  caret by one face's metrics and drawing it in another's. Settle it here, not after.

  **Six steps across about thirty inset sites leaves `xs` and `l` with no caller.** An unused scale
  entry is a decision a look author must make for no reason, and nothing would notice —
  `gen_lib_map.py` raised `KeyError` for an unknown length of time because no target ran it. A test
  asserting every step has at least one caller would catch a dead step at the point it dies.

  **`at_density(s, Density)`** lands here too (D4), with the geometry test that goes with it: no
  control shorter than its text plus padding, and nothing below `minimum.target`, at Compact,
  Comfortable **and** Spacious. That test is what replaces listing twelve themes in the register.

  Remember `rm -f ziman-gui && make gui`: the GUI does not rebuild on a `lib/` change.

  **Done 2026-11-18.** The scales, the twenty functions that gained a `Style`, `at_density` and the
  four proportions the library keeps are D14-D17 in `docs/design/look-and-feel.md` §13.3. The last
  piece was **Q8, answered as D18**: `row_height`, `header_height` and `indent` are **derived**
  (`controls.row_height(m, style)`, `controls.header_height(m, style)`, `controls.indent_for(style)`)
  and `Tabs.tab_width` stays a field, being the one of the four that varies per instance. Twelve
  functions took `widget.Metrics` to measure a row where they used to read it, `Table.header_height:
  0.0` became `Table.headers: bool`, and the two hard-coded row paddings went onto the space scale.
  Rows resize with the face, so curly's geometry baseline moved by under a point a row and was
  re-blessed.

- [x] **F294** **Five state rows, one mechanism.** (L; `lib/ui/controls.zm`, `lib/ui/widget.zm`.
  Implements D5.)

  `States { rest, hovered, pressed, disabled, selected }`, each a
  `Parts { face, ink, border, expansion, corner }`. Every control's paint function asks one question —
  what are this control's parts in this state — so a state cannot be half-implemented and a look
  cannot forget one.

  **This retires four mechanisms**: `pressed_face`, `disabled_ink`, `selection`, and `hover_tint`
  together with the generic overlay in `widget.paint_hovered`. About twenty paint functions start
  selecting their own row. **It also fixes a defect visible today**: a disabled button keeps a
  live-looking face and merely greys its text, which no platform does.

  **Focus and emphasis are deliberately not rows.** A control can be focused *and* hovered *and*
  pressed at once, so focus cannot be one of N exclusive rows; it stays a ring drawn over whatever
  state applies, from `accent`. egui agrees and has no focused row among its five. Emphasis is an
  **axis** — a primary button is emphasised at rest, hovered, pressed and disabled alike — so it is
  `theme.emphasised(style)`.

  ## The expansion invariant, which is the one thing here that can go wrong quietly

  **No state may change a control's bounds.** `expansion` is a paint-time outset and is never an input
  to layout or to hit testing.

  This is the only field in `Parts` that could break the one-function rule — a hit test must read the
  same calculation the widget laid out with. **egui concedes the wart in its own documentation**,
  saying `expansion` "makes hovered things misaligned"; it gets away with it by re-laying out every
  frame, which we do not do. If expansion grew the box, a control would be hovered at a pixel its
  layout never claimed, two neighbours could both claim a boundary, and the result is flicker at
  every edge.

  So **the rest state draws its frame inset from its bounds and a hovered state spends that inset**.
  Layout and hit testing use the resting geometry always; expansion is bounded by the resting inset.
  The drawn frame grows, the box never does, and the invariant holds by construction rather than by
  care. A test should assert it directly: the hit test's answer must not change between states.

  `corner` needs no such rule — a radius affects neither bounds nor a rectangular hit test.

  **Done 2026-11-18.** `Parts`, `States` and `Mood` are in `lib/ui/controls.zm`, with `mood_of` as
  the one place the precedence lives (disabled > pressed > selected > hovered) and `parts_for` as a
  pure index. Eighteen paint functions select a row; `pressed_face`, `disabled_ink`, `selection`,
  `hover_tint` **and `face_border`** left `Style`; `widget.paint_hovered` and `holds_a_control` are
  gone.

  **It needed a decision the entry did not foresee, taken as D19 (Q9): the look, the window's
  measurements and the three names the window holds travel as one `controls.Frame`.** A hover could
  not reach a paint function otherwise, and a third parameter would have been a fourth in F296 and
  a fifth in F297. Twenty-seven public functions and about 280 call sites across both repositories;
  the five `*_input`s that read neither a style nor a metrics kept their signatures, and so did the
  geometry functions.

  **The expansion invariant holds by construction**: `widget.Surface.inset` is read in
  `paint_surface` and nowhere else, `reserve_of` is the largest expansion any row asks for, and the
  frame is drawn at `reserve_of(style) - p.expansion`, which cannot be negative. Three tests assert
  it against a look whose every row expands. curly's `window_geometry.txt` did not move.

  **Four traps, for whoever does F295 to F297.** A design file's body is a single `return` -- "no
  function-local `val`" is a lint rule -- so a `*_ui.zm` reads `f.style` inline, and
  `tests/run_design_check.sh` borrows curly's parser to catch it. The dialect binds a component's
  ambient parameters **by declared type**, so `controls.Frame` needed a `Value.Frm` beside the `Sty`
  and `Met` it already had. `f` was already the font in curly's `app.zm` and `builder.zm`. And
  `./ziman --lint --check` reports **only its entry file**, so lint one file at a time.

- [x] **F295** **`derive`, two ramps, fills, and a computed register.** (L; `lib/ui/theme/`,
  `tests/stdlib/theme_test.zm`. Implements D8 and D10.)

  `ramp(seed, scheme) -> [Color]` of twelve steps carrying Radix's published roles, and
  `derive(seeds, scheme) -> controls.Style` over a neutral seed and an accent seed. Then `plain()`
  becomes `derive(...)` plus a short list of deliberate exceptions.

      window = neutral[1]   panel = neutral[2]   rest = neutral[3]
      hovered = neutral[4]  pressed = neutral[5] border = neutral[7]
      ink = neutral[12]     accent = accent[9]   selection = accent[4]

  **The override list is the measurement.** If `plain()` needs twenty overrides the derivation is
  wrong, and we find out rather than guess.

  **The ramp is what makes F294's rows stop being choices**: `hovered` is step 4 and `pressed` is
  step 5, not two more colours a dark variation can get wrong.

  **The scheme is a parameter, and that is what makes dark mechanical.** Indexing the same ramp from
  the other end produces all four of the dark rules `plain_dark` had to discover by hand: faces
  lighter than the window is simply what step 3 means on an inverted ramp, the hover veil reverses
  because the veil is another step, `on_accent` flips with the accent ramp, and the shadow deepens
  with the neutral one. This is why Material's `fromSeed` takes `brightness` and Radix ships each
  scale both ways.

  **Fills land here and not in F294, because a `Fill` names ramp steps and the ramp arrives in this
  task.** `Fill { from, to, angle }` is what a look writes; `paint.Paint` is what a control draws;
  `derive` converts. `face`, `panel`, `window` and `selection` take paints, while `ink`, `border`,
  `grid` and the caret stay `Color` — a fill is a thing a gradient makes sense for and a mark is not.
  **`from == to` is a flat fill**, so solid and gradient are one form with no `Option` and no second
  field. The gate gets *stricter*: ink must clear 4.5 against every stop, so a gradient face passes
  only if it holds at both ends — and since every stop is provably a ramp step, the ramp can be
  checked once instead of per look.

  ## The register is computed, and the gate must not shrink with it

  D4 kept `all()` at four looks because density changes no colour. **A scheme does change colour**, so
  a register of two looks would make the AA gate quietly stop testing the dark half — a gate
  shrinking because a mechanism got better is the worst outcome available here.

  So `all()` is **computed as looks times schemes**: two looks give four rows, the menu shows four,
  the gate tests four colour-distinct styles, and a fifth look adds two rows without anyone
  remembering to. `Look`'s scheme is then read off the register rather than set by hand.

  **WCAG gates, OKLab derives** (D7). `theme_test` keeps holding every row to WCAG 2 AA with
  `paint.contrast_ratio`, because that is the claim the library makes and what EN 301 549, Section
  508 and the ADA reference. Derivation picks tones by distance in OKLab lightness instead: checking
  a pair and choosing a tone are different jobs, WCAG 2 is not polarity-aware, and deriving with the
  gate's own function would stop the gate being an independent check. APCA is declined as a
  dependency rather than as a model — its constants have moved between revisions, and a gate that
  must stay green should not pin a moving draft. Revisit if WCAG 3 lands.

  **The four looks' exact colours move once**, so any pixel baseline is re-blessed here.

  **Done 2026-11-18.** `theme.ramp`/`accent_ramp` build twelve steps from a seed on published
  lightness tables; `derive(Seeds, Scheme)` builds a whole `controls.Style` from two seeds; `all()`
  is families × schemes, so a fifth look adds two rows and two gate entries without anyone
  remembering to, and `Look.scheme` is read off the register (absorbing F7). `Fill` names two ramp
  steps, `Parts.face` and `Surface.fill` carry paints, and `widget.paint_in` resolves a gradient
  against the box the way `radius_in` resolves a radius.

  **The override list, which is what D8 said would measure the derivation: `plain` 0, `plain_dark`
  0, `modern` 3, `modern_dark` 3 -- and none of the six is a colour** (padding, shape, shadow).
  Twenty written-out colours left `plain` and eleven left `modern`.

  **Two things a ramp could not say, both measured rather than argued, recorded as D20.** The
  surface direction is a *permutation* of three roles and not a second curve -- modern's "white
  cards on a grey canvas" is exactly "the window is step 3, not step 1" -- and it is read only in a
  light scheme, because both dark looks already measure monotone ascending from the window. And
  whether a face wears step 7's border is a look's vocabulary, not a ramp's: derived without a say
  in it, `plain` grew an edge and an existing test caught it in under a minute.

  **The one that nearly shipped**: at the *neutral* table's step 9 a blue accent is 3.41:1 against
  white, under AA, so every derived look would have failed `theme_test`'s own `on_accent` check. An
  accent ramp has its own lightness curve, and `on_accent` is now derived by measuring both ends of
  it against step 9 -- which reproduces what all four hand-written looks had chosen.

  **A trap for F296 and F297**: three control tests encoded plain's old ink as the literal `@0.1`
  and broke the moment a colour moved. They name the look now (`@ink`, `@keyword`, `@literal`).
  Expect the same wherever a test prints a channel instead of naming a token.

- [ ] **F296** **The window reports the desktop's scheme, live.** (M; `lib/ui/desktop/`,
  `src/native_window.c` or a new native file. Implements D11.)

  `window.color_scheme() -> Preference` beside `display_scale()`, and a scheme change delivered like
  a resize. **Platform code stays with the platform and policy stays with the application**, so
  `lib/ui/theme` stays pure data and keeps working on a machine with no portal running — the same
  split as `Style.window`, which the library names and the application hands to `raster.Options`.

  **Cheaper than "platform work" suggests: GIO's D-Bus is already linked into `ziman-gui`.**
  `src/native_ibus.c` calls `g_dbus_connection_call_sync` and `g_dbus_connection_signal_subscribe`,
  and the Makefile says why — "it costs nothing, because at-spi2-atk already brought it. That is the
  whole reason ibus is a binding and not a second backend." The portal call is a pattern already in
  the tree.

  `org.freedesktop.portal.Settings`, namespace `org.freedesktop.appearance`, key `color-scheme`,
  type `u`:

      0 = no preference     1 = DARK     2 = LIGHT

  **1 is dark and 2 is light** — not alphabetical, and easy to invert. Unknown values are to be
  treated as 0.

  **Two compatibility paths, both required.** `ReadOne` is current and `Read` is deprecated, but
  **older portals answer `ReadOne` with "No such method"**, so the fallback to `Read` is not
  optional — Ghostty hit exactly this. And **some desktops historically never emitted
  `SettingChanged`** (a KDE bug fixed around Plasma 5.24), so a stale value must degrade to "no
  preference" and must never hang.

  **Followed live rather than read once**, because GNOME's automatic dark mode switches **at
  sunset**: a startup-only read goes stale during an ordinary session, and the application reads as
  ignoring the user's setting.

- [ ] **F297** **The gallery becomes the theme designer.** (M; `gallery/ui/desktop/`. Implements
  D12, and closes the question of a theme file format.)

  The look-and-feel demo gains controls over the two seeds and the scale steps, repainting every demo
  live; a look is designed with instant feedback and the result pasted into a `.zm` file as two
  seeds.

  **This is what replaced a file format, and the arithmetic is why.** A theme file was ranked last on
  the assumption that a look is thirty-five literals — which a file can carry and a slider cannot.
  After D6, D8 and D9 a look is **two seeds, a scheme, six scale steps and a short override list**,
  so the thing that made a format necessary is gone. The pain the question was really about is the
  loop: `rm -f ziman-gui && make gui` is mandatory and easy to forget, and this answers it with no
  schema, no validator and no new way for a look to be invalid at run time.

  **What a format would uniquely have bought is an outside caller theming an application they did not
  compile, and there is none.** `Style.window` and `Style.accent` were both found *by an application
  needing them*, not by guessing. If such a caller appears, D8 is what will make a file safe: because
  a look is derived, a loader can run the AA check and **refuse** the file — which was never possible
  for hand-written literals.

## Not tracked here

**Platform conventions are not a look.** Dialog button order, Home/End versus Cmd-arrow, and the
double-click interval are chosen by the platform, not from a theme menu. Swing put them in
`UIDefaults` and `LayoutStyle` and so conflated them with the look, which is half of why the same
Swing application answers keys differently per platform. They want their own value and their own
task, and D13 deliberately left them out of `theme`.

**Teaching `font.zm` about family and weight** is the better long-run answer to D9's face index, and
was declined there as scope: it is a font-matching layer with its own fallback policy. Synthetic bold
was declined outright — stroking a glyph changes its advances, so measured and drawn text disagree,
which is the defect `Style.text_font` already caused once.
