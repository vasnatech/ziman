- [x] **F71** **Request logging as a field, not an interceptor -- and the format that had no coverage at all.** (R, ROADMAP.md "Accounts and tokens for backends"; tier-4 #5, the half F59 left; M) The entry asked for "request logging as an interceptor, as a wrapper around `dispatch`", and **the shape is wrong for the same reason F59 recorded when it rejected it for CORS**: a wrapper would have to return a closure and allocate one per request. Worse here, a wrapper around `dispatch` cannot see what `serve` knows -- the peer, the bytes actually written *after* `compressed` has had its say, and the moment the read finished. **Built as `ServeOptions.on_request: Option<fn(RequestLog)>`**, one function value stored once, called per finished exchange. `log_requests` stays as the zero-config line and the two are independent. **`RequestLog` is a struct and that is the point:** the library builds it and the application only reads it, so a field added later cannot break a caller -- the exact inverse of F61's `ServeOptions` problem, where every field of a struct the *caller* builds is required. **`duration_ms` is the time to serve**, from the request being fully read to its response being written: not the client's slowness in sending, nor the idle wait on a keep-alive connection, neither of which is work the server did. **The library's first callback that returns nothing**, so the spelling is set here: `fn(RequestLog)`, not `fn(RequestLog) -> unit`, because a void function's type *is* the former and an application should not have to remember an annotation its own function does not carry. **A finding worth more than the feature: nothing in the tree had ever set `log_requests: true`** -- the one request-log format the library ships had **no coverage whatsoever**, which is why moving it after the write was safe to discover rather than to break. The new fixture covers both halves. **The logging point moved after `write_response`**, where the status and the bytes that actually went out are both known; before it, a compressed body's size was not yet decided. **A weak assertion caught and strengthened:** the fixture first printed "duration plausible" for a non-negative value under a minute, which **would have passed with the field hardcoded to 0**. It now asserts a band -- a handler that sleeps 150ms must land at 50ms or more, the three trivial ones under 50ms -- so a dead timer fails the first and a duration that accidentally measured the whole connection fails the others. **Verified:** 956 fixtures in both builds; **both guards verified by reintroducing their faults** -- unwiring `options.on_request` makes all four hook lines vanish, and hardcoding `duration_ms: 0` flips `/slow` to "under 50ms", which is what proves the band is load-bearing. A `HEAD` request logs 38 response bytes it does not send, which is the documented behaviour and now pinned. **The backend is left on `log_requests`:** it drives the flag from its own config, and choosing a structured format through the `log` module is the application's decision, not the library's -- the hook is there for it to adopt.
- [x] **F72** **The continuation-indent zigzag: `fmt-check` enforced a layout nobody would write.** (SC finding 1; S) Three or more lines each ending in a binary operator indent `+1, +0, +1, +0`, so a five-term sum alternates between 8 and 4 spaces. **It is idempotent**, which is what makes it a defect rather than a wart: `--fmt --check` therefore *requires* the zigzag of anyone who wrote the aligned version, and the library escapes it only by never having more than three such lines, each with a single continuation. Reproduced independently before this task was filed. Expected behaviour is every continuation one level deeper, which is what the first one already does. The fix is in the continuation-indent bookkeeping in `src/format.c`; the test is a fixture whose formatted form is stable *and* uniform, since stability alone is what the current code already has. **Done 2026-10-12.** The guard was `cont_from_prev`, and its intent was right: stop a run accumulating `+1, +2, +3`. Its method was wrong -- it skipped the increment on the second line, cleared itself, and incremented the third. **The fix is to delete it**, because `level` is recomputed from the bracket stack on every line, so a plain `level += 1` for any continued line gives one uniform level and cannot accumulate; the flag was guarding against a problem the surrounding code already prevented. Removing the term left the variable write-only, so it went too rather than staying as dead state (the F54 lesson). **`docs/DESIGN.md`'s R17 entry had the rule right all along** -- "a line ending in an operator indents its continuation one level" -- so this was a case of the documentation being correct and the code implementing only its first line; the entry is annotated rather than rewritten. **The bug was not hypothetical: 12 files in the reference backend had the zigzag baked in**, 51 lines across them, because the gate enforced what the formatter produced -- reformatted in the same change (backend commit alongside this one). **Verified:** 957 fixtures in both builds (956 plus the new one); `make fmt-check` clean over all 99 gated files and the backend's 173 after reformatting; the new `fmt_continuation_indent` fixture takes the *old zigzagged layout as its input* and asserts the straightened output, so it pins the fix in the direction that matters, and includes a seven-term run (which would expose accumulation had the guard been removed without the per-line recomputation), a nested run inside a call argument, and a wrapped `&&` condition. Reverting `src/format.c` fails it. Idempotence rechecked on the formatted output, since stability was the property the old code had and the new code must keep.
- [x] **F73** **An array literal fills greedily while a call and a struct literal go fully vertical, and nothing records why.** (SC finding 2; S) An over-width `f(...)` or `Foo { ... }` goes one item per line with its brackets on their own lines; an over-width `[...]` fills to the width. The mechanism is explicit -- `vertical` is never set for `[` (`src/format.c:239`) -- so it reads as a decision, but F11 describes only the greedy comma break and the asymmetry appears nowhere. The consequence is that a reader cannot predict what `--fmt` does to a long literal without knowing which bracket it is, and an author who hand-breaks an array keeps their layout while one who hand-breaks a call loses it. **Needs a decision before code:** if the greedy fill is deliberate -- array elements are homogeneous, a call's arguments are not -- the reason belongs in `DESIGN.md` beside F11 and this is a documentation task; if not, it is a one-flag change plus the fixtures to pin it. **Decided and documented 2026-10-12.** Menderes chose to keep the asymmetry and write down why, over making all three brackets uniform in either direction. The reason is the content: an array's elements are homogeneous, so forty integers one per line is a column nobody wants to read or review, while a call's arguments are heterogeneous and each earns a line. Making it uniformly vertical was declined because it would turn every numeric and string table in the library and backend into a tall column; uniformly greedy was declined because it loses the one-argument-per-line readability that makes a long call reviewable. Written into a new DESIGN.md entry beside the behaviour it sits next to, verified by running the formatter on a short call broken between arguments (which goes fully vertical) and a wrapped array literal (which does not).

- [x] **F75** **`internal` and `#![...]` had no syntax scope at all, and the grammar had no test.** (SC finding 4; S) `internal` matches nothing in `editors/vscode/syntaxes/ziman.tmLanguage.json` (verified: zero occurrences), and `#![...]` is not matched by `meta.attribute.ziman`, whose `#\[[^\]]*\]` requires `[` immediately after `#` -- so the `!` colours as logical-not and the attribute name is left bare. The grammar already accepts that trade for `unit`, and the comment in the rule says so.
