# F288 and F289 — the split pane and the table

Opened 2026-11-16, asked for in two words: "more controls — split pane, table, etc." The research
behind the "etc." is in [the roadmap](../../roadmap/near-term.md) under *The widget set has nine
controls, and a desktop application needs about thirty*, measured against Swing's standard set and
[JIDE Software](https://www.jidesoft.com/products/)'s fifteen products. Its sharpest single finding
is that **three roles were already declared with no control behind them** — `RadioButton`, `Slider`
and `Link` — which is a gap nothing in the tree would ever have reported.

- [x] **F288** **A split pane: two panes, a divider, and the first control that owns a layout.**
  (M; `lib/ui/controls.zm`, `lib/ui/widget.zm`. 15 unit tests, 6 mutations, 2 new roles.)

  **It is still not a layout container.** `split_pane_widget` takes the two panes as widgets and
  returns a widget, so `widget` keeps every placement rule and this keeps the state and the
  gestures. A `Stack` whose children's sizes came out of a control's state would have put a control
  inside the box model, and the box model is the one part of this layer with no state in it.

  **The position is points from the start, and the first draft was a fraction.** A fraction needs no
  extent at all — two `Expanded` weights say it, and that is genuinely tempting — and it is the
  wrong model: it makes a sidebar *grow* when the window grows, where every file browser ever
  written keeps the sidebar's width and gives the new room to the document. Points cost exactly one
  thing, which is that a number in points has to be clamped against an extent the state does not
  know. That is what `split_at` is for, and it is `thumb_of`'s rule again: one function, read by the
  widget and by every gesture, because a divider drawn at one number and dragged by another jumps
  out from under the pointer on the first press.

  **`position` is written only by a gesture and read only through `split_at`.** So a window squeezed
  too narrow to honour it does not overwrite what the user chose — the clamp is on the way out, the
  stored number survives, and widening the window puts the divider back. That is the complaint
  `JSplitPane` keeps a `lastDividerLocation` to answer, and here it needs no second field.

  **A mutation found the other half of that rule, which fourteen tests had missed.** Storing the raw
  `want` instead of the clamped number passed everything, because every assertion read back through
  `split_at`, which clamps anyway. The difference only shows when the window *changes size after* a
  drag: dragged hard against the end at 300 points, a clamped store stays at 244 when the window
  widens, and an unclamped one opens out to the 997 the pointer was asking for. So a gesture stores
  where the divider *stopped*, not where the pointer *went*, and the fifteenth test says so.

  **When both minimums cannot be met, neither is** — the room is shared in the ratio they asked for.
  Refusing to lay out is not available to a box model, and honouring one minimum would make which
  pane gets squeezed depend on which field was written first: invisible in a wide window and
  arbitrary in a narrow one.

  **Two roles, because the divider is not the pane.** `Role.SplitPane` on the whole thing, declared
  and not a tab stop, so a reader gets a node containing both halves; `Role.Separator` on the
  divider, which *is* the tab stop. A pane that was a tab stop would be a stop in front of whatever
  is inside it, so Tab would reach the split before reaching the tree in its first half — and the
  thing a keyboard user wants to move is the divider. `Separator` is a role the widget set wanted
  anyway, since a standalone separator is on the roadmap list.

  **The second pane is `expand`ed rather than sized.** The first pane and the divider are fixed, so
  whatever rounding is left over goes to the second pane and there is no seam — where two fixed
  sizes that did not quite add up to the box leave a line of background showing between the panes on
  some window widths and not others.

  Not done, deliberately: **one-touch expand** (`JSplitPane`'s two little arrows), **a collapsed
  pane as a state** rather than a divider parked at a minimum, and **three or more panes**, which is
  a split pane inside a split pane and already works.

- [x] **F289** **A table: a header that stays, rows that scroll, columns the user can drag.**
  (L; `lib/ui/controls.zm`, `lib/ui/widget.zm`. 19 unit tests, 8 mutations, 3 new roles.)

  **What this is, by JIDE's own division of its product line**: `JideTable`. A header, row
  selection, scrolling in both directions, and columns the user can resize. Sorting, filtering,
  cell spanning, a tree in the first column and a nested table in a row are all things JIDE layers
  *over* that base — `SortableTable`, `FilterableTableModel`, `CellSpanTable`, `TreeTable`,
  `HierarchicalTable` — and they are deferred here in the same order and for the same reason: each
  is a model on top of the rows, and a base that cannot show rows well makes none of them better.

  **The one thing that complicates a table is that the header is outside the scrolled view.** That
  is also the whole of what makes it a table rather than a list of rows. The consequence is that
  the view the rows scroll in is *not* the control's box, and five separate calculations need the
  body: the press that picks a row, the page a PageDown moves, the reveal that brings a selection
  into view, the scroll bar's track, and whether a press landed on that track. Five copies of
  `bounds.height - header_height` is five chances to forget one, so there is one `table_body` and
  everything goes through it. **The mutation that zeroes the header out of it fails five tests**,
  which is that count exactly.

  **Vertically outside the view and horizontally inside it**, which is the other half: the header
  and the body are scrolled sideways by **one** number, `offset_x`. Two offsets would be a header
  that drifts from its columns, and it drifts only after a sideways scroll — so a screenshot of a
  freshly opened table shows nothing wrong. Cheap to get right (`named_scroll` already takes both
  axes) and invisible to get wrong.

  **A resize grip is a divider again**, and it reuses F288's discipline: `grabbed` holds how far the
  pointer was from the edge when it took hold, and the new width follows where the edge would *land*
  rather than how far the pointer moved — accumulating deltas drifts, and a drag that leaves the
  window and comes back has no delta to add. **The grip is in the header and nowhere else**: four
  points from a column boundary in the middle of the data is a selection in every table ever
  written. **The last column has no grip**, because there is nothing to its right to give the points
  to, and a grip that does nothing is worse than no grip — the pointer changed shape and promised
  otherwise.

  **A test that presses exactly on the edge tests nothing.** The grab offset is zero there, so a
  column that jumped to the pointer on first touch would pass. The test presses two points off,
  which is what makes the mutation that drops `held` fail.

  **A row shorter than the columns is not an error**: `cell_at` answers `""` past its end, and
  `row_label` reads the *columns* in order rather than the row's own length — a reader that said
  "Vitamin D" and stopped would tell the user there are no more columns, where the screen shows two
  empty cells. A table built from a query has a missing value in it sooner or later, and the
  alternative is every caller padding its rows.

  **Three roles, and this is where the accessibility story stops short on purpose.**
  `Role.Table`, `Role.TableRow` and `Role.ColumnHeader`, so a reader hears "table", then "row,
  Aspirin, 100mg, daily, selected", then "column header, Dose". What is *not* here is AT-SPI's table
  interface, which answers questions by coordinate — "what is in row 3, column 2" — and needs a C
  object implementing `AtkTable` rather than a role on a widget. A row whose label is its cells read
  in order gets a reader through a table usefully today; the coordinate interface is the next
  instalment, not a different design.

  **Left and Right scroll sideways, and that is a placeholder with a plan.** They are the keys cell
  selection will want, and when it lands the sideways scroll becomes a consequence of revealing the
  current cell — which is how Swing has it. Until then a keyboard-only user can still reach a column
  that is off the right edge, which they otherwise could not. The sideways keys are also answered
  **before** the empty-table check, because a table waiting for a query still has columns worth
  looking at.

  **A sideways wheel is answered before a vertical one**, because a trackpad sends both at once on a
  diagonal flick and a table that took the vertical component first would never scroll sideways on
  hardware that can.

  **One mutation survived, and the finding is recorded rather than patched over.** Dropping
  `widget.contains(body, p)` from `table_for_the_bar` changes no behaviour: the press does reach
  `table_bar_step`, and `scroll_bar_input` then bounds-checks it against `bar_box(body)` itself and
  answers that nothing moved. The guard is kept because it is the one that is *about this table* — a
  predicate named "is this press for the scroll bar" that answers yes about a point in the header is
  wrong on its face, whatever the code downstream does with the answer — and the comment on it now
  says it is the second of two rather than claiming to be the first.

  Not done, deliberately, and each is its own task rather than a missing piece of this one:
  **sorting** (a comparator per column and a header that shows which way), **filtering**, **multiple
  and non-contiguous selection**, **cell selection and editing** (an `Entry` in a cell, which is
  where `JideTable`'s editor listeners come in), **frozen columns**, **row and column footers**
  (JIDE's `TableScrollPane`), and **a header taller than one line**.

## What both cost in the layers below

A new role is **four** edits, not the three the roadmap entry claimed before this: `widget.Role`,
`a11y.role_word`, `atspi.code_of` **and** `src/native_a11y.c`'s number → `ATK_ROLE_*` table. The
protocol number is private to those last two, which is why it is a pair that has to move together —
`code_of`'s own comment has said so since F275.

Five roles were added here (`SplitPane`, `Separator`, `Table`, `TableRow`, `ColumnHeader`), taking
the vocabulary to 27 numbers. `Role` is switched on without a default arm everywhere it is used, so
each addition is a compile error that leads to the next site — which is how all four edits get
found rather than remembered.
