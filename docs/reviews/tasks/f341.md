# F341 — a file only its owner can read

Done 2026-11-20. `lib/core/fs.zm`, `src/native_fs.c`, `tests/run_private_file_test.sh`.

`fs` could write a file three ways — `write_text`, `write_text_atomic`, `write_bytes` — and **none
of them could say who may read it**. There was no `chmod`, no mode argument, and nothing in `os`,
`io` or `process` either.

So a program that writes a secret had no way to protect it. Found by the health-record port
needing somewhere to keep a bearer token between launches: the web application it copies uses
`localStorage`, and the desktop equivalent is a file in the user's config directory — a predictable
path that has to carry its own protection.

## `fs.write_text_private(path, text)`

Replaces the file's contents the way `write_text_atomic` does, and **creates it 0600**.

**Created private rather than made private**, which is the whole reason this is one function and
not a `set_mode` to call after a write. Writing a file and then changing its mode leaves it
world-readable in between, and that window is exactly when something watching for new files under
a home directory would find the secret. The mode goes in the `open` that creates the file, so
there is no window — and a caller cannot assemble that out of parts the library offers separately.

**0600 and not a parameter.** The only question a caller of this has is *may anyone else read
this*, and the answer that makes the function worth having is no. A program that wants to publish
a file already has `write_text`.

**`O_EXCL` on the temporary name** is what refuses a symlink somebody else planted there. The name
carries the process's pid, so an existing one is this program's own leftover from a crash at
precisely that point: removed once and retried once, and a second failure is reported. The rename
carries the mode with it, so the file at `path` ends up 0600 whether or not it existed.

## Testing a mode from a language that cannot read one

`fs` can now *write* a file's permissions and still cannot *read* them, so a ziman program cannot
see the thing being asserted. `stat` can — hence a shell test, the same reasoning as
`tests/run_clipboard_test.sh`, which is about a property living outside the process.

Four cases, and the third is the one that makes the others mean anything:

| | |
|---|---|
| writes, and overwrites on a second call | a token is replaced when it is refreshed |
| the file is 600 | the point |
| **an ordinary write in the same run is 644** | 600 alone could be the umask rather than the call |
| no temporary is left behind | |

Watched fail: creating it `S_IRUSR|S_IWUSR|S_IRGRP|S_IROTH` reddens the second case at "mode 644,
wanted 600" and leaves the other three green.

## Not done

**The directory is not made private.** `fs.make_dirs` takes no mode, so `~/.config/health-record`
is whatever the umask gives — 755 here. The file is 600, which is the protection that matters; a
0700 directory would be defence in depth, and would want the same treatment as this (a mode in the
call that creates it) rather than a `chmod` after.

**There is still no way to read a mode**, which is why the test is a shell script. No caller has
wanted one; the day one does, it is a separate addition rather than a second half of this.
