# F333 — a canvas, and the chart that needed one

Done 2026-11-20. `lib/ui/widget.zm` (`Widget.Canvas`), `lib/ui/controls.zm` (`ChartView`), a
gallery demo, tests. The widget half of [charts](../../design/charts.md); the drawing half is
[F332](f332.md).

## The toolkit had no way to draw anything

`Widget.Drawing` is **one path in one colour**, which is an icon. Anything with two colours, or any
text, had nowhere to go at all. So the chart widget could not be written without first adding the
escape hatch every toolkit has -- Swing's `paintComponent`, GTK's `draw` -- and this one did not.

**`Widget.Canvas` takes a function of its box**, not a fixed list of ops. `Drawing` authors its
path in a unit box and scales it to its bounds, which is right for an icon and wrong for anything
with words in it: scaling a unit box scales the type with it, so a wide chart would have larger
labels than a narrow one. Being handed the real box keeps a 9-point label 9 points at every size.

**The cost was bounded and the compiler named all of it**: 15 exhaustive switches in ziman (11 in
`widget.zm`, 3 in `a11y.zm`, 1 in the widget test), 1 in the gallery, 2 in curly. That is the
no-default-arm rule paying for itself -- not one site had to be found by hand.

**Except the one it could not name.** `paint` tests variants with `if`, not a `switch`, so a
canvas it did not mention would simply never be drawn: silently, and only on screen. `collect`'s
own comment warns that the next case added will have the same hole, and it was right. There is a
test now that a canvas's ops actually reach the scene.

## What a reader is told instead of a chart

A chart is the one object in a window a screen reader cannot read at all. The usual answers are a
text summary, which is a guess at what matters, or nothing, which is most of the web.

**This library's answer: a chart's accessible form is its table.** `Table` already holds `Value`,
already spells a number in a locale, already sorts, and a reader already knows how to walk one. A
chart and a table of the same numbers are the same `[[Value]]`, built from the same `chart.Chart`
-- so **what a reader hears cannot drift from what is drawn, because there is one set of numbers
and not two.** The demo shows both at once, deliberately.

Three things follow:

- **A chart is focusable**, unlike a card (F323) or a screen (F331). It carries information
  reachable no other way, so it is a tab stop.
- **Left and right walk the readings.** A chart a keyboard cannot walk is a picture, and a picture
  of numbers is what this is trying not to be. The pointer does the same through the same
  `plot_box` the drawing uses, so a readout cannot name one slot while the pointer stands over
  another.
- **A missing reading is `Blank`, not zero.** A series shorter than the labels stops; drawing the
  gap as zero would be inventing a reading, in the one place a number is believed.

## Traps

`ziman --lint` caught a string rebuilt from a copy of itself in `chart_said` -- a `MutableString`
now. The `box` shadowing trap took a sixth victim. And the library is embedded in the binary, so a
`lib/` edit is invisible to the typechecker until `make ziman` has run -- which cost one wrong
conclusion about whether the arms had been added at all.
