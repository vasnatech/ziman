# F334 — the virtualised list that was not needed, and the signal that was

Done 2026-11-20. `lib/ui/controls.zm`, the List demo, tests. This closes the "virtualised list"
item of the port plan §4.2 -- by measuring it out of existence and building the small thing that
was actually missing.

## The item was wrong about the target

§4.2 said "`Viewport` scrolls, but every row is laid out. A record list of thousands is a question
about the accessibility tree as much as about painting."

The target has **no virtualisation library at all** -- not `react-window`, not `react-virtualized`,
not `@tanstack/react-virtual`. It solves long lists two ways, and neither is virtualisation:

1. **Server-side paging.** `getNotifications(page, PAGE_SIZE, …)` with `PAGE_SIZE = 20`.
2. **Incremental reveal.** `AuditView` keeps a `visibleCount`, starts at 30, and grows it by 30
   when an `IntersectionObserver` says a sentinel has scrolled into view.

Both are the *application's* strategy. Nothing in either needs a list that can draw a thousand rows
without laying them out, because **nothing ever asks it to**.

**So this is the third item in a row that measurement shrank or removed** -- after the 28 dialogs
that were already built and the "show one of N" container that was never the library's business.
The pattern is worth naming: an item written from the shape of the problem is usually bigger than
the item written from the code.

## What was missing

One thing: **a list could not tell its caller the user had scrolled to the end.** That is the whole
of what incremental reveal needs from a toolkit, and `ListStep` had no way to say it.

`ListStep.reached_end`, plus a public `list_at_end`. Four decisions:

1. **A transition, not a state.** A flag that stayed true while the user sat at the bottom would
   have an application fetching on every frame it drew.
2. **An arrow key reaches the end too.** An application watching only the wheel would leave the
   keyboard user as the one who could not load the rest of the list.
3. **A list that fits fires nothing, but still answers that it is at its end.** Otherwise a screen
   whose first page does not fill the viewport waits forever for a scroll that never comes -- so
   `list_at_end` is public, to be asked rather than waited for.
4. **Half a point of slack**, because an offset clamped to the bottom can land a hair short of it,
   and a signal that never fired because of rounding is a list that silently stops loading.

The demo grows by four rows each time you reach the bottom, which is the target's pattern at a size
you can watch.

## What this is not

Not virtualisation. Nothing here renders a thousand rows, and **how many rows exist is the
application's business** -- which is the same answer navigation gave about screens, and for the
same reason.
