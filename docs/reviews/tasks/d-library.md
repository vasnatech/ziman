- [x] **D9** **Give `fs` a structured error enum** (`NotFound`/`Denied`/`IsDirectory`/`NotDirectory`/`Other` plus `fs_error_message`), matching `NetError`'s shape. Leave `json`/`regex` on strings. (L2 P1-8; M) The three cases a backend actually branches on are reachable only by substring-matching `strerror`. Done 2026-10-06 with `FsError { NotFound, Denied, IsDirectory, NotDirectory, Exists, Other }` and `fs_error_message`. The cheap part was the classification: `native_fs.c` has exactly one error helper, `fs_err`, used 26 times, so one errno switch there covers everything -- and it hands the category over as the same `"category|message"` string native_net.c already uses for NetError, which fs.zm splits. Neither side builds the other's values, and the enum stays declared in Ziman. The 18 Result-returning natives became private `*_raw` with public wrappers, exactly as net.zm wraps `connect_raw`; the three bool predicates needed nothing. Every variant still carries the OS's own wording, so nothing was lost by making it branchable. **The migration needed a missing primitive**: callers whose own errors are strings had no terse way to adapt, so the prelude gains `result_map_err(r, convert)` -- which makes each site `try result_map_err(fs.read_text(p), fs.fs_error_message)`, reads well because a module function can be passed by name, and will be wanted again by D15. Five library sites migrated (csv, properties, migrate, zone); log.zm needed none because it only uses `is_ok`/`unwrap`, and nor did the reference backend, which discards the error with `Err(_)`. Of 253 fs call sites in fixtures only 7 needed touching, for the same reason. **Deliberately left as strings**: the per-item errors inside `lines`/`chunks`/`walk` (`Result<Iter<Result<string, string>>, FsError>`). Those are "a read failed partway through iteration" rather than "the open failed", and making them variants means constructing the enum in C, which is the thing the category|message convention exists to avoid. Noted in fs.zm. tests/lang/fs_error_enum.zm.
- [x] **D10** **Server-side cookies and CORS**: a `Cookie:` parser, a `Set-Cookie` builder, and CORS as a `dispatch` wrapper. (L2 P1-9; M each) The HTTP *client* has a full `CookieJar` and the server has nothing; both are week-one needs for anything browser-facing. Done 2026-10-06, both halves. **Cookies** went in `http.zm` (the module both sides share): `request_cookies`/`request_cookie` read the header a browser sends, and `SetCookie`/`session_cookie`/`set_cookie_header`/`delete_cookie_header` build the one it is told to store. A malformed pair is skipped rather than failing the request, since a browser can be made to send almost anything and one bad pair should not cost a session; `session_cookie` defaults to HttpOnly, Secure and SameSite=Lax, so the careless path is the safe one. The client's `CookieJar` stays where it is -- it models what a user agent keeps between requests, which a server has no use for. **CORS** went in `server.zm`, generalised from the reference backend's own `route_cors`: `cors_policy`, `cors_preflight` and `cors_apply`. Two functions rather than one handler-wrapping closure, because a wrapper must return a closure and allocate one per request, while these compose with `dispatch`, a hand-written router or anything else by sitting either side of it. A wildcard policy echoes `*` rather than the origin and drops Allow-Credentials, since a browser refuses that combination anyway. **Found while testing: my own C11 diagnostic recommended `p = p with { field: value }`, and the real syntax is prefix, `with p { field: value }` -- the exact defect C9 was about, made by me. Fixed, with its fixture; the reference backend's Ctx comment had the same error in two places and is corrected too (backend commit). tests/lang/http_server_cookies.zm and http_server_cors.zm.
- [x] **D11** **`float` JSON output diverges from `print`/Jackson three ways, and a text round trip loses `Number`'s Float/Int kind.** (D2 item 9, D2 B4; S) Three forms of API divergence against the Spring reference, on a type that appears in every measurement payload. Done 2026-10-06. Of the three divergences, one mattered and is fixed: `%g` dropped the fraction from a whole number, so a float 1.0 was written `1`, 100.0 `100` and -0.0 `-0`. JSON does not separate integers from floats but every reader built on it does -- Jackson and Python's `json` both write `1.0` -- so a client parsed an integer where the API promised a fraction. `put_float` now applies the same "add .0 if it does not already look like one" rule value_display has always applied, by the same `strpbrk` test, so `print` and JSON agree about which values are floats. That also fixes the second half of the report for free: the round trip kept losing `Number`'s kind because `Float(1.0)` serialised to `1` and parsed back as `Int(1)`, and now comes back a Float. The remaining difference is *notation* for large and small magnitudes (`print(1e20)` is 100000000000000000000.0 where JSON writes 1e+20) and is deliberate on print's side -- float_shortest_text uses plain notation up to 1e21 while JSON follows the shortest round-tripping form Jackson and Python also produce, so here JSON is the one agreeing with Jackson. Three fixtures asserted the old output and are regenerated; `json_map_objects` is the useful one, since its int `-5` and its bigints stayed put while only the float `200.0` changed. Worth noting `toml_basic.out` already wrote `ratio = 150.0` in its TOML output beside `150` in its JSON output for the same value -- the TOML writer was right all along. tests/lang/json_float_keeps_fraction.zm.
- [x] **D12** **An accumulating JSON decoder** (`Result<T, [string]>`, or a `json_decode_all` companion). (L2 P2-4; M) The derived decoder stops at the first bad field, so the reference backend hand-rolls `FieldError`/`accumulate`/`validation_result` to report more than one validation failure at a time. Done 2026-10-06 as the companion rather than the breaking change -- `#[derive(Json)]` on a struct now also generates `<type>_from_json_all(j) -> Result<T, [string]>`. The existing decoder keeps its signature, so nothing breaks and nothing it already does gets slower; a caller opts in by name. Four shapes were considered and the choice matters, so: (1) a second "record, do not return" emission mode in derive.c duplicates the emitter's recursion and must be kept in step with it; (2) per-field top-level helper functions would add ~654 generated functions to the reference backend alone (73 Json derives, ~581 fields); (3) changing the existing decoder to `Result<T, [string]>` breaks 18 distinct call sites and still needs one of the others internally; (4) **a lambda per field inside the companion**, which is what landed -- the emitter already ends a failing field with `return err(...)`, and inside a lambda that returns from the lambda, so the existing per-field emission is reused verbatim, including its skip-the-rest behaviour, with no second mode to maintain. Its cost is one closure per field, paid only by callers of the companion, which is why the shape is acceptable here and would not have been in the main decoder. Verified on four simultaneously-wrong fields including a nested array element, a missing required field (3 problems), an absent Option staying None, a non-object document, and that a good document decodes identically either way. Known limits, both documented in SYNTAX.md and at the emission site: a nested struct contributes one message (its own decoder is the single-error one), and an enum gets no companion since its decode either matches a variant or does not. Two fixtures needed updating -- cli_emit_derived (the emitted text grew) and derive_error_position_struct, whose expectation pinned a whole two-error block and now asserts the one line that is its point. tests/lang/derive_json_from_json_all.zm.
- [x] **D13** **One `url` module and one `percent_decode`.** (L2 P2-6, D2 item 19; S-M) Two 80-line URL parsers and two `percent_decode`s with two arities and two error types implement one algorithm across `db` and `http` -- about 160 duplicated lines. Done 2026-10-06 for the duplication, and the two URL parsers are deliberately left alone. `percent_decode` really was one algorithm twice, differing only in whether `+` is a space and in the error type. The obvious fix -- have `db` call `http`'s -- was wrong: `db` does not depend on `http` and should not start to for a `%XX` loop. So the loop moved to a new `lib/core/url.zm` below both, and each keeps its own signature as a thin adapter (http's for the public API it already exported; db's to answer a DbError naming the URL at fault, which a caller cannot work out from "bad %-escape" alone). The generated dependency graph confirms the layering: `db --> url`, `http --> url`, `url --> number`, and no `db --> http`. **The two parsers are not duplicates**, which is worth recording since they look it at 80 and 82 lines: they read different grammars into different shapes -- `Url { secure, host, port, target, userinfo }` for `https://host/path` against `DbUrl { user, password, host, port, database, params }` for `postgres://user:pw@host/db?a=b`. Adding a core module took four registrations (Makefile CORELIB_MODULES, corelib.c's table and its #include, gen_lib_manual.py's GROUPS) and the README's module table. tests/lang/url_percent_shared.zm checks both adapters agree with the primitive.
- [x] **D14** **Add `mapb_get_or`, and audit `Map`/`MapBuilder` for other asymmetries.** (D2 item 20; Trivial) Removes an inline `switch` from every counting loop. Done 2026-10-06. `mapb_get_or` is ordinary Ziman in the prelude rather than a builtin like `map_get_or`, because it is exactly the switch it replaces -- `mapb_set(counts, k, mapb_get_or(counts, k, 0) + 1)` is the whole point -- and its type arguments infer from the builder, so no call site spells them out. Recorded so the next person does not re-derive it. tests/lang/mapb_get_or.zm.
- [x] **D15** **Error-type consolidation across the library: 281 `Result<_, string>`, up from 242.** (D2 item 24; L) The one axis D2 found to have got *worse* since the previous review. D9 is the first concrete instance; this is the general pass, and it wants a decision about which modules keep strings on purpose (`json`, `regex`) before it starts. **Audited 2026-10-06 and closed with no code change: the metric measures the wrong thing.** All 280 were classified -- 55 are internal `*_raw` plumbing behind an already-structured API (net's eleven are *all* private, behind NetError; fs's twenty-one behind FsError; sqlite's five behind DbError), ~184 are parse and format errors where the message is the whole information and nobody branches, 14 are application-supplied callbacks in `server` (`decode: fn([byte]) -> Result<I, string>` -- the app's message to a client, which a library enum would be wrong for), 13 are `os` capability failures a program cannot act on, and 3 are the fs Iter item errors D9 documented. The decisive evidence is D9 itself, the task that fixed exactly what this one is about: it took fs from 21 `Result<_, string>` to **24** while taking its *public* ones from 18 to **3**. A metric that moves the wrong way on its own best-case fix is not the one to track. Every module whose errors callers branch on already has a type -- FsError, NetError, DbError, and JwtError on `verify` (jwt.sign keeps a string, its only failure being a programming mistake). The rule and the full breakdown are now in DESIGN.md so a later review does not re-raise the count; if it is tracked at all, the number worth watching is public `Result<_, string>` in modules whose errors are branched on, which is zero.

- [x] **D18** `mutable_array_push` is superlinear for reference element types: 4M strings take 16.4 s and 904 MB against 0.81 s and 685 MB for the value-semantics `push` that A6 made amortised O(1) -- 20x slower, which inverts SYNTAX.md's advice about which to reach for. Find out why (it is not superlinear for value elements, so the suspicion is the write barrier or per-element retention rather than the growth policy), and until it is fixed correct the manual, since the manual currently recommends the slower path. (DX3 item 7, D6; M for the fix, trivial for the doc) Done 2026-10-14. **Fixed, not just documented, and the cause was not the element type.** Reproduced first (19.72s/915MB against 0.96s/685MB at 4M strings) and the growth curve measured: 0.47 / 1.49 / 5.22 / 15.08s at 500k/1M/2M/4M, about n^1.7, against exactly linear for the value `push`. The profiler said 89% "(garbage collection)" and said the same on `ziman-nogc`, which was the clue -- `nogc` removes Boehm, while Ziman's own `gc_heap` collector runs in both. What actually costs the time is that `mutable_array_push` is **variadic**: every call collapses its tail into a one-element array first, three allocations, two from a collector's heap. The decisive measurement is that the same 2M elements take 0.22s pushed in batches of a thousand and 4.80s one at a time, at the same final memory -- so the cost is per-call, not per-element. Reference elements hurt more only because the temporary is then a *scanned* boxed allocation whose cost compounds with the live buffer, where an int builder's storage is packed and unscanned. The fix is a one-element fast path in `call_function`, selected by comparing the already-cached native pointer so every other call pays two integer tests and a relaxed load: **19.72s -> 0.67s** at 4M, exactly linear across 500k-8M, and now *faster* than the value `push` (0.67s against 0.87s). Ints improved too, 0.72s -> 0.25s. The `ab_table_get` magic and owner checks are preserved, since the fast path goes through the same two functions. **No SYNTAX.md change was needed**, and the report's "inverting SYNTAX.md's advice" is imprecise: the manual's advice is that `insert`/`set`/`remove` are O(n^2) with value semantics and a MutableArray is the answer for *those*, which was and is true -- it never claimed `mutable_array_push` beats `push`, and now it would be right if it did. 1017 fixtures on both builds, `test-gc-*` and unit tests green.
