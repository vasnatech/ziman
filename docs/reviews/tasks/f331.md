# F331 — navigation: a history, and what a screen change owes the user

Done 2026-11-20. `lib/ui/navigate.zm`, a gallery demo, tests. Designed first in
[navigation](../../design/navigation.md), which is what §4.2 of the port plan asked for.

## The item was three times its real size

It was written as "53 views and 28 dialogs need a screen model with history". Two thirds of that
was already built or was never the library's business.

**The 28 dialogs were done.** `controls.dialog_layer` is modal -- the geometry shuts the pointer
out, `takes_keys` shuts Tab out, the scrim says the window is blocked -- and `dialog_keys` gives
Escape and Enter. Nothing was missing, and nothing was added.

**"Show one of N" is not a library problem.** A screen is a widget the caller builds, and a caller
that wants one of fifty-three builds the one. A container taking all fifty-three to draw one would
ask for fifty-two widgets in order to throw them away; `controls.Tabs` holds only the strip for the
same reason. The demo shows this directly -- `body()` returns one screen's content, never three.

So what was built is the part an application gets wrong once per screen.

## The history, and the three things people get wrong

A value. Nothing about it draws.

1. **Back and forward move the position; the entries do not shrink.** A history that popped on
   `back` could not offer `forward` at all. "It is a stack" is the wrong model, and it is the
   model everyone reaches for first.
2. **Going somewhere new throws away what was ahead**, which is what a browser does. The
   alternative is a forward button that goes somewhere the user has never been.
3. **Going where you already are does nothing.** A list that re-opens the record already open
   would otherwise need two `back`s to leave it, and the first would look as though it had failed.

Each has a watched fail: removing the truncation in (2) reddens its test on its own.

## What a screen change owes the user

The part worth a module, because a sighted mouse user never sees any of it go wrong.

- **The focus must move into the new screen.** It is on a control that has just stopped existing,
  so Tab resumes from the start of the window -- a keyboard user dropped at the top of the
  navigation bar every time they open a record. `arrived_at` answers where it belongs.
- **The new screen must be announced.** A reader says what the user moves to, and nobody moved.
  The screen carries a `Role.Status` region holding its title, so F329's `announcements` speaks it
  on arrival and says nothing when the screen has not changed.
- **A screen is not a control**, which is F323's answer for F323's reason: a focusable screen is a
  tab stop sitting in front of its own content. The watched fail reddens two tests, because making
  it a control also breaks `arrived_at`.

## Two traps

**`focus.node_of` does not find a screen**, and should not: a screen is a named group and `focus`
looks up controls. Asking the focus layer for something deliberately unfocusable correctly finds
nothing. `widget.node_named` is the lookup.

**`text.heading` already existed** -- "an application's own headings; no control draws one" -- so a
screen title needed no new token. The first attempt invented `text.title`.

## Not built, deliberately

No router: no URLs, no paths, nothing parsed, and a screen name is a string the library never
interprets. No screen registry. No animated transitions, which want a clock the library does not
have. And nothing about any particular application -- a screen is a titled region with a name, and
what is on it is the caller's, exactly as a dialog's content already is.
