# F347 — a press is hit-tested and a wheel is not

Open. Raised 2026-11-25 by the health-record port, whose sidebar menu scrolled when the wheel was
turned seven hundred points away from it. `lib/ui/controls.zm` (`list_input`).

## What happens

`controls.list_input`'s `Press` arm checks that the point is inside the bounds it was given. Its
`Wheel` arm does not look at `w.at` at all:

```ziman
Wheel(w) { scrolled(l, l.offset - (w.vertical as float) * tall, bounds, tall) }
```

So a list handed a wheel scrolls, wherever the pointer was. Measured in a 1200-point window: a
wheel at (900, 400) scrolled a 207-point sidebar whose box ends at x=207.

## Why it is the untouched sibling of a fix that was made

The `Press` arm carries its own comment about exactly this shape of bug, in the same function:

> This read `p.y` alone, so a list selected a row from a press anywhere at the same height — the
> far side of the window included. … it surfaces where one does not: a sidebar menu beside a wide
> screen took presses meant for that screen, so a button seven hundred points to its right changed
> which screen was showing. Found by pressing that button.

The same sidebar, the same seven hundred points, the other input. The press was fixed and the
wheel was left.

## Why it is "open" and not simply wrong

**The library's design is that the application routes a wheel.** `controls.target` answers which
control an input is for, and its own tests say so — `a_wheel_goes_under_the_pointer_and_not_to_the_focus`,
`a_wheel_over_nothing_goes_nowhere`. An application that routes by `target` never hands a list a
wheel that was not over it, and the health-record frame's pane always did route that way.

So there are two defensible readings and they want different fixes:

- **The hit test belongs in `list_input`**, as it already does for a press, and a caller should be
  able to hand any input to any control and get the right answer. This is the reading the `Press`
  comment takes, and it makes the two arms agree.
- **The hit test belongs to the caller**, and `bounds` is for page size and row arithmetic only.
  Then the `Press` arm is the odd one out, and what is missing is a line in `list_input`'s doc
  comment saying the caller must route — because nothing says so now, and the asymmetry reads as
  an oversight rather than a contract.

Either is better than the present state, where a reader cannot tell which rule applies and the
answer differs by input kind. The first is the one to do unless there is a reason not to: a guard
that costs four comparisons cannot be the thing that makes a toolkit slow, and a caller that has
already routed correctly is charged only those four.

**The application does not wait for it.** `screen/frame.zm` grew `wheel_outside`, which is the
routing half the library expects, with the measurement in its comment and a test that a wheel away
from the menu leaves it alone.
