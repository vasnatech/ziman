# F303 to F312 — four more controls, the mouse button nobody could see, and the calendar made real

Opened 2026-11-19, after F298–F301. Four controls were asked for; building the first of them found
a defect underneath all of them, which is why there are six entries here and not four.

**F298–F301's file argued that a toolbar was an arrangement and belonged in an application.** That
was wrong, and it is worth saying why rather than quietly doing the opposite. The argument was that
a toolbar is a row of icon buttons — and a row of icon buttons is exactly what it is to *look* at.
What it is to *use* is one stop in the tab order with its own arrow keys, which no arrangement of
controls can be: `focus` counts tab stops by walking the tree, so eight buttons are eight stops
however they are laid out. The test that settled it is in the suite —
`a_toolbar_is_one_tab_stop_however_many_commands_it_holds` — and it fails against any arrangement.
The same file's claim about a status bar and a breadcrumb still stands.

Effort: **S** = a day or less, **M** = a few days.

---

- [x] **F303** **The pointer keeps the text shape over a number field's steppers.** (S;
  `lib/ui/controls.zm`, a test.)

  `cursor_at` decides the pointer's shape from the role of the control under it, and a number
  field's steppers are deliberately not controls — two nested controls would be two tab stops and
  two things for a reader to announce. So the whole field declared itself a `SpinButton`, the role
  table answered `Cursor.Text`, and the I-beam covered the arrows: a pointer saying "type here"
  over a thing you click.

  Resolved from the laid tree instead. Within a `SpinButton`, a point inside either stepper's laid
  box is an `Arrow`; everywhere else in the field it stays `Text`. **In `cursor_at` and not in a
  `number_field_cursor` beside `table_cursor`**, and the distinction is real: a table's column
  edges live in the `Table` value, so only the application can compute them, while the steppers are
  already laid out and their boxes exact in the tree. The test asserts the shape at exactly the two
  points `a_press_on_a_stepper_steps_it` presses, which is what pins the cursor and the click to
  the same two places.

- [x] **F304** **An expander.** (S; `lib/ui/controls.zm`, a demo, tests.)

  A titled section that folds away. **A button that happens to hide something**, which is both the
  design and the accessibility story: neither ATK nor ARIA has an expander role and neither is
  missing one — a disclosure is a button whose `expanded` state says what pressing it did.
  `State.expanded` has been in `widget` since accessibility was built, and until now a tree row was
  the only thing that ever set it.

  **A shut section is not in the tree at all**, rather than laid out and hidden. Content that is
  present but invisible is content a reader announces and a Tab lands in, and a window whose focus
  disappears into a folded section is one the keyboard has lost its place in.

  **The header is the control and the section is not** — a group holding a focusable header and,
  when open, the content. One control with the content inside it would nest every button in the
  section underneath a button. It is the number field's rule the other way up: there one control
  had to swallow its parts, here the parts must not be swallowed.

  A rendered PNG found the thing no test stated: the content sat flush with its own header and read
  as the next thing down the column rather than as the thing inside. It is indented to the title now.

- [x] **F305** **The secondary mouse button, which the library could not see.** (S;
  `lib/ui/controls.zm`, `lib/ui/desktop/desktop.zm`, `lib/ui/desktop/window.zm`, 21 switch arms.)

  Found while asking what a context menu would need. `Input.Press` carried a point and no button,
  and `desktop.input_of` threw away the button number the platform already supplied — so **every
  button on the mouse arrived as a left click**. A right-click or a middle-click on any button in
  any window fired it; on a list it chose a row; in a field it moved the caret. This had been true
  for as long as that function has existed.

  `Input.SecondaryPress` is a variant and not a flag on `Press`, because a number on `Press` is a
  number each of the twenty-odd places that match on a press has to remember to check, and the one
  that forgets is exactly the bug being fixed. **The compiler named all twenty-one sites**, which
  is the no-default-arm rule paying for itself. `input_of` now routes button 1 to `Press`, button 3
  to `SecondaryPress` and **drops the rest**: the middle button means different things on different
  desktops, and answering nothing is the library saying so honestly. A release is only ever button
  1, because the grab only ever began on button 1.

  `target` routes a secondary press by position, like a press — the gesture means "what can I do
  *here*", and routing it to the focus would open one control's commands over another's pixels.

- [x] **F306** **A context menu.** (M; `lib/ui/controls.zm`, a demo, tests.)

  **A menu that hangs off nothing**, which is all of the new work. A `Menu` is opened by pressing a
  title that says "File", so the title's laid box answers both where the popup goes and how wide it
  is — which is why `menu_popup_layer` leaves that arithmetic to its caller. A context menu is
  opened by a gesture at a point, so it measures its own rows and places itself, and pushes itself
  back inside a window whose size it is told rather than knows. The rows, the arrows, Home and End,
  Escape and the highlight are `Menu`'s, reused whole.

  **One function answers where it goes**, asked by both the layer and the hit test: worked out
  twice, a menu could be dismissed by a click on one of its own rows.

  **The keyboard opens it too** — the Menu key, and Shift+F10 for keyboards without one. A context
  menu reachable only by the mouse is an inaccessible control, and the gallery's own gate is what
  caught it: `every_demo_lays_out_and_declares_at_least_one_control` failed because the demo's
  panel was a part rather than a tab stop, and a panel nothing can focus is a panel whose commands
  no keyboard can ask for. The Menu keysym is named in `window.key_name` now; Shift+F10 already
  arrived as `Other("F10")`.

- [x] **F307** **A toolbar.** (M; `lib/ui/widget.zm` and the role's three mappings,
  `lib/ui/controls.zm`, a demo, tests.)

  **One tab stop, and the arrows move inside it**, which is the whole reason it is a control. A row
  of eight buttons is eight stops in the tab order, so a user reaching the field below presses Tab
  nine times. `Role.ToolBar` is what tells a reader that the arrows will work here and that Tab
  will leave.

  **Its commands are drawn by `button_inside`**, extracted from `button_widget` so that a toolbar's
  commands are buttons rather than things that look like buttons — a theme cannot reach one and not
  the other. What they are not is `Focusable`s of their own: parts for a click and for a reader,
  one stop for Tab, which is the tab strip's arrangement exactly.

  **A rule is not a `Separator`.** That role means a draggable divider here and `cursor_for` turns
  it into a resize arrow from the shape of its box, so a toolbar's rule is deliberately not one — a
  cursor is a promise, and decoration must not make it.

  **What does not fit goes into an overflow menu rather than off the edge**, measured with
  `widget.measure` — the same measurement layout will make, so the strip cannot decide that seven
  fit and then draw an eighth over the edge. Room for the overflow button is reserved *before*
  anything is counted, which is the arithmetic that is wrong in every toolbar that hides one
  command behind a button wide enough for three. The overflow's rows are never stored, only its
  open-or-shut: which commands overflow depends on the width the strip was given.

  `toolbar_input` takes the laid tree where a tab strip takes a box and divides it. A strip of tabs
  is a row of equal columns; a toolbar's commands are an icon, a word and a rule, and only their
  laid boxes know where they ended up.

- [x] **F308** **A date field and a calendar.** (M; two roles and their three mappings each,
  `lib/ui/controls.zm`, a demo, tests.)

  **The text is the value and the calendar is a way of writing it.** A field holding a `LocalDate`
  and showing text derived from it cannot hold what a user is halfway through typing: `2026-11-` is
  not a date and is plainly on the way to one. That is the number field's argument met again, and
  it ends the same way — the `Entry` holds the truth and `date_in` answers an `Option`.
  `time.parse_localdate` is the judge, so a string this accepts and one the rest of the program
  accepts cannot drift apart.

  **Paging the months writes nothing.** The calendar's highlight is not the value: a user looking
  for next March has chosen nothing, and a calendar that moved the value as the highlight moved
  would leave a date behind every time somebody went looking for one. Enter commits, Escape does
  not.

  **Six rows, always.** A grid sized to its month would resize five times a year under the pointer
  — February in a common year starting on a Monday needs four rows and a 31-day month starting on
  a Sunday needs six. The days either side are real dates drawn faded, not holes.

  **The weekday names are the first row's own dates, formatted**, and the month's name comes from
  `time` — so both are right in whatever language the machine is set to, where a table in
  `controls` would know them in English alone. Monday is column zero, worked out from the epoch day
  rather than a table: 1970-01-01 was a Thursday.

  Two defects a rendered PNG found and no test stated: the month pager's two arrows pointed right
  and *down* rather than back and forward, and at the first cell width the header read "WedThu"
  with no gap. Both are fixed; the arrows are one triangle and its mirror, so a theme that changed
  one changes both.

- [x] **F309** **The focus ring painted over everything, popups included.** (S; `lib/ui/widget.zm`,
  a test.)

  Reported from the gallery: a context menu opened behind the selection border of the control that
  was clicked. It was not behind it — the ring was being drawn **on top of the menu**.

  `paint_focused` collected the whole tree and then pushed the ring, so the ring was the last op in
  the scene and landed over everything painted before it, every layer included. A context menu is
  exactly the case that shows it, because a secondary press moves the focus to what was clicked and
  *then* opens a menu over it.

  The walk carries the ring now and emits it as the focused control's own subtree finishes, so
  anything painted later covers it. **One place is every place**: a `Control` is never a `Scroll`
  or a `Sized` itself — those wrap it or sit inside it — so the ring goes in after the final child
  loop and nowhere else.

- [x] **F310** **The week starts where the locale says it does.** (S; `lib/core/locale.zm`,
  `src/native_locale.c`, `lib/ui/controls.zm`, tests.)

  The calendar started on a Monday because it was written in a country that does. Sunday in the
  United States and Japan, Monday across most of Europe, **Saturday in much of the Arabic-speaking
  world**.

  `locale.first_weekday` asks the host. **Not a table here**: a list of which countries start on
  which day is a list that goes out of date, that is wrong for the locales nobody on the team
  speaks, and that disagrees with the rest of the same machine. glibc already holds the answer.

  **The trap, which cost an hour**: `_NL_TIME_FIRST_WEEKDAY` is an *enumerator* in `<langinfo.h>`,
  not a macro, so `#ifdef` on it is false however available it is. Written that way the native
  compiled, ran, and answered Monday for every locale on earth — which looks exactly like a feature
  that works, because Monday is the commonest answer. A C probe against five locales is what found
  it. The guard is `__GLIBC__`.

  Measured afterwards: `en_US` Sunday, `en_GB` Monday, `de_DE` Monday, `ja_JP` Sunday, `ar_EG`
  **Saturday**, `tr_TR` Monday. The test asserts two locales *and* that they differ on this
  machine, so it cannot pass by both answering the same thing.

  The locale is a field on `DateField` rather than read from `locale.default()`, for `Style`'s
  reason: a module that reaches for a global cannot be tested against two of them, and the first
  day of the week is precisely what differs.

- [x] **F311** **The calendar gets months and years.** (M; `lib/ui/controls.zm`, tests.)

  A year twelve years away was a hundred and forty-four presses on a month arrow. The header is a
  button now: days zoom to months, months to years, and choosing zooms back in — which is what
  every date picker settled on, for this reason.

  **Choosing a month is not choosing a date.** A user who picked March has said nothing about which
  March day they mean, so it steps in rather than writing a value. Escape zooms in before it shuts,
  so one key undoes one step instead of throwing away three.

  **One size for all three views**, taken from the day grid. A popup that resized as a user zoomed
  out would move under the pointer between the press that opened the months and the press that
  chose one. Years come in blocks of twelve on fixed boundaries, so paging forward and back returns
  to the same twelve rather than drifting by one each time.

- [x] **F312** **The gallery's toolbar shows icons.** (S; the demo.)

  A toolbar of words is a menu bar. Five drawn marks — a dart, a square, an arrow down to a line,
  two sheets, an arrow up from a line — with `label: ""` so the *icon* carries the name:
  `announced_name` falls back to it, a reader says "Send, button" and the tooltip shows the same
  word.

  **Drawn and not typed**, which is F302 for the third time. The first draft used filled ellipses
  for Save and Share and they were indistinguishable in the render — two icons a user cannot tell
  apart are worse than one, so they became an arrow down to a line and an arrow up from one.
