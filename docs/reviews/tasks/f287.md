# F287 — the box model learns to centre

Found 2026-11-12 while checking whether F286's widened box was enough to write a second look and
feel against. It was not, and the reason turned out to have nothing to do with looks and feels:
**`lib/ui` could not centre anything, and had not been able to since F271.**

- [x] **F287** **Alignment, across a stack's direction and along it.** (M; `lib/ui/widget.zm`,
  `lib/ui/controls.zm`. 11 unit tests, 2 control-level ones, 6 mutations, and the layout cost
  measured because this is `place_stack`.)

  **The evidence that started it, measured rather than looked at.** A `Send` button laid out in a
  200-point-wide box had a face 200 wide and its label at **x=8** -- the left padding and nothing
  else. Every platform centres a button's label. It had gone unseen for sixteen tasks because
  `curly gui` puts `widget.expand` on the field beside its buttons, so they take exactly the width
  of their text and the spare room that shows the bug is zero.

  The second consequence is how it was found. A check box's face is **9x22 points**, taller than
  it is wide, because that box is a `Stack` whose only child is the mark glyph -- so its width is
  one glyph's advance and its height a line height, and a glyph is always narrower than a line is
  tall. F286's rounded theme drew it as a capsule. **The radius did not make it the wrong shape; it
  made the wrong shape visible**, and the first diagnosis -- that one `corner_radius` across every
  control is wrong -- was a true statement about a symptom.

  **The gap was deliberate and then forgotten**, which is the part worth keeping. `Fixed`'s own
  comment has said since F271 that a stack hands every child the parent's full extent across its
  direction, and that "choosing otherwise means an alignment rule (top, centre, end), which belongs
  with the widget set rather than here". The widget set never built one. Nothing else in
  `widget.zm` mentioned alignment, so there was no second place for the omission to be noticed --
  the note that deferred it was also the only record that it was missing.

  **`Across` and `Along`, which are not the same enum.** `Across` has `Stretch`, `Start`, `Centre`
  and `End`; `Along` has the three without `Stretch`, because stretching along the direction is
  what `flex()` already means and a second spelling of it would be a second thing to keep in step.
  They live together in one `Alignment` on `Stack`, for the reason `Surface` is one field and not
  four: a literal names every field in this language, so a struct keeps the churn to one line per
  site and the two halves of one idea in one place.

  **`Stretch` is the default and nothing moved.** Every one of the 29 `Stack` literals got
  `align: widget.stretched()`, which is exactly what the layer did before, so all 227 existing
  widget and control tests passed untouched and `tests/lang/ui_widget.out` is byte-identical. The
  same discipline F286 used, and the same reason: a change to a box model that re-blesses pixels is
  a change nobody can review.

  **`Stretch` measures nothing, which is what keeps the default free.** The other three options
  need the child's natural size across the direction, and that is a `measure` this layer did not
  use to make. The `switch` is written so a stretched stack never reaches it.

  **A flexible child leaves no spare room, so aligning along the direction does nothing** -- and
  that falls out of the arithmetic rather than being a case to remember: `flex()` consumes the
  spare by definition, so the shift computes to zero. It has its own test because the obvious
  implementation adds the shift unconditionally and pushes the content of an exactly-full container
  off its end.

  **A child too big for its room overflows at the end rather than being centred off the near
  side.** An unclamped `(room - natural) / 2` is negative for an oversized child, which puts it
  above the top of its own parent -- so the span is clamped to the room first, which is also where
  `place_stack` already leaves an over-full container.

  **The button centres now**, and that is the whole visible result: the same button in a 200-point
  box puts its label at x=86, which is `(200 - 28) / 2`, while a shrink-wrapped one stays at x=8
  because its spare room is zero. The vertical half of `centred()` matters only when a button is
  taller than its text, which is what centring should mean.

  ## What it costs, which is the thing a change to `place_stack` owes

  Fifty and two hundred rows of label-box-label, laid out ten times, interleaved stretch-then-
  centre, three passes:

  | rows | stretched | centred |
  | --- | --- | --- |
  | 50 | 12-18 ms | 11-18 ms |
  | 200 | 47-50 ms | 49-51 ms |

  **Inside the noise at both sizes**, and the reason is F285's finding being paid back: `measure`
  already runs for every fixed child to find its extent along the direction, and `Sized`
  short-circuits it, so the extra call an aligned stack makes hits the same bound rather than
  walking a subtree. The duplicate `measure` could be removed by keeping the first loop's answers
  in an array -- and should not be, because F285 measured exactly that and found the per-stack
  allocation cost more than the walk it saved.

  ## Mutations, and the one that got away first time

  Six, all caught after a fix: `Centre` behaving as `End` across and along, a flexible child no
  longer suppressing the shift, the oversize clamp removed, and `across_of` reading the wrong axis
  (caught by six tests, because a column aligns across its *width* and a row across its *height* --
  one `switch` the wrong way round is the obvious bug here and a row-only test suite would pass).

  **The sixth survived: nothing asserted that the button centres.** I had found that defect by
  measuring and fixed it without writing a test for it, so reverting `centred()` to `stretched()`
  left the suite green. Two control-level tests now pin it -- one that a stretched button's label
  is centred, one that a shrink-wrapped button's label has not moved -- and the second matters more
  than it looks, because it is what says the change was additive.

  ## Not done

  **The check box is still 9x22.** Squaring it is now *possible* -- a `Fixed(side, side)` holding a
  stack with `centred()`, inside a row that aligns `Across.Centre` so the square keeps its height
  -- but it needs a decision this task does not have: what a check box's side should be in terms of
  `style.text_size`, since `check_box_widget` takes no `Metrics` and so cannot ask for a line
  height. That is the next user of this feature and the one that will say whether it is shaped
  right.

  **No `space-between`.** Aligning along the direction moves the whole run and leaves the gaps
  alone, which is what a button's label and a toolbar want. Distributing the spare *between*
  children is a different feature and nothing has asked for it.
