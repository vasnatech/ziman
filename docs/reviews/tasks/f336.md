# F336 — the first form, and the text area that measured nothing

Done 2026-11-20. `lib/ui/controls.zm` and two tests here; the form itself is
`health-record/health-record-frontend-ziman`, which is a new application and not part of this
repository.

`AllergyDialog.tsx` — thirteen fields, one of which fills in five of the others — is the first
**form** any application has built on this toolkit. Six things met their first real caller:
`Autocomplete` (F322, which until now had only the demo it was written beside), `ComboBox`,
`Entry`, `DateField`, `dialog_layer`, and `Widget.Grid`, which had laid out nothing but its own
demo.

## The defect

**A text area measured 0 × 0.**

`Entry.rows` is documented as *"How many lines tall. 1 is a field and anything more is a text
area"*. `multi_line_widget` makes its control's child a `named_scroll`, and a `Viewport` measures
as nothing **on purpose** — "it has no natural size, and that is the whole point of it". So:

    rows=1 -> 29.0 x 32.8
    rows=2 ->  0.0 x  0.0
    rows=5 ->  0.0 x  0.0

In a column — which stretches its children *across* but not *along* — that is a control at full
width and no height. It disappears, with its own label still drawn above it, which is exactly how
it was found: a form whose Notes caption had nothing under it.

The fix is one `tall_of` inside the control, so it asks for the height its own field claims. A
caller's `tall_of`/`expand` still wins, because a `Fixed` fixes what it *measures* and not the box
it is laid into.

**The gallery could not have found it.** Its text area demo is
`widget.tall_of(area_height, it.area)` — the demo supplies the height the control was failing to
ask for, which is the workaround this removes. That is the second time in two days that a demo's
own scaffolding hid the defect it was meant to expose; the badge (F335) was the first.

**The watched fail**: `a_text_area_measures_its_rows` reddens at `actual 0.0 is not greater than
bound 32.0` with the `tall_of` taken out again.

## The measures-as-nothing trap, and what is different about this one

`widget.Fixed.constrains` counts the victims of "measures zero and stays zero unless a parent
stretches it", and this is another. **But it is the first where the control had a documented size
of its own.** The header band, the link, the slider's thumb and the rest were all cases where a
caller had to supply a size the control genuinely did not have. A text area says `rows: 2` and
means it.

Worth asking of the remaining `Viewport` users: *does this control know its own size?* If it does,
it should say so rather than leave a caller to.

## What the form found that is not fixed here

| | |
|---|---|
| no width anywhere | `dialog_layer` sizes to content and a grid of `Share` tracks has no natural width, so thirteen fields went into **290 points** with every caption painted over its neighbour. The application says its own width; whether a dialog should be able to is a question for a second one. |
| three layout passes | a suggestion list inside a modal hangs under a field whose position nothing knows until the modal is laid out. The gallery needs two. Nothing is wrong with it — it is worth recording that the number is not two. |
| `DateField` cannot be empty | it holds a `LocalDate`, not an `Option<LocalDate>`, and nine records in ten have no onset date. The application added a check box rather than invent a date. |
| `Autocomplete` suggests `[string]` | so a suggestion row cannot carry a badge or a description, which the target's does. |

The last two are shapes rather than defects, and both should wait for a second form to ask for
them.

## Gates

`make check-fast` with the fix in. The application's `check.sh` — typecheck, lint, **33 units**,
the design dialect — all green, and `src/test/other/live.zm` ran create, update and delete against
a real backend and left the record store exactly as it found it.
