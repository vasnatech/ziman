- [x] **F2** Interpreter speed: resolve identifiers to slots or compile to closures (a loop is about 28 times slower than CPython; 500-650 requests per second that does not scale with clients). (L P2-1, D; L) Diagnosed 2026-09-28, not fixed: this is two separate problems, not one. The "does not scale with clients" half is the Boehm collector, not the connection pool the developer review also suspected -- `tests/bench/server_concurrency.sh` (new) shows the collector build flat-to-declining across concurrency (347/584/429/361 req/s at c=1/4/8/16) while a `make nogc` build of the same code climbs the whole way (500/1319/1711/2552), 7x faster at c=16; a real multi-connection pool (file-backed SQLite instead of `:memory:`) made no difference, ruling that suspect out. See DESIGN.md "The collector, not the connection pool...". The raw-speed half (28x slower than CPython, `strcmp` identifier lookup) is untouched by this finding and still needs slot resolution or closures/bytecode, independently of whatever the collector ends up costing under concurrency. A tuning pass (same day): a bigger initial heap is a free 30-80% win at every concurrency level with no rebuild (`GC_INITIAL_HEAP_SIZE=512M`), more marker threads add nothing on top of it, and incremental mode is not just slower but catastrophic under concurrent load (~8x, reject it) -- but no configuration closes the gap to `ziman-nogc` (still 4.8x at c=16 even with the best config found), so this needs either less per-request allocation or the deeper memory-reclamation redesign already on the roadmap, not more tuning. See DESIGN.md "A tuning pass on the follow-up above...". Not done: an actual fix for either half; a decision on whether to ship the bigger initial heap as the new default given its RSS cost. Raw-speed half, first fix, 2026-09-28: profiling the loop with `perf record` before writing a resolver found the reviews' own diagnosis was wrong -- `strcmp`/`env_lookup` were under 5% of total time; ~70% was the Boehm collector's own allocation machinery (`GC_build_fl`, `GC_allochblk_nth`, mutex lock/unlock), from a brand-new `Env` (plus its binding array, plus a `strdup`'d loop-binder name) allocated and freed on *every single loop iteration*. Fixed by giving `STMT_WHILE`/`STMT_FOR` one scope for the whole loop, `env_reset` (new, `env.c`) between iterations instead of `env_new`/`env_free` around each one. `tests/bench/loop_bench.zm` (new, the reviews' own 3M-iteration loop): 1.4s to ~0.3s, about 4-5x; `scalar_arrays_bench.zm`: 3.99s to 3.06s, about 25%; `fib_bench.zm` (new, recursive, no loop): unchanged, as expected, since `call_function`'s own per-call scope allocation is a separate, still-open cost. See DESIGN.md "Interpreter speed (F2): the GC, not strcmp, was the loop's real cost". Raw-speed half, second fix, 2026-09-28: slot resolution, done -- `Expr`/`Stmt` gained a `(resolved_depth, resolved_slot)` pair, computed once by the type checker (`env_lookup_resolved`) and used by the interpreter (`env_at_slot`) to jump straight to a name's binding instead of re-comparing strings down the scope chain every time the expression runs. Found three genuine ways the type checker's `Env` tree and the interpreter's independently-built one can disagree on a slot's meaning (a lambda capture, a global val, a capturing lambda's own declared parameter -- each excluded from the fast path rather than fixed, since excluding them costs nothing the benchmarks care about) and one bypass worth closing at the source instead (`defer`'s hidden variables, never `env_define`d at check time though the interpreter defines them at run time -- fixed by making the type checker define them too). Each bug was caught by the full test suite, not a design review: `global_val_basic`, `lambda_basic`, `migrate_basic` each failed with a confidently wrong answer (not a crash) before its respective fix. See DESIGN.md "Slot resolution, and three ways two independently-built Env trees can disagree". `loop_bench.zm`/`fib_bench.zm` re-measured pinned to one core (this machine is a hybrid P-core/E-core Intel chip; an earlier unpinned reading looked like a 2x regression that pinning showed was pure scheduling noise): loop-heavy code (`loop_bench.zm`) improves further on top of the scope-reuse fix (12.964s to 3.385s for 6 pinned runs); call-heavy code with few local lookups per call (`fib_bench.zm`) is statistically unchanged (4.951s vs 4.990s for 6 pinned runs), as expected -- `fib` was never lookup-bound. Raw-speed half, third fix, 2026-09-28: `call_function`'s own costs, done -- profiling `fib_bench.zm` (unchanged by slot resolution, as predicted, since it never crosses that fix's pattern) found `find_function`'s linear scan over every loaded function re-run by name on every single call, and a fresh `Env` allocated per call, the exact per-iteration allocation problem the loop fix above already solved, just for calls instead of iterations. Fixed with `call_fn` (new `Expr` field, ast.h): `check_call` already runs `find_function` once at type-check time to validate the call; caching that result there instead of discarding it means the interpreter never re-scans. Second fix: a per-thread `Env` free-list pool (`env_pool_acquire`/`env_pool_release`) that `call_function` takes from and gives back to instead of `env_new`/`env_free`, safe for recursion since call/return is strictly LIFO per thread. A third, smaller fix found along the way: skip the ~48-branch builtin-name `strcmp` chain entirely once `call_fn` says definitively this isn't a builtin. Phase 3, fourth implementation increment done 2026-09-30: the conservative stack scan itself (`src/gc_scan.c`/`.h`, `make test-gc-scan`) -- scans the calling thread's own C stack, word by word from near the current stack pointer up to the thread's real upper bound (new `stack.c` accessor `ziman_stack_bounds`, reusing the codebase's own existing "address of a local is the stack pointer" idiom rather than a new technique), feeding each word through `gc_lookup` and reporting whatever resolves to a real object. Always the calling thread's own stack, never another's -- this design's entire premise (one heap per thread, collected on its own time) means there is never a need to pause or inspect any other thread's stack, so no locking or suspension machinery exists here at all.
