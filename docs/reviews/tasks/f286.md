# F286 — the box widening

Asked for 2026-11-12: "I want ui to support multiple look and feels." The roadmap entry written
that day found the block was not the palette -- `controls.Style` is colours and
`controls.default_style()` says in its own comment that it is "the thing an application replaces",
so a dark theme needed nothing -- but that **`widget.Stack` carried `background: Option<Color>` and
nothing else**. No border, no radius, no outline. Every container in every theme was a flat
rectangle, and what distinguishes one look and feel from another is shape. This is that entry's
first step, which it said needed no decision from anyone.

- [x] **F286** **A container's box says more than one colour.** (M; `lib/ui/widget.zm`,
  `lib/ui/controls.zm`. 11 unit tests and 5 control-level ones, 8 mutations, and the frame cost
  measured before shipping rather than after.)

  **Done: `widget.Border`, `widget.Surface`, `Stack.surface`, `Style.face_border`,
  `Style.corner_radius`.** The capability was always one layer down -- `shape.round_rect_path`,
  `circle_path` and `rect_path` have existed since F141, and `paint_focused` has stroked a path in
  this very module since F270. Only the way to ask for it was missing, which is why this was a
  struct and not an architecture.

  **A border is one value, not two fields.** `Border { colour, width }`, held as
  `Option<Border>`: either there is a border and it has both its numbers, or there is none. Two
  loose fields can express a width with no colour and a colour with no width, which are both a
  border that half exists -- and a struct able to express a state nothing can draw is a struct that
  eventually holds one. The same rule `tab_width` and `bar_thickness` follow for the number they
  share with a hit test.

  **`background` was replaced rather than joined, and that was the point.** Ziman has no field
  defaults, so every struct literal names every field -- which makes a rename a *complete
  worklist*: the type checker named all 25 `Stack` literals across four files, one at a time, and
  the job was finished when it stopped. Adding a fourth field beside `background` would have
  compiled everywhere and left the question of which sites should have been using it to memory.
  (The one thing to be careful of: `raster.options()` and `scene.Group` have their own
  `background` fields, so a search-and-replace over the name would have edited two unrelated
  modules. Only the lines the checker pointed at were touched.)

  **The default look did not move by a pixel, and that is what let this ship in one commit.**
  `default_style()` leaves `face_border` absent and `corner_radius` at zero, so `filled(colour)`
  paints exactly the one square fill `background: Some(colour)` did. All 211 existing widget and
  control tests passed untouched -- nothing re-blessed, no screenshot re-taken, and nothing an
  application already ships moved. **A look and feel is what you get by setting them**, and the
  cost below is paid only by whoever does.

  **The border is stroked inside the box, so it costs no layout.** A stroke straddles the path it
  follows, so a 4-point border along the bounds hangs two points outside and into whatever is
  beside it -- in a dense form, the neighbouring control. The path is inset by half the width,
  which is the same arithmetic and the same bargain `paint_focused`'s focus ring already makes;
  this is the second place it appears, which is why the comment now lives beside the shared rule
  rather than only in the ring. The consequence worth stating: **a border changes no box's size**,
  so the application's padding is what leaves room for it, and nothing in the layout pass had to
  change.

  The inset path's radius shrinks by the same half so the border's curve stays concentric with the
  fill's instead of bulging away at the corners.

  **`face_of` and `highlight_of`, because a selected row is not a face.** Every control with a face
  goes through one helper -- button, check box, entry, multi-line, tabs, menu title, a dialog's
  panel, a scroll bar's thumb and track -- so a look and feel set on `Style` reaches all of them
  rather than whichever ones someone remembered. A control painting its own `widget.filled(...)` is
  the one that stays flat when the theme changes, and that bug presents as one widget out of
  fifteen looking wrong. A list's and a tree's selected row take the **radius but never the
  border**: a border around each row is a box inside a box, and over twenty rows it reads as a
  table rather than a selection, where the rounded pill is what a modern look and feel actually
  draws. The two share the radius and part company over the border, which is why there are two
  functions and not a boolean parameter.

  **The scrim is never styled.** It covers the whole window, so a radius would round the corners of
  the display and a border would draw a frame around it; both look like a bug rather than a theme.
  It keeps its plain `filled`, and a test asserts that an edged style does not reach it.

  **One radius, not four corners**, which is what a design tool offers and what no application here
  has wanted. The day one does, this is where it widens, and a single number cannot disagree with
  itself in the meantime.

  ## What mutation found, and it was not a missing test

  Eight mutations. Six were caught: a border stroked along the bounds instead of inside them, the
  border painted before its own fill, `face_of` dropping the border, a selected row edged like a
  face, the scrim styled like a face, and `default_style` no longer being plain.

  **Two survived, and both were equivalent mutations that exposed redundant code of mine.** I had
  written a `surface_path` helper choosing `rect_path` for a zero radius, and a clamp stopping the
  border's `radius - half` from going negative. Removing either changed no output -- because
  `shape.round_rect_path` already ends with `if rad <= 0.0 { return rect_path(n) }`. Both guards
  were written before that was checked. They are gone, `paint_surface` calls
  `round_rect_path` directly, and the two tests that covered them now say in as many words that the
  guarantee is `shape`'s and is pinned from here because this is where it is depended on. **A
  surviving mutant is not always a missing test; sometimes it is a branch nothing can observe.**

  ## A test of mine that passed for the wrong reason

  **The control-level op counters did not recurse into a `Nested`, and a list paints as one.** A
  list clips its rows, so the whole control arrives as a single `scene.Op.Nested` group -- and
  `strokes(ops)` walking only the top level saw no fills, no strokes, and cheerfully agreed that a
  selected row had no border. `test.assert_eq(strokes(ops), 0)` passed without testing anything.

  It was caught only because the *paired* assertion in the same test -- that the row is rounded --
  failed, which sent me to dump the ops and find one `Nested` where I expected several fills. Had I
  written the test with the border assertion alone, it would have gone green and stayed there.
  **Fourth vacuous test in this run of work**, and the second whose vacuity was in the test's own
  helper rather than in its fixture.

  ## The cost, taken before shipping a look and feel rather than after

  The roadmap entry made this an obligation, because F284 had already found that a frame is
  dominated by building and laying out rather than painting. A form of 40 and 200 label-and-field
  rows with buttons at the foot, built from the shape an application lays out rather than one that
  isolates the variable, interleaved flat-then-edged, three passes (`tests/bench/look_and_feel.zm`):

  | at 40 rows | flat | edged | |
  | --- | --- | --- | --- |
  | ops in the scene | 244 | 326 | +34% |
  | building the ops | 0.55-0.75 ms | 1.9-2.0 ms | **3.0x** |
  | build + lay out + ops | 3.0-4.6 ms | 4.6-5.4 ms | +40% |
  | **rasterising it, 900x1660, 4x samples** | **21-36 ms** | **99-109 ms** | **3.3x** |

  At 200 rows the op building goes 3.1-4.05 ms to 11.6-13.1 ms, the same multiple.

  **The op-building figure would have been read as the answer and it is not.** `paint_ops` builds a
  list; it does not touch a pixel. The number that decides affordability is the last row, and it
  says a full-window repaint of an edged, rounded look costs about **105 ms against 30 ms** -- nine
  frames a second where flat gets thirty. A stroked rounded path is genuinely more expensive than a
  span fill, and the multiple holds at both sizes.

  So: **the capability is affordable to ship and a default that used it would not be**, at
  full-window repaint. Two things make that an acceptable place to stop rather than a problem.
  F270's regional repaint exists precisely so that a frame redraws what changed and not the window
  -- it got that to 0.7-1.0 ms -- and `curly gui` builds a frame only when something changed it, so
  an idle window pays nothing. And the default is unchanged, so **nobody pays this who has not
  asked for it**. The honest next number, if a second look and feel is actually written, is what an
  edged look costs *through* a damage region rather than over the whole window.

  ## Not done, and named rather than left to be found

  ## Two more looks were written against it, and here is what they found

  The roadmap entry said step two should be taken only if the widened box proved insufficient, and
  that the way to find out is to write a second look and feel and see what it cannot say. So two
  were written -- **soft** (rounded 6pt, a 1pt grey edge, lighter faces) and **outlined** (no fill
  at all, a 2pt blue edge, 3pt corners) -- and rendered beside the flat default through the real
  rasteriser.

  **Both are visibly different looks, and no control's code changed to produce them.** That is the
  widening doing its job: a theme is a `with controls.default_style() { ... }` and nothing more.
  An outlined "ghost button" theme works because `fill: None` on a face is genuinely usable and not
  merely expressible.

  **But one radius for every control is wrong, and the pictures show it.** `Style.corner_radius` is
  shared by a 90-point-wide button and a check box's mark box of about fourteen points, and at a
  radius of 6 the check box renders as a capsule -- `round_rect_path` clamps at half the shorter
  side, which for a small square is still a semicircle. A button at 6 looks right and the check box
  beside it looks broken, in the same theme, from the same number.

  This entry argued the other way above -- "a theme with four-point buttons and square selection is
  not a theme, it is two" -- and that is still true of *selection*, which is why `highlight_of`
  shares the radius. It is not true across controls of very different sizes, and the experiment is
  what settled it. **The day a second number is needed has arrived, and for a reason the entry did
  not anticipate**: not four corners, but a sense of scale.

  Two candidate answers, neither taken here: clamp the radius against the box being painted at
  something tighter than half (which makes small controls square automatically and costs a theme
  its say), or let a control scale it (which is the thin end of step two).

  **Correction, same day, after measuring instead of looking.** The paragraph above is true and it
  is not the cause, and anyone taking the design pass on the strength of it would fix the wrong
  thing. The check box's face is **9x22 points** -- taller than it is wide -- because that box is a
  `Stack` whose only child is the mark glyph, so its width is one glyph's advance and its height is
  a line height, and a glyph is always narrower than a line is tall. **A radius did not make the
  check box the wrong shape; it made the wrong shape visible.** A capsule is what rounding a 9x22
  box looks like, and it would look wrong at any radius a theme picked.

  **And it cannot be fixed by making the box square, because this layer has no alignment.** A
  square mark box needs its glyph centred in it, and `widget` has no centring: `Fixed`'s own
  comment says an alignment rule "belongs with the widget set rather than here", and the widget set
  never built one. The same gap has a second and more visible consequence that nothing had noticed
  -- **a button stretched wider than its text puts its label at the left padding**. Laid out in a
  200-point box, a "Send" button's face is 200 wide and its label sits at x=8. Every platform
  centres a button's label. It has gone unseen because `curly gui` puts `widget.expand` on the
  field beside its buttons, so they shrink-wrap and the bug never shows.

  So the design pass this entry asks for is **alignment in the box model**, which is a bigger and
  more useful thing than a second radius -- and the radius question may partly dissolve once a
  check box is square, though a radius of 6 on a 14-point square would still be nearly a circle.
  Recorded as its own entry in the roadmap. **The first thing anyone taking it should do is lay a
  button out in a box wider than its text and look at where the label went.**

  **Step two is still step two, and now has evidence rather than only a hypothesis.** A `Skin` of
  replaceable per-control builders -- `{ button: fn(Button, Style) -> Widget, ... }`, which Ziman's
  function values support -- is what a look and feel needs to differ in *structure*: a check box as
  a tick beside a label rather than a filled square, a tab as an underlined word rather than a
  raised rectangle. Neither is expressible now, and nor is a bevel, which wants a light top edge and
  a dark bottom one where `Border` has a single colour. None of those is in the way of the two looks
  that do work.

  **A rounded container still clips square.** `collect` builds a viewport's clip as
  `shape.rect_path(l.bounds)`, so a scrolling list with a corner radius rounds its fill and clips
  its rows to the square box -- content can sit in the corner the fill has rounded away. The clip
  is a `Path` and `scene.Group` already accepts any, so the fix is to pass the same
  `round_rect_path`; it is not done because no application has a rounded viewport yet, and doing it
  blind would be a second place for the radius to be computed.

  **No shadow and no gradient.** `Surface.fill` is a `Color`, where `paint.Paint` can already carry
  more, and a shadow needs either a blur the raster backend does not have or a stack of translucent
  strokes. Both are what a look and feel asks for next; neither is in the way of one existing.
