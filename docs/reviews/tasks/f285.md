# F285 — the layout rewrite, declined on measurement

Asked for directly on 2026-11-12, off the back of F284's finding that layout is **O(n x depth)**:
`place_stack` asks each fixed child how big it wants to be, `measure` on a group walks that
child's whole subtree, and the answer is thrown away and recomputed one level down. The fix is
textbook -- measure bottom-up once into a parallel tree and let the placing pass consume it.

- [x] **F285** **Measure bottom-up once instead of from every ancestor.** (L; **built, measured,
  and reverted** -- two versions, both slower on the layouts that exist)

  **Both versions were built and both produced byte-identical layouts.** The gate was a dump of
  every node of a rich tree -- nested stacks both ways, padding, spacing, unequal flex weights, a
  fixed box, a control, a viewport with an offset, placed and unplaced layers, an empty stack --
  at three window sizes, 564 nodes. Neither version moved a node by a thousandth of a point, and
  `make test` and `make lib-tests` stayed green throughout. The rewrite was correct. It was just
  not worth having.

  ## What was measured

  Five interleaved samples, 100 layouts of a 200-row tree in a 280x640 sidebar -- the shape
  `curly gui` actually lays out:

  | | median |
  | --- | --- |
  | as it is | **531 ms** |
  | each child measured once per stack | 585 ms (1.10x slower) |
  | full two-pass `Measured` tree | 757 ms (1.43x slower) |

  And on the shape that motivated the task, 200 leaves under nested bare columns:

  | depth | as it is | measured once | two-pass |
  | --- | --- | --- | --- |
  | 1 | 1.8 ms | 1.5 ms | 1.9 ms |
  | 16 | 6.5 ms | 3.6 ms | 1.6 ms |
  | 64 | 23.8 ms | 13.1 ms | 2.0 ms |

  **12x at depth 64, and a regression at every depth anyone writes.**

  ## Why, and this is the part worth keeping

  **`Sized` already is the barrier the rewrite was going to add.** `measure` answers a `Sized`
  node's declared size without looking inside it, so the quadratic is bounded not by the depth of
  the tree but by the distance to the nearest enclosing `Sized` or viewport -- and real layouts are
  full of both. Every fixed-height list row, every fixed-width column, every band across a window
  is a `fixed_of`. In `curly gui` that distance is one or two levels, so there was nearly nothing
  to recover, while the parallel tree cost an allocation per node and the per-stack cache cost one
  array per stack.

  **The probe that justified the task measured a shape nobody writes.** 200 leaves wrapped in 64
  bare `column_of`s has no `Sized` anywhere, which is exactly the case the short circuit does not
  cover. The number was right and the conclusion drawn from it was wrong, which is the third time
  in one day a measurement has reversed a reading taken from a different span.

  ## What is left, if layout has to be faster

  The profile of a pass, after F284's string removal: `place_stack` 16.7%, garbage collection
  15.5%, `place` 14.4%, `measure` 13.4%, `flex_weight` 8.4%, `name_of` 7.8%, `size_of` 7.4%,
  `rect_of` 3.9%. There is no hot spot left -- it is the box model's own walk, spread evenly, which
  is F270's conclusion reached again: **the remaining cost is the interpreter's per-operation
  overhead, and the one thing that removes it is a port to C.** `place` and `measure` are small,
  pure, and have an exact oracle in the dump above, so that port is a well-shaped task whenever
  the need is real. It is not today: the idle fix took the frame cost that mattered to zero, and
  what is left is paid only on frames that genuinely changed.
