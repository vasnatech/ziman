# F269 to F277 — desktop applications (route B)

The seven phases of a GUI toolkit that draws its own widgets, plus the two build decisions they
force. Designed first, in [../../design/desktop-applications.md](../../design/desktop-applications.md),
and **route B was the user's choice on 2026-11-10** against that document's own recommendation of
route A — recorded here because the reasoning matters to whoever picks these up: route A's hard
problems (text input, accessibility, platform conventions) come free with a native toolkit, and on
route B every one of them is ours. F273, F274 and F275 are those problems.

**The order is correctness before speed, and it is deliberate.** `tests/bench/ui_frame.zm` measures
~1.2 µs per pixel for `raster.render`, so a pure-Ziman repaint of a 1280x800 window costs about
1.3 seconds before a single shape is drawn — the design document's §3. The obvious response is to
write the C renderer first. The order here does the opposite: F269 presents a framebuffer that
Ziman produced *however it likes*, so the whole pipeline is correct and demonstrable at a slow
frame rate, and F270 then replaces the slow part with `raster.zm` standing as its pixel-exact
oracle. A renderer written first would have nothing to be tested against.

Effort: **S** = a day or less, **M** = a few days, **L** = a week or more, **XL** = longer than
that, which three of these are and which is worth saying out loud.

- [x] **F269** **A window, a framebuffer and an event queue: the platform floor.** (M; and the two defects its last clause found)

  The four things `lib/graphics` cannot do: open a window the OS will show, hand it a block of
  RGBA pixels, read what the user did, and put everything back when the program ends. A `window`
  module over `src/native_window.c`, with the backend behind `ZIMAN_X11` so **the default build
  gains no dependency** — see F276.

  `present` takes an `[byte]` of `width * height * 4` and nothing else, so it does not care whether
  those bytes came from `raster.render`, from F270's renderer, or from a test. That is the seam the
  whole route hangs on and it is one function wide.

  `with_window` is a scope rather than an `open`/`close` pair, for the reason `with_raw` is one: an
  early return should not leak what it opened. **It is not guarding against a crash, and that is
  where this differs from `terminal`** — a terminal's settings outlive the process, so `terminal`
  restores them from a signal handler; a window does not, because the display server drops it when
  the connection goes. So there is no signal machinery here and none is missing. (This entry claimed
  the opposite when it was written, by analogy rather than from the API.)

  Done when: a Ziman program opens a window, presents a known pattern, reports key, pointer, scroll,
  resize and close events, and `xprop` confirms the window mapped. Gated by screenshotting the real
  window with `import -window` and comparing pixels against the pattern — a stronger gate than it
  sounds, and the reason the pattern is known rather than pretty.

  **As built.** `lib/core/window.zm`, `src/native_window.c`, `make gui` → `ziman-gui`, 15 unit tests
  over the pure event protocol (`tests/stdlib/window_test.zm`, which needs no display), and
  `tests/run_window_test.sh`, which opens a real window, confirms it with `xprop`, screenshots it
  and compares the four quadrant centres — verified discriminating by breaking the channel packing,
  which turns red into black, green into red, blue into green and white into yellow. 22 checks,
  1.4 s.

  **The last clause took a second pass, and it is the reason the first pass was not ticked.** This
  entry said a real key press had never arrived as an `Event`, because the machine has no
  `xdotool`. It turned out not to need one: `xdotool` is a wrapper over X's own input synthesis,
  whose header and library were already installed, so `tests/tools/x11_inject.c` is that wrapper cut
  down to six commands — key with a modifier, click, scroll, motion, resize, close — compiled on
  demand by the test script so that libX11 stays a dependency of `make gui` alone. The program now
  prints a line per event and the script asserts eleven of them, including that a control-modified
  key composes no text, that the wheel arrives as a signed `Scroll` and not as buttons 4 and 5, and
  that `with_window` returned on its own.

  **Not XTEST, deliberately, and this is the one real limitation.** XTEST asks the server to behave
  as though the hardware fired, which is the whole real path — but it cannot be aimed at a window,
  and on a Wayland session the focus it follows belongs to the compositor, which no X client can
  claim: the first attempt sent its keys to the terminal and the window under test saw nothing. So
  the injector uses `XSendEvent`, which posts onto one named window's queue and is what
  `xdotool key --window` does. That proves the client's half — keycode through the server's keymap
  to a keysym and to text, modifier mask to flags, button and coordinates — and not the server's
  half, focus and delivery, which is Xlib's code rather than ours. Written down rather than glossed,
  because the gate is worth exactly what it checks.

  **Two defects, and neither was reachable from Ziman.**

  * **Every window close aborted the process.** `XCreateImage` takes ownership of the pixel buffer
    and `XDestroyImage` frees it with libc's `free` — while in this build `malloc` *is* `GC_MALLOC`,
    because `src/zgc.h` is force-included and `$(GC_FLAGS)` is in the default `CFLAGS`. So the
    buffer came from the collector and went to libc's free: `free(): invalid size`, on every close,
    on every machine. The file's own header already stated the rule and the code had been read
    several times; what found it was letting the program exit on its own and reading its status,
    which nothing had done before, because nothing could close the window. Fixed with the
    `push_macro` idiom `src/iter.c` and `src/native_http.c` already use, and
    `tools/check_libc_free.py` now checks this direction too — it had covered only the mirror case,
    libc memory released through the collector build's no-op free, which leaks where this corrupts.
  * **The composed character arrived before the keystroke that produced it.** `poll_raw` appended
    the `Char` where it computed it, inside the `KeyPress` case, and the `KeyDown` at the bottom of
    the loop. A program that decides from the `KeyDown` whether to consume the character could not
    have worked. No test over `decode_events` could have seen it: the order is the native's and the
    decoder only maps what it is handed. The two appends are now one `push_event`, which is also
    where the duplicated growth arithmetic went.

    **The contract was not missing — it was written down and unenforceable.**
    `tests/stdlib/window_test.zm:118` says "the native emits the key first and the text second",
    and its fixture is in that order, which is why it passed throughout: a decoder test builds the
    array it decodes, so it asserts the order of its own fixture and never the order the native
    produces. A gap between prose and behaviour, with a passing test sitting on top of it.

  **And a third, in the gate itself.** Flipping the scroll sign in the native left
  `window_event_scroll_down` passing: both scrolls were sent to the same point and each check greps
  the whole log, so the line the *up* injection produced satisfied the check for down. They now go
  to different points. That is the second time on this task list that deliberately breaking the code
  found a fixture that was not discriminating — and the only way such a check ever shows itself.

- [ ] **F270** **The renderer in C, with `raster.zm` as its oracle.** (XL)

  A `Scene` to pixels in C, because §3 says 60 fps at 1280x800 needs 16 ns per pixel and the
  interpreter gives 1,220. This is the same division JavaFX makes with Prism and Flutter makes with
  Impeller: the managed language describes the scene, native code rasterises it.

  **The gate is what makes this tractable**, and it already exists: render the same `Scene` through
  C and through `raster.zm` and compare pixels. `raster.zm` is a correct, slow, 700-line reference
  implementation with anti-aliasing under both winding rules, stroking with caps and joins and
  dashes, clip paths, gradients and glyph caching — so every feature of the C renderer has an
  answer to be checked against, per-pixel, with no screenshots and no human judgement. That is a
  far better position than most renderers start from.

  XL and not L: this is `lib/graphics`'s phase 5 again, in C, and that phase was not small.

  Target: a frame of F269's shape under 5 ms at 1280x800, against ~1950 ms today.

  **Progress (2026-11-10): the floor is done, the drawing is not.** The two loops with no geometry
  in them -- `clear_to` and `finish`, four floats per pixel each way -- are now
  `src/native_raster.c`, reached through two private `native fn`s in `raster.zm`. They were chosen
  first because an *empty* 1280x800 scene was two thirds of a frame, so a renderer that started with
  the shapes would have left that untouched.

  | 1280x800 | all Ziman | now |
  | --- | --- | --- |
  | empty scene | ~1290 ms | 28 ms |
  | fills only | ~1640 ms | 397 ms |
  | full frame | ~1950 ms | 625 ms |

  The oracle argument held without a new test: `tests/lang/graphics_raster.zm` asserts pixels across
  anti-aliasing, both winding rules, strokes, gradients, alpha and all three output formats, and is
  byte-identical across the change. It needed `ziman_mutable_array_float_data` exported from
  `src/prelude.c` so a native can work on a canvas in place rather than copying 32 MB a frame.

  **Progress (2026-11-10, instalments two and three).** Second: `fill_shape`'s inner loop and
  `blit`'s -- the same shape, once per pixel of a shape's bounding box or a glyph's tile -- for the
  **solid** case. Third: the coverage pass both of those feed, being the row-window clear and
  `add_span`, whose middle run is per pixel per sub-scanline.

  A gradient, a tiled paint or an image still evaluates per pixel through `ready_at` in Ziman,
  because moving it would mean moving the paint model with it; the fast path sits beside the general
  one rather than replacing it. **So a gradient-heavy scene has seen none of this.**

  | 1280x800 | all Ziman | now | ratio |
  | --- | --- | --- | --- |
  | empty scene | 2548 ms | 36 ms | 70.7x |
  | fills only | 3295 ms | 72 ms | 45.7x |
  | full frame | 3859 ms | 232 ms | 16.6x |

  **Measured by alternating two binaries in the same minute, three rounds each**, which is the
  technique `fill_shape`'s own comments use -- and it had to be, because this machine's absolute
  figures moved about 2x between two batches an hour apart with no code change: the same frame read
  ~1950 ms and later 3849 ms. The earlier progress notes above quote absolutes that were each
  internally consistent and are **not** comparable with these; the ratios are.

  **Oracles: both paths are gated now.** `tests/lang/graphics_raster.zm` (418 lines, anti-aliased
  edges, both winding rules, strokes, gradients, alpha, all three output formats) and
  `graphics_stroke.zm` are byte-identical across every instalment.

  Text had no committed-pixel fixture while the four instalments were written, because the
  repository vendored no TrueType face and a fixture cannot rely on a system one -- so each
  text-touching change was verified by A/B instead: twelve runs at varying sizes and quarter-pixel
  offsets plus one clipped off the left edge, identical SHA-256 of the encoded PNG. That caught the
  author's mistakes and nothing else. **`vendor/fonts/Caladea-Regular.ttf` (59 KB, Apache 2.0,
  checked from the font's own `name` table rather than the distribution's packaging) and
  `tests/lang/graphics_text.zm` close that**, asserting glyph ids, advances, coverage totals,
  per-column coverage, anti-aliasing levels, the clipped-run case, the sub-pixel shift, Gray8 output
  and the refusal naming a character the face cannot draw.

  Two things came out of writing it. The face's `cmap` is **format 4**, where the one this work was
  developed against is format 12 -- so `truetype.lookup4`, the half of the character-map code most
  real fonts use, had no coverage at all until now. And the first draft **did not discriminate**:
  `ink_sum` is translation-invariant, so a run shifted one pixel sideways has an identical total,
  which is exactly the positioning bug `draw_text`'s quarter-pixel quantisation exists to prevent.
  Per-column bands fixed that, and the fixture then caught all three breaks tried against it -- a
  one-pixel shift, `floor` where `round` belongs, and a dropped advance. A fourth, removing the
  blit's left-edge clamp, is **not** caught, and that is right rather than a gap: the native
  bounds-checks the same condition, so either defence alone gives identical output.

  **Progress (2026-11-10, fourth instalment): the text cost was `truetype`, and no C was needed.**

  The note here previously named the per-glyph string cache key as the largest remaining item. **It
  was wrong, and measurably so**: replacing that key with a packed integer was A/B'd twice,
  interleaved, and made no difference either time (236/231/232 ms against 231/232/233), so the
  change was reverted rather than kept for tidiness. Decoding UTF-8 straight from the bytes instead
  of through `chars`, which removes two allocations per character, moved 170 ms to 164 -- also
  nearly nothing.

  The cost was underneath, in `truetype`'s byte accessors. `u32_at` was four calls to `u8_at`, each
  returning its own `Result`, so a four-byte read allocated five -- and `lookup12`, the binary
  search over a full-Unicode `cmap`, does about twenty such reads per character. Roughly a hundred
  allocations to map one character to a glyph. One bounds check and direct indexing instead:

  | 4290 characters | before | after |
  | --- | --- | --- |
  | `font.glyphs_of` | 281 ms | 74 ms |
  | `truetype.advance_of` | 7 ms | 4 ms |
  | `truetype.glyph_outline` (39 distinct) | 8 ms | 8 ms |

  Two smaller fixes came with it: the `cmap` subtable is chosen in `parse` and stored on the `Face`
  rather than re-chosen per character (`best_subtable` walked every record in the table each time),
  and `font.glyphs_of` decodes UTF-8 from the bytes directly.

  **This one touched everything in `truetype`** -- outlines, metrics, the PDF embedding -- so it was
  checked against every graphics fixture and example rather than the usual two: `graphics_raster`,
  `graphics_stroke`, `graphics_pdf`, `graphics_geometry`, `graphics_image` and the `truetype`,
  `font`, `pdf`, `raster` and `image` examples are all byte-identical, and the text A/B digest is
  unchanged.

  **The lesson worth keeping is about the method, not the code.** "Move the per-pixel loop to C" was
  the right answer four times and the wrong answer the fifth, where it was "stop allocating" -- and
  both wrong guesses before it were things this file had already written down as the next step.
  Nothing here should be moved to C before a probe says where the time is.

  **Progress (2026-11-10, seventh): the probe was run, and it found a correctness bug instead.**

  The lesson above says nothing should move to C before a probe says where the time is, so `--profile`
  was run over `ui_frame.zm` before touching anything. **It contradicted this entry for the fourth
  time.** Against a 156 ms frame on this machine state:

  | bucket | self | ≈ms |
  | --- | --- | --- |
  | `mutable_array_filled` + collection | 26% | 41 |
  | the edge walk (`crossings_at`, `spans_from`, `row_coverage_at`, `advance_active`, `edges_of`) | 20% | 31 |
  | the cmap (`u32_at`, `lookup12`, `u16_at`, `u8_at`, `glyph_for`) | 13% | 20 |
  | `to_bytes_premul` (already native) | 9% | 14 |

  Item 1 below claimed the cmap was "still the largest part". It is **third**. The largest is the
  canvas: `new_target` asks for `width * height * 4` floats per render — 4,096,000 at 1280x800,
  measured at **16.5 ms a frame to allocate and zero**, with the collector printing
  `Repeated allocation of very large block (appr. size 32004 KiB)` of its own accord. The same call
  throws away the glyph cache, whose comment says so deliberately: *"a cache that outlived the call
  would need invalidating when a face changed and bounding so a long-lived process could not grow
  one forever. A page is where the reuse is anyway."* That reasoning was written when the target was
  a page. F269 and F277 make the target a window repainting at interactive rates, so the premise is
  gone and the decision is worth retaking — which is a different thing from the comment being wrong.

  **And looking at that comment found the bug it half-predicted.** "Would need invalidating when a
  face changed" understates it: the glyph cache key was the transform, the glyph id and the subpixel
  offset, with **nothing naming the face**, so the problem was not stale entries across renders but
  wrong glyphs *within* one. Two faces at the same size under the same transform shared entries, and
  a glyph id present in both was served from whichever drew first.

  Not a corner case: it is regular and bold of one family in one scene, which share a character set
  and so share glyph ids. Probed against two system faces first (`AdwaitaSans` Regular and Italic,
  both 2048 units, `a` glyph 507 in both: ink 301.1 where 311.8 was correct), then against the pair
  now vendored — `Caladea-Regular` and `Caladea-Bold` are **both 1000 units per em with 420 glyphs**
  and `a` is glyph 68 in each, so every component of the old key matched exactly. Ink 212.3 where
  316.7 was correct: the bold `a` drawn as the regular one.

  Fixed by keying on `truetype.face_id`, a new public function answering the `head` table's
  `checkSumAdjustment` — a content fingerprint the font's own builder computed and stored, four
  bytes to read, where hashing the face per run would cost 59 KB of work per text run. The units per
  em and glyph count go in beside it so a face whose checksum is absent still separates from most
  others rather than from none.

  **The oracle could not have caught this, and that is the fifth fixture gap this task has found.**
  Every text fixture used one face, so no key that ignores the face could fail. `Caladea-Bold.ttf`
  is vendored (58,892 bytes, Apache 2.0 read from its own `name` table, as the Regular's was) and
  `graphics_text.zm` now draws the shared glyph id in both faces in one scene. It asserts three
  things, because each alone would pass for the wrong reason: that the two faces are
  indistinguishable by their metrics, that their ink differs when drawn *alone*, and that the bold
  drawn after the regular in one scene matches the bold drawn alone at the same place — compared by
  column band, since `ink_sum` is translation-invariant. Reverting the key change makes it read
  71.4392 against 107.3961 and fail.

  Every other graphics fixture — `graphics_raster`, `graphics_stroke`, `graphics_pdf`,
  `graphics_geometry`, `graphics_image` — is byte-identical, which is what a key gaining a component
  should do to a single-face scene.

  **What is left:**

  1. ~~**The canvas, which the probe says is the biggest item.**~~ **Done (eighth instalment):
     `raster.Surface` and `render_into`.** A caller keeps a surface and its glyph cache across
     frames; `render` is unchanged and still allocates per call, because a one-off render of a page
     should not have to manage one. Interleaved against `render`, three passes of ten 1280x800
     frames: **1.82x, 1.72x, 1.86x**, with 35 glyphs surviving all ten frames.
     `tests/bench/repaint.zm` is the benchmark, written because `ui_frame.zm` renders each scene
     once and so cannot see any of this.

     **Called a surface, not a canvas, because `image.Canvas` already exists** one module away and
     is a different thing — a buffer of bytes a caller sets pixels on. Two `Canvas` types in one
     library layer, one of which ignores `image.set`, is a confusion worth not creating.

     The two conditions `Target`'s comment set for a cache outliving a call are met: the key carries
     `truetype.face_id` now, so a changed face cannot be served a stale entry, and the cache is
     bounded. The bound is checked at the **start** of a frame rather than on insertion, so a frame
     needing more than the limit still finishes with a working cache and the next begins empty —
     evicting mid-frame would thrash and be worse than no cache. Dropped wholesale rather than
     least-recently-used, because an LRU needs an order maintained per hit and the next frame
     refills what it draws.

     **Two of my own fixtures did not discriminate, and breaking the code is what showed it.**
     Asserting that a first frame on a surface matches `render` passes even with the clear removed,
     because a fresh surface starts zeroed — it takes a *second* frame on the same surface to see a
     missing clear, and a third after a heavier scene to see that the clear is not merely idempotent
     for one frame. And the cache bound, first written as "draw the same text twice and the count is
     unchanged", is true whether or not the bound does anything: the second frame either refills
     exactly what it dropped or finds it all there. Only a frame of *different* glyphs separates the
     two, so it is now asserted against a default surface given the same two frames — bounded ends
     holding the second text alone, unbounded holds both. Both versions fail with the respective
     code removed; neither did before.

     The glyph limit is a **field** on the surface and not only a constant, so a fixture can set it
     to 2 and reach the bound in two renders instead of needing 8192 distinct glyphs. An untested
     bound in a long-lived process is the thing the comment was worried about.

     Still to do on this item: **a per-face memo of code points on the surface**, which is where
     item 2 below now belongs — the surface is the natural home for it, and it was not added here
     because the canvas was measured and the memo was not.
  2. **The cmap lookup.** ~17 microseconds a character against ~65 before, and 13% of a frame rather
     than the largest part of it. `lookup12`'s search is now about twenty direct reads and one
     `Result` each; a native, or a per-face memo of recently seen code points on the surface above,
     would take it further. **Measure the memo before building it** — this entry has now been wrong
     four times about which item is largest.
  3. **The paints: done (fifth and sixth instalments).** A full-canvas solid fill of
     1280x800 measured 47 ms and the same fill with a linear gradient 2625 ms -- 56x, for a scene
     that looks no more complicated, because a gradient is an inverse transform, a stop search and a
     lerp per covered pixel. `composite_row_gradient` now does a scanline of either gradient in C,
     with the paint crossing as **one flat `[float]`** (kind, inverse matrix, geometry,
     premultiplied stops) rather than a dozen parameters -- which is the shape the tiled and
     placed-image inks can reuse without changing the signature.

     | 1280x800, full canvas | per-pixel | native | ratio |
     | --- | --- | --- | --- |
     | linear | 2524 ms | 67 ms | 37.6x |
     | radial | 2481 ms | 52 ms | 47.7x |

     `tests/bench/gradient_fill.zm` is the benchmark, written because `ui_frame.zm` is all solid
     fills and could not see this at all. The solid path pays about **1%** of a ui_frame frame for
     the once-per-fill call that decides which path to take, and nothing measurable on fills alone.

     **The image inks followed (sixth instalment)** on the same spec, extended with two more
     `kind` values — the pixels as a separate `[byte]` argument, since an image's bytes cannot live
     in a `[float]`, which is the only reason it is a second native rather than two more kinds on
     the first.

     | 1280x800, full canvas | per-pixel | native | ratio |
     | --- | --- | --- | --- |
     | tiled pattern | 2871 ms | 55 ms | 52.2x |
     | placed image | 2632 ms | 54 ms | 48.7x |
     | solid, for comparison | 51 ms | 47 ms | 1.0x |

     Sampling stays nearest-neighbour. `raster.zm` calls that "honest and obviously improvable,
     where a half-finished bilinear would be neither", and improving it in C alone would make the
     two implementations disagree.

     **Every ink is now native, so the paints are done.** `tests/bench/paint_fill.zm` (renamed from
     `gradient_fill.zm`) measures all four against solid.

     Gated, and two more gaps found while proving it. `graphics_raster.zm` asserts a placed image by
     four pixel triples and a pattern by four quadrants under a scaling matrix, and it caught the
     pattern's own inverse matrix being dropped. It did **not** catch the image's width and height
     being swapped, nor the destination rect's origin being dropped — because every image in it is
     square and every destination sits at (0, 0). A 4x1 strip placed into `rect(4, 2, 8, 4)` was
     added, which catches both. That is the second fixture gap this task has found by deliberately
     breaking the new code, and in both cases the gap predated the change.

     Gated, and checked for it: `graphics_raster.zm` already covered linear, radial and single-stop
     gradients, and the fixture caught a swapped gradient axis and dropped stop offsets. It did
     **not** catch a zeroed inverse-matrix translation, because every gradient in it sat under an
     identity transform -- the one thing the new code computes per pixel had no coverage. A case was
     added for a ramp inside a translated and scaled group, which catches it.
  4. **Curve flattening and stroking.** `stroker.zm` is the largest piece and the least per-pixel,
     so it may be worth leaving in Ziman longest.
  5. **`crossings_at` and `spans_from`.** **Now measured at 20% of a frame, the second largest
     item.** The edge walk and the winding rules. Smaller than they were, and the most intricate.

- [x] **F271** **The widget tree: retained, pure, and testable without a window.** (L; the box model)

  A tree of widgets with layout and a `Scene` as output — `fn render(tree, bounds) -> Scene` — so
  the whole model is pure functions over immutable values and unit-testable with no display at all.
  curly's TUI is the precedent worth copying: `tui/rows.zm` and `tui/render.zm` are pure and only
  `tui/app.zm` touches the terminal.

  **Retained, not immediate**, and the reason is F275 rather than taste. The immediate-mode
  libraries have the nicer API and suit a language of immutable values well, but an accessibility
  tree cannot be destroyed and rebuilt every frame: assistive technology has to be told *what
  changed*, which a tree that persists can say and a call sequence cannot. The documented
  workaround for immediate-mode toolkits is a retained tree underneath, which is this.

  `layout.zm` already does paragraphs, columns, rows and tables; this is the box model and the
  widget identity on top, not a text engine from scratch.

  **Built as `lib/ui/widget.zm`** -- a new directory, because F272 to F277 add focus, text editing
  and accessibility beside it and none of those are graphics. `Widget` is `Nothing`, `Text`,
  `Group` (a row or column with spacing, padding and an optional background), `Sized`, `Flex` and
  `Expand`; `measure` answers a natural size, `layout` places a tree inside a rect as a `Laid` tree
  carrying bounds, a path and a name, and `paint` answers a `Scene`.

  **Measurement is injected.** `layout` takes two functions rather than a font, so nothing here can
  fail and nothing needs a face: `metrics_for` builds the real pair from a `FontRef` and fails
  *once*, at that call, because `font.advance` answers a `Result` and a `Metrics` that could fail
  would make every box in a window a fallible computation. 24 unit tests run against a fake whose
  numbers make the arithmetic visible.

  **`Expand` was not in the first draft, and a failing test found it.** A `Flex` has no children and
  a `Group` always takes its natural size, so flexibility could not cross a container -- the
  commonest layout there is, a bar of its own height above a content area filling the rest, had no
  spelling, and a column holding only a spacer measured zero and collapsed. `Expand` is the one
  place a subtree is told to be bigger than it measures.

  Two semantics worth knowing, both now written where they are decided. An over-full container
  **overflows rather than shrinking its children**, because silently shrinking hides the mistake and
  clipping is a scroll container's decision. And a stack **stretches its children across** its own
  direction, so a `Sized(40, 80)` in a row 60 tall is laid out 40 by 60 -- choosing otherwise means
  an alignment rule, which belongs with the widget set.

  `tests/lang/ui_widget.zm` is the integration gate on top of the unit tests: a toolbar, a fixed
  sidebar and an expanding content area, each with its own background, laid out and **rasterised**,
  with a pixel sampled in each region. That is the pair of failures the unit tests cannot see -- a
  paint order that hides a widget behind its own background, and a layout that agrees with itself
  and disagrees with the pixels.

- [x] **F272** **Hit-testing, focus and keyboard navigation.** (M; `lib/ui/focus.zm`)

  Which widget is under the pointer, which has focus, and what Tab does. Small in code and the
  thing that decides whether the toolkit feels broken: focus order that does not follow the visual
  order, or a click that lands on the wrong widget by a pixel, are both immediately obvious to a
  user and invisible to a test that only compares scenes.

  **Built as `lib/ui/focus.zm`, with `widget.Focusable` in the tree beside it.** A control is a
  wrapper, not a widget kind -- when F277 adds buttons, a button *is* a `Focusable` around a group
  with a label, so focus, hit testing and F275's accessibility all agree on what a control is from
  one declaration. 16 unit tests, all over names and positions, none over pixels.

  Four decisions, each written where it is made:

  - **Focus is held by name, never by path or by node.** A path changes when a sibling is inserted
    above it and a node is rebuilt every layout, so either would move focus when an unrelated part
    of the window changed -- which a user sees as the cursor jumping for no reason.
  - **Tab order is tree order.** Sorting by position reads as the obvious answer and is worse: it is
    ambiguous for anything not on a grid, it changes when a resize reflows a row, and a programmer
    cannot see the order by reading the code that builds the window. For an ordinary nesting the
    two agree.
  - **Bounds are half-open**, so a point on the boundary between two controls belongs to exactly
    one. A click on the line between two list rows has to select one of them, and which one must
    not depend on search order.
  - **A click on nothing leaves the focus alone**, and **a focus the tree no longer holds restarts
    from the first control** rather than answering nothing -- a control can disappear between
    layouts, and the keyboard has to keep working.

  **A name is inherited by descendants that have none**, which is what makes a click on a button's
  *label* report the button: a pointer lands on the innermost node, and without inheritance only
  the outermost would carry the name. The first version passed it down one level only, so a
  two-level nesting answered "" -- found by a hit test, not by reading the code.

- [x] **F273** **Text editing: a caret that moves by grapheme, selection, and the clipboard.** (L; `lib/ui/edit.zm`, except the system clipboard)

  Caret movement over grapheme clusters rather than code points or bytes, double-click word
  selection by locale rules, drag selection, undo, and the system clipboard with more than one
  flavour. **Route A would have given all of this.** It is listed as its own phase because a text
  field that gets any of it subtly wrong is worse than no text field.

  **Built as `lib/ui/edit.zm`: the editing model, 32 unit tests, and two honest shortfalls.**
  `Editor` is a string and two code-point indices -- caret and anchor, equal when nothing is
  selected, so there is no separate flag to keep in step. Insert, backspace, forward delete, word
  delete, move by character, word and line, select all, double-click word selection, and undo.

  **Grapheme clustering is a deliberate subset of UAX #29, not an implementation of it**, because
  the language has no character property tables and a half-table claiming conformance would be
  worse than a rule that says what it is. Four rules, covering what a user actually types: a CRLF is
  one cluster, a combining mark joins the character before it, a zero-width joiner binds both sides,
  and two regional indicators are one flag. What it gets wrong is written down -- a rare mark
  outside the main blocks, Hangul sequences, Indic conjuncts. All five grapheme tests were checked
  against the naive one-code-point implementation and all five fail there, so the clustering is
  doing the work rather than decorating it.

  **Word segmentation is not locale-aware, and the entry above asked for it.** The rule is the one
  every editor's double-click uses -- runs of letters-and-digits, whitespace, or anything else --
  and three kinds rather than two, because with two `foo.bar` is one word and a double click takes
  all of it. Real segmentation is UAX #29 again: a Thai string has word boundaries with no spaces
  in it, and knowing that needs the same tables. Named rather than implied.

  **The system clipboard is not here**, and that is platform work rather than a missing function:
  owning a selection on X11 means answering `SelectionRequest` with a list of targets and an INCR
  protocol for large transfers, which belongs beside `src/native_window.c`. `copy` and `cut` answer
  the text and a caller holds it; `paste` takes it back. That seam is where a platform layer plugs
  in.

  Undo keeps **states, not inverse operations**: a field's whole state is a string and two integers,
  and a stack of those cannot disagree with the document, which is the bug every operation-based
  undo eventually has. Bounded, oldest dropped, and recording clears the redo side.

- [ ] **F274** **Input methods: pre-edit, candidates, and commit.** (XL)

  Composing Japanese, Korean or Chinese text means a pre-edit buffer the application must display
  with the right styling, a candidate window positioned at the caret, and commit events that
  replace the pre-edit; dead keys and compose sequences do the same for Latin scripts with
  diacritics. On X11 that is XIM or an ibus connection.

  **This is the phase where a second backend earns its place.** SDL3 provides window, input,
  clipboard, cursors, DPI and input-method handling across Linux, macOS and Windows, and reports
  improved IME handling over SDL2; F269's backend seam is where it would plug in. Taking it means a
  dependency the X11 backend does not need, which is why it is a phase and not an assumption.

- [ ] **F275** **Accessibility, in the first widget rather than the fiftieth.** (L; the tree is built, the platform binding is a decision)

  A UI that draws its own widgets is a blank rectangle to a screen reader unless it says otherwise,
  and retrofitting is harder than building in, because the accessibility tree has to mirror a widget
  tree that was not designed to be mirrored.

  **AccessKit is the reason route B is possible at all here**: it abstracts UI Automation on Windows
  and the AT-SPI D-Bus interfaces on Unix for toolkits that render their own widgets, is used by
  egui, and ships a C API covering both its data structures and its platform adapters — C being the
  only extension surface this interpreter has.

  Scheduled after F271 because it needs a tree to mirror, and before F277 because the widget set is
  what would make it expensive to retrofit.

  **Split, because only one half of it is a dependency decision.** The expensive-to-retrofit part is
  not the platform binding — it is the vocabulary: a role and a state per widget, declared where the
  widget is built. Fifty widgets without it is the retrofit this ordering exists to avoid, and it
  needs nothing installed. So that half is built and this entry stays open for the other.

  **Built (2026-11-10).** `widget.Role`, `widget.Toggle` and `widget.State` on
  `widget.Focusable`, and `lib/ui/a11y.zm` projecting a laid-out tree into a flat `Tree` of `Node`s.
  25 unit tests, a worked example that prints what a reader would say, and `widget.control_of` /
  `widget.labelled_control` beside the `focusable_of` the focus tests use.

  * **The vocabulary lives on the widget, not in `a11y`**, which is the whole of what the title
    means. `a11y` is a projection and owns nothing: it copies what was declared, computes what only
    a laid-out tree and a focus can know, and guesses at nothing — a control whose role nothing
    declared comes out `Unknown` and is announced as "control", rather than as a button it might not
    be.
  * **The flattening is the algorithm, and it is subtractive.** A node is emitted for a control, for
    text outside any control, and for the root; a row, column, spacer or fixed box emits nothing and
    its children attach to the nearest ancestor that did. Six layout boxes around one button give a
    tree of two nodes. Without this a user arrows through eleven anonymous groups to reach a button.
  * **`name` and `label` are different fields on purpose.** `name` is the identifier focus is held
    by; `label` is what a person hears. One string for both is why a home-grown toolkit announces
    "btn_save_2", and it is the most common defect of the kind. `label` is empty in the common case
    and the name comes from the text inside, so a button wrapping a label called "Save" announces
    "Save" with nothing declared.
  * **Text inside a control is that control's name and so is not a node.** This needed a *second*
    collector, which the first draft of the module did not have — and its own test caught it: the
    tree came out `@ save @0/0` where `@ save` was asserted, which is a reader saying "button, Save"
    and then "Save". Every toolkit that builds its accessibility tree by copying its widget tree
    makes exactly that mistake, and this one did too, for about ten minutes.
  * **Keyed by string, not by integer id.** An adapter sends updates, so identity has to survive a
    relayout; an integer that changes when a sibling is inserted makes a reader lose the user's
    place every frame. A control's `name` already has that property and is already required for it.
    AT-SPI addresses objects by string path anyway, and interning to AccessKit's or UI Automation's
    integers is a few lines in the adapter beside the id table it already keeps. Integers here would
    have meant hashing names and pretending the collisions away.
  * **`checked` and `expanded` are `Option`.** A control that cannot be checked is not a checkbox
    that is off: a reader says "unchecked" for the second and nothing for the first, and a `bool`
    would make every button in the window announce itself as unchecked.
  * **Declared state and derived state are different fields of different types.** `focused` is not
    in `State` and cannot be: focus is held by name outside the tree precisely so that rebuilding
    the tree cannot move it, so a `focused` on a widget would be a second copy of that fact, free to
    disagree. `a11y.Node` computes it from the focus passed in. Same for `focusable`, which is
    being a control and not being disabled.
  * A disabled control **is** in the tree — a user needs to know the button is there and dimmed —
    but `reachable` excludes it, and a focus left on one reports `None`, as a focus on a removed
    control does.
  * `announce` renders one node as one line, which is **for tests and a terminal reader, not for an
    adapter**: a real reader's voice, language and verbosity settings pick the words. It is there
    because a test asserting `"check box, Notify me, checked"` says what a user would hear, where a
    test asserting six fields says only that six fields were copied.

  **What is left is the platform binding, and it is a dependency decision.** Measured on this
  machine rather than assumed: `atspi-2`, `atk` and `dbus-1` are **already installed**, so a Unix
  binding over AT-SPI needs nothing new and is C, which is this interpreter's only extension
  surface — but it is Unix-only. AccessKit covers Unix, Windows and macOS from one API and is a Rust
  crate whose C API is built with `cargo-c`, which is a build-time Rust toolchain and a vendored
  crate, against this repository's rule that building needs no network and no other tools
  (`vendor/bdwgc` is vendored C for exactly that reason). Either way the seam is `a11y.Tree`, which
  is why the tree was worth building first: it is the same value whichever adapter consumes it.

  **And two findings beside the work.** `tools/check_site.py` reported `index.html` as missing links
  to six worked examples — `terminal`, `window`, `widget`, `focus`, `edit` and this one — of which
  five predate this task; the workflow that runs it triggers on `docs/lib/examples/**` and `lib/**`,
  so **ziman.dev's deploy has been failing since the widget example landed**. The links are added.
  The checker then still reported this one, because its pattern for a linked example was
  `[a-z_]+_example\.zm` and `a11y` has digits in it — so the directory side could see the file and
  the page side could not. Widened, and verified by removing the link again.

- [x] **F276** **A GUI build, without making every `ziman` depend on a display.** (S; 9299a67b)

  `src/native_window.c` compiles in the default build with its backend behind `ZIMAN_X11`, so the
  module is always present, `--api window` always answers, and `make check` is unaffected; the
  natives refuse with a message saying this build has no backend. A `make gui` target adds
  `-DZIMAN_X11 -lX11`.

  **Establishes a pattern this repository does not have yet.** `tls-if-available` and
  `pdf-if-available` skip *tests* when a tool is missing; nothing here compiles a native
  conditionally, and sqlite and OpenSSL are hard dependencies. A command-line `ziman` that will not
  start without X11 installed would be a worse tool, so this is a decision rather than a build
  detail.

  **As built: a separate binary, not a flag on the default build.** `make gui` produces `ziman-gui`
  from `$(SRC)` in one step, exactly as `ziman-nogc` already did, because a `-D` added to `CFLAGS`
  is invisible to make -- `make gui && make` left the X11 objects in place and the "default" binary
  still linked libX11, and the no-backend skip path then reported a pass for a build that could not
  have produced one. The reverse failed to link outright. `tests/run_window_test.sh` prefers
  `./ziman-gui` when it is there and skips with a message naming `make gui` when it is not.

- [ ] **F277** **The widget set: buttons, entries, lists, scrolling, menus, dialogs.** (XL;
  instalments 1 and 2 of 4 built)

  The volume phase, and deliberately last. Each widget is a small amount of code over F271's tree,
  F272's focus and F273's editing — and each one is wrong until F275 can describe it.

  Not a goal: pixel parity with any platform's own widgets. Route A would have used the platform's;
  this route should not promise an imitation it cannot keep, which is the criticism Flutter's own
  users make of it.

  **Instalment 1 (2026-11-10): the interaction model, and the two controls that prove it.**
  `lib/ui/controls.zm` — an `Input` vocabulary, `target` for routing, `Button` and `CheckBox` with
  their update functions and their widgets, and an injected `Style`. 23 unit tests, and a worked
  example that applies four gestures and prints what a reader would say after each.

  **The architecture is forced by the language rather than chosen, which is the finding worth
  keeping.** Every widget set hands a widget a callback — `on_click: fn()` — that mutates the
  application's state. Ziman will not compile it: *"a lambda cannot capture 'count' because it is a
  'var' … captures are by value, so the lambda and the enclosing function never share mutable
  state"*. So a control cannot act, only answer: every update takes a state and an input and returns
  a new state plus what happened, and the application keeps the state. This was checked against the
  compiler before any of it was designed, rather than assumed from the memory of it. `focus.clicked`
  already had exactly that shape, so the model is the existing grain of the thing.

  A corollary: **this module owns no registry of controls and cannot**, since no shared mutable
  state exists to hold one. The application holds its own controls' states, routes an input with
  `target`, and calls the update for the control it was for. The example is 40 lines and shows the
  whole loop.

  The rules each test pins, all of them invisible in a rendered frame:

  * **A press inside and a release outside does not fire.** Dragging off a button cancels it, which
    is why `held` is state rather than the button simply reporting clicks — a button that fired
    anyway is a defect a user does not report, because they assume they misclicked.
  * **Space arms on the way down and fires on the way up; Enter fires at once.** The keyboard
    mirrors the pointer so that it can be cancelled the same way, except for the key a default
    button answers. Both are the platforms' own split.
  * **A release is routed to the focus, not to what is under the pointer.** This looks wrong and is
    what makes the cancel work at all: the press moved the focus to the button, so the release
    reaches that button even after the pointer has left it — and the button is the only thing that
    can decide the drag was a cancel. Routed by position, the release would go nowhere and the
    button would stay drawn pressed for ever.
  * **A wheel goes to the control under the pointer and ignores the focus**, which is what a user
    means; over nothing it goes nowhere rather than falling back to the focus.
  * **A mixed check box becomes checked, never unchecked.** "Toggle" suggests otherwise and every
    platform does this: mixed means some of the things under it are on, and a user clicking it is
    asking for all of them. Clearing it would throw away choices already made.
  * A disabled button **is released** as well as inert, or it is drawn pressed by a frame nobody
    pressed.
  * The check box's drag-cancel is the button's rule and not a copy of it — `check_box_input`
    delegates — which breaking the rule proved: both tests failed from the one edit.

  **The return on F275 being ordered first is visible here.** `button_widget` declares its role, so
  a button announces "button, Save" from one call with nothing else told. And `check_box_widget`
  has to declare its *label*, because the text inside it is the mark as well as the label — without
  that a reader says "x Notify me", which the test asserts by building the undeclared version by
  hand beside it.

  **Instalment 2 (2026-11-10): the text entry.** `Entry` over `edit.Editor` and `edit.History`,
  `entry_input`, `entry_widget`, `caret_at_x`, and `Input.Paste`. 21 more tests, 44 in the module.

  * **The caret is placed by the layout, not computed.** The widget is a row of the text before the
    caret, a one-unit box, and the text after it — so the same metrics that measure the text place
    the caret and the two cannot drift. A selection is the same trick with a background behind the
    middle run. Computing a caret's x separately is how a caret ends up half a character off in one
    font and right in another.
  * **`caret_at_x` answers the nearest boundary, not the character the pixel is inside.** Clicking
    the left half of a character puts the caret before it. The other rule makes the caret feel one
    place behind the pointer, which nobody reports and everybody notices. Measured as prefixes
    rather than as a sum of per-character widths, because a sum ignores kerning and would disagree
    with the layout that drew the text — O(n²), which is right for one line and wrong for a
    document.
  * **A run of typed characters is one undo step**, and a delete, paste, caret move or click ends
    the run. Without it, Ctrl-Z after typing a word steps back a letter at a time. One `bool` on
    `Entry`, and `Input.Paste` is a separate variant from `Input.Text` for exactly this reason: a
    paste is one step whatever its length.
  * **The clipboard is an output and an input, never a thing this layer reaches.** `EntryStep.copied`
    carries what the field wants put somewhere and `Input.Paste` carries what came back; F273 left
    owning an X11 selection as platform work beside `native_window.c`, and this is the seam it will
    plug into. Cutting from a read-only field **copies** rather than doing nothing: the user asked
    for the text, and withholding it is not what read-only means.
  * `changed` is separate from the new state, and false for a caret move: a form is not dirty
    because the user pressed an arrow key.

  **A gate of mine was not discriminating, and breaking the code is what showed it.** The
  round-trip case — place the caret at *i*, lay out, read the caret's x, feed it back to
  `caret_at_x`, expect *i* — passed with two units of spacing added to the widget's row, because
  `caret_at_x` snaps to the nearest boundary and so answers the right index for any drift under half
  a character. Which is precisely the drift the case claimed to catch. It now asserts the caret's x
  **exactly**, against the measured prefix, and keeps the round trip as the weaker second half; the
  exact line fails on the spacing alone. Third time on this task list that deliberately breaking
  working code found a fixture that was asserting less than it appeared to.

  Remaining instalments: lists and scrolling (3), menus and dialogs (4).
