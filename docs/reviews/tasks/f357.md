# F357 — the plan is a filter in front of a filter

Done 2026-11-27. `lib/graphics/raster.zm`, `tests/stdlib/raster_test.zm`.

The second item out of the measurement that produced [F356](f356.md), and the one that survived
being measured properly. Two others did not, and this file is as much about them.

## What it is

`fill_shape`, `clip_mask` and `rasterise_tile` each order a path's edges by the row they first
touch, so that `advance_active` can carry a live list down the page and hand `row_coverage_raw` a
short one. The ordering is `plan_of`: a counting sort whose **bucket array is one per row of the
shape**.

For the shapes a window draws that trade is upside down. A panel, a viewport or a background is the
height of the canvas, so the sort is about 1,440 interpreted steps to put fifty edges in order, and
then `advance_active` walks a list on every one of those rows. **The scan it saves costs about two
nanoseconds an edge, in C.**

So the plan is built only where it can pay for itself — above `plan_worth_edges`, which is 128 —
and everything else hands the native every edge.

**This cannot change what is drawn, and that is the point.** `row_coverage_raw` already tests every
edge it is given against the row it is drawing (`sy >= low && sy < high`), so `live` is a filter in
front of a filter: handing it all of them produces the same crossings in the same order. The choice
is purely about cost.

## Measured

Per frame of the health-record window at 1960x1440, over about a hundred fills, with a clock inside
each part of `fill_shape`'s setup:

| part | per frame |
|---|---|
| `edges_of` (flattening every curve) | 43-128 ms |
| `transform_path` | 15-22 ms |
| **`plan_of`** | **15-20 ms** |
| `prepare` and the row buffer | ~1 ms |
| `advance_active`, down the rows | 17-20 ms |

`tests/bench/ui_frame.zm`, four alternating rounds of two binaries:

| case | before | after | |
|---|---|---|---|
| 1280x800 fills only | 25-30 ms | 24-28 ms | **1.16x** |
| 240x24 row | 4-5 ms | 4 ms | 1.12x |
| 1920x1080 full frame | 133-148 ms | 119-134 ms | 1.10x |
| 1280x800 samples=1 | 102-119 ms | 94-106 ms | 1.09x |
| 640x480 full frame | 84-102 ms | 73-92 ms | 1.08x |

Every case that draws anything is faster in every round. The one that is not — an *empty* 640x480
scene, 3 ms against 4 ms — has no paths in it at all and cannot be affected by this.

## The two that did not survive measurement, and why that matters

Both looked at least as promising as this one and both were reverted.

**`shape.flat_outline`** — flattening a path allocates a `Point` per vertex, six more per
subdivision step and a `[Point]` per polyline, and `edges_of` then walks the result to turn it back
into pairs of numbers. Rewriting the subdivider to push bare floats, with `flattened` rebuilt on top
so there was still one subdivider, was byte-identical on all six graphics fixtures — and
**measurably slower**: 1280x800 fills only went 28-32 ms to 39-45 ms, consistently, in every round.

The reason is worth keeping: in this interpreter **passing eleven scalars is not cheaper than
passing four points and allocating six**. Every argument is an evaluation and a binding, and the
recursive subdivider makes two calls per step. The arithmetic was the same; the dispatch was not.
This is the same shape as F270's finding that two Ziman-level rewrites of the coverage loop each
measured 1.00x.

**Raising the GC heap floor** (`ZIMAN_GC_HEAP_FLOOR_MB=256`, with garbage collection at 26% of the
profile) measured 1.11x on one screen and 0.80x on another. Not a result.

## And the instrument, which is the real lesson

The first measurements of all three were taken the way [F356](f356.md)'s were: launch the window,
click between two screens, take medians over ~15 painted frames. **That method has a noise floor of
about 30%, and all three changes are inside it.** It read this one at 1.09x and 0.92x on two
screens of the same application in the same pass — no result either way — and it read `flat_outline`
at 0.87x and 1.05x, which is a regression it could not see.

F356 was a threefold win and the method could not miss it. Everything after it needed
`tests/bench/ui_frame.zm`, which renders a fixed scene in one process with no window, no data and
no X11 — and whose own header already says so: *read the ratios, not the milliseconds, and measure
A against B in the same minute.*

**A measurement method is fit for an effect size, not for a question.**

## The tests, and what they are really guarding

Two in `tests/stdlib/raster_test.zm`, both comparing the planned path against the unplanned one on
*the same geometry*: a rectangle whose upright sides are cut into sixty-six pieces each has 134
edges and takes the plan, while the plain rectangle has four and does not. A vertical edge's
crossing is its own x whatever fraction of it a sample line falls in, so the two must be the same
picture.

Watched, and the second line is the one that matters:

| break | reddens |
|---|---|
| `advance_active` drops an edge a row early | both new tests; **every graphics fixture stays identical** |
| `plan_of` returns an unsorted order | both new tests; **every graphics fixture stays identical** |
| the threshold lowered to 4, so the plan is used everywhere | nothing, as the claim above predicts |

So this change moved almost everything off the planned path, and **without these two tests
`plan_of` and `advance_active` would now be exercised by nothing in the repository.** A fast path
that takes over the common case also takes the coverage with it.

## What is next

`edges_of` is still 43-128 ms a frame and is the largest single item in painting, and garbage
collection is still 26% of the profile. `flat_outline` was the cheap attempt at it and it failed;
what is left is the expensive one — the flattening in C, as F270 did for the per-pixel loops — or
caching the rasteriser's inputs across frames, which is F345's open reuse question. Neither is a
cliff, and the bench above is now the instrument for judging either.
