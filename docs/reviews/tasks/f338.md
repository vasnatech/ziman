# F338 — a label that wraps, and the width the measure protocol never had

Done 2026-11-20. `lib/ui/widget.zm`, nine tests.

`Label`'s own doc comment used to say:

> A run of text. **No wrapping**: a label is one line, and a paragraph that wraps is a different
> widget with a different measurement.

That was not a simplification. It was the layout protocol: **`measured(w, m)` is handed the
metrics and not the width it will be laid into**, and the height of wrapped text is a function of
the width. Nothing could report how tall it would be, so nothing in `lib/ui` could wrap — and
every application that needed a paragraph either cut it short or let it run off the edge.

Found by the health-record port, twice over: a free-text reaction measured 420 points on one line,
made a 492-point column lay its rows out 704 wide, and pushed every row's delete button out past
the pane beside it. The first workaround was `flow_of`, which wraps *widgets* at layout and
measures one line — so the row was then too **short** and the wrapped line drew over the row
beneath. The second was to elide. Neither is what the target does: `<p>` wraps.

## What changed

**`measured_in(w, m, within)`**, where `within` is the width this widget will be laid into or
`unconstrained()`. `measured(w, m)` is that with no width, so the eight existing callers are
untouched.

**A column passes its width down; a row does not.** A column divides height and hands every child
the same width, so it knows what to say. A row divides *width*, and no child's share is known
until every child has been measured — asking a child "how tall are you at this width" before
deciding the width is the circle CSS breaks with separate min-content and max-content passes. This
layer does not have those, and inventing them for one widget would be the wrong place to start.

So a paragraph in a row measures its one line, which is the honest answer to "how wide would you
like to be", and `wide_of` is how it wraps there. **That limit is a test**, not a footnote:
`a_wrapping_label_in_a_row_measures_one_line`.

**`Label.wrap` is off by default**, and that is the right default rather than the compatible one.
A button's label, a column heading and a table cell are one line *by intent*; wrapping them would
make a control two rows tall the moment a window narrowed. A paragraph says so, with
`wrapping_label`.

**One breaker, called twice.** `broken_into_lines` is public and is what both `measured_in` and
`collect` use. A label measured at three lines and painted as one run is a run drawn straight off
the end of its row — which is the defect `multi_line_widget` avoids in the entry only because its
scroll and its draw are the same loop.

**Greedy, first-fit, and never inside a word.** Knuth-Plass makes a better paragraph and needs the
whole paragraph before it can place the first line, which is not a trade a label in a list row
should make. A word longer than the line is left overlong rather than cut: an unreadable word is
worse than an untidy one, and the case that matters — a URL in a notes field — is worse hyphenated
than overhanging.

## Two watched fails, and the second only existed because the first was not enough

| removed | what reddened |
|---|---|
| the column passing its width down | `a_wrapping_label_is_taller_in_a_narrower_column`, at 20.0 against 20.0 |
| the break in `collect` | **nothing** |

The second is the finding. Seven tests asked about geometry — measured heights, laid heights, the
row limit, the `wide_of` spelling, word breaking, empty text — and **not one of them looked at the
ink**. A painting that drew one run where the measurement said three would have shipped green.
`a_wrapped_label_is_painted_one_run_per_line` counts the `scene.Op.Text` runs and checks each sits
one line height below the last; with the break removed it reddens.

Worth keeping: *a watched fail that does not fail is a missing test, not a passing one.* It is the
second time in two days — the dead divisor search in F337 was the first, and that one meant the
opposite, that the code was redundant rather than the test.

## What it does not do

- **A row still cannot tell a child its width.** See above; `wide_of` is the spelling.
- **No hyphenation, no justification, no bidi line breaking.** Breaking on spaces is what a label
  in a list row needs; a paragraph that needs more belongs in `lib/graphics/layout`, which already
  has `measure(block, width, document)` and a real line breaker — and which needs fonts rather
  than `widget.Metrics`, which is exactly why this could not borrow it.
- **`controls` draws no wrapped text yet.** Nothing in the control set needed one today; the port
  uses `widget.wrapping_label` directly.
