# F356 — a clip that is a rectangle should not cost a canvas

Done 2026-11-27. `lib/graphics/raster.zm`, `src/native_raster.c`, `tests/stdlib/raster_test.zm`,
`tests/lang/graphics_raster.zm` (a comment).

Raised by the health-record port's owner: **"work on making ui paint faster and respond faster."**

## What the window was doing

A frame of the health-record window at two pixels a point, 1960x1440, under a real record:

| phase | before | after |
|---|---|---|
| build the widget tree | 0 ms | 0 ms |
| lay it out | 80 ms | 80 ms |
| build the scene | 33 ms | 33 ms |
| **paint the damage** | **784 ms** | **262 ms** |
| publish the accessibility tree | 3 ms | 3 ms |
| **a frame that paints** | **896 ms** | **402 ms** |

Medians over three interleaved before/after passes of six screen changes each, same machine, same
data, binaries built from the same tree and alternated rather than run in sequence — the method
[F339](f339.md) had to adopt for the same reason.

## Finding it

The first measurement split `desktop.repaint` into rasterising and presenting, which it had never
been split into: **rasterise 784 ms, present 14 ms.** The blit was never the problem.

The second put a clock inside each of the eight per-pixel natives. **They totalled 30 ms of the
784.** So 96% of painting was interpreted Ziman *around* the pixel loops — which is the opposite of
what F270 left behind, and it meant no amount of work on the loops would have shown.

`ziman --profile` on the running window then named it outright:

```
  self%  samples  function
   25.7     3220  (garbage collection)
   15.0     1875  raster::clip_mask
    5.0      629  shape::with_point
```

**`clip_mask` allocates a float for every pixel of the canvas** — 2,822,400 of them, 22.6 MB —
fills it with an interpreted loop over the clip's area, and `snapshot`s it, which copies all 22.6
MB again. Per clipped group. Per frame. The garbage collection above it is mostly that.

Counting the calls is what made it legible: the slow screen made **one** such mask and the fast
screen made **none**, and that was their entire difference. One mask was 450 ms.

## Why the fast path that already existed did not fire

`window_clip` turns a clip into a narrower write window and no mask at all — which is free, and
which the comment above it says is "the only case that occurs in a window". It requires the
rectangle's edges to land on **whole device pixels**, and that is a correctness condition: a window
has hard edges where a mask has soft ones, so a rectangle at `x = 10.5` must keep its half-covered
column.

A scroll viewport lands on a half pixel whenever the layout above it measured to a half point,
which at two pixels a point is most of the time. So the condition held or failed for reasons
nothing in the screen explained, and the window was three times slower on some screens than
others.

## What it is now

**An upright rectangle never needs a mask, on the grid or off it.** `rect_profile` draws one as a
narrower window plus **one row** of coverage — 1,960 floats instead of 2,822,400, with no copy —
and `Mask.step` is how a row is found: the canvas's width for a general clip path, and **zero** for
a rectangle, so every row reads the same profile.

Why one row is exact and not an approximation: `row_coverage_raw` samples a row at `y + 0.5` and
takes each span's exact overlap horizontally, so every row whose sample line falls inside the
rectangle crosses the same two vertical edges at the same two x. Rows outside it have no coverage
at all and are cut from the window rather than multiplied by zero. **The profile is not a second
implementation of that** — it is one call to the same `row_coverage`, on the same edges, for a row
inside the rectangle.

**`samples` must be 1, and it is checked.** Above one sample the first and last rows of a rectangle
catch only some of their sub-scanlines and need profiles of their own. Every window in this
repository and in curly sets `samples: 1`; `raster.options`'s default of 4 is for rendering to a
file, where a mask is paid once rather than sixty times a second. So the restriction costs a window
nothing — but it is why `tests/lang/graphics_raster.zm` went on taking the mask and stayed
byte-identical, which is worth knowing before reading that fixture as coverage of this.

The four compositing natives gained a `mask_base` argument: the mask's index for the row's column
zero, separate from the canvas's `row_base`. That is the whole of the C change.

## The tests, and the hole the first version of them had

All six graphics fixtures were byte-identical on the first build, and **that proved nothing**: at
four samples none of them reaches the new path. The first four breaks of the fix were watched, and
all four stayed green — the same shape as [the stale-binary trap of F354](f354.md), except that
here the binary was current and the tests were blind.

The tests are in `tests/stdlib/raster_test.zm` and their oracle is **a second render, not a
recorded number**, because regenerating a committed `.out` blesses whatever it was given. A fill
large enough to cover every pixel it touches completely, clipped to a rectangle, has to come out as
exactly that rectangle filled on its own.

Six breaks, each reddening its own test:

| break | reddens |
|---|---|
| the bottom row off by one | the rectangle, the nest, the gradient |
| the profile read from a row outside the rectangle | all four |
| a nested clip ignoring the outer one | the nest |
| the left column dropped | the rectangle, the nest, the gradient |
| the gradient native reading the canvas index | the gradient |
| the blitter native reading the canvas index | the words |

The last two are why there are four tests and not one: **a glyph does not reach
`composite_row_flat`.** It is rasterised into a tile and blitted through `composite_span_flat`,
which reads the clip at an index it is handed, so a mask index wrong in the blitter alone passed
every other assertion.

And one break that *should* pass and does: reading the profile from the row below `y0` rather than
`y0`. Both rows are inside the rectangle, so the answer is the same — which is the claim the whole
change rests on, asserted by a break instead of by a sentence.

## What this did not fix

Painting is still 262 ms and the profile after the change has no cliff left in it:

```
   26.1     3156  (garbage collection)
    5.5      667  shape::with_point
    3.6      440  charset::scan_utf8
    2.6      318  raster::advance_active
```

**Garbage collection is now the largest single item**, and the names under it say where the rubbish
comes from: `shape::transform_path` builds a new path for every op of every frame, `hull_of` walks
it allocating a `Hull` per point, and `edges_of` flattens every curve again. None of it is cached
across frames, which is the same reuse question F345 left open — a frame is still rebuilt, re-laid,
re-sceneed and re-pathed from nothing on every input. That is the next item and it is diffuse,
where this one was a cliff.
