# F348 — a tooltip could not name the one control that needs one

Done 2026-11-25. `lib/ui/controls.zm`, `tests/stdlib/controls_test.zm`.

Raised by the health-record port, whose sidebar collapses to a rail of **seventeen icon-only rows**
with no words on any of them. Resting the pointer on one showed no tip, ever, and nothing said why:
the hover reported the row's name correctly, `tip_due` came true, and `tip_words` answered `""`.

## What it was

```ziman
pub fn tip_words(h: Hover, laid: Laid) -> string {
    return switch focus.node_of(laid, h.on) {   // <-- tab stops only
        Some(node) { words_unless_shown(node) }
        None { "" }
    }
}
```

`focus.node_of` is documented as "the laid node of the **focused** control", and it is built that
way: it walks `focus.controls`, which pushes a node only `if widget.is_tab_stop(l)`. That is right
for a focus — a focus is always a tab stop — and wrong for a pointer, because **a pointer lands on
parts**. A list's row, a tab and a tree's item are each a `widget.part_of`: a control a click and a
reader can reach, that Tab cannot, and that holds no state of its own. `node_of` cannot see any of
them, so `tip_words` answered `""` for all of them.

**And a part is the control a tooltip is for.** The whole rule in `words_unless_shown` is "show the
words a control declares and does not draw" — an icon button, a number field's range. A list row
drawn as `Value.Mark` is precisely that: an icon, its words declared through `value_text` (which
answers the icon's own name) and nothing on screen showing them.

Probed on the port's own window: `frame/menu/0` through `frame/menu/16` were all absent from
`focus.node_of` while `focus.control_at` found each of them by position — the hover was reading the
tree one way and the tip reading it another.

## The fix

`widget.node_named`, which is the door for exactly this and says so two functions above its own
definition: "**Not `focus.node_of`, which only ever looks at controls.** A name belongs to any
widget that has a slot for one." It walks every node by name, so it reaches a part; and
`widget.tip_in` answers `""` for a node that is not a `Control`, so a name that belongs to a group
or a label still has no tip rather than a wrong one.

One line, and no signature moved.

## Watched fail

`a_tip_names_an_icon_only_list_row` lays out a three-row rail — two `Value.Mark` rows and one
`marked` row that carries its words — and asserts the first two name themselves and the third says
nothing. Putting `focus.node_of` back reddens it at the first assertion (445 passed, 1 failed).

**Why no existing test caught this.** `a_tip_names_an_icon_button_and_stays_quiet_over_a_labelled_one`
and `a_description_is_what_a_tip_prefers` ask about a button and a number field. Both are tab stops,
so both were reachable, and the entire tab-stop/part distinction was outside what the tests asked
about. The new test's third row is the other half: a part that *does* draw its words gets no tip,
so the fix cannot be "answer with the label whatever happens".

## The second half, which is the application's

The port's rail still showed no tip after this, for a reason of its own: `screen/frame.ticked`
accumulated the hover clock into a local and returned it only when `tip_due` *flipped*, so with a
500 ms pause and a 16 ms tick the count was thrown away every frame and never reached 500. That is
fixed in the application (health-record `dev`), and the two halves are independent: either one
alone leaves a rail no one can read.

**It is also the same confusion as F345's frame-skip, pointing the other way.** The window's loop
reads `Some` from `ticked` as "draw this", so a tick that advanced a clock and changed no pixel had
nowhere to put its answer — and a library whose `ticked` returned one value could not have been
used correctly. An application loop needs *two* answers from a tick: the state after it, and
whether anything about it has to be drawn.
