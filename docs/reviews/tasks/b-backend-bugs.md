- [x] **B8** **Bound concurrent password hashing and rate-limit `/api/auth/*`.** Also stop registration disclosing which emails exist. (D2 item 5, D2 S2; S) 64 unauthenticated registrations move RSS from 66MB to 1.09GB permanently (Argon2id with no concurrency cap), and there is no rate limiting anywhere. The email-existence leak undoes the login hardening done deliberately elsewhere. Done 2026-10-06 in the backend repo (9723dfc) for the hashing cap, with the other two parts split out below because each turned out to be a decision rather than a fix, and with the report's stated cause corrected. **The cap works and does not fix the memory.** Every hash and verify now goes through `common.hash_password`/`verify_password`, holding a token from a channel semaphore (`app.security.max-concurrent-hashes`, default 4) and returning it with `defer`; instrumenting the server confirmed 16 concurrent registrations entered the hash 16 times with a peak of 1 inside when the cap was 1. RSS still went 61 -> 347 MB. The growth is glibc giving each thread its own malloc arena and keeping the 19 MiB Argon2id buffer in it: 16 sequential registrations grow 20 MB, 16 concurrent grow 286 MB, and the same 16 concurrent under MALLOC_ARENA_MAX=1 grow 40 MB. It plateaus (347/367/367 MB over three rounds), so the ceiling is (threads that have hashed) x 19 MiB -- exactly the 1.09 GB the review saw at max-connections 64. See B9. The key is `max-concurrent-hashes`, not `...-password-hashes`, because properties.zm masks any key containing "password" and the first name printed as **** in the startup report.
- [x] **B9** **The server's resident memory ceiling is (threads that have hashed) x 19 MiB**, because glibc gives each thread its own malloc arena and keeps Argon2id's buffer in it. (from B8, measured 2026-10-06; S to change, M to be confident) `mallopt(M_ARENA_MAX, n)` early in `src/main.c` would bound it -- 16 concurrent registrations go from 286 MB of growth to 40 MB at `MALLOC_ARENA_MAX=1` and 59 MB at 2 -- but that is a global policy change for every Ziman program and arena count trades directly against allocation throughput under concurrency, which F7 and both 2026-10-05 reviews already call this project's worst problem. So it wants measuring against F7's benchmarks before it lands, not a one-line commit. Cheaper interim levers that need no code: lower `server.max-connections`, or set `MALLOC_ARENA_MAX` in the service's environment. The capping of concurrent hashes (B8) is in place and is not the lever -- its own comments say so, because I believed it was until I measured. **Measured 2026-10-07 and done: the trade-off this was filed on does not exist.** `server.serve` now calls `mallopt(M_ARENA_MAX, 1)` once, unless `MALLOC_ARENA_MAX` is already set, in which case the operator has decided. Placed in `serve` rather than `main.c` so only a program that actually serves adopts it -- which was the whole objection to the one-line commit. **Memory**, 48 registrations at 16 concurrent, three interleaved rounds: uncapped 307 MB growth (307.4/307.0/307.3, remarkably stable), capped from `serve` **136 MB**, `MALLOC_ARENA_MAX=1` in the environment 98 MB, `=4` 212 MB. The code default cannot reach the environment's floor because glibc reads its variable at the process's first allocation while `mallopt` only bounds arenas created after it runs, and three threads are alive before `serve` -- so the env var stays documented as the way to go further, and the override demonstrably wins. **Throughput**, paired and interleaved: authenticated read at c=16 1656 -> 1593 rps (-3.8%), c=32 1514 -> 1539 (+1.7%), c=64 1402 -> **1499 (+7%)**, registrations 79.9 -> 83.4/s, and an allocation-heavy eight-thread program with no server in it 2322 -> 2295 ms. **Why there is no cost**, which is the part worth keeping: Ziman's own allocation never touches glibc's arenas -- `zgc.h` routes malloc through Boehm and Boehm takes memory from mmap -- so what the cap constrains is what third-party C libraries allocate, which is exactly OpenSSL's retained Argon2id buffer. F7's work (allocation calls 9.96M -> 2.57M the same day) is likely why the c=64 figure now favours the cap. Limits: one machine, one glibc, and the reasoning applies to the collector build the server ships -- a `nogc` build does use real malloc.
- [x] **B10** **Rate-limit `/api/auth/*`** -- which needs the client address, and `lib/http/server.zm` deliberately does not expose it. (from B8, D2 item 5/S2; M) The library's own comment is the position to argue with first: "It cannot tell one client from another, so a determined flood from many addresses is a job for a firewall or the proxy in front (see the roadmap)." So this is two decisions, not one: whether the HTTP server should hand a handler the peer address (and `X-Forwarded-For` when behind a proxy, with the trust question that opens), and only then what the application does with it. Per-account lockout already exists for login and MFA (V027), and it throttles the email tried whether or not the account is real, so the gap is specifically unauthenticated volume -- registration above all, since that is the endpoint that does 19 MiB of work for an anonymous caller. Until then B8's cap bounds how much of that work runs at once, and B9 bounds what it costs in memory. **Done 2026-10-07, in three layers (ziman 9af21c4 + 5c3aa4a, backend a394029).** First, the task's premise: the comment it names as the position to argue with is about the connection *timeouts* not telling clients apart, which is true and unrelated. The real gap was lower -- `net` had `getsockname` and **no** `getpeername`, so a peer address was unreachable from Ziman, not merely withheld from handlers. (1) `net.peer_address` and `Request.peer`, filled in by `read_request` and `None` on a hand-built request. **A field, not a synthetic header**: an injected `X-Ziman-Peer` would have broken nothing and cost no API change, but a client could send that name, so it would be safe only while the parser stripped it -- the exact subtlety a peer address exists to avoid. Cost 13 literals; two with `if ... { } else { }` inside defeated brace-matched editing and the suite caught it. (2) `server.rate_allow` in C, because Ziman has no cross-thread mutable state so an application *cannot* write it; fixed window, 4096 keys, documented worst cases (twice the limit across a window boundary; a full table hands a legitimate caller a fresh allowance, chosen over refusing or allowing everyone). Plus `rate_allow_at` taking the clock like `jwt.verify_at`, and 429 which the library lacked. `server.forwarded_for(req, trusted_hops)` counts proxies **you own** from the right, never read by default, no auto-detection. (3) The backend throttles `/api/auth/*` in `routes.route`. **The default was measured**: at 20/minute three of its own suites failed (the lockout test makes eleven wrong passwords on purpose), which models several users behind one NAT -- 20 was not conservative, it was broken; 100 passes all twenty suites and still refuses a flood. New `throttle_test.py` checks that a spoofed `X-Forwarded-For` buys nothing at 0 hops and that distinct forwarded addresses are distinct callers at 1.
- [x] **B11** **Decide whether registration may keep disclosing which emails exist.** (from B8, D2; S once decided) `service/auth.zm`'s `register` answers `Email already in use`, which lets anyone enumerate accounts. It is also byte-for-byte what the reference does -- `health-record-backend-spring`'s `AuthService.java:39-41` performs the same `existsByEmail` check and throws the same message -- and API equivalence with that backend is a stated goal of this project, with several open tasks (E20) about closing divergences. So the two goals conflict here and the resolution is a choice, not a fix: keep parity and accept the disclosure, change both backends together, or diverge deliberately and write down why. Note the login path was hardened against exactly this (the lockout throttles the email tried whether or not it exists), which is what makes registration the odd one out. B10 would reduce how fast an enumeration can run either way. **Decided 2026-10-07: change both backends together, done (health-record 36aa350).** Registration answers the same thing whether or not the email is taken, and returns **no token**; a client logs in afterwards. **The message was never the disclosure** -- a token for a new email and an error for a taken one is a perfect oracle whatever the text says -- which is why a generic message would have achieved nothing. Three things match, not just the body: the password is hashed in both branches (a duplicate used to return *before* the Argon2id work and so answered faster; now 28.8ms against 29.8ms), the response is built from the request so it cannot leak the stored account's name, and the status is the same. **Stated rather than overclaimed: enumeration is dearer, not impossible.** Register-then-login still distinguishes, because a new account can be signed into and an existing one cannot with the wrong password -- that is two requests against B10's throttle instead of one, and leaves AUTH_REGISTER_DUPLICATE in the audit log. Closing it entirely needs an emailed verification link, and **neither backend has an email channel by design** (this product resets passwords through an administrator), which is also where someone who forgot they have an account now ends up. Four codebases: both backends, plus the web and Android clients that would otherwise break. Tests that asserted the old behaviour now assert the new property -- `auth_test` that a duplicate is *indistinguishable*, `AuthServiceTest` that nothing is saved and no token is minted at all, `AuthIT` that it is 200 with no token. Verified: ziman 20 suites / 978 checks, Spring 759 tests, web `tsc` clean, Android `compileDebugKotlin` clean.

The 2,268 behavioural checks missed it entirely because none of them asserts an order. Add `order_by: string` to `Crud`, default `"created_at, id"`, set explicitly for the six. (DX3 item 4, D4; S) Done 2026-10-14 in the backend (cd2cb7f). `order_by: string` on `Crud`, set for all ten resources that use it, each value taken from the Spring repository's own derived method name rather than guessed -- `findAllByPatientIdOrderByPerformedDateDescCreatedAtDesc` is `performed_date DESC, created_at DESC`. `id` is appended to every one as a final tiebreak, which Spring does not have and which stops two rows equal on every sort column from swapping between requests. The other four keep `created_at, id`, checked rather than assumed: their Spring repositories are a bare `findAllByPatientId` with no `OrderBy`, so this backend is stricter than parity there, not diverging. **The second half is why it could happen**: `resources_test` now has an `order_first` column and a pass of its own on a fresh user, creating the two rows in the *opposite* order to the expected one. Verified both ways -- eight ordering checks pass, and with the hard-coded `ORDER BY` put back exactly six fail, the six this task names.
- [x] **B13** The backend verifies tokens with bare `jwt.verify` (`service/security.zm:40`) although D8 added `jwt.verify_claims(issuer:, audience:)` to the library for exactly this, and `token.zm` stamps no `iss` or `aud`. Two services sharing a signing key therefore accept each other's tokens. The library half is done; this is the adoption half, and it is the clearest case in this file of a capability added and never used. (DX3 item 10, S1; S) Done 2026-10-14 in the backend (18f78b8). `app.jwt.issuer`/`app.jwt.audience` through `JwtConfig` and `JwtSettings`; all three issuing paths go through one `identified()` and both verifying paths through one `verified_claims()`, so neither half can change without the other. **Not a parity fix, and a deliberate divergence**: Spring stamps neither claim either (its only `issuer` is a TOTP label), so a Spring-issued token is no longer accepted here -- which is exactly the interoperability S1 identifies as the hole, and `version_of`'s comment saying it was intended is updated. Tokens in circulation stop working on deploy, the same cost as rotating the secret. A test in both suites asserted the old behaviour ("a token minted with the secret for a real user is accepted"); it is now three checks each -- no claims is 401, wrong `aud` is 401, both right is accepted, the third earning its place because without it the first two would pass if hand-minting had broken for any unrelated reason.
