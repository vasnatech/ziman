- [x] **F28** **The primitive type names are undiscoverable, and the rule meant to help points the wrong way.** (from the F27 pilot, 2026-10-09; S) The pilot's largest single consumer of budget, found independently by five of ten runs and reproduced by hand: `fn f(n: u64)` says *a type name must start with an uppercase letter*; `U64`, `Int`, `String`, `Str`, `Bool` then each say *unknown struct or enum type 'X'* with no suggestion. - [x] **F31** **`Map`/`Set` constant factors: the ranked first item is mis-ranked, and the one cheap fix left for the real cause does nothing.** (R, ROADMAP.md:714; M) No code shipped, which is the right outcome and took four measurements to establish. The entry ranks "`get` allocates an `Option` and `contains` does not, which costs ~9x" as "the largest and clearest win available", attributing it to "the wrapper allocation and the collection work it causes". **Reproduced the gap and then took it apart:** `map_get` is 6,424ns net against `map_get_or`'s 106ns, a 60x rather than 9x. But an `Option.Some` allocation measured *on its own* is **94-123ns**, so the wrapper is ~2% of that, not nine tenths. The actual mechanism: the same enum allocation costs **165ms per million with nothing else alive and 6,829ms with a 100,000-entry map alive -- a 41x slowdown of an allocation that never touches the map**.
