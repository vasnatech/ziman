- [x] **F139** **`server.max_connections` is a hard ceiling on concurrent keep-alive *clients*, and past it the server does not degrade -- it stalls.** (found 2026-10-15 while measuring MEMORY.md item 3; M) `serve`'s own doc says "one thread per connection, at most `max_connections` at once (the limit is a channel used as a counting semaphore: a client past it waits in the kernel's accept queue)", which is accurate and reads like back-pressure. With keep-alive it is not back-pressure, because an occupant does not release its slot at the end of a request -- it holds it until `idle_timeout_ms`. So clients past the cap wait for a timeout, not for a request. **Measured** on the reference backend (`server.max-connections=64`, `server.idle-timeout-ms=30000`), 2,000 requests, `ab -k -c 256`, server and client pinned to disjoint CPU sets:

    | cap | rps | failed |
    | --- | --- | --- |
    | 64 | 64.2 | 64 |
    | 128 | 64.7 | 19 |
    | 256 | **2176.6** | 0 |
    | 512 | 2044.2 | 0 |

  A 34x cliff the moment the keep-alive client count crosses the cap, and the ~64 rps either side of it is the arithmetic of the timeout rather than of any work: 2,000 requests at 64 rps is 31 s, against a 30 s `idle_timeout_ms`, so the run is one timeout cycle. Nothing is overloaded -- at cap=256 the same clients get 2,176 rps with no failures on the same cores.

  **Items (1) and (2) answered 2026-10-16, with measurements -- and the first figure in this entry
is corrected by them.** The "34x cliff / 64 rps" above is an artefact of measuring with
`ab -n 2000`: the over-cap run is gated by `idle_timeout_ms`, not by throughput, so its *elapsed
time* is ~30s whatever the request count and the rps figure is just (requests / 30s). Measured on
`/health` at cap=64, c=256 keep-alive: **2,000 requests -> 30.5s (65 rps), 20,000 -> 31.5s,
50,000 -> 32.9s (~1,510 rps)**. Throughput is not the defect. The defect is that **192 of 256
clients are held for a full idle timeout before being served at all**, in silence.

  **(2) Yes, Tomcat diverges, and not in the way this entry guessed.** Measured against a minimal
Spring Boot app on the real Tomcat connector (the parity backend itself would not build -- its
pinned Lombok emits `ClassFormatError: Invalid method Code length 0` on this machine's JDK 25, so
the probe was compiled with JDK 21 and Maven's compiler plugin bypassed). Same endpoint shape,
20,000 requests, 256 keep-alive clients:

    cap >= clients   tomcat 9,271-9,728 rps, 0 failed   ziman 9,876 rps, 20,000 in 2.0s
    cap = 64         tomcat 19,813 done in 14.3s (~1,380 rps), then a connection reset
                     ziman  19,837 done in 31.5s (~630 rps), in silence

  So Tomcat is *not* multiplexing its way out of this -- it is also bounded, and it also fails to
serve everyone promptly. **The difference is where the limit is applied.** Tomcat limits at accept:
excess connections are never accepted, the OS backlog fills, and clients get an immediate reset
they can retry. `serve` accepts first and *then* blocks on `receive(slots)` **inside the accept
loop** (`lib/http/server.zm:2596`), so an already-accepted client holds an open socket with no
thread behind it until an occupant's `idle_timeout_ms` expires -- and the loop is not accepting
anything meanwhile. Fail-fast against fail-slow, not multiplexed against thread-per-connection.

  **(3) is therefore much smaller than "should `serve` multiplex idle connections".** Three
candidates, with the constraint that rules the obvious one out:

  - *Take the slot before accepting.* The clean fix -- the loop then refuses to accept what it
    cannot serve, and the OS does the rejecting exactly as Tomcat's does. **But it breaks shutdown
    responsiveness:** `accept` returns on a shutdown request (accept_raw polls
    `ziman_shutdown_requested` in 250ms slices), while a blocking `receive(slots)` has no such
    wakeup, so a shutdown with every slot busy would hang the accept loop until a connection
    finishes. It needs a `try_receive` poll loop with a shutdown check, which is the shape
    accept_raw already uses for the same reason.
  - *Accept, then `try_receive`, and close immediately when no slot is free.* No reordering and no
    shutdown concern, and it turns a 30s silence into an immediate signal. Harsher than today on a
    transient burst -- a 65th connection against a cap of 64 is closed even if a slot would free in
    2ms -- though that is exactly what Tomcat does past `max-connections`.
  - *The same, with a bounded wait before closing.* Graceful for transient bursts, bounded for real
    overload; needs a name and a default, which makes it the one real API decision here.

  All three are behaviour changes to a shipped server contract, so they are a decision rather than
a fix, and none is applied.

  **Done 2026-10-16, and the design intent that settled it was "serve should support more
  concurrent clients than threads".** None of the three candidates above is what shipped: each one
  only changes *where* a client waits, and the measurement that killed them is that waiting was
  never the cost. A slot was held for a connection's whole life, so an occupant doing nothing kept
  it through `idle_timeout_ms` -- which is why elapsed time was one idle timeout whatever the
  request count.

  So a slot now means **a request in flight**, not a client connected. A connection that has
  finished a request goes to a poller thread that owns every parked connection and holds none open
  with a thread of its own; `net.wait_readable` (a new `net` primitive, landed separately in
  `e91bad2` with its own fixtures) says which have a request to serve, and only then is a slot
  taken and a worker spawned.

  | cap=64, 256 keep-alive clients | before | after |
  | --- | --- | --- |
  | elapsed | 31.5s | **1.5-2.0s** |
  | completed of 20,000 | 19,808, then an abort | **20,000** |

  cap=64 and cap=256 now measure the same, where they were 20x apart -- which is the whole claim.
  Non-keep-alive throughput *improved*, since a slot is no longer held across an idle connection:
  c=1 487-497 -> 530-637, c=4 1196-1225 -> 1587-1630, c=8 1388-1431 -> 2199-2208, c=16 1477-1554 ->
  2140-2146.

  Three wrong turns are recorded in `server.zm` where each happened, because each is the kind a
  reader would reintroduce: routing *newly accepted* connections through the poller (a fresh
  connection has a request on its way, and the poller may be part-way through a 250ms wait, so
  connection-per-request paid that in latency and `server_concurrency.sh` stopped finishing inside
  ten minutes); parking after every single request (a thread spawn and two channel hops per
  *request* rather than per *connection*, 9,876 -> ~3,000 rps, fixed by peeking with
  `wait_readable([sock], 5)` before parking -- a peek rather than a short read, since a read that
  times out cannot be told from a client stalling mid-request and `read_request` answers that with
  a 408); and cleaning up only on the normal path, which leaked a connection whenever a handler
  failed.

  What is left of this entry: `max_connections`'s default of 64 is no longer a client ceiling, so
  the question of raising it is closed by the change rather than by a decision.

- [x] **F140** **Every builtin call pays a linear `strcmp` chain, so a builtin's cost depends on its position in that chain -- `contains` costs ~95ns more per call than `map_get_or` for no reason but being 22 branches further down.** (found 2026-10-15 while cutting the `Map`/`dict` gap; M) `exec_call` (`src/interpreter.c:1300-1600`) dispatches every builtin through **60 sequential `strcmp(e->as.call.callee, "...")` tests**. Position is the whole story: `len` is 5th, `map_get` 21st, `map_get_or` 22nd, `contains` 44th, and the measured per-op costs line up with exactly that order (`len` 19-39ns, `map_get_or` 87-119ns, `contains` 182-220ns on a 100,000-entry map, 1,000,000 ops, loop overhead subtracted).

  **Proved, not inferred:** hoisting `contains` from 44th to 5th and changing nothing else took `Map contains` from **182-220 to 78-124 ns/op** and `MutableMap contains` from 166-189 to 88-111. That is ~95ns of string comparison per call, about 4.3ns per `strcmp`, and **every builtin call in every Ziman program pays its own share of it** -- this is not a map problem, it is the call path.

  **Do not fix it by reordering the chain.** Order is load-bearing: `"set"` is matched in two separate branches (`interpreter.c:1355`, inside an `||`, and again at `:1466`), so the first match wins and moving either one changes which handler a `set` call reaches. That is also why the cheap "hoist the hot ones" change is not the answer even though the spike above used it to measure.

  The fix is to resolve a callee name to an integer once and switch on it: stamp an id onto the call node (the node already caches `resolved_type`, so there is precedent), compute it where the name is already being validated in `typecheck.c` -- single-threaded, before any `spawn`, so no lazily-filled-cache race of the kind `g_scalar_types` was written to avoid -- and leave the existing chain as the fallback for an unresolved id. A first-character `switch` before the chain is a cheaper half-measure worth measuring if the full change looks too invasive: 60 names over ~20 first letters is ~3 comparisons instead of ~30.

  Two map-specific wins already landed from the same measurement pass and are not part of this task: `mutable_map_get_or` became a native (580-612 -> 70-81 ns/op, `fd5e394`) and the `Option` type is now one shared constant instead of a `strdup` plus a 64-byte `malloc` per Option-returning native call.

  **Done 2026-10-15.** Not by either route this entry proposed, and the reason is worth recording. Stamping a resolved id on the call node is still the better long-term answer, but it needs an id assigned in all 62 branches -- a large edit to the interpreter's hottest path for a win that turns out to be available mechanically. All 66 comparisons are now `CALLEE_IS(lit)`, which guards the `strcmp` with the first character: for a string literal that character is a compile-time constant, so a branch whose name starts with a different letter costs one byte compare instead of a call. Exactly equivalent to what it replaced -- `callee[0]` is always readable on this path, and a matching first character falls through to the same `strcmp` -- and it preserves the chain order exactly, which is what makes it safe where reordering is not.

  **Measured:** `Map contains` **182-220 -> 93-94 ns/op**, `MutableMap contains` 166-189 -> 99-110, which is the whole of what the hoist spike predicted (78-124).

  **A follow-on, and it measured nothing -- recorded because the diagnosis it corrects is the useful part.** After the above, `contains` on a `MutableMap` was still ~25ns slower than the equivalent `mutable_map_get_or`, and the visible suspect was a second name-based dispatch below the chain: `call_contains` does a `strcmp` against `"Mutable"` to rule out the cell, then `ziman_builder_contains` does two more against `"MutableArray"` and `"MutableString"` -- and none of those can short-circuit on the first character, because all five mutable types are named `Mutable`+suffix. Classifying once (`ziman_mutable_kind`, prelude.h, switching on the index-7 divergence and confirming with a short suffix `strcmp`) and passing the result into `ziman_builder_length`/`ziman_builder_contains` removed two of the three comparisons. `MutableMap contains` went 99-110 -> 103-127 ns/op: **no change, inside the noise.**

  So the residual is not those `strcmp`s. It is the guarded chain's own length: `CALLEE_IS` made each comparison a byte compare rather than a call, but `contains` still performs 44 of them against `map_get_or`'s 22, and ~20ns is what that difference is worth. Which means the full fix this entry originally described -- a resolved id stamped on the call node, so dispatch is O(1) rather than O(position) -- is the only thing left that can close it, and the mechanical trick above has been taken as far as it goes.

  **The resolved id, done 2026-10-15, which is this entry's own answer and does close it.** `Expr`
gains `call_builtin` (ast.h): 0 "not looked up", -1 "not a builtin", positive = a `BuiltinId`. The
interpreter resolves it on the node's first evaluation with a linear scan over the 63 names -- once
per call *site*, never per call -- and every one of the 66 branches is now an integer compare, which
is a shape GCC can turn into a jump table. Filled lazily rather than by the type checker, which
recognises builtins in a dispatch of its own well before it reaches `call_fn`'s assignment, and read
and written with relaxed atomics because threads share one AST: two may resolve the same node at
once and both compute the same value, so the requirement is only that the int store be
well-defined rather than a data race.

  Chain order is untouched, which still matters -- and it is three names, not one: `set`, `insert`
and `remove` are each tested in two branches, so first-match-wins decides the handler in all three
cases.

      builtin fn len(s: string) -> int

      builtin fn len<K, V>(m: Map<K, V>) -> int
      builtin fn len<T>(b: MutableArray<T>) -> int
      ...

  **This is not overload resolution and the design should say so in those words.** The interpreter
  already dispatches these on `args[0]` -- `call_len(args[0])`, `clear(args[0])`,
  `snapshot(args[0])`, `mutable_array_from(args[0])` -- so a `builtin fn` set is a dispatch table

  moment a second `fn` of the same name is legal in a program, this is C++ overloading and the "no

  **The alternative, which the language can already express.** Bounds exist -- `Eq`, `Ord`, `Hash`,
  used today in `lib/core/test.zm` (`assert_eq<T: Eq>`, `assert_lt<T: Ord>`) and by `min`/`max`,

  rather than user-implementable. Fewer lines, no new dispatch concept, and it names what
  docs/SYNTAX.md already calls *"the four questions every collection answers"*. **Against it:** a
  bound restores the single declaration but not the visibility, and visibility is the whole
  complaint -- the failure above was "I could not see that `MutableArray` was accepted", which
  `<T: Countable>` does not answer either. Nine explicit lines are greppable; one bound is not.

  **What `native` and `builtin` actually differ by today**, since the proposal turns on it. A
  `native fn` is *a function whose type can be written down*: declared in the prelude, registered
  by name to one C function of one fixed shape
  (`Value f(Value *args, int argc, int line, int col)`), checked by the **ordinary call path** --
  so it gets generics with inference, `variadic`, and even default arguments
  (`mutable_array_new(capacity: Option<int> = 20)`). A builtin is *a rule the checker implements*:
  a name mapped to an enum id (`{"len", B_len}`) and branched on inside `eval_call`, which means it
  holds the whole call **expression** rather than only the values -- `e->resolved_type`, the
  argument `Expr`s, even the callee's spelling (`e->as.call.callee[12] == 'u'` picks
  union/intersect/difference out of one branch). Builtins are also barred from named arguments
  (`BUILTINS_NO_NAMED_ARGS`) where natives are not.

  1. **The shape is not a shape**: `len`, `contains`, `snapshot`, `clear`, `push`, `insert`, `set`,

  2. **The rule reads more than types**: `format` validates its template against the argument list;

  3. **Not callable names at all**: `$map_lit`, `$set_lit`, `$is_variant`, `$unwrap_variant` are

  (raised 2026-10-18 from a review question -- *"how about mutable array initialization?"*, then

- [x] **F158** **`mutable_array_truncate` is gone, replaced by `narrow(b, start, end)`.**
  (raised 2026-10-18 -- *"i want to remove mutable_array_truncate"*, then *"we need slice
  alternative of MutableArray"*, then *"narrow for MutableArray only"*; S) F157 had taken the
  function from twelve call sites to one, `lib/graphics/raster.zm`'s `advance_active`. That site
  needs the builder itself to shrink -- `live` carries the active-edge set from row to row across
  three scanline loops -- so the either-world `slice` could not serve it: a query answers a value,
  and writing the value back would be `clear` plus `mutable_array_push_all` and a round trip.

  **Why not `slice`, and why not `mutable_array_filter`.** `slice` on an array is a *query*: it
  answers a value and leaves its source alone, which is the half of the mutation/query split that
  has governed every one of these decisions -- it is why `set(b, i, v)` is refused in favour of
  `b[i] = v`. Narrowing in place under the name `slice` would have put a mutation where a query is
  everywhere else. And `mutable_array_filter`, which *is* that site's loop in C, was considered and
  **not** used: it would have put a closure call per element into a rasteriser inner loop whose
  current cost is two native calls plus interpreted arithmetic per element. Which is faster was not
  obvious, so rather than measure it the review changed only the shrink at the end, leaving the
  hand-written compaction alone. Nothing in the hot path moved.

  **`narrow` adds the half truncate could not do.** Truncate kept a prefix; `narrow` keeps any
  window, so dropping a *prefix* is one pack-aware memmove where it used to be
  `mutable_array_remove(b, 0)` in a loop -- O(n) a call, quadratic overall. `clear(b)` is
  `narrow(b, 0, 0)` and stays the word for emptying. Builder-only, like `clear` and `snapshot`:
  an immutable array has nothing to narrow, and the refusal says `slice` instead.

  **It deliberately does not clamp.** `truncate(b, 99)` on a length-2 builder was a silent no-op,
  which hides a wrong computation; `narrow` reports a range past the length as a runtime error, as
  `slice` and an index already do. That is a behaviour change at the one surviving call site, where
  `write` is bounded by `len(live)` by construction, so it cannot fire there.

  added hours earlier in F156 told the reader to use *"`mutable_array_truncate`-style rebuilding"*,

  **The builder halves cost almost nothing to write, and the reason is the earlier items.** Nine of
  the eleven array versions are ordinary Ziman over `for x in`, `len(x)` and `x[i]` -- all of which
  took either world from the moment those questions stopped having per-type names (F149) -- so each
  twin is the same body with one word changed in the signature. Only `map` and `flat_map` are
  natives and needed real twins, each allocating a builder for the result where the native
  allocates the array directly: one allocation more out, a whole copy of the input saved in.

  **`array_join` was deleted rather than renamed.** It was one line delegating to `join`, kept for
  the positional calling convention since `join`'s parameters are all `Option`-typed. `join` owns
  the bare name and does strictly more (`prefix`/`suffix`), so 48 callers now say
  `join(separator: s, pieces: a)` -- exactly what the wrapper expanded to. Its own history argued
  for it: it had been a hand-written quadratic loop (18.05s on 40,000 pieces against 0.01s) kept
  alive by a comment that wrongly denied `join` could take an array, and when that was corrected
  nobody asked whether the name should outlive the implementation.

  **Three things I got wrong, all caught by fixtures rather than by reading.**

  *The rename stripped type arguments the calls needed.* `array_map<int, int>(xs, fn(n) { n * 2 })`
  supplies `U` for an un-annotated lambda, and `map(xs, f)` cannot. Type arguments **do** survive
  the rewrite -- `map<int, string>(xs, f)` works -- so the pass had to preserve them, and the 17
  ziman files were reverted and redone. The backend was fixed forward instead, carrying edits from
  five earlier passes that a revert would have lost.

  *A paren-matching converter that did not know about string literals.* `array_join(x, ", ")` split
  inside the separator, and before the assertion fired it had already rewritten `array_join`'s own
  **declaration** into `fn join(separator: sep: string, ...)`. It also rewrote the text inside a
  comment I had just written. A converter that edits code has to lex strings.

  *An empty literal cannot be dispatched on.* The arm type-checked argument one before choosing a
  world, so `first<int>([])` and `map<int, int>([], f)` became errors they had not been. `[]` can
  never be a handle, so it now dispatches to the array half unchecked and takes its type from that
  function's parameter -- which also retired the workaround F162 had put into `array_extras.zm`.

  86 call sites renamed, 48 converted, 0 fixture failures, backend clean.

- [x] **F164** **A program's function may shadow a builtin, which a `use`d module could always do.**
  (raised 2026-10-18 when F163 turned the suite red, answered *"c"* out of three options; M) Taking
  `count`, `sum`, `find` and `first` as builtin names broke three fixtures with *"'count' is a
  builtin function and cannot be redefined"*. The sweep that should have preceded the rename found
  the scale: **`count` is declared by fifteen files in this tree** -- five of them modules, which
  were allowed it, and ten of them programs, which were not.

  **The asymmetry was the finding.** `typecheck` runs on the root module only, so an imported
  module's functions never reached that check: the rule was "the main file may not", not "the
  language may not". The review chose to make the main file behave like a module rather than rename
  ten fixtures or give the four names back.

  **Three attempts, each wrong in its own way, and each found by running.** Dropping the error was
  not enough: every builtin arm runs *before* `find_function`, so a declared `count` was accepted
  and then unreachable by a bare call -- worse than the error it replaced. Jumping to the
  ordinary-call path was not enough either, because `find_function` answers the *first* declaration
  of a name, which for a shadowed name is the builtin's -- so the shadow list had to carry the
  declaration, not just the name. And registering it off a prior `builtin fn` declaration missed
  the **eleven dispatched builtins that have no declaration**, so `fn error_message(x: int)` was
  accepted and still routed to the arm; it keys off the dispatched names now, which is what the
  deleted check did.

  **The fourth problem was the dangerous one.** A shadow is global to the module, and the prelude's
  functions sit in that same list -- so a program declaring `fn len(x: string)` made every
  `len(...)` *inside lib/prelude.zm* resolve to it, and the prelude stopped type-checking. Shadowing
  is now visible only from program bodies. Found by trying the scariest case rather than the
  convenient one.

  **One argument in DESIGN.md dissolved with it.** That file used this reservation to explain why
  `add` could never be a builtin: it appears 14 times in the repo and promoting it would make every
  one a type error. That barrier is gone; what stands against `add` is the other half of its
  argument, about the verb reading as "hand it over, the collection decides".

  **Three more resolution paths surfaced only when the suite ran the fixtures I had not edited.**
  My per-fixture check covered the files `git status` listed, which is wrong for a change to name
  resolution -- the affected set is every file, and that mistake is what let each of these through
  a local "0 failures" twice in one block.

  *`spawn` resolves its callee itself*, in both passes, so `spawn count(path, out)` found the
  builtin's declaration and reported a void function as "returning int" -- and once the checker was
  fixed, the **interpreter** re-resolved by name and found the bodyless `builtin fn`, so the thread
  ran nothing at all and the program printed nothing. The statement now carries the checker's
  resolution, exactly as `EXPR_CALL` has carried `call_fn` for the same reason.

  *The dropped-result gate keys on the name*, so `count(opened)` -- a program's own `count` called
  for its effect -- was reported as a discarded pure builtin. It now ignores a shadowed name.

  *`map()` had its own diagnostic*, since reaching for the `Map` type by its lower-case name is a
  real first-day mistake. The arity complaint is now true as well, so the message gives both
  readings rather than burying the likelier one.

  Two fixtures changed sides -- `error_message_redefine_builtin_rejected` and
  `result_redefine_builtin_rejected` asserted the old error and now assert the shadow -- plus a new
  one pinning that the prelude keeps its own `len`, `fold` and `join` while a program shadows
  `count` and `sum`. The per-call cost is a walk of a list that is empty in every program that
  shadows nothing.
