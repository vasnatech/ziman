- [x] **F209** **`b[i]` on a builder stops being a call, and the last two prefixed element
  accesses go.** (follows F208; user-raised, "lets remove mutable_array_get and mutable_array_set
  from array.zm"; done 2026-10-21.) F149 made `b[i]` and `b[i] = value` work on a MutableArray by
  rewriting them into `mutable_array_get`/`mutable_array_set` calls, which is why those two names
  had to be declared, and why they were `pub` rather than `internal`: the frame a traceback prints
  is `fn->name`, so `b[5]` out of range printed `at mutable_array_get` for code that never wrote
  one, and hiding the declaration would have pointed a stack trace at a name `--api builtins`
  denied existed. **F208's entry gives that as the reason the two stay. It is a correct argument
  about the rewrite and the wrong conclusion** — the thing to remove was the rewrite.

  **A MutableArray is indexed now, not called.** `EXPR_INDEX` tells the two worlds apart by the
  value (an array holds its elements, a builder a handle) and reads through
  `ziman_mutable_array_index_get`. `STMT_INDEX_ASSIGN` becomes **the one statement kind that
  reaches the interpreter as itself**: the array half is still rewritten into the rebinding it
  stands for, which is what earns it the ordinary `val`/`var` diagnostic for free, and the builder
  half is evaluated where it stands. No frame, and the message loses a prefix that existed only to
  tell two function names apart: `index 5 out of bounds (MutableArray length 1)` beside an array's
  `index 5 out of bounds (array length 1)`. **F149 was about one syntax over two statements; the
  errors agree with the syntax now, which they did not while one of the two went through a
  function.**

  **139 call sites still spelled the access as a call** — 142 occurrences of the two names in
  `.zm` files less the two declarations and the one value-position reference in
  `generic_value_native_rejected`, counted as
  `git grep -h -o -E 'mutable_array_(get|set)[<(]' <before> -- '*.zm'` — F208's finding again, one layer
  on: `--api builtins` listing a name is not what teaches it, and the corpus was written before the
  sugar existed. Converted with a paren- and quote-aware pass run to a fixpoint, not a regex:
  `counts[b] = counts[b] + 1` is a `set` whose *value* holds a `get`, so one pass leaves the inner
  call behind. It refuses a base that is not an atom rather than inventing `(a + b)[i]`; nothing in
  the corpus needed that, and the only two refusals were the declarations themselves.

  **The old names answer with syntax, which needed a second table.** `renamed_builder_fn` is held
  by `tools/check_builtins.py` to naming a declaration that exists — F205's guard, added after four
  of its entries rotted — and `b[i]` is not a declaration, so putting the syntax answers there
  would have meant weakening the guard. `renamed_to_syntax` gets its own shape instead:
  *"'mutable_array_get' is gone — write 'b[i]' instead: element access is an index rather than a
  function, so there is no name left to offer."* `ab_get`/`ab_set` move there too, having pointed
  at `mutable_array_get`. (F211 gave each entry its own reason rather than one shared sentence,
  when `map_from_arrays` joined them with a different story.)

  **Two stale repair suggestions found beside the work.** Indexing a Set advised
  *"add with 's = set(s, value)'"*, writing one advised *"'s = insert(s, value)'"* — F199 made
  `add` the word in both set worlds and F206 made the checker refuse both spellings, so each
  message was telling the reader to write a type error. Same rot as F208's two vacuous name lists.

  Also moved: `generic_value_native_rejected` needed a new generic native and takes
  `mutable_array_filled`, the fixture having already been repointed once when `slice` became a
  builtin; `prelude_internal_still_callable` stops pinning an element access as a call;
  `lint_builder_array_read_in_place` and `lint_builder_snapshot_in_loop` record `b[i]` as the
  reader advice. 1,112 fixtures, `make check` exit 0 with the North Star.

  manual entries turn out to be the reason to.** (user-raised, "put overloaded functions close
  together"; done 2026-10-21.) The file header has claimed "each builder twin beside the immutable
  form it mirrors" since F203 split the prelude. **It was not true of most of the file**: the
  builder twins sat in one block of 220 lines at the end, two sections of prose away from their
  array forms, and 25 of the file's overload sets were split by between 76 and 594 lines. Each

  header names, carrying the rationale all the twins share — and `tools/gen_lib_manual.py` attaches

  `binary_search`, `flat_map` and the builder `sort_desc`/`sort_by_desc`. Pairing forces the
  question, because a twin moved out of the block takes nothing with it. The shared rationale is
  one paragraph in the header now and each twin says what is specific to it — usually the copy it
  saves, which differs per function and is the thing a reader wants.

  **Four comments had been written for a group of two and read wrongly once split.** The builder
  `sort`'s said *"ascending or descending. **These two** make two copies"* and the builder
  `sort_by`'s *"**The same two** by a computed key"*. Both now describe one function, and the

  in the array `sort_desc`'s *"not `array_sort`'s result reversed"* and one in the builder `sort`'s

  prelude files byte for byte before it was allowed to reorder anything, then by hand for the
  prose. `array.zm` is 969 lines and no set in it is split; `docs/lib/prelude.md` has **no blank

  organised by world rather than by name, so pairing them is a separate decision and not this one.
  1,112 fixtures, `make check` exit 0 with the North Star.

- [x] **F212** **`PURE_BUILTINS` was half-renamed, which was silently accepting thirteen discarded
  results — and the arm beside it was segfaulting on five names.** (user-raised, "fix
  PURE_BUILTINS too", following the note left in F211; done 2026-10-21.)

  **The list and the hole are the same rename, half-applied.** F195-F201 took the prefix off
  fourteen entries — `set_union` → `union`, `map_keys` → `keys`, `set_insert_all` → `add`,
  `map_remove_all` → `remove_all` and ten more — and **each rename left the old name in the list
  and added none of the new ones.** F211's note called the fourteen stale entries the defect; they
  are not. A call to a name that does not resolve fails earlier, so a stale entry can never match
  and costs nothing. **The missing thirteen were the bug**: `union(s1, s2)`, `intersect`,
  `difference`, `is_subset`, `items`, `keys`, `values`, `merge`, `get`, `get_or`, `filter`, `add`
  and `remove_all` were all accepted in statement position with their whole output thrown away,
  which is the single mistake this list exists to catch. Measured by probing each name rather than
  by reading, which is also how the direction of the error was found — I had it backwards.

  **Two names could not be listed until `#[effectful]` existed.** `add(s, items...)` and
  `remove_all` answer a bool *and* write the container, so the name alone would have refused "make
  sure these are in here". Their builder members carry the attribute now, which fixes the
  complementary wart recorded in F208: `add(mutableSet, x)` discarded had been a type error since
  F199, so `val _ = add(s, x)` was the spelling the corpus was forced into. Both directions of that
  name were wrong, in opposite ways.

  **The arm beside it was worse than stale.** `check_call` still accepted `mutable_set_union`,
  `mutable_set_intersect`, `mutable_set_difference`, `mutable_set_is_subset` and
  `mutable_map_set_all`, type-checking each against a real signature — and F195-F201 had removed
  their runtime dispatch, so each reached the interpreter as a builtin id no name maps to.
  **Four of the five segfaulted.** `mutable_set_is_subset` looked safe only because it answers a
  bool and the dropped-result gate refused the statement form before anything ran;
  `print(mutable_set_is_subset(ms, s))` crashed like the others. The arm is deleted and the five
  answer with their bare names. Third time an arm has been found keeping a spelling alive after
  the declarations retired it (F206, F208), and the first time the consequence was a crash. The
  five unreachable `B_mutable_set_*`/`B_mutable_map_set_all` ids and their dead disjuncts went too.

  **The guard is the point.** `tools/check_builtins.py` now holds every `PURE_BUILTINS` entry to
  being a name the interpreter dispatches or a name a rewrite records in `rewritten_from` (which
  is what makes `mutable` a legitimate entry). Proven by putting `set_union` and `map_keys` back
  and watching it fail. Half a rename cannot pass again — this is the third table in that file to
  get such a check, after `BUILTIN_NO_SIGNATURE` (F148) and `renamed_builder_fn` (F205).

  **`is_Some` and `is_None` were also removed, and leave a hole this records rather than hides.**
  `check_call` rewrites them into `Option.is_Some(o)` enum accesses, so by the time the gate looks
  the statement is not an `EXPR_CALL` and the entries could never match. Discarding one is still
  accepted. Closing it means teaching the gate about enum accesses, or giving that rewrite a
  `rewritten_from`; neither belongs in this pass.

  Two new fixtures (`discarded_pure_collection_result` pins all thirteen,
  `prefixed_set_ops_point_home` pins the five that crashed), `discard_overload_purity_allowed`
  extended for the two now-legitimate discards, and `docs/SYNTAX.md`'s last `mutable_map_set_all`
  reference is `merge`. 1,114 fixtures, `make check` exit 0 with the North Star.

  arm to delete**: `slice` never had one. Its type rule was already its two signatures and its
  diagnostics already derived from them, so all three messages are unchanged —
  *"'slice' expects [T] or MutableArray<T>, found int"*, *"argument 2 of 'slice' expects int,
  found string"*, *"no declaration of 'slice' takes 2 argument(s)"*. §11 named diagnostics as what
  gates these conversions; for this one there was nothing to lose.

  **Two of the usual payoffs did not apply, which is worth recording before the next candidate.**
  `slice` was in `BUILTINS_WITH_NAMED_ARGS`, so it already took named arguments, and the corpus
  already wrote `slice<byte>(buf, 0, n)` — a builtin with a declaration is not barred from either.
  The gain is that the resolver owns it, the id and its branch are gone, and purity is now per
  declaration rather than a name in `PURE_BUILTINS` (the entry is deleted; F212's new guard would
  have failed on it otherwise, since nothing dispatches `slice` any more).

  **The obstacle I expected was already solved.** `ziman_slice_array` returns a placeholder type and
  the arm overwrote it with `e->resolved_type`; a native cannot see the Expr. But the `call_fn` path
  already does exactly that fixup for any generic native
  (`fn->is_native && fn->type_params.count > 0`), so the two new shims needed no new
  implementation — they are three-argument wrappers over the functions the arm already called,
  registered as `array_slice` and `mutable_array_slice`.

  **Measured, because id dispatch is inline and a native call pushes a frame.** Interleaved runs of
  two binaries built from the same tree: on a loop whose body is nothing but `slice` + `len`,
  **+8% at 10M calls, about 8 ns a call**; on a real consumer (`tests/bench/bytes_bench.zm`),
  **-3.2%**, which is to say no difference the machine can resolve. The microbenchmark cost does
  not reach code that does anything with the window it takes. One new fixture
  (`slice_paired_declarations`). 1,116 fixtures, `make check` exit 0 with the North Star.

- [x] **F215** **array.zm has no `builtin fn` left: all nine become native declarations, and the
  conversion turns out to be *faster*.** (user-raised, "most builtin functions in array.zm can be
  native functions", then — after I put two back on measurement — "stop bringing builtin functions
  back. builtin approach is not scalable. That is why we added function overloading to ziman.";
  done 2026-10-21.) `make overload-sets-check` moves to **46 resolver-owned sets and 14 polymorphic
  builtins**, from 43/17. `to_set`, `to_mutable_set`, `narrow`, `swap` and the array halves of
  `push` and `insert` all follow `slice` (F214); `grep -c '^builtin fn' lib/prelude/array.zm` is 0.

  **I was wrong twice, and the user's direction was right both times.** First I converted `narrow`,
  hit a bad diagnostic, and reverted it rather than fixing the cause. Then I converted `swap`,
  measured 7–11% on `reverse`, and reverted that too. Both reverts were the local optimum and the
  wrong call: the id table is what does not scale, and trading a name back onto it to save 10% of
  one prelude loop is how the table reached seventy entries. Correcting course produced a better
  answer than either revert, for both problems.

  **The diagnostic was a real gap, and fixing it unblocks every name of that shape.** `narrow`'s
  only parameter is `MutableArray<T>`, so an array argument binds no `T` and inference failed with
  *"cannot infer type argument 'T' … write it explicitly"* — advice no `T` can satisfy.
  **`unify_type` leaves a top-level shape mismatch unreported by contract**, deferring to
  `check_value_against_param_type`, which runs only once every type argument is bound; when the
  mismatch is *why* one is unbound, nothing reported it. `shape_cannot_match` records the first such
  argument and the failure now blames it: *"argument 1 of 'narrow' expects MutableArray<T>, found
  [int]"*, with `#[when_unmatched]` appended — a single-declaration name never reaches the overload
  resolver that otherwise adds that line. The old message survives for a genuinely uninferable call
  (`mutable_array_new()`), where every argument fits and none mentions the parameter.

  **And the performance objection was mostly an artefact of the shim, not of native dispatch.**
  Interleaved runs of three binaries from one tree:

  | | builtin id | native | native + fast path |
  |---|---|---|---|
  | 2M `a = push(a, i)` (tip reuse) | 0.276 s | +67.8% | **−32.3%** |
  | 500k `insert(a, 2, x)` | 0.107 s | −23.6% | **−21.1%** |
  | 4M swaps via `reverse()` | 0.396 s | +10.9% | **+8.0%** |
  | 2M `slice<byte>` | 0.234 s | +1.2% | +5.0% |

  `push`'s +68% was **`collapse_variadic_args` allocating a one-element array on every call**, not
  the frame — `a = push(a, i)` with one value is how the array-building loop is always written. The
  builder half has skipped that since D18 (`ziman_mutable_array_push_one`); the array half now has
  its twin, and is then **a third faster than the builtin ever was**, because an id walks a chain of
  ~48 `else if` comparisons where a resolved `call_fn` is one pointer. `insert` is a fifth faster
  for the same reason. **Only `swap` is genuinely slower** (+8%: `reverse` is a loop whose body is
  nothing but the call), and rewriting `reverse` over `b[i]` is not the answer — that is 63% worse,
  three handle lookups against one.

  **The same mistake twice in one sitting: converting a name means deleting its arm, not only its
  id.** `to_mutable_set` shared an arm with the `$mutable_*_from` names; leaving it there while
  taking its id away made `items(to_mutable_set(xs))` **segfault**, because the arm answers before
  the resolver and `call_fn` stayed NULL. I wrote that lesson into a comment — and then restored
  `narrow`'s arm during the revert and segfaulted `narrow_mutable_array` the same way an hour later.
  `to_set` had no arm, which is why it worked first time.

  **F212's guard caught my own change twice.** Converting `swap` left `"swap"` in `PURE_BUILTINS`
  with nothing dispatching it; converting `push`/`insert` left them in the builtin roster with no
  `builtin fn` declaration. `make api-check` failed with exactly the messages those checks exist to
  give, one commit after they were written.

  `to_mutable_set`'s diagnostic improved by moving: the arm's *"needs an element type that supports
  '==' and hashing"* is the `T: Eq + Hash` bound now, which answers *"type argument Channel<int>
  does not satisfy bound 'Eq' required by type parameter 'T'"*. 1,116 fixtures, `make check` exit 0
  with the North Star.

- [x] **F217** **Derived queries: a repository function's name is its query, built from the design
  written the day before.** (user-raised, "lets resume our derived repository functions work";
  done 2026-10-28.)

  `#[repository]` on a bodyless `pub fn` now reads the function's own name against the module's
  `#![repository(Entity)]` entity and writes the body. `docs/design/derived-queries.md` was written
  2026-10-27 as design only; **§§1-8 needed no revision once they met the compiler**, which is the
  whole argument for settling the name grammar on paper first. The nine questions the
  implementation had to answer for itself are that document's new §10; the three that are about the
  language rather than about the feature are docs/DESIGN.md's 2026-10-28 entry.

  **The grammar, and the two refusals that are the point of it.** `verb [_by_ predicate]
  [_order_by_ ordering]`, where every column is a field of the entity; `find`/`count`/`exists`/
  `delete`; `between`/`in`/`not`/`is_null`/`is_not_null`/`ignore_case`. Cardinality comes from the
  return type and nowhere else, so there is no `_all`.

  * **Parameters bind by name.** After the connection they are the predicate's terms, named for
    their columns in that order, and the type is checked against the entity's field too. The same
    query written against a positional binder -- `findByIdAndPatientId(patientId, id)`, two UUIDs
    transposed -- compiles, boots and answers another patient's rows forever.
  * **Two readings of a name is a refusal, not a precedence rule.** The search enumerates every
    parse instead of taking the longest column at each position, so `find_by_name_and_type` against
    an entity that has `name`, `type` *and* `name_and_type` is refused showing both readings. It
    cannot fire on the sample backend's 36 entities (no column there contains `_and_`, `_in`,
    `_not`, `_between`, `_asc` or `_desc`); the point is the first schema where it can.

  Every refusal is checked from the `StructDecl` and the signature before any SQL exists, and
  reported at the function's own line -- which the design committed to in §6 after measuring the
  alternative during the `eql` adoption, where a real mistake arrived with three frames of library
  code and not one line of the repository that caused it.

  **Three structural things, each cheap and none predicted.** A derived query is the *author's*
  `FunctionDecl`, so there is nothing to splice at: `parse_and_splice_into` fills in its `body` and
  the declaration keeps its own position, name, parameters and return type. That makes §9's
  "splices at the module attribute's position" complaint structural rather than an argument to
  change -- and leaves the keyed CRUD rightly at the attribute, since those nine functions appear
  nowhere in the source. Its query val is **appended** where every other derived val is prepended,
  because it reads `<entity>_meta`, itself a prepended derived val when the entity is in the same
  module. And `fn_has_body` now asks whether the body is there rather than listing the kinds that
  never have one, because a derived query is the first bodyless kind that *acquires* a body -- the
  fix that function's own comment recommended for the next such kind.

  **Seventeen fixtures, twelve of them refusals.** One of the five that run,
  `cli_emit_derived_query`, asserts the generated text itself: one private `Translated` val per
  function, translated when the module loads, and the body that binds to it.
  1,280 fixtures, `make check` exit 0 with the North Star.

  unusable.

  derivable.** From `repository.not_found`'s own comment, written long before any of this:

  reader met the internal name. That is why it is an argument rather than derived from the

  never has to guess which argument is which. An unknown argument is refused by name.

  column and that column renders as text: `uuid.format` for a `Uuid`, `str` for a number, the
  string itself. **Deliberately not `format`**, which prints a struct as its fields

  Without the argument the entity's own name is the label, so `"Note not found: 42"`. The fallback
  changed too, because it is better than the first attempt's wording whether or not a project gives

- [x] **F232** **A template's context is a `Json` object: step 3 of the expression language, and

  budgeted "the five generators migrate mechanically and the fixtures prove the output is

  exactly one thing: **the new engine renders the same text**. Six generators, byte-identical,
  1,303 fixtures. The migration is now optional rather than owed.

  hold is already a `string`, which made "how is a number formatted" unaskable. It is askable now:

  missing word in generated code.

- [x] **F236** **ECDSA over P-256: the first asymmetric signing in the language.** (the primitive
  ES256 needs, and the one thing SMART Health Cards were blocked on; done 2026-10-29; M.)

  Everything `crypto` had was symmetric -- a MAC or a cipher under a shared key, where anyone who
  can check a signature can also make one. A verifiable credential needs the other thing, and
  `jwt` was HMAC-only (HS256/384/512) with no public-key signing anywhere in the module. Five
  natives on OpenSSL, which was already linked: `ecdsa_p256_generate`, `ecdsa_p256_public_pem`,
  `ecdsa_p256_public_point`, `ecdsa_p256_sign`, `ecdsa_p256_verify`.

  **Three decisions, each visible in a signature:**

  * **Keys are PEM text.** It is what `openssl ecparam` writes and what a deployment keeps in a
    file or a secret. A JWK is a `Json` object and belongs in Ziman, built from
    `ecdsa_p256_public_point` -- so the C holds no JSON and a JWK's spelling can change without
    touching it.
  * **A signature is raw `r || s`, 64 bytes, not DER**, because that is what JWS requires
    (RFC 7515 §3.3) and because the two cannot be confused: a DER signature's length varies with
    its integers, so a caller holding the wrong form finds out at the far end instead of at the
    call. The conversion both ways is done in the one place that knows both.
  * **`verify` answers a `bool`, not a `Result`.** A wrong signature, the wrong key, a malformed
    key and a signature of the wrong length all mean one thing -- these bytes are not to be
    trusted -- and a `Result` would invite distinguishing cases that must not change the decision.

  **The curve is checked rather than assumed.** A P-384 key signs happily and produces 96 bytes;
  taking the first 64 would be a valid-looking signature of nothing. A key on another curve is
  refused by name.

  **Interoperability was tested against an implementation that is not this one**, which is the
  only check that means anything here -- a round trip through my own code proves self-consistency
  and nothing else. Python's `cryptography` (46.0.7) loads ziman's PEM public key and verifies
  ziman's signature after converting `r || s` to DER, and refuses it against a tampered message;
  in the other direction ziman verified **200 signatures python made of one message, 2 of which
  had a short `r` or `s`** -- the leading-zero case a DER-to-raw conversion gets wrong by dropping
  the pad, and the reason the count is 200 rather than one.

  `tests/lang/crypto_ecdsa_p256` **generates its key pair rather than carrying one**: a committed
  PEM private key is a key in a public repository forever, however harmless, and generating also
  proves two of the five natives. It asserts what holds for every key -- a 64-byte signature, a
  verify that holds and three that must not, two signatures of one message differing (ECDSA is
  randomised, so a fixture asserting signature bytes would be asserting the nonce), a truncated
  signature refused, and a public point whose halves are a JWK's 43-character `x` and `y`.

  Next, and not in this entry: `jwt` ES256 on top of it, which needs its own entry point because
  `jwt.sign` is keyed on `[byte]` and an EC key is PEM text.

  longest 272**, every one a literal with nowhere to break.

  A `\` at the end of a line now continues a string literal onto the next. The pieces are joined
  **in the lexer**, end to end with nothing added, so the parser and the type checker see one
  `TOK_STRING_LIT` -- which is the whole point: a wrapped `format` string is legal and still
  checked.

  **The first design was bare adjacency -- two literals in a row are one string, as in C and
  Python -- and it was withdrawn after being tested against this repository's own code.** The
  user had chosen it on a comparison that said "the C footgun does not arrive", which was true
  only of two literals on *one* line. Then:

      val all_nine = ["insert", "update", "find", "find_or_error", "exists", "delete", "find_all",
                      "count_all", "delete_all"]

  Drop the comma after `"find_all"` and adjacency compiles it to a five-element array holding
  `"find_allcount_all"` -- a generator that emits eight CRUD functions and hunts for one nobody
  wrote. **That is a syntax error today**, and the newline restriction does not save it: a
  forgotten comma in a vertical list is exactly one newline apart, and a vertical list of strings
  is the commonest shape there is. A language that refuses an ambiguous derived-query name rather
  than resolving it by precedence should not accept a silent join here, so the fold is explicit and
  costs one character, paid by whoever wants it.

  **What it took**, which was more than the "one lexer rule" first estimated: the fold itself; a
  `\` case in the lexer that clears `prev_can_end_stmt` so the newline after it is swallowed (the
  mechanism a trailing comma already uses); a check in `emit`, the one place every non-string token
  goes through, for a continuation nothing followed; an end-of-file check; and **one rule in the
  formatter**, which has its own scanner and so sees the pieces rather than the folded literal --
  it indents a continuation one level past the line it continues, the same treatment a line ending
  in a binary operator gets, and it never re-joins or re-breaks them, because where a sentence
  breaks is a judgement about reading rather than about width.

  Five fixtures: `string_continuation` (the fold, a wrapped `format`, escapes at a seam, a comma
  still separating two elements, a continued text block) and four refusals, of which
  `string_continuation_missing_comma` is the one that pins what the `\` was chosen for.

  Adopted where it came from: `verb_returns` and one other constant `concat` are literals now, and
  **13 long literals were wrapped -- `derive_repository.zm` has no line over 120 columns left**.
  All 13 derived-query refusal fixtures still pass, which is what proves the messages are
  byte-identical.

- [x] **F239** **A named call that omits optional parameters cannot resolve against an overload
  set.** (found by F238; done 2026-10-30; S-M.)

  `jwt.verify_claims(token: t, key: k, now: n)` resolves while `verify_claims` is one declaration
  with five further `Option` parameters. Add a second declaration differing only in one
  parameter's type and **the call stops resolving at all** -- "no declaration of
  'jwt::verify_claims' takes 3 argument(s)", listing both candidates, each of which takes eight.
  The resolver is matching arity before names, so the omitted-`Option` rule that makes named calls
  pleasant is not applied per candidate.

  Worth fixing because the two features are each load-bearing here -- named calls with omitted
  options are how this library's wide functions stay readable (F167-F202's whole subject), and
  overloading on a key's type is what makes `jwt`'s families safe -- and they currently cannot be
  used together. The workaround in `jwt` is a second name (`verify_claims_pem`), which is a cost
  this would remove.

  **It was one line, and it was a bug rather than a design choice**, so it did not need the user
  after all. `ovl_arity_fits` -- step 2 of `overload_resolve`, which culls candidates before any
  type is compared -- read `argc == params.count`. Named calls already discriminated by type
  correctly; only this gate was wrong. It now takes a `named` flag and, for a named call, accepts
  `argc` between `ovl_min_named_arity` (the count of parameters that are not `Option<T>`, which is
  exactly what `canonicalize_named_args` fills in) and the parameter count. A *partial positional*
  call stays as strict as it ever was, and must: `f(1)` would otherwise go from choosing
  `f(a: int)` to ambiguous the moment an `f(a: int, b: Option<T>)` joined the set
  (`tests/lang/overload_partial_positional_still_rejected`).

  **Fixing the gate exposed that selection was name-blind**, which had been invisible because the
  gate refused these calls first. Steps 3 and 4 matched call position against *parameter* position,
  so `verify(key: 1, token: "t")` compared `1` against `token: string` and no declaration accepted
  it. `ovl_arg_param_index` now maps the two per candidate, and a declaration with no parameter of
  that name is dropped from the set -- the same judgement `canonicalize_named_args` makes as "has
  no parameter named 'x'", made early enough to narrow a set rather than be reported against
  whichever declaration happened to be chosen. That elimination is what lets the two `verify_claims`
  below tell themselves apart.

  **Two further messages had quietly assumed the old gate.** `overload_pick`'s "every candidate is
  short" branch inferred "every candidate is variadic" for free, since the variadic arm used to be
  the only one that kept a short candidate alive -- so `pick(a: 1)` against two
  `pick(a: int, b: Option<T>)` was told its last parameter was variadic and needed a value. And an
  ambiguity's escape, "name the argument to choose", is useless when what the candidates differ in
  is a parameter the call *left out*; it now looks for that parameter and asks for it by name
  (`tests/lang/overload_omitted_ambiguous_rejected`).

  **The `overload-sets-check` gate's notion did need looking at, and the answer was to leave it.**
  Probing from the named floor rather than the parameter count duly reported
  `validate.positive(value: Option<int>)` against `positive(value: Option<float>)`: `positive()`
  reaches both and has no argument left to choose by, so the invariant "every call can tell them
  apart" is now literally false for a set the library is built out of. Keeping the stricter probe
  would have forced four honestly-named `positive` declarations (F167-F202) to be renamed to
  satisfy a check. So the invariant is the narrower one it can keep -- every call *that gives its
  arguments* -- and an ambiguity only omission can reach is found by making the call, with the
  message above, not at the declaration.

  **F238's workaround is gone**, which is the point: `verify_claims_pem` is a second
  `verify_claims`, and the parameter a caller names chooses the family (`key:` the secret form,
  `public_key_pem:` the PEM one) exactly as the type does for the positional `verify`/`verify_at`
  pair. `tests/lang/jwt_es256` and `jwt_claims` produce byte-identical output across the rename.

  from `validate.Violation` to this application's `FieldError`: a library that answered `FieldError`
  would have the dependency upside down.

  `#[pattern(regex:)]` is the ninth attribute and arrives when something needs it (it did, in F251),
  but the *rule* is here already (`validate.matches`), `regex` being a bundled module. An unreadable
  pattern is a violation naming the pattern, not a crash.

  **Stage 5 followed the same day** (user-raised: "lets use validation on request types in
  backend-ziman"): **24 request structs** converted, with `accumulate` going from 37 call sites to
  3 and `optional_not_one_of` from 30 to 1. Three findings worth carrying:

  * **The shape that does not convert is a rule on something that is not a field.** Six query
    parameter checks stayed hand-written across four services. It is the only recurring leftover,
    and stage 4 had already shown it.
  * **Three rules are not facts about one field** -- a date against today, one field against
    another, an indexed element -- so `service.broken_rules` grew a sibling, `field_errors`, which
    answers the list rather than the `Option<ServiceError>`. Generated and hand-written violations
    then accumulate onto one list, and the client is still told about every field at once. The
    three want a `#[past]` attribute, a class-level constraint, and §6 cascading respectively.
  * **`message:` earned itself immediately.** Four password fields keep Spring's "size must be
    between 8 and 2147483647" -- the artefact §3 of the design argued against inheriting *by
    default*. Inheriting it **on purpose, visibly, in the attribute** is a different thing from a
    hand-written check that hides the decision, and the user chose it with both readings in front
    of them.

  And one rule was not the attribute it looked like: `register`'s password tested `== ""` rather
  than `is_blank`, so a password of spaces fell through to the length check. `#[not_empty]` with
  the message overridden, not `#[not_blank]` -- a difference the conversion only found because an
  attribute forces the question.

- [x] **F247** **`ziman test a.zm b.zm` fails when more than one file loads a deriving module.**
  (found 2026-10-29 while running the North Star's unit tests two files at a time; S.)

  `ziman test src/test/unit/service_test.zm src/test/unit/mapper_test.zm` reports

      module error: the generator for 'Json' failed: 'capacity$default$8' is read before it is
      initialised: module-level vals are initialised in file order, and this one is reached by an
      initialiser that runs earlier

  against a struct in a module the *second* file loads. Each file alone is fine, and swapping the
  order moves the error, so it is the second load that breaks: a synthesised default-argument val
  from the first program is still in scope when the second one's generated code is spliced.

  **It predates F246** -- it reproduces on the commit before it, on files that have nothing to do
  with validation -- and the North Star's own runner hides it by giving `ziman test` one file per
  invocation. Worth a fixture of two files run together.

  **It is not a curiosity: it blocks a `#[derive(..)]` declaration in `tests/stdlib/` entirely**
  (found 2026-10-30 adding `#[valid]`'s tests). `make lib-tests` -- which `make check-fast` runs --
  passes every file in that directory to one `ziman test`, so the first deriving struct there fails
  with `'capacity$default$16' is read before it is initialised`.

  **Fixed 2026-10-30 (user-raised: "fix F247"; S).** It was one slot holding two programs.

  `g_global_env` is a single static, and **the generator program is a program**: `load_generators`
  builds it once per process and initialises its globals through `ziman_init_module_globals`, which
  sets `g_global_env`. The next user program's `interpret_tests` replaces that slot. So deriving in
  the *second* file ran the cached generator's functions against the *first* file's env, where none
  of the generator's own module vals or parameter defaults exist -- hence a missing
  `capacity$default$N`, which is `mutable_array_new`'s omitted `capacity` hoisted to a module-level
  val by `param_default_key`.

  `ziman_call_in_module` already saved and restored `g_program` around a cross-program call. **It
  did not save the env**, and that is the whole bug. `Module` carries a `globals` field now, set by
  each of the three places a program's globals are built, and a call into a module runs against the
  env that module was initialised with.

  **That alone turned a clean error into a segfault**, which is worth recording: `gc_mark_interpreter_roots`
  roots the *current* `g_global_env` and nothing else, so the generator program's env was being
  collected the moment a user program started. Holding a pointer to it was worse than not having
  one. So `ziman_keep_globals` keeps the envs that outlive their program reachable, and the mark
  phase walks them -- two entries, because the only thing that needs it is the generator program.

  The regression test is `make lib-tests` itself: `tests/stdlib/validate_test.zm` carries two
  `#[derive(Validate)]` declarations now (`#[valid]`'s own tests, moved back from `tests/lang`),
  and the whole directory runs in one invocation -- **418 tests**, where the first deriving
  declaration used to fail the gate. The two- and three-file repros also pass under `--gc-stress`,
  which is the flag that would have found the collection bug on its own.

- [x] **F249** **The compiler stops reading what a field attribute means.** (user-raised
  2026-10-30: "lets fix pk and valid"; M.)

  Three reads, all gone:

  * **`#[pk]`, twice in `src/derive.c`.** A repository's imports were chosen by looping over fields
    whose `is_pk` was set -- the key's `to_sql` converter and the key type's own name -- and a
    derived query imported `uuid` for a `Uuid` *key*. Both are structural now: a converter for
    **every** field type, which is a superset of what the keys need, and the `uuid` import keyed on
    the field's **type**. That second comment used to say keying on `#[pk]` was "as close as a
    structural rule gets"; a type is closer, and it does not ask the compiler what an attribute
    means.
  * **`#[column]`, nowhere.** `Param.column_name` was already **write-only** -- the parser filled
    it, `ast.h` and `generators.c` both claimed `src/derive.c` read it, and nothing did. `eql` does
    that work in Ziman off `meta.Field.attrs`.
  * **`#[valid]`, in `check_cascade_targets`.** It read the attribute off each field, walked the
    type to the nested struct and required `<snake>_violations` in scope. That bought a better
    message -- "add derive(Validate) to 'Plain'" -- at the price of the compiler knowing what a
    field attribute means, and it was the newest of the three, added the same day. Deleted, with
    the trade written into the fixture: what is left names the file, the declaration, the generator
    and the missing function, and is the same report any generator gets for any unresolved call.
    The good message returns for free when a generator can declare the names its output needs
    (user-generators.md §5b).

  **`Param` carries nothing but the generic list now**, and the only field-attribute names left in
  `src/` are the eleven in `FIELD_ATTRS` -- the *grammar*, which is what §5a makes extensible. A
  grep for any of them outside that table finds three unrelated hits (`math.min`, and `len`/`size`
  in two did-you-mean suggestions).

  `serve.zm`, the module that loads `routes.zm` and with it most of the application. **About a third
