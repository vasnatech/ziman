# F355 — a button is not a row tall

Done 2026-11-27. `lib/ui/controls.zm`, one test added.

Reported by the health-record port's owner, looking at the window: **"datepicker select and cancel
buttons can have shorter height."** They could, by twelve points, and the twelve points had a
name.

## What it was

`foot_in` reserved the band under the grid like this:

```ziman
return row_height(f.metrics, f.style) + f.style.padding.top + f.style.padding.bottom + calendar_pad(f)
```

and `foot_boxes` handed `foot_in - calendar_pad` to each of the two buttons as its height.

**`row_height` is a list's measure, not a control's.** It is `line_for(body) + Style.row_air`, and
`row_air` exists so that a line of a list, a tree or a table is readable down a column —
[F343](f343.md) added it and [F349](f349.md) is the whole story of what happens when the wrong
thing asks for it. A button has nothing to do with that scale: `button_inside` lays
`padded_for(style)` around a label and that is its entire height.

So the calendar's two buttons stood `row_air` taller than every other button in the same window.
In the health-record look that is **twelve points**, and the dialog those buttons sit inside draws
its own `Save` and `Cancel` at the shorter height — two pairs of buttons, one window, one of them
wrong.

## The fix

```ziman
fn button_tall(f: Frame) -> float {
    val pad = padded_for(f.style)
    return line_for(f.metrics, f.style.text.label) + pad.top + pad.bottom
}
```

and `foot_in` is `button_tall(f) + calendar_pad(f)`.

**The same arithmetic `button_inside` does**, deliberately: this answers what a button measures
rather than predicting it. `padded_for` rather than `style.padding`, so a look that reserves a
focus ring is counted the way a real button counts it — the old line read `style.padding`
directly and would have been short by two rings in such a look, which is a second defect that
never showed because this application's `reserve_of` is zero.

**The popup got shorter and now opens downward where it used to open upward**, because
`calendar_box` flips above the field when there is not room below. That is the fix working, not a
second change.

## Watched fail

`a_calendars_footer_buttons_are_exactly_a_button_tall` measures the laid `due/cancel` and
`due/select` against `widget.measure` of a real `button_widget`. Confirmed by putting
`row_height` back: **red**, "actual is not within 0.001 of expected".

**Measured against a button rather than against a number**, which is
`a_toggle_group_is_exactly_a_button_tall`'s rule ([F352](f352.md)) and the reason it is one: a
test carrying its own copy of the arithmetic goes on agreeing with itself while the two drift
apart.

## The pattern this is the third of

[F349](f349.md), [F352](f352.md) and this one are the same defect three times: **a height derived
from the wrong scale.** A combo box took a list's row air; a segment gave up a step it did not
have; a footer button asked for a row. Each was reported as one control looking wrong beside
another, and in each the fix was to make the control ask for the thing it actually is.
