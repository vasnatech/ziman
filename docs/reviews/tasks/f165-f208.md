- [x] **F166** **`sort_by`/`sort_by_desc` replace `sort_by_keys`/`_desc`.** (raised 2026-10-19 from
  Group C, answered *"add sort_by and sort_by_desc, remove sort_by_keys"*; S) The key-array form
  asked the caller to build the keys itself and then took **two** sequences, which is why Group C
  could not pair it: first-argument dispatch cannot choose among four world combinations when two
  of the arguments are collections. One sequence and a key function is the shape `group_by`,
  `index_by`, `min_by` and `max_by` already dispatch on, so the replacement pairs for free -- four
  declarations, two array bodies, two in-place twins, one dispatch-table entry each.

  **The name and the bound came from the family, not the proposal.** The signature arrived as
  `sort_by<T, F>(items, mapper: fn(T) -> F)`; the four existing `_by` builtins all spell it
  `<T, K: Ord>(a, key: fn(T) -> K)`, and `F` carried no bound at all, which would have let a key
  type with no order through the declaration and failed inside `array_order_of` instead.

  **It found a hand-rolled copy of itself.** `lib/http/client.zm`'s `sort_matches` built an `[int]`
  of path lengths into a builder, snapshotted it and called `permute(cookies,
  sort_scalar_order(...))` -- which is exactly what `sort_by_desc` expands to for an int key, down
  to the same single permute and the same native sort. Six lines became one. The two `migrate.zm`
  callers lost their `versions` array the same way. That is the third hand-rolled builtin this
  review has found, after `join` and `contains`.

  **`inverse` cannot cover the descending form.** It flips an `fn(T, T) -> int`; a key extractor is
  not one, so `sort_by_desc` is its own name rather than `sort_by(xs, inverse(key))`.

  **Two tests were deleted, not ported.** `sort_by_keys_length_mismatch_rejected` and its `_desc`
  twin covered the fatal mismatch between `items` and `keys` that P2-4 made fatal (see DESIGN.md's
  "Programmer errors are fatal"). With the keys computed by `array_map` from the items themselves,
  a mismatch is no longer a bug a caller can write -- the condition is structurally gone, so the
  fixtures went with it rather than being kept green against nothing.

  **Fixed in passing:** the `inverse` doc comment had been spliced into the middle of
  `array_sort_with`'s, leaving `array_sort_with` undocumented and `inverse`'s text attached to the
  wrong function; `array_sort_indices`'s comment claimed "`sort` and `sort_by_keys` are built on
  this" when `array_sort` reaches `sort_positions` directly; and SYNTAX.md's bare-array list still
  named `array_join`, deleted in F162.

  **Still unused after this:** `sort_indices`/`_desc` have no caller outside the prelude. They are
  the Group C item left standing, and the one place in the tree that genuinely wanted a permutation
  (`sort_matches`) reached past them to `sort_scalar_order` and is now a `sort_by_desc` call.

- [x] **F170** **Group D, the two renames: `array_present` -> `filter_present`, `iter_of_array` ->
  `iter`.** (raised 2026-10-19 from Group D; S) Neither is a pairing change -- both are names that
  were answering a question nobody asked.

  **`array_present` -> `filter_present`.** The `array_` prefix means "this is the immutable
  world's spelling" everywhere else it appears, and the other world's name sits beside it. Here
  there is no other world: the argument is a *variadic* `Option<T>`, a written-out list of maybes,
  so the prefix named a world the argument could not have come from. `filter_` says what it does
  and puts it next to `filter`, where a reader looking for "keep some of these" already is. This
  also empties the "still said with the prefix" list down to `array_order_of` alone.

  **`iter_of_array` -> `iter`.** The argument already says what the source is, the way `to_set` is
  named for its result; `iter_from` beside it is the other constructor, so the family reads
  `iter(array)` against `iter_from(next, close)`. The "cannot take a builder" rule is unchanged
  and is now stated on the declaration itself rather than only in Group A's comment: the `Iter`
  outlives the call, so a handle's contents could move underneath it, and `iter(snapshot(b))` is
  the builder route with the copy being the point rather than a cost to remove.

  **The rename inverted a fixture's premise, which is the interesting part.**
  `diag_method_hint_unknown_name` exists because of F92: a benchmark run wrote `a.iter()`, was
  answered `e.g. iter(a, ...)`, and there was no `iter`, so it spent 194 compiler invocations
  concluding `Iter<T>` was unreachable. The fixture pinned that the hint now *names the absence*
  for a name the prelude does not have. After this rename `iter` is a prelude function and that
  exact hint is correct advice -- so the fixture's own example had become the opposite of what it
  tests. A blind rename left its comment reading "there is no `iter` ... when `iter` exists".
  `a.collect()` carries the absent half now (still iterator vocabulary, still not a function, not
  one of F28's seven hand-mapped names), and `a.iter()` stays to pin the other half, which the
  fixture's comment always claimed to cover and did not. DESIGN.md's account of the same wave got
  a note for the same reason -- it said "there is no `iter`" in the present tense.

  **The dated benchmark runs were left alone.** `docs/reviews/benchmark/runs/*` still say
  `iter_of_array`, because they record what a model wrote on 2026-10-12 and editing them would
  falsify the record. Nothing compiles them -- `benchmark-check` and the `--fmt` gate both read
  `reference/` only, which was renamed.

  **F168's gate took its second customer:** `array_present` and `iter_of_array` added to the

  the rest did not, each in order. Shaped after `filter_present` exactly -- variadic, with an
  array in hand going in as `filter_ok<T, E>(items: existing)`.

  **This is a capability addition, not a de-duplication, and the corpus says so.** The tree holds
  exactly **one** `[Result<T, E>]` and it is an empty-array placeholder (`lib/core/csv.zm:437`).
  Of the `if Ok(..) =` / `if Err(..) =` sites, all but one are early-return propagation, which
  these two deliberately do not do. The single collection-shaped caller,
  `lib/http/http.zm`'s `quality`, was **left alone on purpose**: it is a fold with a filter, not a
  plain collect, so `filter_ok` would allocate an intermediate array the loop does not. F166 found
  a hand-rolled `sort_by_desc` and deleted six lines; there is no such find here, and saying so is
  more useful than manufacturing one.

  built one -- which is the argument *for* adding them, but it is an argument, not evidence.)

  **Both type arguments are written on every call** even though each function answers only one of
  them: `Result<T, E>` names both, Ziman infers neither, so `filter_ok<int, string>(..)` is `[int]`
  and `filter_err<int, string>(..)` is `[string]` over the identical input.

  **`pub`, which in `lib/prelude.zm` means only "`--api builtins` lists it"** -- the prelude is
  merged into every program, so visibility never gated calling. `result_to_option` and
  `option_to_result`, the closest siblings these two have, already carry it for exactly that
  reason, so this follows the file's own convention rather than inventing one. **`filter_present`
  was missing it** and is now marked too: it was one of the 21 prelude functions a reader asking
  "what exists" cannot see, and shipping a three-member family with one member invisible is worse
  than either consistent answer. The other 18 are their own task -- and this confirms the fix for
  them is one word per declaration, not a change to `src/main.c`'s condition, which would also
  list the 50 rewrite targets and put `array_fold` beside `fold`.

  **Not propagating is the point and the risk**, and the doc comment says so rather than leaving a
  reader to find out: `filter_ok` silently discards every failure. It is for a bad `Accept` range

  reports what was lost.

- [x] **F172** **Group D3/D4: the five natives behind the sorts are `internal`, and `internal` in
  the prelude now means "reachable but not advertised".** (raised 2026-10-19 from Group D, done
  2026-10-19.) `is_sortable_scalars`, `sort_scalar_order`, `sort_scalars`, `permute` and
  `sort_positions` were listed by `ziman --api builtins` and offered by the editor, under a block
  comment that told the reader to call something else instead. Neither half was a decision:
  `fn_is_global_vocabulary` is `is_native || is_builtin`, so a `native fn` was advertised by the
  mechanism alone with no way to say otherwise, and the comment had rotted in three places around
  it -- it named `collections` (deleted in F120), `array_sort`/`array_map` (renamed in F162-F166)
  and "the database drivers", which never called any of the five.

  **Measured first, which changed the mechanism.** The plan was to make `pub` the marker for a
  `native fn` too. Two findings killed it: that would have meant adding `pub` to **238**
  declarations in order to hide five, and `fn_is_global_vocabulary`'s *other* caller is
  `loader.c`'s `prelude_has_function`, which answers "is there such a function" for the
  method-syntax hint -- so the same edit would have made `xs.sort_positions()` reply that no such
  function exists. That is the F92 trap, which F170 sprang once already in this same group.

  **So the two questions were separated instead.** `fn_is_advertised` (ast.h, beside the predicate
  it is deliberately not) is `visibility != VIS_INTERNAL`; `--api builtins` and `lsp.c`'s
  `build_globals` consult it, `loader.c` keeps consulting reachability. Nothing about the
  language's visibility system changed -- `internal` already existed as a soft keyword, and it
  already parsed before `native fn`. 245 listed names became 240, the diagnostic still names
  `sort_positions(xs, ...)`, and all five still run.

  **Two things found on the way.** `src/main.c`'s comment claimed "the prelude's own non-pub
  helpers are not callable from a program", which is false -- the prelude is merged into every
  program, so `pub` there has only ever meant "`--api builtins` lists it" (F171 established this
  experimentally; the comment is now corrected and SYNTAX.md states the rule). And the generated
  `docs/lib/prelude.md` had been filing `array_map` and the rest of the bare array helpers under
  "Used by the bundled modules", because that block's own header is a doc comment rather than a
  `// ----` banner; hiding the five made it visible, and the missing banner was added.

  **`array_order_of` stays a plain non-pub `fn`, and that is now a decision rather than a
  leftover** (user, 2026-10-19, asked immediately after this landed). It is the one piece of this
  a caller might plausibly want -- the permutation-of-keys seam, generic over the key type -- so
  the question was whether to make it the single advertised name in the area. Three things
  against, and the third is the one that settled it:

  1. Advertising it would publish its doc comment, which `--api builtins` prints beside the
     signature, and that comment names four functions the same listing now refuses to show --
     with "Feed the result to `permute`" as an instruction to call one of them. So it was never
     the one-word change it looked like.
  2. `array_order_of` returns `[int]`, and after this change the only advertised thing a caller
     can do with an index array is subscript by hand. `permute` is the consumer, and it is
     `internal`. Publishing a producer whose consumer is hidden hands the reader a value with
     nowhere to take it.
  3. `sort_by`/`sort_by_desc` exist precisely so that nobody holds the index array. There is no
     call site in the repo or the North Star that wants one. The gap would be hypothetical.

  Reopening it means publishing `permute` alongside, as a decorate-sort-permute **pair**, and the
  trigger would be a real call site that needs "order array A by array B's keys" -- something
  `sort_by` genuinely cannot express. Until then the sort family's public face is `sort`,
  `sort_desc`, `sort_with`, `sort_by`, `sort_by_desc`, which is complete and dangles nothing.

  **The generated manual needed a sweep this exposed.** `docs/lib/prelude.md` includes every
  declaration that is not `internal` -- a third rule, distinct from both `--api builtins` and the
  editor's list -- so hiding the five left six prose references in it pointing at entries the page
  no longer has. Fixed at the source: the implementation detail moved out of the three doc
  comments into the function bodies, where the call it describes is one line away. One reference
  remains on purpose, in the note above explaining that reopening the question means publishing
  `permute` too.

- [x] **F174** **A design document for overloading available to a declaration.**
  (raised 2026-10-19 by the user, after asking for the AI perspective on doing the work before a
  Map/Set pass; done 2026-10-19.) `docs/design/first-argument-overloading.md`, 304 lines. **Design
  only — nothing is built, and the document does not argue for starting**, which is the ROADMAP
  entry's own stance and the habit that declined `..=`.

  **Its one real finding, which was not known when the ROADMAP entry was written:** measured by
  script against `lib/prelude.zm` at `6a69848`, the proposed rule — *"may share a name when they
  differ in the first parameter's type"* — **covers 43 of the 50 existing sets, not all of them.**
  Five (`mutable_set_union`, `_intersect`, `_difference`, `_is_subset`, `mutable_map_set_all`) have
  the *same* first parameter and are chosen by argument two. `concat` has both that problem and a
  worse one: its one-argument spread rule reinterprets the same argument type by arity, which no
  per-parameter signature can state. `mutable` has a `(item: T)` arm matching everything its three
  siblings match, needing the specificity ranking the rule forbids. So the rule as written would
  reject seven sets the language ships today. The document proposes argument one then argument
  two, covering 48, with `concat` and `mutable` staying documented arms.

  **Two measurements taken along the way, both recorded in the document.** Purity is keyed per
  *name* in `PURE_BUILTINS` and the builder case is excluded by a **proxy** — `t.kind != TY_VOID`
  in the discard check (`typecheck.c:5975`) — which works only because every builder overload
  happens to return void; the comment there already records two bugs it caused. And
  `BUILTINS_NO_NAMED_ARGS` has **128 entries for 99 distinct names**, 29 listed twice because a
  paired name had to be written once per world, with consumers deduping. Both are symptoms of
  name-keyed tables modelling a set-keyed world.

  The document stages the work so stages 1-5 are refactors with an observable invariant (corpus,

- [x] **F175** **Design doc rewritten for *full* overloading.** (raised 2026-10-19 by the user —
  *"lets do full overloading"*, with the candidate-list rule *"show the signature of 3 or 5 and
  add '{n} more'"*; done 2026-10-19.) `docs/design/full-overloading.md` supersedes
  `first-argument-overloading.md`, which is kept and marked, because its §3 is the measurement
  that forced the choice: the first-parameter rule covered 43 of the 50 existing sets and would
  have rejected five the language ships.

  **I argued against full resolution and was wrong about the reason.** The objection was that it
  is circular — `expr_needs_expected_type` (`typecheck.c:2313`) names five kinds of expression
  that cannot be typed until something says what is expected, and they are exactly what collection
  calls carry (a lambda, `[]`, `ok(...)`, a bare `Some`, a value block). Picking an overload seemed
  to need argument types that need the overload. **The code already disproves it.**
  `infer_call_type_args` (`:2455`) solves the identical problem for C3 type-argument inference: it
  walks the arguments, skips every one that predicate flags, types the rest and unifies. Overload
  resolution reuses the same partition. No speculative checking, no backtracking, no undo log over
  the 24 AST-rewrite sites, no constraint solver — a filter, not a search. The architecture cost I
  quoted was for a design nobody needed.

  **What carries the positions the filter cannot type:** their *shape*, which is syntax and free
  to read. A lambda's arity separates `fold(a, init, fn(acc, x))` from `map(a, fn(x))`; `[]` is an
  array and never a `string` or a builder; `ok(x)` is a `Result`; `Some(x)` an `Option`.

  **The empty-literal exception survives by construction** rather than by care: `[]` is
  context-dependent, so it is never checked during resolution, and the `WORLD_PAIRED` comment's
  recorded regression (checking argument one eagerly made `first<int>([])` and
  `map<int, int>([], f)` errors they had not been) cannot come back through this path.

  **Candidate lists are truncated to the user's rule:** five or fewer print in full, more than five
  print three and `… and {n} more`, with the three ranked by how many argument positions they
  matched before elimination so the list is relevance-ordered and deterministic. `len` and
  `contains` have nine members each, so this is not hypothetical.

  Still rejected at the declaration, and keeping their arms: **`mutable`** (a `(item: T)` member
  matching everything its three siblings match — no specificity ranking means no ordering exists)
  and **`concat`** (its one-argument spread rule reinterprets the same argument type by arity,
  which no per-parameter signature states). Stage 2 of the plan is the check that must reject
  exactly those two and nothing else; a third rejection means the design is wrong.

- [x] **F176** **Full overloading, stage 1: the resolver, running beside the arms.**
  (`docs/design/full-overloading.md` §7 stage 1; done 2026-10-19.) The new resolver is built and
  wired, decides nothing, and is gated. `ZIMAN_OVERLOAD_SHADOW=1` makes it answer every dispatched
  call alongside the hand-written arm and report where the two differ; without it nothing in the
  compiler, the LSP or `make check`'s other targets behaves differently.

  **Result: 1372 files, 661 dispatched calls, 661 agreed, 0 disagreed** — fixtures, the 50
  benchmark references, all of `lib/`, and the North Star backend.

  **The design's central claim held.** Resolution is a filter, not a search: `overload_resolve`
  types only the arguments `expr_needs_expected_type` says can be typed alone, reads the
  syntactic *shape* of the rest (a lambda's arity, `[]` being an array, `ok(x)` a Result,
  `Some(x)` an Option), and never checks an argument speculatively. So it needed no undo log over
  the 24 AST-rewrite sites and no constraint solver, which is what made it safe to run as a shadow
  pass at all — a search would have mutated the tree it was supposed to be observing.

  **One genuinely new piece of logic:** `param_accepts`, a non-fatal matcher. `unify_type` could
  not be reused — it is a *binder*, and on a kind mismatch it returns silently rather than
  reporting failure, which is right for inference and useless as a filter. `type_equals` has no
  notion of a type variable standing for something. `param_accepts` mirrors `type_equals` case for
  case so the two cannot drift.

  **The first run reported 400 disagreements, every one of them the harness.** The arm names an
  implementation (`array_map`); the resolver names a declaration (`builtin fn map(a: [T], ...)`).
  They were never going to be the same string. What has to agree is the *world*, which the arm
  reads from the argument and the resolver from the chosen declaration's own first parameter —
  and on that they agreed everywhere, including the `MutableArray` cases. Comparing raw names
  would have made stage 1 look like a failure and sent the next stage chasing nothing.

  **The gate asserts a positive, not an absence.** A run that observes zero calls prints no
  complaints and would pass a naive check, which is exactly what a mis-wired hook looks like — so

- [x] **F177** **Full overloading, stage 2: declaration-site checking.** (`docs/design/full-overloading.md`
  §4 and §7 stage 2; done 2026-10-19.) Two members of an overload set are *indistinguishable* when
  their arities overlap and, at every position inside that overlap, their parameter types accept
  some common type. Such a set cannot be resolved by any call, so it is a defect in the
  declarations rather than a surprise at the first ambiguous call site.

  **The prediction held: 50 sets, 48 resolvable, exactly `concat` and `mutable` not.** Same answer
  from the fixtures, every `lib/` module and the North Star backend — none of which adds a set of
  its own, overloading not being available to library code until stage 7.

  **But the design had `concat`'s reason wrong, and the real one generalises.** The document said
  `concat` fails because its one-argument spread rule reinterprets an argument by arity, which no
  signature states. True, and not what the check found. `concat` fails at **the arity where a
  variadic tail is empty**: `concat()` cannot choose between `variadic string` and `variadic [T]`
  because there is no argument to look at, and `concat(b)` cannot choose between the two
  `(b: MutableArray<T>, parts: variadic ...)` members because the position that separates them is
  in a tail that is not there. **Two members whose fixed prefixes are identical always collide at
  their minimum arity** — a general rule about variadic overloads that any future set will hit,
  not a fact about `concat`. §4 now says both, in that order.

  `mutable<T>(item: T)`, the catch-all that matches whatever its siblings match.

- [x] **F187** **Stage 8 step 2: `#[when_unmatched("...")]`.** (done 2026-10-19.) The per-set hint
  F186 established was necessary: one extra line on the error a call gets when it matches no
  member of an overload set, carrying what the declarations cannot.

  **It needed no new grammar.** `#[deprecated("...")]` already takes a string argument at exactly
  this position, and the formatter already round-trips an attribute with one — checked before
  writing any of it, since a formatter that dropped the attribute would have been found by
  `fmt-check` and not by me. So this is a new *name*, parsed beside `deprecated`, stored on

  first.

  case: there the message is optional decoration, here it is the entire content, so

  because stage 7 opened overloading to program code. The mechanism therefore has a real user and
  real fixtures *before* any builtin is converted, so step 3 can check each conversion against a
  message that already works rather than against one invented alongside it.
