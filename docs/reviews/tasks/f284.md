# F284 — the scroll bar

Raised 2026-11-12 by `curly gui`, which scrolls in three places and shows it in none: the request
tree, the response text area and a long list all move under the wheel with nothing on screen
saying there is more, or where in it you are.

- [x] **F284** **A scroll bar.** (M; `lib/ui/controls.zm`. Geometry, gestures and a painter.
  **Every viewport now shows one; dragging one is still open** — see "what is left" at the end.)

  **Done: `controls.ScrollBar`, `thumb_of`, `scroll_bar_input`, `scroll_bar_widget`.** 16 unit
  tests, one bus check, three mutations.

  **A view of someone else's offset, not the owner of one.** The offset lives in the control that
  scrolls -- a `List`, a `Tree`, an `Entry` -- and a bar keeping its own copy is two numbers that
  can disagree about one thing. The bar holds only what nothing else does: whether a drag is in
  progress and where the thumb was taken hold of.

  **One `thumb_of`, used by the widget and by every gesture.** A bar drawn by one calculation and
  dragged by another jumps under the pointer; the test for it reads the thumb's box out of the
  laid tree and presses at its own middle. The drag keeps the point the thumb was grabbed at,
  which is the single thing a hand-written scrollbar gets wrong -- grab its middle and it should
  not leap so that its middle is under the pointer.

  **Not a tab stop**, which every platform agrees on, and the reason it publishes no value: the
  content takes the focus and its arrows scroll it. A reader walks rows that this layer publishes
  whether or not they are scrolled into view, so the bar is an affordance for the eye. The one
  check in the a11y fixture is that the node exists and `focus` does not offer it.

  A mutation worth keeping: removing the second clamp on the thumb's length -- the one that stops
  the twenty-point floor exceeding a shorter track -- was caught by **nothing**, because every
  test used a track of a hundred points. A bar beside a two-row list is fifteen points tall, which
  is now a test.

  ## Not done: how a control gets one, and why the obvious way is out

  A thumb's size is the view's share of the content, so a bar needs the **view extent** -- and
  nothing knows that until the layout has run. The obvious answer is to lay the window out, read
  the extent, and lay it out again with the bar; `curly gui` already does exactly that for an open
  dropdown.

  **Measured, and it is not affordable.** One layout pass of a tree in a 280x640 sidebar:

  | rows | building the widget | one layout pass | per frame |
  | --- | --- | --- | --- |
  | 50 | 0.4 ms | 1.5 ms | 1.9 ms |
  | 200 | 1.3 ms | 5.1 ms | 6.3 ms |
  | 1000 | 8.4 ms | 34 ms | 43 ms |

  So a second unconditional pass doubles the cost of every frame, and at a thousand rows it is the
  frame twice over. **The last column is its own finding and a bigger one than this task**: F270
  spent fourteen instalments getting a regional repaint to 0.7-1.0 ms, and the build-and-lay-out
  that precedes it costs 6.3 ms at 200 rows and 43 ms at 1000 -- under 25 frames a second from
  layout alone, before a pixel is drawn. `curly gui` pays it on every frame, because F271 chose a
  pure tree rebuilt each time and `damage_between` skips the *painting*, not the layout.

  Three ways out, none of them taken yet:

  1. **The control remembers the extent it was last told.** `tree_input` and `list_input` are
     handed `bounds` on every input, so a control could keep it. Wrong after a resize, which
     produces no input to the control -- the thumb would stay sized for the old window until the
     user touched it.
  2. **The control owns its bar in its own box**, laying out a row of viewport and bar. This is
     what every toolkit does, and it does not help: the widget is built *before* layout, so it
     still has no extent to size a thumb with.
  3. **A post-layout pass paints the bars**, as `widget.paint_focused` already paints the focus
     ring -- the proven pattern here for something that cannot be known at widget-build time, and
     the only one of the three that is exact and costs no second layout. A scroll node already
     carries its offset in the laid tree, so the pass has both extents. The gestures stay where
     they are; what moves is only the drawing.

  (3) is what was built, as `controls.paint_scroll_bars` -- a pass over the laid tree where all
  three numbers simply are: a viewport's own box is the view, the box its child was placed in is
  the content, and `Viewport.offset_y` is where it sits. No second layout, nothing to reserve, and
  uniform over every viewport in a window rather than per control. It lives in `controls` rather
  than `widget` because it needs `thumb_of` and a `Style`.

  **An indicator, not a control**: it says there is more and where you are, and the wheel and the
  arrows are what move it. Dragging needs the bar to have a box a press can be routed to, which
  means a scrolled control reserving a gutter in its own layout -- still open, and
  `scroll_bar_input` is written and tested for when it is done.

  ## What it found on the first frame

  **A wheel over a list's row had never reached the list.** `target` routed a wheel with
  `focus.control_at`, the *innermost* control -- which for a list or a tree is a `part_of`, a thing
  no application holds a state for -- so the name matched no branch and the input was dropped. A
  press has always resolved to the nearest tab stop instead, and `focus.clicked`'s own comment says
  why; the wheel wanted the same answer and got the other one. **Every list and every tree ever
  built here has had a dead wheel**, and the reason nobody noticed is that there was nothing on
  screen to notice it *with*. The indicator sat still over a 200-row sidebar, which is the first
  time the absence was visible.

  ## What the measurement led to instead

  Going after the per-frame cost rather than the bar found two things, both bigger than it.

  **An idle window was not idle.** `repaint` skips a scene that has not changed, and `curly gui`'s
  loop said in a comment that an idle window therefore "costs this sleep and a poll" -- while
  everything *before* the repaint ran anyway, sixty times a second. Over 200 saved requests an
  idle window burned **66% of a core**; over the seven-request demo collection it was 0%, which is
  why nobody had seen it. Building the frame only when something changed it took the 200-request
  window to 0%. (curly 0a1ed94.)

  **Layout built a path string for every node, and `a11y` was the only reader.** `Laid.path` was
  the slash-separated position, used to key an *unnamed* node in an accessibility tree -- so it
  was constructed for every node of every layout and read by almost none. The profile put 9.7% in
  `join_path` and its `concat`, besides the garbage two allocations per node make. `Laid.index` is
  an int now and `a11y` joins the indices as it walks, which reproduces the same paths exactly
  because every walk it does descends through real children. **1.17x**, measured interleaved,
  three passes each.

  ## Still open, and bigger than either: layout is O(n x depth)

  `place_stack` measures each child to find its natural size and then recurses into it, and the
  recursion measures again one level down -- so every node is measured once per ancestor. The same
  200 leaves, wrapped in nested columns:

  | depth | one layout pass |
  | --- | --- |
  | 1 | 1.5 ms |
  | 4 | 2.3 ms |
  | 16 | 5.1 ms |
  | 64 | 19.7 ms |

  Linear in depth with the leaf count fixed, which is the signature of measuring the same subtree
  from every level above it. A real window is six to ten deep, so this is a factor of two or three
  today rather than thirteen -- but it is the shape of the remaining cost, and no amount of making
  `measure` cheaper changes the exponent. The fix is a box model that measures bottom-up once and
  hands the sizes to the placing pass, which is a rewrite of `widget.zm`'s core and wants its own
  task.
