# `a11y`

The accessibility tree: what a screen reader is told about a window drawn from `lib/ui/widget`.

docs/reviews/tasks/f269-f277.md F275. **A UI that draws its own widgets is a blank rectangle to a
screen reader unless it says otherwise.** The platform does not know that a particular group of
rectangles is a button, because nothing on the screen says so -- only the program knows, and only
if it was built to say. That is why this is scheduled before the widget set rather than after:
the vocabulary a widget declares (`widget.Role`, `widget.State`) has to exist before there are
fifty widgets to add it to.

**This module is a projection, and owns no vocabulary.** Roles and declared state live on
`widget.Focusable`, where a widget is built; everything here either copies what was declared or
computes what can only be known once the tree is laid out and the focus is known. Nothing here
guesses: a control whose role nothing declared comes out as `Role.Unknown` rather than as a
button, because a reader that announces the wrong kind of control is worse than one that
announces an unfamiliar one.

**Pure, and deliberately not a platform binding.** `tree_of` answers a value; a platform adapter
in C turns that value into AT-SPI's D-Bus objects or UI Automation's providers. Keeping the
transformation here means the part with the design decisions in it -- which nodes exist, what
each one is called -- is unit-testable without a desktop, a screen reader, or either platform's
libraries, and that is the part that is wrong in every home-grown toolkit.

`use a11y` -- or `use a11y.Name` to bring one item in bare.

## Example

```
use a11y
use geom
use paint
use widget

// A fake metrics, so the example needs no font: ten units per character.
fn metrics() -> widget.Metrics {
    return widget.metrics_of(
        fn(text: string, size: float) -> float { return (len(text) as float) * 10.0 },
        fn(size: float) -> float { return size * 2.0 }
    )
}

fn words(text: string) -> widget.Widget {
    return widget.label_of(text, 8.0, paint.black())
}

// A small form: a heading, a text field, a checkbox and two buttons.
//
// Each control declares what it *is* where it is built, which is the whole point of F275's
// ordering: a role added later would have to be guessed from a tree that was not built to be
// guessed about.
fn form() -> widget.Widget {
    val email = widget.Widget.Control(widget.Focusable {
        name: "email",
        role: widget.Role.TextField,
        label: "Email",
        description: "",
        value: "ada@example.org",
        state: with widget.no_state() { required: true },
        child: widget.fixed_of(120.0, 20.0, widget.Widget.Nothing)
    })
    val notify = widget.Widget.Control(widget.Focusable {
        name: "notify",
        role: widget.Role.CheckBox,
        label: "",
        description: "",
        value: "",
        state: with widget.no_state() { checked: Option<widget.Toggle>.Some(widget.Toggle.On) },
        child: widget.fixed_of(120.0, 20.0, words("Notify me"))
    })
    val save = widget.control_of("save", widget.Role.Button, widget.fixed_of(60.0, 20.0, words("Save")))
    val revert = widget.Widget.Control(widget.Focusable {
        name: "revert",
        role: widget.Role.Button,
        label: "",
        description: "nothing to undo yet",
        value: "",
        state: with widget.no_state() { disabled: true },
        child: widget.fixed_of(60.0, 20.0, words("Revert"))
    })
    return widget.column_of(
        4.0,
        [words("Contact details"), email, notify, widget.row_of(4.0, [save, revert])]
    )
}

fn main() {
    val laid = widget.layout(form(), geom.rect_of(0.0, 0.0, 200.0, 120.0), metrics())

    // The focus is held by name, outside the tree, and passed in -- so rebuilding the tree cannot
    // move it, and `focused` is computed here rather than declared on a widget.
    val tree = a11y.tree_of(laid, "Contacts", "notify")

    // **What a reader would say, node by node.** Four controls and a heading, out of a laid-out
    // tree of a dozen rows, columns and fixed boxes: a layout box is not a node, and the text
    // inside a control is that control's name rather than a node of its own.
    for node in tree.nodes {
        printf("{}\n", a11y.announce(node))
    }

    // A disabled control is still described -- a user needs to know the button is there and dimmed
    // -- but a Tab cannot reach it.
    val reachable = mutable_array_new<string>()
    for node in a11y.reachable(tree) {
        push(reachable, node.key)
    }
    printf("\ntab reaches: {}\n", join(separator: " ", pieces: snapshot(reachable)))

    // The focused node, as the adapter would be told it.
    if Some(key) = tree.focus {
        printf("focus is on: {}\n", key)
    }

    // A checkbox's name came from the text inside it, with nothing declared.
    if Some(node) = a11y.node_of(tree, "notify") {
        printf("the checkbox is called: {}\n", node.name)
    }
}
```

Output:

```
window, Contacts
Contact details
text field, Email, ada@example.org, required
check box, Notify me, checked
button, Save
button, Revert, dimmed, nothing to undo yet

tab reaches: email notify save
focus is on: notify
the checkbox is called: Notify me
```

### `root_key`

```
pub val root_key = "@"
```

The key the root is addressed by. The root carries no name, so it keys like any unnamed node: see
`Node.key`.

### `Node`

```
pub struct Node {
    key: string
    role: Role
    // What a reader says. Never the `name` a control is focused by: see `widget.Focusable`.
    name: string
    description: string
    value: string
    // What the application declared -- see `widget.State`.
    state: State
    // Computed here, from the focus passed to `tree_of`, which is why it is not in `State`.
    focused: bool
    // Whether a Tab could reach it: a control, unless it is disabled. Not declarable, because it is
    // implied by being a control and by `state.disabled`, and a third copy of that fact could
    // disagree with the other two.
    focusable: bool
    // In the same coordinates the layout used, so an adapter can answer "what is at this point" and
    // "scroll this into view" without a second tree.
    bounds: Rect
    children: [string]
}
```

One node of the accessibility tree.

**Addressed by a string key rather than an integer id**, which is not the obvious choice and is
the right one. A platform adapter sends *updates*, so a node's identity has to survive a relayout
-- an id that changes when a sibling is inserted above it makes a reader lose the user's place on
every frame. A control's `name` already has exactly that property, and is already required for
exactly that reason (focus is held by name). Integers would mean hashing those names here and
pretending the collisions away; AT-SPI addresses objects by string path anyway, and interning a
key to whatever integer UI Automation or AccessKit wants is a few lines in the adapter, next to
the id table it already keeps.

So: **a node with a name is keyed by its name, and a node without one by `"@"` and its path.** A
label has no name, so its key moves if the tree's shape changes -- the same bargain `Laid.path`
already documents, and acceptable for static text in a way it would not be for a control.

### `Tree`

```
pub struct Tree {
    nodes: [Node]
    root: string
    // The focused node's key, or `None` -- which is a real state, not an error: a window of labels
    // has nothing to focus. A focus naming a control this tree no longer holds is `None` too, for
    // the reason `focus.holds` exists.
    focus: Option<string>
}
```

A whole tree, flat.

**Flat rather than nested, because every platform API asks for one node at a time.** AT-SPI and
UI Automation both hand a reader an object and let it ask for that object's children; AccessKit's
update is literally a list of nodes with a root and a focus. A nested tree here would have to be
flattened by the adapter in C, which is the wrong place for a tree walk.

`nodes` is in tree order, **parents before children**, so an adapter can register a node knowing
its parent is already registered.

### `tree_of`

```
pub fn tree_of(l: Laid, title: string, focus: string) -> Tree
```

The accessibility tree for a laid-out window, under the focus the caller is holding.

`title` is the window's own name, which has to be passed in because the widget tree does not know
it: a window's title belongs to the window, and `lib/core/window` is where that is.

### `node_of`

```
pub fn node_of(t: Tree, key: string) -> Option<Node>
```

The node with that key, or `None`.

### `reachable`

```
pub fn reachable(t: Tree) -> [Node]
```

Every node a Tab could reach, in tree order. The same set `focus.controls` answers over a `Laid`
tree, minus the ones that are disabled -- which is the difference worth having, since a disabled
control is still a control and still has to be described.

### `announce`

```
pub fn announce(n: Node) -> string
```

What a screen reader would say about one node, as one line.

**For tests and for a terminal reader, and not what a platform adapter uses.** An adapter hands
over the structured node and the reader's own voice settings, language and verbosity decide the
words -- so a real reader says something close to this but not this. It is here because a test
that asserts `"check box, Notify me, checked"` says what a user would hear, where a test that
asserts six fields says only that six fields were copied.

The order is the one every reader uses: what it is, what it is called, what it holds, then how it
differs from the ordinary. `focused` is not spoken, because a reader announces a node *when* it
takes focus -- saying "focused" as well would be saying it twice.
