## The mark phase: `gc_copy.c`'s traversal, marking instead of copying -- and a second use for `gc_lookup.c` nobody built it for (2026-09-30, F2)

Mark-sweep's remaining piece besides `gc_heap.c`: `src/gc_mark.c`/`.h`, `gc_mark_value(const Arena *a, Value v)`. As anticipated when `gc_copy.c` was reclassified out of Phase 3's collector role (previous entry), this is largely that module's own per-kind structure -- one static function per `Value` payload shape, switching on `Type.kind` -- with the allocation-and-recurse step replaced by an idempotent mark-and-recurse: check `gc_is_marked`, return immediately if already set (this is what keeps a shared substructure, reachable from more than one place, from being retraced once per incoming reference -- a real, common shape, the identical concern `gc_copy.c`'s own dedup map exists for, just resolved here by the mark bit itself rather than a separate table), otherwise `gc_set_marked` and recurse into the object's own fields.

**`gc_lookup.c`, built for a completely different reason, turns out to be exactly the interior-pointer fix marking needs too.** `gc_copy.c` sidesteps the interior-pointer problem (a string view, an `array_obj_view` slice sharing a parent buffer at an offset) by always copying fresh bytes of the Value's own known length, never needing to find where the underlying allocation actually starts. Marking can't take that shortcut -- there is no "fresh copy" to make; the *real, existing* buffer has to be marked, or `gc_heap_sweep` will reclaim it out from under a value that still points into it. But `gc_set_marked` has the identical "exact payload start only" contract `gc_alloc` always had (see `gc_object.h`), so marking a string's `v.as.str.ptr`, or an array's `boxed_items`/packed buffer, first resolves it through `gc_lookup` to the enclosing object's real start. This is the same primitive built to resolve a *conservative stack scan's* candidate words, reused here for a second purpose nobody designed it for at the time -- exactly the kind of validation that a general-purpose primitive, built correctly for its first job, tends to be right for a second one too. `docs/MEMORY.md`'s own "Phase 3 design" notes are corrected in place to reflect this (the original "make Phase 3 a copying collector" resolution to the interior-pointer problem is superseded, not just silently abandoned).

**A real, explicitly flagged performance question, not a claim that there isn't one.** `gc_lookup` was designed and documented as fine for a conservative stack scan's own handful of calls per collection cycle -- not necessarily for one call per string or array view encountered while tracing an entire live graph, which could make marking itself `O(objects × interior references)` in the worst case if a heap has many such references. Left as-is rather than prematurely optimized (a sorted, binary-searchable index, or tracking a view's parent explicitly in `value.h` instead of reverse-engineering it from a raw pointer, are both real options) until an actual end-to-end cycle exists to measure against the concurrency benchmark this whole effort is ultimately for -- the same "measure before optimizing" discipline this project has followed throughout (profiling before assuming which part of the interpreter's own loop overhead was real, tuning the collector's heap size only after `GC_PRINT_STATS` confirmed what was actually slow).

**One classification inconsistency noticed, not fixed, because nothing currently depends on it**: `gc_copy.c` allocates a boxed `BigNum`/`Decimal` wrapper as `GC_ATOMIC`, even though the wrapper struct itself holds a `digits` pointer -- not actually "a leaf holding no pointers of its own," `GC_ATOMIC`'s own stated contract. Harmless today because nothing (`gc_lookup`, `gc_next_object`, and now `gc_mark.c`) ever branches on `GcKind` to decide whether to trace further -- `gc_mark.c` dispatches purely on the Ziman-level `Value.type.kind`, which is strictly more precise anyway, and the only place a `GcKind` is currently a *decision* rather than descriptive metadata is `gc_heap.c`'s own `GC_FREE` check. Worth fixing if something later (a heap-dump tool, MEMORY.md's own "what this doesn't solve" list) ever needs to trace purely from a `GcKind` header with no `Value` type information available; not touched here, to keep this increment about building `gc_mark.c`, not auditing `gc_copy.c`'s kind choices.

Verified: `make test-gc-mark` (18 checks -- every `Value` kind marks its own structural object(s) and reaches into its own fields correctly; the interior-pointer case exercised directly (a 5-byte string and a 3-byte, same-start-address view of it -- marking the view correctly marks the *parent* buffer via `gc_lookup`, not nothing); an empty array (`boxed_items == NULL`) marks without crashing; a value graph with the same `StructObj` reachable from two different array elements terminates and marks it, the concrete test for the idempotent-marking design; a `Channel` value is left untouched, never traced into) passes with zero failures on the first run; `valgrind --leak-check=full` reports zero self-introduced leaks (only the same by-design, permanent-AST `type_*` allocations `gc_copy_test.c` also shows, since this test needs the identical real-`Value`-construction dependency chain); the full interpreter test suite (829 fixtures) is unchanged on both builds, confirming `gc_mark.c` compiling into the wildcarded source tree has no effect on anything yet -- nothing outside its own test calls it. Still ahead: the collection trigger, and wiring `gc_scan_stack_roots` + `gc_mark_value` + `gc_heap_sweep` into one real end-to-end cycle against actual interpreter roots.


## A real, live bug caught by the narrowest possible slice: marking a not-yet-migrated object corrupts its own adjacent field (2026-09-30, F2)

The first attempt at wiring a real allocation site (`value_string_copy`, `value.c`, via a new `src/gc_thread_heap.c` owning a per-thread `GcHeap`, and a collection trigger checked at `exec_stmt`'s own entry -- the one safe point free of the `EXPR_CALL`-style temporary-buffer gap worked through before writing any of this) found a genuine, deterministic memory-corruption bug before it reached any committed state, exactly the outcome the project owner's own caution ("narrowest possible slice first, verify exhaustively") was asking for.

**The bug, reduced to its smallest form**: `struct Opts { flag: bool }`, built as `Opts { flag: false }` and passed to a `spawn`ed function, printed `true` inside that function -- consistently, on every run, the moment a real collection cycle ran during the spawned thread's own execution. Confirmed absent on the prior commit; confirmed to disappear when the collection trigger's own threshold was raised so high it never fired, with every other line of the new wiring left in place -- isolating the cause to the mark phase actually running, not merely existing.

**Root cause: the mark phase assumed every structural object it could reach had a real header, which is false for most of this interpreter today.** `gc_mark_struct`/`gc_mark_array`/`gc_mark_result`/`gc_mark_enum`/`gc_mark_closure`, and the boxed `BigNum`/`Decimal` cases, called `gc_set_marked`/`gc_is_marked` directly on a wrapper pointer -- reading and writing the header bytes `gc_object.c` always expects immediately *before* an object's own address. That header only exists if the object was built by `gc_alloc`. A struct crossing a `spawn`/`Channel` boundary is built by `value_copy.c`'s `arena_struct_copy`, which calls bare `arena_alloc` -- no header at all, by design (that arena was never meant to be collected). Marking such a struct wrote a "marked" bit into whatever bytes actually preceded it in the outbound arena's own bump-allocated layout -- in this reduced case, directly into the tail of the struct's own single-element `fields` buffer, landing on the `bool`'s own byte and flipping it. **This was never limited to spawn-crossed values**: since only `value_string_copy` had been migrated to real `gc_alloc` allocation at the time, *every* `ArrayObj`/`StructObj`/`ResultObj`/`EnumObj`/`ClosureObj`/boxed `BigNum`/`Decimal` anywhere in a running program was equally exposed the moment `gc_mark_env_chain` (two entries ago) reached one through any `Env` binding at all -- this was a latent, universal correctness gap in the mark phase, not a spawn-specific one, simply first observed through the one path (a value crossing a thread) already known to use a header-less arena.

**Why `mark_interior_capable` (strings, array buffers) never showed this**: it already resolves its pointer through `gc_lookup` first, which returns `NULL` for anything not actually inside the given arena, and only marks a non-`NULL` result -- correct by construction, coincidentally, not because anyone had reasoned through this exact failure mode when writing it.

**The fix**: a new `is_gc_heap_object(a, ptr)` (`gc_lookup(a, ptr) == ptr` -- an exact-match confirmation, not just "resolves to something") gates every direct `gc_set_marked`/`gc_is_marked` call in every per-kind marking function. When it's false, the object's own mark bit is left untouched entirely -- but its fields are still traced, every time, since a plain (not-yet-migrated, or permanently outbound-arena) object can perfectly well hold a field that *is* `gc_heap`-allocated, and that field still needs protecting. This costs the "already visited, skip" idempotency guard specifically for objects without a real header -- accepted, not overlooked: the graph is still a DAG (established when `gc_copy.c`/`gc_mark.c` were designed), so this cannot loop, only potentially retrace a deeply-shared, not-yet-migrated substructure more than once. A second, explicitly flagged, unmeasured performance cost stacks directly on the one `gc_mark.h`'s own header comment already carries for `mark_interior_capable`: now *every* structural object touched during marking pays a `gc_lookup` call, not just interior-pointer-capable buffers.

**Verified as a real fix, not just a plausible one**: reverted the `is_gc_heap_object` guards back to unconditional marking and confirmed the exact minimal repro (`Opts { flag: false }` through `spawn`) reproduces `true` again; restored the fix and confirmed `false` again, five runs each way. A permanent regression fixture, `tests/lang/gc_collect_preserves_thread_crossed_value.zm`, does the same before/after discrimination against the real collection trigger (not a hand-rolled repro): a `spawn`ed worker receiving `Opts { flag: false }` reads 3,000 lines from a file via `fs.lines` (the one interpreter-level path that already allocates through `value_string_copy`, reliably crossing the collection trigger's own 64 KB threshold at least twice) before checking `o.flag` -- confirmed to fail (`true`) with the bug reintroduced and pass (`false`) with the fix restored, the same discriminating-test discipline `thread_crossing_native_handle.zm` already established for the earlier native-handle bug.

Verified overall: all nine standalone `gc_*` unit tests (`test-arena` through `test-gc-interp-roots`) pass, each Makefile target updated for `value.c`'s own new transitive dependency on `gc_heap.c`/`gc_thread_heap.c` (every test linking `value.c` now needs the full chain, since `value_string_copy` itself allocates through it); the full interpreter test suite is 830/830 on both builds (829 plus the new regression fixture) -- including `docs/lib/examples/server_example.zm`/`client_example.zm`, which failed non-deterministically-looking but actually deterministically the moment the trigger first fired in real usage, before this fix; the real `health-record-backend-ziman` suite (823 checks) passes against a freshly built binary; `valgrind --leak-check=summary --undef-value-errors=no` against the real interpreter running the new regression fixture reports zero errors.

**A second, related correctness gap identified while root-causing this one, not yet fixed, deliberately deferred**: `t_heap` (the new per-thread `GcHeap*` in `gc_thread_heap.c`) is reachable only through `__thread` storage -- exactly the shape that already required `GC_MALLOC_UNCOLLECTABLE` for `t_defer_envs`/`t_env_pool`. Fixed proactively, before it could manifest as its own silent bug: `gc_heap_create` now allocates the `GcHeap` struct itself via `GC_MALLOC_UNCOLLECTABLE` (under `ZIMAN_GC`), matching that established pattern, safe for every other caller too (a stack-local `GcHeap*`, as every test here uses, since uncollectable memory is still ordinarily readable and writable -- it just means `gc_heap_destroy` is the only way to free it, already true of every `GcHeap` regardless).

Still open, not yet reached: the `EXPR_CALL`-style temporary-buffer root-source gap remains real for any *future* trigger point less restrictive than "only at `exec_stmt`'s own entry" (documented in `interpreter.c`'s own `maybe_collect` comment); migrating any allocation site beyond `value_string_copy` will need the identical `is_gc_heap_object`-style care this fix just proved necessary, not assumed safe by extension.


## `gc_mark_object`, and the first real end-to-end cycle: scan, mark, sweep, composed and proven together (2026-09-30, F2)

Two pieces landed together, since neither is independently useful without the other.

**`gc_mark_object` (new, `gc_mark.c`/`.h`): the bridge a conservatively-found root actually needs.** `gc_scan_stack_roots` resolves a candidate stack word to a real object via `gc_lookup`, but hands `visit` only that bare pointer -- there is no `Value`, and so no `Type.kind`, for `gc_mark_value` to dispatch on. `gc_mark_object` dispatches on the object's own `GcKind` header instead (`gc_kind_of`), which is everything a *root* actually has: `GC_ATOMIC` is a leaf, marked and done; the five structural kinds hand off to the same per-kind functions `gc_mark_value` itself uses; `GC_FREE` (a stray stack word resolving to an already-reclaimed chunk -- the same class of harmless false positive conservative scanning always risks) and `NULL` are no-ops. The one case worth calling out: `GC_VALUES` found bare, with no enclosing `ArrayObj`/`StructObj`/`ClosureObj` around it at all -- not a hypothetical shape, but exactly what a `Value[]` buffer looks like mid-construction, gc_alloc'd before the wrapper that will eventually hold it exists. Traced by walking `gc_size_of(obj) / sizeof(Value)` elements, the only way to know the count at all without a wrapper to ask.

**`gc_heap_collect` (new, `gc_heap.c`/`.h`): scan, mark, sweep, wired into one call.** Scans the calling thread's own stack into the heap's own arena, marks every root `gc_mark_object` finds, then sweeps. Skips the whole cycle, not just the scan, if the thread's stack cannot be measured at all (`gc_scan_stack_roots` returning failure) -- sweeping without having marked anything reachable only through the stack would reclaim live objects; the same graceful-degradation choice `ziman_stack_slow` already makes for the recursion-depth guard, applied here.

**Explicitly not yet a complete root set, and not yet safe to wire into the real interpreter -- built and tested anyway, to prove the pieces compose before closing that gap.** This codebase's own thread-local state (`t_defer_envs`/`t_env_pool` in `interpreter.c`, `error.c`'s own call-frame stack) is not reliably found by a conservative stack scan at all -- documented in MEMORY.md's own "Phase 3 design" section since before any of this was implemented, as the exact reason those are already `GC_MALLOC_UNCOLLECTABLE` -- and none of it is walked here as an explicit, additional root source yet. `gc_heap_collect`'s own doc comment says this plainly rather than implying a false sense of completeness.

**The test is the actual milestone here, not the code**: a real graph -- an array containing a struct containing a string, reachable through exactly one `volatile` stack root -- survives a genuine `gc_scan_stack_roots` → `gc_mark_object`/`gc_mark_value` → `gc_heap_sweep` cycle with its content fully intact, while a second, unreferenced object of a similar size gets its slot reclaimed and reused by a later allocation. This is the first point in the whole effort where "does this actually work end to end" has an answer instead of a plan.

**A real test bug caught while running it, not a bug in the code under test**: the first version compared a dead object's address directly against a local variable read *after* `gc_heap_collect` ran -- which forces the compiler to keep that variable live across the call (it's needed afterward), spilling it onto the exact stack region the scan reads, making the "dead" object into a legitimate, correctly-found root by the test's own construction. The check failed *every* run, not intermittently, which is what gave this away as a real, deterministic effect rather than the ordinary run-to-run staleness conservative-scan tests already expect (`gc_scan_test.c`'s own comment on this). Fixed by stashing the address in a file-scope `static` variable instead -- outside the C stack entirely, so it is genuinely invisible to the scan, and the comparison afterward tests what it was meant to.

Verified: `make test-gc-mark`'s own suite grew to 24 checks (6 new, covering `gc_mark_object` directly: a bare `GC_ATOMIC` root, a bare `GC_VALUES` root with its own elements traced, a bare structural root, a `GC_FREE` root correctly left untouched, `NULL`); `make test-gc-heap` grew to 22 (5 new, the composed end-to-end cycle above), all passing, rerun five times deliberately (stack contents vary run to run) with no failures; `valgrind --leak-check=full` (`--undef-value-errors=no` for the `gc_heap` test specifically, for the same inherent reason `gc_scan_test.c` needs it) finds zero errors beyond the same by-design permanent-AST allocations every `Value`-construction-heavy test here already shows; the full interpreter test suite (829 fixtures) is unchanged on both builds -- `gc_heap.c` now transitively depends on `gc_scan.c`/`gc_mark.c` (and so needs their own dependency chains linked into `test-gc-heap`'s Makefile target now too), but nothing outside these modules' own tests calls any of it yet. Still ahead: the collection trigger (when to actually call `gc_heap_collect`), the explicit thread-local root walk that closes the remaining correctness gap above, and wiring a real per-thread `GcHeap` into the interpreter's own allocation sites.


## The second root source: an `Env` chain, and a gap found broader than expected (2026-09-30, F2)

Working out exactly what "the explicit thread-local root walk" (previous entry's own open item) needs to cover, before writing it, turned up a real gap wider than the name suggested.

**An `Env` (`env.h`) is not itself allocated in any thread's `GcHeap` arena -- `env_new`/`env_pool_acquire` use the ordinary allocator (`GC_MALLOC`/`malloc`), a completely different heap.** The moment a `Value` is stored into a binding (`env_define`), its own pointer fields move off the C stack -- where `gc_scan_stack_roots` could see them as raw words -- into `Env.items`' own heap-allocated storage. `gc_scan_stack_roots` only ever reads raw stack bytes and tests each word against `gc_lookup`; it never dereferences a pointer it finds to look inside whatever it points to. So an `Env*` sitting on the stack (say, `call_function`'s own local `env`) is correctly *not* found as a root at all (it isn't an address inside the `GcHeap` arena), and nothing then goes on to look at what `env` itself contains. **This affects every ordinary variable binding in the interpreter, not just `interpreter.c`'s `t_defer_envs`/`t_env_pool`**, which is the narrower shape "Phase 3 design" section 3 (docs/MEMORY.md) originally named -- those two are a real instance of the same problem (an `Env` reachable only through `__thread` state the collector doesn't scan), but the underlying cause turns out to be structural, not specific to thread-local storage at all: *any* `Env`, however it's reached, needs its own bindings walked explicitly, because conservative scanning can never see past the pointer that leads to it.

**`src/gc_env_roots.c`/`.h` (new): the smallest correct piece of this, built and tested on its own before touching `t_defer_envs`/`t_env_pool`/`error.c`'s frame tracking, or the interpreter at all.** `gc_mark_env_chain(const Arena *a, const Env *env)` marks every `Value` bound in `env` and walks `->parent` iteratively (not recursively -- a long scope chain has no reason to also cost C stack depth here) up to wherever the chain terminates. `caps` (the type checker's own field, always empty for an interpreter-built `Env`) and `defers` (`Expr*`, permanent AST, evaluated later against this same `env`'s own bindings -- see `run_defers`) are deliberately not walked: neither ever holds a `Value` of its own to mark.

**Still ahead, not resolved by this increment**: wiring this into `error.c`'s existing call-frame tracking (extending `ZimanFrame` to also carry each active call's own `Env*`, so a collection cycle can walk every currently-active scope, not just one handed to it directly), walking `t_defer_envs`/`t_env_pool` themselves the same way, and deciding how `g_global_env` fits in once globals are ever routed through a `GcHeap` at all (still Phase 4/5, design-only). `gc_heap_collect` is not yet updated to call this -- doing so before the frame-tracking wiring exists would only mark whatever single `Env` happens to be passed to it, not the whole active chain a real collection needs.

Verified: a new standalone test (`tests/c/gc_env_roots_test.c`, `make test-gc-env-roots`, 7 checks -- a two-scope chain marks both the inner and outer scope's own bindings; a scalar binding doesn't crash; a scope with no parent terminates correctly; an empty scope doesn't crash; a structural value (a struct holding a string) bound in a scope is marked and traced into correctly, composing with `gc_mark_value`'s own recursion rather than duplicating it) passes with zero failures on the first run; `valgrind --leak-check=full` finds zero self-introduced leaks (the same by-design permanent-AST `type_struct` allocation every `Value`-construction-heavy test here already shows, plus confirmation that `env_free`'s own cleanup is genuinely clean -- 16 allocs, 15 frees, the one remainder being that documented exception); the full interpreter test suite (829 fixtures) is unchanged on both builds, confirming `gc_env_roots.c` compiling into the wildcarded source tree has no effect on anything yet.


## Wiring `error.c`'s existing frame tracking to carry each call's own `Env*` (2026-09-30, F2)

Closes the "still ahead" item the previous entry left open: `gc_mark_env_chain` can walk *one* `Env` chain, but a real collection cycle needs every currently active call's own scope, and the only place that already knows the full set of active calls, per thread, is `error.c`'s existing `ZimanFrame` stack (built for stack traces, long before any of this GC work started).

**A new field, set separately from when the frame itself is pushed.** `ZimanFrame` gains a `void *env` (kept untyped so `error.c` -- used by the lexer, parser, and type checker too, none of which know about `Env` at runtime the way the interpreter does -- doesn't gain a new dependency on `env.h`). `call_function` (`interpreter.c`) pushes its own frame *before* its `Env` exists (`ziman_push_frame` is the very first thing it does, ahead of argument binding), so a new `ziman_set_frame_env(void *env)` sets it separately, called right after `Env *env = env_pool_acquire(...)` -- one new line at that one call site. A native call's frame is never given one (natives have no `Env` at all), leaving it `NULL`, which is exactly the value a caller walking every frame needs to know to skip.

**Read back through two small accessors, not by exposing the frame array itself**: `ziman_frame_count()` and `ziman_frame_env_at(int i)`. Kept this way rather than handing back a `void **` into `t_frames`'s own storage, since the `env` field isn't contiguous across frames (it's one field inside each `ZimanFrame` struct, interleaved with `name`/`file`/the call position) -- a caller iterating `0..ziman_frame_count()` and calling `ziman_frame_env_at` each time never needs to know that layout at all, matching the same "don't leak internal structure" instinct `gc_object.c`'s `gc_next_object` was built with.

**Deliberately minimal, and deliberately verified against real interpreter behavior, not just left as an isolated addition.** This is the first change in the whole Phase 3 effort that touches `interpreter.c`/`error.c` themselves rather than landing as a new, uncalled-from-anywhere module -- `ziman_set_frame_env` is called on every function call now, on the real, hot path, even though nothing yet reads what it stores. Verified accordingly: full interpreter test suite (829 fixtures) unchanged on both builds; the real `health-record-backend-ziman` suite (19 Python test files, 823 checks total, including `admin_test.py`'s own account-deletion-with-medications case, the one that originally caught the native-handle bug) passes unchanged against a freshly built binary -- this session's own standing rule for anything touching interpreter behavior, not skipped just because the change looked small.

Still ahead: actually calling `gc_mark_env_chain` for every frame `ziman_frame_env_at` returns (plus `g_global_env` and `t_defer_envs`/`t_env_pool`) from within a real collection cycle -- this increment only gives a future one the data to read; `gc_heap_collect` itself is still unchanged.


## `gc_heap_collect` gains a seam for the second root source, without learning what it is (2026-09-30, F2)

The piece that actually lets a caller close the root-completeness gap: `gc_heap_collect` (`gc_heap.c`/`.h`) gains a third parameter, `void (*extra_roots)(const Arena *a, void *ctx), void *ctx`, called (if non-`NULL`) after the conservative stack scan and before sweeping.

**Why a callback, not a direct call into `interpreter.c`.** `g_global_env`, `t_defer_envs`, and `t_env_pool` are all `static` (or `static __thread`) inside `interpreter.c` -- genuinely private, not something `gc_heap.c` can or should reach into directly. `gc_heap.c` has stayed decoupled from any specific caller's own state through every increment so far (it doesn't know what a `Value` is beyond a `GcKind` tag, doesn't know what "marking" even means beyond calling out to `gc_mark_object`); reaching into `interpreter.c`'s internals for this one root source would break that on the very last piece. `extra_roots` keeps the same shape `gc_scan_stack_roots`'s own `visit` callback already established: `gc_heap_collect` knows how to *run* whatever a caller supplies, with no opinion on what it does. The eventual real caller (still ahead) will pass a small `interpreter.c`-local function that calls `gc_mark_env_chain` on `g_global_env`, on every `ziman_frame_env_at(i)` the previous entry's frame tracking now exposes, and (once that's also designed) `t_defer_envs`/`t_env_pool`'s own entries.

**Every existing caller passes `NULL`, which is a real, called-out gap, not an oversight left implicit.** `gc_heap.h`'s own doc comment says plainly: passing `NULL` omits `Env`-reachable roots entirely, and `gc_heap_collect` is not yet safe to wire into the real interpreter until a caller supplies a complete one.

**Proven with a genuine case the stack scan cannot reach on its own**, not just a signature change exercised in the abstract: a string bound in an `Env`, referenced by nothing else in the test, survives a real `gc_heap_collect` cycle specifically because the new callback (`mark_env_ctx`, calling `gc_mark_env_chain`) runs and marks it -- the exact shape "the second root source" entry identified as invisible to conservative scanning alone.

Verified: `tests/c/gc_heap_test.c` grew to 24 checks (2 new, the `extra_roots` proof above), rerun five times (stack contents vary run to run) with zero failures; `valgrind --leak-check=full --undef-value-errors=no` clean (only the same by-design permanent-AST allocation every real-`Value`-construction test here shows); the full interpreter test suite (829 fixtures) is unchanged on both builds. `gc_heap.c` now transitively depends on `env.c`/`gc_env_roots.c` too (added to `test-gc-heap`'s own Makefile target), but nothing outside `gc_heap.c`'s own test supplies a real `extra_roots` yet -- the interpreter itself still never calls `gc_heap_collect` at all.


## The interpreter's own root sources, aggregated -- and kept testable by not reading `interpreter.c`'s private state directly (2026-09-30, F2)

`src/gc_interp_roots.c`/`.h`: `gc_mark_interpreter_roots` is what `gc_heap_collect`'s `extra_roots` seam has been waiting for -- it marks the global scope, every currently active call's own frame (via `error.c`'s frame tracking from two entries ago), and `interpreter.c`'s own `t_defer_envs`/`t_env_pool`, in one call.

**A real practical constraint shaped this function's signature, not just style preference: `interpreter.c` cannot be linked into a standalone unit test.** Every other module in this whole effort (`arena.c` through `gc_env_roots.c`) has had its own dedicated test, built by linking exactly the small set of `.c` files it actually needs. `interpreter.c` is different in kind, not just size -- it pulls in every native module, the parser, the type checker, `corelib.c`'s embedded library sources, essentially the entire program minus `main.c`. Reading `g_global_env`/`t_defer_envs`/`t_env_pool` directly (they are `static`/`static __thread`, genuinely private to `interpreter.c`) would have made this function's own correctness untestable except by exercising the real interpreter end to end, which is exactly the class of "hope it works" verification this whole effort has tried to avoid at every prior step.

**The fix: take that state as explicit parameters instead of reading it.** `gc_mark_interpreter_roots(const Arena *a, const Env *global_env, Env *const *defer_envs, int defer_env_count, Env *const *env_pool, int env_pool_count)` -- a synthetic `Env**`/count pair a standalone test builds by hand exercises the *identical* code path a real interpreter's own `t_defer_envs`/`t_env_pool` would. The one piece read directly rather than passed in is the active call frames, via `error.c`'s already-general, already-exposed `ziman_frame_count`/`ziman_frame_env_at` -- depending on `error.c` (a small, foundational module built for exactly this) is a different kind of coupling than depending on `interpreter.c`'s own internals, and doesn't cost this function its testability (`error.c` links standalone easily, as every earlier test using it has already shown). `interpreter.c`'s own eventual wiring, once it exists, is reduced to a thin `extra_roots` wrapper passing its own state through -- one line per field, no logic of its own to get wrong.

**`env_pool`'s entries are walked even though a real one should never have anything to mark** -- `env_reset` already clears every pooled `Env`'s own bindings before it goes back on the list (see `interpreter.c`'s own comment on `env_pool_release`), so walking one is an immediate no-op today. Walked anyway, deliberately: it costs nothing, and it means this function's own contract doesn't quietly depend on that pooling invariant staying true forever -- if it ever didn't, this would still do the right thing rather than silently miss something.

**A verification bar this specific function cannot fully clear, stated plainly rather than glossed over**: the standalone test proves the *aggregation logic* is correct (every frame gets walked, a native call's frame with no `Env` doesn't crash, an empty pooled `Env` doesn't crash, every real root source's own binding is found) against synthetic stand-ins for `interpreter.c`'s state -- it cannot prove `interpreter.c` will one day call this with the *right* state, since nothing calls it yet. That last mile of verification will come from the full test suite (and the real `health-record-backend-ziman` suite) once a real per-thread `GcHeap`, a collection trigger, and the actual wiring into `call_function`/`interpret` all exist -- any fixture that then survives a real, triggered collection will be implicit end-to-end proof this aggregation was supplied correctly; one that doesn't would fail loudly, the same way `admin_test.py` once did for the native-handle bug.

Verified: a new standalone test (`tests/c/gc_interp_roots_test.c`, `make test-gc-interp-roots`, 6 checks -- the global scope's own binding is marked; two nested active frames (outer and inner, pushed via `ziman_push_frame`/`ziman_set_frame_env`) each have their own binding marked, proving every frame is walked, not just the innermost; a native call's frame (pushed with no `Env` at all) doesn't crash the walk; a tracked defer scope's binding is marked; an empty pooled `Env` doesn't crash) passes with zero failures on the first run; `valgrind --leak-check=full` reports zero errors and zero leaks (this test's own `Value`s use only `type_scalar`, which unlike `type_struct`/`type_array` allocates nothing, so unlike every other real-`Value`-construction test here, this one is genuinely, fully clean); the full interpreter test suite (829 fixtures) is unchanged on both builds. Still ahead, the last remaining pieces: the collection trigger (when to actually call `gc_heap_collect`), creating a real per-thread `GcHeap`, and wiring `interpreter.c`'s own allocation sites (`value.c`'s constructors, `env_new`, `array_obj_new`, ...) to use it.


## Closing the temporary-buffer gap for real: `gc_unsafe_enter`/`gc_unsafe_leave`, and a second, milder bug found finishing the job (2026-09-30, F2)

Migrating `struct_obj_new` (the natural next step after `value_string_copy`) broke two fixtures immediately -- `net_dropped_socket_reclaimed` (a timing issue, resolved below) and, more seriously, `csv_extended`, which failed with `internal error: field 'cells' not found at runtime`: real corruption, not a symptom of a slow trigger.

**The gap, precisely.** `EXPR_STRUCT_LIT`'s `fields[]` (and `EXPR_CALL`'s `args[]`, `EXPR_ARRAY_LIT`'s `items[]`, `EXPR_WITH`'s `fields[]`) is a plain `malloc`'d buffer, populated *one element at a time* by repeated `eval_expr` calls. If evaluating one element recurses into a function call, that call's own body runs `exec_stmt`, which can trigger `maybe_collect` -- while *earlier* elements already sit in the buffer, referenced by nothing the collector can see (not the C stack, since they're inside a heap block the stack scan never dereferences into; not any `Env`, since the buffer hasn't been handed off yet). The previous entry's "only at `exec_stmt`'s own entry" safe-point analysis checked that these buffers never dangle *across* statement boundaries -- it never considered a collection firing *mid-construction*, triggered from a nested call. **This was never specific to `struct_obj_new`, or even to `interpreter.c`**: the already-shipped `value_string_copy` wiring carries the identical exposure (a string sitting in an earlier `args[]` slot while a sibling argument's evaluation recurses); it simply hadn't been hit, because `fs.lines`-sourced strings rarely appear alongside a call-triggering sibling argument in the same expression, unlike structs, which do constantly in ordinary code. A latent bug the existing suite hadn't exercised yet is still a bug -- confirmed real, not hypothetical, before treating it as such.

**A wider audit than expected, and why it stayed bounded.** The first instinct -- find and guard every site across `interpreter.c` *and* every native module that might build such a buffer -- turned out to be the wrong shape for the fix, since `prelude.c`'s `native_array_map`/`filter`/`flat_map` (and `iter.c`) call back into Ziman closures from inside their own loops too. But `grep -ln "native_call_closure\|call_closure_value" src/*.c` shows only three files ever call back into Ziman at all (`prelude.c`, `iter.c`, `interpreter.c`), and `call_function` itself is never called from outside `interpreter.c` -- meaning **every** native function's own callback goes through exactly two choke points, `call_closure_value` and `native_call_closure`. Guarding those two functions' own internal `call_function` invocation protects every `prelude.c`/`iter.c` caller automatically, without touching either file: it covers both a calling native's own `args[]` (which, for a *native* call specifically, is *never* bound into an `Env` at all, since natives get no `Env` -- the only thing that could ever protect it is the guard covering the window the callback itself is on the stack for) and any temp buffer that native is still building. `interpreter.c`'s own four `EXPR_*` sites, plus one inline `map_filter`/`set_filter` loop that calls `call_function` directly (not through either choke point), needed their own, narrower guards around just their own loops. Six guarded regions total, not an open-ended, easy-to-miss multi-file audit.

**The mechanism**: `t_gc_unsafe_depth` (a `__thread int`), `gc_unsafe_enter`/`gc_unsafe_leave` incrementing and decrementing it, and `maybe_collect` skipping entirely whenever it's nonzero -- stricter than "only at `exec_stmt`'s own entry" alone, but actually safe this time, confirmed by tracing every site rather than assumed. The window each guard covers ends the moment its own loop (or callback) finishes, not when the resulting value is finally consumed: once a buffer is fully built and handed to `call_function`, it becomes safe immediately on entry (parameter binding happens before any `exec_stmt` in the callee runs, for an ordinary call; for a native call, the choke-point guard already covers the only way it could be unsafe) -- verified by re-checking every remaining direct `call_function` call site in `interpreter.c` against this exact question before concluding none of them needed a separate guard.

**A second, milder, separately-diagnosed bug surfaced by the same migration**: `net_dropped_socket_reclaimed` (a fixture that already existed, checking that Boehm's own collector reclaims dropped `net.Socket` structs within a bound) started failing too -- not corruption, but *over-retention*: `net.Socket`'s own `StructObj` wrapper is now `gc_heap`-allocated, into an arena registered with Boehm (`arena_create_scanned`, needed since before -- see the native-handle bug two entries up). `gc_heap_sweep` reclaims a dead object's *header* (converts it to `GC_FREE`) but never zeroed its *payload* -- so a disguised socket-handle address sitting in an already-dead-but-not-yet-swept struct's own bytes kept looking like a live reference to Boehm's conservative scan of that same arena, for as long as the bytes went unreused. Compounded by the fact that Phase 3's own 64 KB trigger essentially never fires for 40 small struct allocations, so the dead structs simply accumulated, unswept, for the test's whole duration.

**The fix, two parts**: `gc_heap_sweep` now zeroes a reclaimed object's own payload before relinking it onto its free list (`gc_heap.c`) -- a small, unconditionally-good change (stale bytes that merely *resemble* an address are exactly the false-positive risk conservative scanning already accepts, but there's no reason to manufacture more of them than necessary once an object is confirmed dead). And a new `ziman_force_collect()` (`interpreter.h`/`.c`) lets `os.collect_garbage()` (`native_os.c`) run a real Phase 3 collection on the calling thread *before* Boehm's own `GC_gcollect()` -- so an explicit request to collect garbage cleans up this thread's own `gc_heap` content first, rather than leaving it for Boehm to (correctly, conservatively, but unhelpfully) treat as still reachable. `ziman_force_collect` respects `t_gc_unsafe_depth` the same way `maybe_collect` does, and stays inside the same `#ifdef ZIMAN_GC` guard `os.collect_garbage()` already had (a nogc build's own "never reclaims anything" property is preserved on purpose, not accidentally widened).

**A valgrind finding investigated and ruled out, not glossed over**: running the fixed binary against `csv_extended.zm` under `valgrind --undef-value-errors=no` still reports 255 "Invalid read of size 8" errors, all inside Boehm's own `GC_mark_from`, reading "thread 1's stack." Before assuming this was pre-existing rather than newly introduced, checked directly: `tests/lang/thread_crossing_native_handle.zm` -- a fixture that predates all of this session's Phase 3 work and already calls `os.collect_garbage()` -- shows the *identical* `GC_mark_from`/"thread's own stack" pattern (85 occurrences) under the same valgrind flags. Confirmed pre-existing, not caused by anything in this increment: Boehm's own conservative mark phase reads stack memory in a way valgrind's stricter "has this actually been written" tracking flags as invalid, a well-known interaction for Boehm-based programs generally, unrelated to Phase 3.

Verified overall: full suite 830/830 on both builds, stable across five repeated runs (the socket-timing fixture's own nature made this worth confirming, not just trusting once); all nine standalone `gc_*` unit tests still pass; the real `health-record-backend-ziman` suite (823 checks) passes against the freshly built binary; `valgrind --leak-check=summary --undef-value-errors=no` against both the new regression fixture and `csv_extended.zm` reports zero errors beyond the confirmed-pre-existing Boehm/valgrind interaction above.

`struct_obj_new`'s own migration (the wrapper only -- `fields` stays on the ordinary allocator, the same "narrowest slice within the slice" discipline `value_string_copy` established) is the second real allocation site now routed through Phase 3's collector, and the first to be exercised by ordinary, unremarkable Ziman code (every struct literal and `with` expression in the language) rather than one narrow native function -- a meaningfully broader test of the whole pipeline than `value_string_copy` alone could provide, which is exactly what surfaced both of today's findings.


## `array_obj_new` migrates, and a fundamental gap in the second root source it uncovered: `Env` chains never walk downward into nested scopes (2026-09-30, F2)

Two small fixes preceded the migration itself. `gc_heap_alloc`'s reused-chunk path never cleared the free-list link `gc_heap_sweep` writes into a dead object's first `sizeof(void*)` payload bytes -- a reused chunk's own "always zero-filled" guarantee (matching `arena_alloc`'s) was quietly false for exactly those bytes. Fixed by reading the link out first, then zeroing before returning; a new `gc_heap_test.c` check confirms a reused slot's *entire* payload, not just the parts a caller happens to set, is zero. `gc_heap_create` also now allocates the `GcHeap` struct itself via `GC_MALLOC_UNCOLLECTABLE` rather than plain `malloc` -- it is reachable only through a `__thread` pointer (`gc_thread_heap.c`), which Boehm does not reliably scan, the identical reasoning already applied to `t_defer_envs`/`t_env_pool`.

`array_obj_new` then migrated to `gc_heap_alloc(ziman_thread_heap(), GC_ARRAY, sizeof(ArrayObj))` (the wrapper only, same discipline as `struct_obj_new`; `items` stays on the ordinary allocator). This immediately segfaulted `spawn_defer_gc_stress.zm` -- a real crash, not a wrong-output symptom, root-caused with a precise `gdb` backtrace (via `coredumpctl`) rather than guessed at: the crash landed in `native_ab_append` (`prelude.c:748`), reached through several nested `exec_stmts_in_scope` frames.

**The gap, once traced back.** `ziman_set_frame_env` (`error.c`) is called exactly once per call, by `call_function`, recording that call's *top-level* `Env` -- confirmed via `grep -n "ziman_set_frame_env" src/interpreter.c` showing exactly one call site. `gc_mark_env_chain` only ever walks a recorded `Env`'s `->parent` chain *upward*, toward the global scope -- `Env` has no way to be walked downward into a child. But every `for`/`while`/`if`/plain `{...}` block creates its own child scope via `env_new(parent)`, funneled through the single `exec_stmts_in_scope` (found, as with the choke-point technique two entries up, by grepping every call site rather than trusting a mental model of the code). **A variable declared inside a loop body -- an entirely ordinary shape, not a corner case -- has been invisible to root-finding since this frame tracking was first built**, for exactly as long as that block's own execution lasted. It simply hadn't been exercised by a fixture with enough allocation pressure inside a nested scope until `array_obj_new`'s migration made array/builder construction (already common inside `spawn_defer_gc_stress.zm`'s own deliberately-stressful, deeply-nested fixture) a real collection trigger for the first time.

Given `struct_obj_new` (already shipped, committed) is exposed to the identical gap, asked the user how to proceed rather than deciding unilaterally: fix `Env` tracking now, holding `array_obj_new`'s migration until it's fixed and verified against the exact crashing fixture -- confirmed, and followed.

**The fix**: `exec_stmts_in_scope` -- the single function every nested scope's execution already funnels through -- now saves the frame's current `Env`, calls `ziman_set_frame_env(scope)` for the duration of running that scope's own statements (including `run_defers`), and restores the saved value before returning. This makes the frame's *recorded* `Env` always reflect whichever scope is *actually* executing, at any nesting depth, at the moment a collection might fire -- and since `gc_mark_env_chain` already walks `->parent` upward from wherever it starts, a deeply nested scope's own recording is enough; the walk finds every enclosing scope's bindings the same way it always found a call's own top-level ones.

Verified: compiled cleanly; `array_obj_new`'s migration re-applied; the exact crashing fixture run three times directly, all producing the correct output (`28`) with exit 0; `regex_cache.zm` (the other fixture the migration broke) confirmed matching via `diff`; the full suite (830/830) stable across five repeated runs on both builds; all nine standalone `gc_*` unit tests pass.


## A third root-source gap, found by the real health-record-backend-ziman app: `ArrayBuilder`/`MapBuilder`/`SetBuilder`'s own buffer is invisible to the mark phase (2026-09-30, F2)

Running the real `health-record-backend-ziman` suite against the freshly built binary (the standing "always run it for anything touching interpreter behavior" rule) failed all 823 checks at once, every request answering 500: `runtime error at 782:13: internal error: field 'parts' not found at runtime` -- `lib/http/server.zm`'s `shape_matches`, reading a field off a `Pattern` struct that had been swept out from under a still-live binding.

**Root-caused with minimal reproductions, not guessed at.** `lib/http/server.zm`'s `routes<C>` builds its whole routing table once at start-up: `ab_new<Pattern>()`, then `ab_append<Pattern>(patterns, compile_pattern(e.pattern))` across ~100+ routes, then `ab_to_array<Pattern>(patterns)`. A minimal fixture reproducing exactly this shape (an `ArrayBuilder<Pair>` of a two-field struct, appended to across a loop, `os.collect_garbage()` forced every iteration) failed within 50 iterations; the same shape with `ArrayBuilder<string>` survived 200 forced collections -- not because builders of strings are safe, but because `concat`/`str` still allocate through the *old*, unmigrated allocator (`zalloc_atomic`, confirmed by reading `native_concat`), so those particular strings were never part of the new collector's responsibility at all. Once the struct wrapper is gc_heap-migrated (as of the previous entry), the same exposure is real for any element type Phase 3 now manages.

**The gap, precisely**: `ArrayBuilder<T>`'s backing buffer (`ArrayBuilderBuf.items`, `src/prelude.c`) is a plain `malloc`'d `Value*` array, reachable only through a disguised `int64_t` handle stored in the builder's own wrapper struct's `fields[0]`. Neither of the mark phase's two root sources can see into it: the stack scan finds no pointer shape in a bare int, and a struct's generic field walk marks each field by its own `Value.type.kind` -- an int carries nothing further to trace. An appended element was therefore only as safe as whatever *else* independently referenced it: true for the loop-local variable that built it, for exactly as long as that one iteration lasted. Once the loop moves on, an earlier `Pattern` sitting only in the builder's buffer is invisible to every root source, and a real collection landing mid-loop sweeps it. `MapBuilder`/`SetBuilder` share the identical shape (a `MapObj*` behind the same disguised-handle scheme) -- and, per `gc_mark.h`'s own pre-existing comment, an ordinary (non-builder) `Map`/`Set` value is *not* similarly exposed: `gc_mark_into`'s `TY_MAP`/`TY_SET` case already walks every entry via `mapobj_entries` regardless of whether the `MapObj` itself has a real header, a documented, deliberate `Map`/`Set` root-finding path that already existed before this session. The gap is specific to the three *builder* wrapper structs' own disguised handle, not `Map`/`Set` generally.

Given the severity and the architectural weight of the fix, asked the user how to proceed: fix builder-content marking directly, rather than a broader audit or reconsidering the migration order -- confirmed, and followed.

**The fix**: a new seam, `gc_mark_register_struct_content_marker(type_name, mark_contents)` (`gc_mark.c`/`.h`), lets a module whose own struct type wraps a disguised handle teach the mark phase to trace through it. `gc_mark_into`'s `TY_STRUCT` case calls the registered marker (if any) for the value's own `Type.struct_name`, in addition to (not instead of) the ordinary `gc_mark_struct` walk. **Deliberately unconditional, never gated by the struct's own mark bit**: a bare stack pointer to the same wrapper may already have been marked by the type-less `gc_mark_object` path earlier in the same cycle (`gc_scan_stack_roots` always runs before the `Env`-chain `extra_roots` in `gc_heap_collect`), and the ordinary "already marked, skip" guard would otherwise silently skip content-marking on the one visit that had a type name to dispatch on at all. Safe to call more than once per cycle for the same accepted reason every other per-kind function's own redundant-retrace cost already is: the value graph is a DAG, so there's no loop risk, only possibly-repeated work on a builder still being appended to. `prelude.c` registers content markers at `prelude_register` time: `mutable_array_mark_contents` (walks `MutableArrayBuf.items`, skipped entirely in packed/scalar mode, where there are no `Value`s to trace) for `"MutableArray"`, `mutable_map_mark_contents` (walks the `MutableMapBuf`'s own `MapObj` via `mapobj_entries`, mirroring `gc_mark_into`'s existing `TY_MAP` handling) for both `"MutableMap"` and `"MutableSet"`, and `cell_mark_contents` for `"Mutable"`.

Verified: both minimal reproductions (struct- and pair-of-arrays-typed builders under forced collection) now pass; confirmed the fix actually discriminates by reverting it (`git stash`) and reproducing the failure again on the unfixed binary, then restoring it; a new permanent regression fixture (`tests/lang/gc_arraybuilder_contents_survive_collection.zm`) added, verified to fail without the fix and pass with it; the real `health-record-backend-ziman` server now answers `/health` 200 and its full Python suite passes (19 files, ~950 checks, 0 failed, sqlite mode); the full interpreter suite (831/831 with the new fixture) stable on both builds; all nine standalone `gc_*` unit tests pass; `valgrind --undef-value-errors=no` against the new fixture and `spawn_defer_gc_stress.zm` shows only the same pre-existing, already-investigated `GC_mark_from`/"thread's own stack" Boehm/valgrind interaction from two entries up (more occurrences here only because `spawn_defer_gc_stress.zm` spawns 8 threads, each with its own call-stack context for the identical pattern) -- no new class of error, correct output in both cases.

Together, these three findings (the header-corruption bug, the temporary-buffer timing gap, and now this) describe a consistent shape: **the "narrowest possible slice" strategy has, every single time so far, surfaced its bug at the moment a migrated allocation site meets a *pre-existing* mechanism that was never designed with a real collector in mind** -- `value_copy.c`'s outbound arena, `EXPR_STRUCT_LIT`'s temp buffer, `Env`'s upward-only parent chain, and now `ArrayBuilder`'s disguised-handle buffer. Each was validated exhaustively at the time it was built, against the collector that existed *then* (no real collector at all, for the first three; a collector with only two root sources, for the last). None of these were guessed at in advance and pre-empted -- every one was found by shipping the next narrow slice and watching real code (increasingly, the real `health-record-backend-ziman` app) break in a specific, traceable way. This is the strategy working as intended, not failing.


## A fourth root-source gap becomes a hard crash: Boehm's root-set table has a fixed capacity, and nothing was ever reclaiming it (2026-09-30, F2)

Re-running `tests/bench/server_concurrency.sh` (F2's own concurrency benchmark) for the first time since any `gc_heap`-backed migration shipped -- overdue, but every step so far had its own more immediate fire to put out first -- the server itself `abort()`-ed outright, before any throughput number could even be measured, at as low as `c=16` against 3000 total requests.

**Root-caused with a `gdb` backtrace off the core dump (`coredumpctl`), not guessed at**: `abort()` inside Boehm's own `GC_add_roots_inner`, reached from `arena_create_impl` <- `gc_heap_create` <- `ziman_thread_heap`, on a freshly `spawn`ed connection-handling thread's very first allocation. `GC_add_roots`'s own implementation (`vendor/bdwgc/mark_rts.c`) is unconditional: `if (n_root_sets == MAX_ROOT_SETS) { ABORT("Too many root sets"); }` -- a **fixed-capacity** table (2048 entries in this build's configuration), never grown, and never shrunk for a registration nobody ever calls `GC_remove_roots` for. `arena_create_scanned` registers every arena it creates via `GC_add_roots` (needed so Boehm's own conservative scan can find a disguised native handle sitting in one -- see `arena.h`'s own comment); a thread-per-connection server (`lib/http/server.zm`'s `serve`) creates a fresh `GcHeap` -- and so a fresh scanned arena -- on every connection-handling thread's own first allocation, and nothing had ever destroyed one. Two independent, pre-existing sources of this exact leak, both hit at once:

**First: `ziman_thread_heap()`'s own per-thread `GcHeap` was never destroyed at thread exit.** Every other piece of this interpreter's own `__thread` state (the env pool, tracked defer scopes, the call stack) already had its own release call in `spawn_thread_entry` -- this one was simply missing, not deliberate. Fixed directly: a new `ziman_thread_heap_release()` (`gc_thread_heap.c`/`.h`), called from `spawn_thread_entry` alongside the others. Safe because nothing on another thread should ever hold a pointer into a dying thread's own heap -- crossing a `Channel`/`spawn` boundary already deep-copies first (see below), never sharing a sender's own `gc_heap` objects directly.

**Second, and the harder one: `value_copy.c`'s own "outbound arena" was *never* destroyed, by design, until now.** Documented plainly in its own header comment since the day it was built: "every thread gets its own outbound arena, created lazily on first use and never destroyed -- deliberately leaked, the honest interim answer MEMORY.md already gives, until a real reclamation story... gets designed." That design note turned out to be exactly right about what was missing, and exactly where the second half of this crash came from: any thread that ever calls `send`/`spawn` burns one more permanent `GC_add_roots` registration, forever.

Given the severity and that a real fix meant genuine design work with real tradeoffs (not a one-line patch), this was a case for asking rather than guessing: raise `MAX_ROOT_SETS` as a stopgap, design real reclamation, or stop and reassess scope. Chosen: design real reclamation now.

**The design.** `value_deep_copy` (one function, one `__thread` arena reused forever) becomes two: `value_copy_send(v, &arena_slot)` on the sending side, `value_copy_receive(v)` on the receiving side. `arena_slot` is lazily created -- *only* the first time something actually needs `arena_alloc` (a new `lazy_arena` helper, threaded through every `arena_*_copy` helper in place of a bare `Arena *`) -- so sending a scalar, or a `Channel` itself, costs nothing at all: no `mmap`, no `GC_add_roots` call, exactly as cheap as before this fix existed. Several values crossing together (a `spawn`'s own args plus its `on_error` handler) share one arena via the same `arena_slot`, rather than each getting its own. `value_copy_receive` is the new half: a full second traversal, mirroring `value_copy_send`'s own per-kind shape exactly, but calling the *real* constructors (`value_string_copy`, `struct_obj_new`, `array_obj_new`, `value_bigint`, `result_obj_new`, `enum_obj_new`, a hand-built `ClosureObj` preserving the original's own `Type` the same way the send side already does) instead of `arena_alloc` -- so a received value becomes, from the receiving thread's own perspective, indistinguishable from one it built itself. Once every value sharing a given arena has been through `value_copy_receive`, that arena is `arena_destroy`-ed -- `GC_remove_roots` runs inside `arena_destroy` already, so the registration is undone the moment it's no longer needed, not left to accumulate.

**Two crossing points, wired the same way, one already-existing (transparent) and one new.** `ChannelObj`'s own internal queue (`value.c`) now holds `{Value, Arena *owner_arena}` pairs instead of bare `Value`s -- `owner_arena` NULL for an ordinary send (`prelude.c`'s `guard_finalizer`, unchanged). Every receive-side function (`channel_receive`/`_timeout`/`try_receive`, and `select2` transitively through `try_receive`) now finalizes transparently: pops the pair, and if `owner_arena` is non-NULL, runs `value_copy_receive` and `arena_destroy`s it before returning -- *no interpreter.c receive-side call site needed to change at all*. `channel_send`/`channel_try_send_status` gained an explicit `owner_arena` parameter, and destroy it themselves on the "never actually queued" paths (channel closed, or full for the non-blocking `try_send`) so a value nobody will ever receive doesn't leak its own crossing arena either. `STMT_SPAWN`/`spawn_thread_entry` (interpreter.c) is the second crossing point, with no `ChannelObj` involved: `SpawnArgs` gained a `crossing_arena` field, and `spawn_thread_entry` runs `value_copy_receive` on every arg plus the handler (if any) *before* `call_function` or a failure path's own `thread_failed` ever reads them, destroying the shared arena once, only after all of them are done -- never partway through, which would use-after-free whichever value hadn't been copied out yet.

**A second, genuinely new bug this same redesign surfaced, found empirically, not by inspection**: `thread_crossing_deep_copy.zm` (an existing regression fixture) started intermittently failing -- the very last line, an `on_error` handler's captured string, printed blank instead of its real content. Adding a debug `fprintf` to inspect the value made the failure disappear entirely -- the signature of a genuine race, not a logic bug, confirmed by running it ten times in a row and getting ten clean passes. **Root cause**: `sa->handler` (`SpawnArgs`), once safely re-copied via `value_copy_receive`, is referenced by nothing except `sa` itself -- a plain `malloc`'d struct -- from that point until `thread_failed` actually reads it, which only happens *if* the call later fails, arbitrarily far into that call's own execution. Under the old design, this was always safe *by accident*: the captured string lived in an arena Boehm itself treated as a scanned target, and Boehm scans every `GC_MALLOC`'d block (`sa` included) on every cycle, needing no explicit rooting at all. The moment `value_copy_receive` moved that string onto *this thread's own `gc_heap`* (this session's own mark-sweep collector, which only ever finds roots via the C stack or an `Env` chain -- never by scanning arbitrary heap structs), the accidental protection vanished: nothing this module's own two root sources already walk would ever find `sa->handler` again. The debug `fprintf`'s own local variable, sitting on the C stack, was accidentally providing exactly the protection that had quietly gone missing.

Fixed the same way every other root-source gap this session has been closed: a new, explicitly-scoped root source, `t_pending_handler`/`t_has_pending_handler` (`interpreter.c`, mirroring `t_defer_envs`/`t_env_pool`'s own shape), set the moment `spawn_thread_entry` has its own safe copy of the handler, walked by `mark_this_threads_roots`, cleared once the call either succeeds (handler moot) or `thread_failed` has already used it. `sa->args[]` needed no equivalent fix: `call_function`'s own parameter binding happens in straight-line C code immediately after they're copied, with no `exec_stmt`/`maybe_collect` call possible in between -- only `sa->handler`'s conditional, arbitrarily-delayed use was exposed.

Verified: `thread_crossing_deep_copy.zm` (the fixture that caught this) passes cleanly ten runs in a row after the fix; the "closed channel" and "full channel" `try_send` failure paths each confirmed directly (a small fixture per case) to still report the correct status *and* not leak the arena (`valgrind --leak-check=full`, 0 bytes definitely lost in both); the full suite (831/831) stable across five repeated runs on both builds; all nine standalone `gc_*` unit tests pass (the five that link `value.c` needed `src/value_copy.c` added to their own Makefile targets, a new real dependency `channel_finalize_received` introduced); `valgrind --leak-check=full --undef-value-errors=no` against `thread_crossing_deep_copy.zm` reports 0 bytes definitely or indirectly lost. **And, for the first time since any of this session's `gc_heap` migrations shipped**: `tests/bench/server_concurrency.sh` against the real `health-record-backend-ziman` app completes all four concurrency levels (`c=1,4,8,16`, 3000 requests each) with zero failures and no crash -- `c=1` 474 req/s, `c=4` 773 req/s, `c=8` 689 req/s, `c=16` 454 req/s. The underlying *throughput* shape this benchmark was originally built to diagnose (declining past its own peak under rising concurrency) is still present and not yet this entry's concern -- fixing the crash was the prerequisite for being able to measure it at all, not a fix for it. Still ahead, unchanged from before: more allocation sites need migrating (`env_new`/call frames next) before that shape itself can be meaningfully re-addressed.


## "env_new/call frames" turns out to be narrower than it sounds, and a `perf` profile under real concurrent load confirms the collector (not any one allocation site) is still the dominant cost (2026-09-30, F2)

Before touching anything, re-read every `env_new`/`env_free`/`env_reset` call site in `interpreter.c` rather than assuming the roadmap's own phrasing described unexplored ground. It didn't: `call_function`'s own top-level scope has gone through `env_pool_acquire`/`env_pool_release` (reused across calls, no Boehm churn in steady state) since before this session began, and *every* loop kind (`while`/`for`-range/`for`-iterator/`for`-map/`for`-array) already allocates one scope for its *whole* run, `env_reset` per iteration -- also pre-existing. The one unpooled, per-execution `env_new`/`env_free` pair left anywhere in the interpreter was `exec_block` (every `if`/`else` body, every bare `{...}` block). Flagged this re-scoping to the user rather than guessing at which reading of "env_new/call frames" was intended -- chose pooling `exec_block` first, then re-measuring, over going straight for a full Env-to-`gc_heap` redesign.

**The fix itself was a one-line change**, not a new mechanism: `exec_block` now calls `env_pool_acquire(parent)`/`env_pool_release(scope)` -- the exact function pair `call_function` already uses -- instead of a bare `env_new(parent)`/`env_free(scope)`. Already fully generic (re-parents on acquire, only assumes `defer_count` is already 0 on release, true here for the identical reason it's true for `call_function`: `exec_stmts_in_scope`'s own `run_defers` call, which every path through here already goes through). Verified: full suite 831/831 stable across repeated runs on both builds; the real `health-record-backend-ziman` suite passes in full (every request handler's own `if` statements now exercise the pool).

**Re-measuring found this didn't move the needle, and said something more important along the way.** Three concurrency-benchmark runs (one before pooling, two after) at `c=16`: 454, 432, 528 req/s -- a 20% swing between two *consecutive* runs of the *identical* binary, meaning the pooling change's own effect, if any, is smaller than this benchmark's own run-to-run noise on this machine. The decline-past-`c=4` shape persists in every run, pooled or not.

**Rather than guess at another allocation site to migrate blind, profiled the real server under real concurrent load with `perf record` (`-g --call-graph dwarf`, wrapping the server as `perf`'s own child -- attaching to an already-running PID was silently restricted in this environment, 0.003 MB captured; launching the server *as* `perf record`'s own child worked immediately, 300 MB).** `ab -n 3000 -c 16` against `/api/me/allergies` while recording. The flat profile confirms F2's own original diagnosis in concrete, current numbers, not just repeats it: `GC_mark_from` alone is **18.17%** of all sampled CPU time; `pthread_mutex_trylock`/`GC_generic_lock.part.0`/`__GI___lll_lock_wait`/`__GI___pthread_mutex_unlock_usercnt`/`GC_header_cache_miss` (Boehm's own locking and bookkeeping around its shared heap) add another **~26%**; this session's own `gc_mark_struct`/`gc_mark_closure`/`gc_mark_into`/`gc_mark_array`/`gc_lookup` (triggered because `value_string_copy`/`struct_obj_new`/`array_obj_new` *are* migrated, and every real `gc_heap_collect` cycle now has to trace through them) add roughly another **7%**. **Altogether, close to half of all CPU time under this exact concurrent workload is garbage-collection-related** -- confirming the whole premise of the "one heap per thread" redesign is still the right target, not something this session has already over-invested in.

**`env_define`/`env_lookup`/`exec_stmts_in_scope` together are under 1.3%** of the same profile -- hard, direct confirmation that `Env` was never where the remaining volume lives, exactly consistent with the inconclusive benchmark result above. Caller attribution for Boehm's own `GC_malloc_kind`/`GC_generic_malloc_many` came back too fragmented across many small call paths (the largest single caller fraction under 0.3%) to single out one obvious next allocation site the way `value_string_copy`/`struct_obj_new`/`array_obj_new` each were in turn -- unlike every migration so far, there isn't yet a clear "this one thing" to point at next.

**A second, separate, already-acknowledged cost also showed up clearly, explicitly out of scope here**: `__strcmp_avx2` alone is **8.9-10.9%**, with `native_lookup` (name-based dispatch for every native function call) adding another ~2%, and `eval_expr`'s/`exec_stmt`'s own name-comparison chains contributing more underneath both. This is F2's own *other*, already-diagnosed half -- "resolve identifiers to slots or compile to closures... independently of whatever the collector ends up costing under concurrency" -- not a new finding, and not this entry's concern: `env_lookup_resolved`/`env_at_slot` already solved this for ordinary variable references (env.h's own doc comment), but evidently not yet for native-function dispatch by name, which this profile shows is still a real, separate cost under concurrent load specifically because every request runs through many native calls (`concat`, `len`, JSON/SQL/HTTP natives, ...).

Not yet decided: what the next allocation site to migrate actually is, given this profile didn't hand over an obvious single answer the way the first three did. Reporting these findings rather than guessing at one.


## `result_obj_new`/`enum_obj_new` migrate, a mechanical change that uncovered a genuinely new class of root-finding gap -- and a second, much worse bug in the first attempt to fix it (2026-09-30, F2)

With profiling unable to single out one obvious next allocation site, picked the next most natural continuation of the "narrowest possible slice" sequence anyway: `result_obj_new`/`enum_obj_new` (`value.c`) are the two remaining simple Value-wrapper constructors still on the ordinary allocator, and `gc_mark_result`/`gc_mark_enum` (`gc_mark.c`) already handle both kinds correctly, `is_gc_heap_object`-gated, since the header-corruption bug three entries up -- nothing had ever actually allocated one this way yet. The change itself was as mechanical as `struct_obj_new`/`array_obj_new` were: swap `malloc` for `gc_heap_alloc(ziman_thread_heap(), GC_RESULT/GC_ENUM, ...)`, nothing else.

**`csv_records.zm` (an existing fixture) started segfaulting immediately, every run.** Root-caused with a precise `gdb` backtrace (an `-O0` debug build, since `-O2` optimized away too many locals to inspect): the crash lands in `iter_handle_of` reading a `StructObj` whose own header, inspected directly (`gc_header_span()` bytes before the pointer), reads `GC_FREE` -- a real, swept object, not wild memory. The struct in question is an *inner* `Iter`, captured by an *outer* `Iter`'s own `close` closure (`lib/core/csv.zm`'s `csv.records` wraps `fs.lines`'s own line-reading `Iter` inside its own `iter_from`-built record `Iter`, closing the inner one from the outer's own `close`).

**The gap, once traced back**: `iter.c`'s `FromState`/`ArrayIterState` (the native state behind `iter_from`/`iter`, the latter named `iter_of_array` at the time) hold whatever `Value`s their own closures/arrays were built with (`FromState.next`/`.close`, `ArrayIterState.items`), referenced *only* through `it->state` -- a plain `calloc`'d (`GC_MALLOC`'d) struct, invisible to both root sources, for however long the `Iter` stays open. This is the identical shape to `ArrayBuilder`'s own disguised-handle gap two entries up -- and the fix built for that (`gc_mark_register_struct_content_marker`) already exists and is exactly the right tool. Registered one for `"Iter"` (`iter_mark_contents`, `iter.c`): looks up the real `IterObj*` behind the disguised handle, discriminates `FromState` vs. `ArrayIterState` by comparing `it->next` against `from_next`/`array_iter_next` (the same function pointer set once at construction, doubling as a tag, no separate one needed), marks whatever it finds. An `Iter` a program has already closed (not in `g_iters` any more) needs nothing marked, mirroring how `iter_advance`/`iter_close_handle` themselves already treat that state as done.

**This alone did not fix the crash -- the registered marker was never being called at all.** `gc_mark_register_struct_content_marker` only fires from `gc_mark_into`'s type-directed `TY_STRUCT` case (it needs a `Value`'s own `Type` to look the registration up by name); the *outer* `Iter` in `STMT_FOR`'s own `ITER`-loop handling (`interpreter.c`) is a bare C local (`iterable`), found only by the stack scan, which dispatches through the type-*less* `gc_mark_object` -- no `Value`, no type name, no way to reach the registration at all. `ArrayBuilder`'s own fix never hit this gap because an `ArrayBuilder` value is always bound to a real Ziman `val`/`var` while alive, so `gc_mark_env_chain`'s own walk (type-directed) always finds it regardless of what the stack scan does. A for-loop's own `iterable`, by contrast, is never a Ziman-level binding at all -- purely this interpreter's own internal bookkeeping for the loop's duration.

**The first fix attempt made this dramatically worse, not better, in a way that looked nothing like a GC bug at all.** Tried binding `iterable` into the loop's own `scope` Env under a reserved name (`env_define(scope, "<iter>", ...)`), reasoning that this would put it on the type-directed path `gc_mark_env_chain` already walks. It compiles, it runs -- and corrupts a *different* program entirely: the type checker's own `env_lookup_resolved` had already assigned `binder1`/`record` a fixed compile-time slot index (`env_at_slot`'s whole point, docs/env.h's own comment), computed with *no knowledge* that this extra runtime-only binding would ever exist. Adding it shifted every later binding's *actual* runtime slot by one, silently, while the type checker's own resolved index kept assuming the old layout -- any fast-path read of `record`/`binder1` through `env_at_slot` now read the *wrong slot*, surfacing as reading uninitialized/garbage stack memory (`type.kind` a nonsense four-billion value, not a `GC_FREE` header) rather than anything recognizable as a sweep. A completely different failure *signature* from everything else is itself worth noticing, not explaining away: it was a hint that one bug got traded for a different one, not that anything got fixed. Caught immediately by re-running the exact crashing fixture under the new "fix," seeing the corruption pattern change shape, and treating that shape change itself as evidence rather than assuming progress.

**The real fix**: `t_active_iters` (`interpreter.c`), a `__thread` stack of the `Iter` value(s) a `for ... in <iter>` loop on *this* thread is currently driving, innermost last (nested `Iter`-loops are the only way more than one is ever active on one thread at once) -- mirroring `t_defer_envs`'s own exact shape (a `GC_MALLOC_UNCOLLECTABLE`-backed growable array, for the identical "the collector does not reliably scan thread-local storage" reason `t_defer_envs`'s own comment already states), marked directly by `mark_this_threads_roots` via `gc_mark_value` (type-directed, so the registered content marker *does* fire). Pushed right before the `ITER`-loop's own `while` begins, popped on every exit path (both the early `CTRL_RETURN` return and the loop's own normal/`break` fallthrough) -- no `Env`/slot-resolution machinery touched at all, sidestepping the first attempt's entire failure mode by construction.

Verified: the exact crashing fixture (`csv_records.zm`) passes clean, fifteen runs in a row; a new, dedicated, minimal regression fixture (`tests/lang/gc_iter_state_survives_collection.zm` -- two nested `iter_from` sources, the outer's `close` closing the inner, `os.collect_garbage()` forced every outer iteration) confirmed to crash reliably without the fix (`git stash` on just the source changes) and pass cleanly with it; full suite 832/832 (with the new fixture) stable across five repeated runs on both builds; all nine standalone `gc_*` unit tests pass; the real `health-record-backend-ziman` suite passes in full; `valgrind --leak-check=full --undef-value-errors=no` on the new fixture reports 0 bytes definitely or indirectly lost, errors beyond that only the same already-characterized pre-existing Boehm/valgrind `GC_mark_from` interaction. A separate, pre-existing, unrelated 4,800-byte `getline`-buffer leak in `csv_records.zm` (`iter.c`'s own `LineSource.buf` management) was checked against the pre-migration baseline and confirmed to already exist there too -- not introduced by, or this entry's concern to fix as part of, this work.


## `Map`/`Set`'s own wrapper migrates -- the bigger, costlier step flagged in advance, and a third instance of the same root-finding shape (2026-09-30, F2)

The next candidate after `result_obj_new`/`enum_obj_new` was less obvious than the first four: `MapObj` (`mapobj.h`) wraps a persistent hash trie (`MapNode`/`Leaf`, 32-way, bitmap-compressed), not a flat struct, so migrating it meant a genuinely new `GcKind` and new mark-phase logic, not just swapping `malloc` for `gc_heap_alloc` in an already-handled kind -- and migrating only the 24-byte wrapper (leaving the trie itself, where a map's real memory lives, on the ordinary allocator) had real, honestly-uncertain payoff. Flagged this explicitly before starting (bigger step, uncertain win, a proven pattern of surfacing bugs each time) and asked how to proceed; chose to go ahead.

**The migration itself, scoped narrowly on purpose.** A new `GcKind`, `GC_MAP` (`gc_object.h`), for the wrapper only. `gc_mark_map` (`gc_mark.c`) mirrors every other per-kind marker here exactly: `is_gc_heap_object`-gated header mark, then always walks entries via the existing `mapobj_entries` call regardless (a plain not-yet-migrated `MapObj` can still hold gc_heap-managed keys/values, same reasoning as every other kind). Wired into both dispatch paths -- `gc_mark_into`'s `TY_MAP`/`TY_SET` case (type-directed) and `gc_mark_object`'s new `GC_MAP` case (type-less, for a bare stack-scan-found candidate) -- a lesson directly carried over from the `Iter` entry just above: a kind only reachable from *one* of the two paths is a kind with a real gap, so both got it from the start this time, not after a second crash. Four allocation sites migrated (`mapobj_empty`/`mapobj_set`/`mapobj_remove`/`mapobj_snapshot`); `mapobj_mut_new` (the builder-private, in-place-mutated `MapObj` behind `MapBuilder`/`SetBuilder`) deliberately left alone -- it is never wrapped in a `TY_MAP`/`TY_SET` Value directly, only a `mapobj_snapshot` of it ever is, so it was reasoned to need no real header at all.

**That reasoning missed that `mapobj_mut_new` is `return mapobj_empty();`** -- the exact function just migrated. `map_set_builders.zm` (an existing fixture) and `http_endpoints.zm` (which builds its own routing table through the same builder path) both started segfaulting, reliably, every run: `GC_realloc` crashing inside `node_insert_mut`, reallocating a `root` `MapNode` pointer read back out of a wrapper whose own bytes had already been zeroed. Root cause: `mb_mark_contents` (`prelude.c`), the content-marker already registered for `MapBuilder`/`SetBuilder` from the `ArrayBuilder` entry two up, only ever traced the map's *entries* (`mapobj_entries`, then marking each key/value) -- it never touched the wrapper's *own* mark bit, because when it was written `MapObj` had no real header to mark at all. The moment `mapobj_empty` gave it one, a real collection saw `buf->m`'s header as unmarked and swept it -- the third time this exact session has found a native-handle-held `Value` invisible to both root sources (`ArrayBuilder`'s own buffer, `Iter`'s own `FromState`/`ArrayIterState`, now a builder's own `MapObj` wrapper), but the first time the handle *itself*, not something it merely points to, needed protecting.

**The fix reuses existing machinery rather than adding more**: `mb_mark_contents` now builds a throwaway `Value` (`type_scalar(TY_MAP)`, `.as.map = buf->m`) and calls the already-public `gc_mark_value` on it -- `gc_mark_map`'s own `is_gc_heap_object`-gated header handling runs exactly as it would for any other `TY_MAP` value, no logic duplicated. (`gc_mark_map` never reads anything off a `Value`'s `Type` beyond the `.kind` tag that dispatches to it, so `type_scalar`'s zeroed `elem`/`struct_name` fields are harmless.)

**A related, pre-existing inconsistency, found while auditing rather than by a failing test**: `gc_copy.c` (Phase 3's own superseded copying design, confirmed unused by the live interpreter -- its own test file already documents skipping `Map`/`Set` coverage for exactly this reason) builds its own `TY_MAP`/`TY_SET` case through `mapobj_empty`/`mapobj_set`, which now allocate into the *calling thread's* `GcHeap`, not the `dest` arena `gc_copy_value` is explicitly handed -- a real inconsistency with that function's own contract, but one nothing currently exercises. Documented in `gc_copy.h`'s own comment rather than fixed: fixing it properly needs a design decision (thread a `GcHeap` through `gc_copy_value`, or give `mapobj_empty`/`set` an explicit-destination variant) that's out of scope for a migration serving the live interpreter, not dead code.

Verified: both fixtures the bug broke (`map_set_builders.zm`, `http_endpoints.zm`) pass clean, ten runs each; a new dedicated regression fixture (`tests/lang/gc_mapbuilder_wrapper_survives_collection.zm` -- fifty `mapb_set` calls, `os.collect_garbage()` forced after each) confirmed to crash reliably without the fix (`git stash` on just `prelude.c`) and pass cleanly with it; full suite 833/833 (with the new fixture) stable across five repeated runs on both builds; all nine standalone `gc_*` unit tests pass; the real `health-record-backend-ziman` suite passes in full; `valgrind --leak-check=full --undef-value-errors=no` on both the new fixture and `map_set_builders.zm` reports 0 bytes definitely or indirectly lost, errors beyond that only the same already-characterized pre-existing Boehm/valgrind interaction. `tests/bench/server_concurrency.sh` afterward, run twice: 475/929/843/570 and 484/943/802/591 req/s (`c=1,4,8,16`) -- both runs, at every concurrency level, above the best of the three *pre*-migration runs (492/892/689/528), `c=8` and `c=16` by a clear margin (689->802-843, 528->570-591) well outside the run-to-run noise band those three earlier runs established (a ~20% swing between back-to-back runs of the *identical* binary, per the "env_new/call frames" entry above). A real improvement, not yet rigorously isolated from everything else changing between these measurements (this is still the same `c=4`-peak-then-decline shape the original diagnosis described, just shifted upward), but consistent with the story: routing and JSON construction (this real app's own dominant `Map`/`Set` use, via `lib/http/server.zm`'s own route table and every JSON response body) now allocate their map wrappers off Boehm's shared, locked heap instead of through it.
