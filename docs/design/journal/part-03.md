## Variadic, `Ord`-bounded `min`/`max` (2026-09-28)

`min`/`max` had quietly fallen behind `compare`/`sort`: fixed at exactly two arguments, and hardcoded to the four numeric scalars (`int`/`float`/`bigint`/`decimal`) even though `Ord` -- the bound `compare` and `sort` already generalize to any scalar, struct, enum, array, `Option` or `Result` that supports it -- existed for exactly this purpose. A user asked for it directly: `fn <T: Ord> min(T... items)`.

**Variadic, the same convention a declared `T...` parameter already gives a caller.** Two or more individually-listed arguments, or exactly one already-built array as the whole list (`min(a, b, c)` and `min(items)` both work, never both at once) -- not a new mechanism, the identical rule "Variadic parameters" documents for an ordinary function, just implemented by hand in `min`/`max`'s own special-cased type-check block (`typecheck.c`) since a builtin doesn't go through the parser's `param...` machinery at all. At least one value is required: `min()` is a compile-time error, an empty array argument a runtime one (there is no identity element for "the smallest of nothing," unlike `sum`'s `0`).

**`Ord`-bounded, via `type_supports_ordering` -- the exact function `compare`'s own type-check already calls.** Every argument (or the array's element type) must satisfy the same rule `compare`/`sort` use: the six scalars, or an array/`Option`/`Result` of `Ord` parts, or a struct/enum with its own `<type>_compare`. `byte` was previously excluded from `min`/`max` specifically (`docs/SYNTAX.md`'s old wording: "not a number to compute with... no abs/min/max"), on the reasoning that arithmetic and `byte` don't mix. That reasoning still holds for `abs` -- but `min`/`max` here are not arithmetic, they're an ordering choice, and `byte` already satisfies `Ord` (`compare`/`sort` already treat it as ordered): excluding it from `min`/`max` specifically was an inconsistency this generalization surfaced and fixed, not a new decision to make.

**No new native fast path needed for numbers or strings.** The runtime side (`value_min_max` in `interpreter.c`) is one linear scan calling `value_compare` per candidate -- the exact function `compare`'s own runtime dispatch already uses, whose `TY_INT`/`TY_FLOAT`/`TY_BIGINT`/`TY_DECIMAL`/`TY_BYTE`/`TY_STRING` cases are already direct C comparisons, not a call through the interpreter. That already *is* the native path a hand-written one would have added; only a struct/enum falls through to actually calling a `<type>_compare` `FunctionDecl`. This is unlike `collections.sort`, which gives a packed `[int]`/`[float]`/`[byte]`/`[string]` array its own native sort routine for real -- that optimization pays for itself at O(n log n) comparisons; `min`/`max` only ever do O(n), where the per-call dispatch overhead `value_compare` already avoids for scalars is the whole story.

Verified: `tests/lang/min_max_variadic` (ints, an array argument, strings, a single argument, a struct via `person_compare`), `min_max_no_args_rejected`, `min_max_empty_array_rejected`; `min_max_type_mismatch` updated for the new "every argument" wording (previously "both arguments", back when there were only ever two).

*(2026-10-22: both of the implementation claims above have expired, and in the direction this entry was pushing.* **`min`/`max` are ordinary `native fn` declarations in the `math` module now, called `math.min(a, b)` behind a `use math`.** *Two steps on one day. First the special-cased type-check block went: the declaration `#[at_least_one] pub native fn min<T: Ord>(values: variadic T) -> T` says everything the block said -- `variadic T` is the two-call-shape convention this entry had to implement by hand "since a builtin doesn't go through the parser's `param...` machinery at all", `T: Ord` is the bound, `#[at_least_one]` is the arity -- so the hand-written version was restating the declaration in C. All three of its refusals survived, two of them sharper: a mixed call now names the argument that fixed `T`, and the no-argument case comes from the attribute. Being an ordinary declaration also bought what a dispatched builtin could never take, a type argument and a named one: `math.min<int>(values: [1, 2])`.*

*Then the three of them left the prelude. `abs`, `min` and `max` were bare vocabulary -- no `use`, like `print` -- and are the `math` module's now, which cost 76 call sites across lib/, tests/, docs/ and the backend repo. The reason is the one this entry's own `byte` paragraph argues from: the prelude is the names a program gets without asking for them, and arithmetic beyond the operators is not among them. `math.floor` and `math.round` were already a `use` away and are no more specialised than `math.abs`. What stayed is `print`, `str`, `hash` and `compare` -- the first two accept anything, so no type's file could hold them, and the last two are the `Eq`/`Ord`/`Hash` protocol's verbs rather than arithmetic.*

*`value_min_max` in `interpreter.c` is `native_math_min_max` in `native_math.c`, unchanged except for how it reaches `compare`: a native is handed only its arguments, so the Module that `value_compare` needs to find a struct's own `<type>_compare` comes through a new `native_value_compare` in native.h -- the same reach-through `native_call_closure` already was. The scan is still one `compare` per candidate for the reason this entry gives, which has not expired.*

*One piece of it got simpler rather than moving. `collapse_variadic_args` runs before a native is entered, so `args[0]` is one array however the call was written, and the "two or more arguments, or exactly one array" test is gone from the implementation entirely. That test was also the one piece that could not be right for every `T`: `Ord` admits `[int]`, so `min` of two arrays and `min` of one array to spread looked identical to it. The declaration distinguishes them. `math.min([[3, 9], [1, 2]])` is `[1, 2]`.)*


## A bits module (2026-09-28, F3/P2-6)

Ziman has no bitwise operators in its own syntax (`&`, `|`, `^`, `~`, `<<`, `>>` don't exist as lexer tokens) -- P2-6 from the language-design review bundle. A user asked directly for bitwise functions on `int` and `bigint`, plus `BitSet`/`BigBitSet` "check Java for inspiration."

**A new module, not `number.zm`.** `number.zm` is about representation and conversion (hex, base64, byte-order, parsing); bitwise logic is a different concern with its own vocabulary (`and`/`or`/`xor`/`not`/`shift_left`/`shift_right`/`popcount`) that would swamp `number.zm`'s existing organization for six-times-three functions plus two set types. A sibling module, `bits`, keeps each file's job legible -- the same reasoning `math` split out of `number` for earlier for the rounding/`decimal_*` functions (see "Shortest-round-trip float display, and a `math` module" above).

**Naming: `<type>_<op>`, matching the existing `int_to_hex`/`bigint_to_hex` precedent** -- `int_and`/`bigint_and`, not a generic overload-by-argument-type scheme Ziman's function resolution doesn't support anyway. *(2026-10-19: it supports one now, F184 -- `int_and` and `bigint_and` differ in argument one and could be a single `and`. That `and` is a poor name for a function is a better reason to keep these apart than the one given here, which has expired.)*

**`int` is trivial; `bigint` is not.** `int`'s six functions are one-line wrappers over C's native `&`/`|`/`^`/`~`/`<<`/`>>` on `int64_t` -- the only wrinkle is that a shift amount must be range-checked to 0-63 (a runtime error outside that range, rather than the undefined behavior C itself gives a native shift by the operand's own width or more). `bignum.c` stores `bigint` as sign-magnitude in base-1,000,000,000 decimal limbs -- fast string conversion, no binary view at all -- so there is no bit pattern to `&` two bigints together. Matching Java's `BigInteger`/Python's `int` exactly means matching *infinite* two's complement: a negative number conceptually has infinitely many leading 1-bits, so `bigint_and(-1n, 5n)` is `5n`, not `0n`. The algorithm (`native_bits.c`): convert each operand's magnitude to little-endian base-2^32 words (repeated `bignum_divmod` by 2^32, reversed by Horner's method back into a `bignum_mul`/`bignum_add` chain when going the other way -- the same "not chasing performance, reuse the tested arithmetic" tradeoff the decimal-limb choice itself already made); bring a negative operand into two's-complement form over a common, padded word count (invert then add 1); do the operation word by word; read the top word's sign bit to know whether to negate the result back out to sign-magnitude. `bigint_not(x)` needs none of this -- it's `-(x + 1)`, Java's own definition, exact via plain bignum arithmetic. `shift_left`/`shift_right` go through a `bignum_pow2` (exponentiation by squaring on the existing `bignum_mul`) rather than word-level shifting, again reusing tested code over writing a second arithmetic primitive. `shift_right` floors (rounds toward negative infinity) for both `int` and `bigint`, unlike `/` which truncates toward zero: `int_shift_right(-3, 1)` is `-2`, not `-1` (`-3 / 2`).

**Validated against Python's own `int`, not hand-derived.** Every `bigint` test value in `tests/lang/bits_bigint.zm` was cross-checked with `python3 -c "print(...)"` -- Python's arbitrary-precision `int` already implements the exact target semantics, so this is an oracle, not a second hand-worked derivation that could repeat the same mistake twice. All values matched exactly, including large numbers and every sign combination.

**`byte` came later, added after finishing `int`/`bigint`/`BitSet`/`BigBitSet` in response to a follow-up question ("should we add byte flavor of bit functions?").** It rounds out all three integer scalars and is the simplest of the three: unsigned, so `not`/`shift_right` need no sign handling at all, and shifts are naturally bounded to 0-7 (a byte is 8 bits). `popcount` exists for all three types (`int_popcount`/`bigint_popcount`/`byte_popcount`); `bit_length` only for `bigint`, where it earns its keep computing `BigBitSet.length()` in O(digits) rather than a scan (see below). `crypto.bytes_xor` was already there for `[byte]` arrays; this module's `byte_*` functions are for a single scalar byte, a gap that existed but was left for later on purpose during the initial design conversation.

**`BitSet`/`BigBitSet`: a Java-`BitSet`-inspired value type, not a native handle.** `BitSet` (backed by one `int`, indices 0-63) and `BigBitSet` (backed by one `bigint`, unbounded) both give `new`/`of_<repr>`/`to_<repr>` (raw conversion), `set`/`clear`/`flip`/`get`, `and`/`or`/`xor`/`and_not` (set algebra), `is_empty`, `cardinality`, `length`, `to_string`. `BitSet` rejects an out-of-range index (>= 64, and negative); `BigBitSet` rejects only a negative index, since it has no upper bound. Both are ordinary Ziman value types, not a native opaque handle -- `set`/`clear`/`flip` return a new value, same as every other Ziman type.

**Decided against mutable native-handle builders, after actually checking whether they'd help.** `ArrayBuilder`/`MapBuilder` exist because their backing storage is a real buffer that grows -- pushing into one avoids an O(n) copy per push. A `BitSet`/`BigBitSet`'s entire state is one scalar (`int` or `bigint`); there is no O(n)-copy cost a builder would save, since a single `int_or`/`bigint_or` already touches the whole "buffer" either way. Presented as an explicit choice ("no real performance benefit, unlike ArrayBuilder/MapBuilder... 3 options") and the user picked skipping builders entirely -- `var` plus the immutable functions above do the same job with no new machinery.

**`BigBitSet.length()` uses `bigint_bit_length` (native, O(digits)), not a scan** -- a loop with no fixed bound to stop at would be far slower for a set with a very large member, exactly the reasoning that put `popcount`/`bit_length` in `native_bits.c` in the first place rather than building them from the bitwise primitives in pure Ziman.

**A real performance bug found and fixed during implementation: `big_bitset_to_string` recomputing `1n << i` from scratch per scanned index.** The first version looped `i` from 0 to `length - 1` calling `big_bitset_get(bs, i)`, each call computing `bigint_shift_left(1n, i)` independently -- O(length log length) bignum multiplications on a growing operand, since each of `length` calls redoes the full exponentiation-by-squaring for its own `i` rather than reusing the previous one's work. For a set with a member near index 2000 this took ~12 seconds, past the test harness's 5-second-per-fixture timeout. Fixed by scanning with a single working copy shifted right one bit at a time (`bigint_shift_right(remaining, 1)`, testing `bigint_and(remaining, 1n)` each iteration) instead of independently reconstructing `1n << i` per index -- O(length) small shifts instead of O(length log length) multiplications on operands that grow with `i`. This is specific to `BigBitSet`: `BitSet`'s `int_shift_left(1, i)` is a single native CPU shift regardless of `i`, so the fixed-size version's identical-looking scan was never at risk.

Verified: `tests/lang/bits_int`, `bits_int_shift_out_of_range_rejected`, `bits_bigint` (26 assertions, Python-oracle-checked), `bits_bigint_negative_shift_rejected`, `bits_byte`, `bits_byte_shift_out_of_range_rejected`, `bitset` (14 assertions covering the full API), `bitset_index_out_of_range_rejected`, `big_bitset` (indices past 64, including the AND/OR/XOR/AND-NOT set operations), `big_bitset_negative_index_rejected`.


## `number` limit constants: `byte`/`int`/`float` only, no `Double.MIN_VALUE` naming trap (2026-09-28)

A user asked whether `MAX_INT`/`MIN_INT` existed as global vars -- they didn't, anywhere in the language. Added `byte_min`/`byte_max`, `int_min`/`int_max`, `float_min`/`float_max`/`float_min_positive` to `number.zm`, as plain `pub val` (the same shape `math.pi`/`math.e` already use, not `MAX_INT` shouting-case -- this codebase's constants are lowercase `snake_case`, matching every function name).

**`bigint` and `decimal` get nothing, on purpose.** Both are arbitrary-precision; there is no finite bound to report, and inventing one (some "practical cap") would misrepresent the type -- the same "no artificial cap on ordinary arithmetic" reasoning `bigint_shift_left`'s own doc comment already gives for why its shift amount has no upper bound of its own.

**`float_min` means most negative, deliberately not Java's `Double.MIN_VALUE` meaning.** Java's `Integer.MIN_VALUE` is the most negative int, but `Double.MIN_VALUE` is the smallest positive *nonzero* double (a denormalized value near zero, not the most negative double) -- a well-known gotcha, asymmetric with its own `Integer` naming. Ziman's `float_min`/`float_max` are kept symmetric (`float_min == -float_max`) to match `int_min`/`int_max`'s own shape, and the denormalized-near-zero value got a distinct name entirely, `float_min_positive`, added after the user asked for it specifically as a follow-up ("I [want] smallest positive nonzero float as well. what should we name it?"). Presented as an explicit naming choice and confirmed by the user before implementing.

**Crossing a float limit overflows to infinity; crossing an int limit is a runtime error.** `float_max * 2.0` is `inf`, not an error -- float arithmetic already treats infinity as an ordinary representable value (this codebase's own stance: only `1.0 / 0.0` specifically is checked and rejected, not overflow in general). `int_max + 1` is a runtime error ("integer overflow in '+'"), consistent with every other `int` arithmetic overflow already in the language -- `int` never wraps around.

Verified: `tests/lang/number_limits` (all seven constants, `float_min == -float_max`, overflow to `inf`/`-inf` past either float end, underflow to `0.0` past `float_min_positive`), `number_int_max_plus_one_rejected`.


## Interpreter speed (F2): the GC, not `strcmp`, was the loop's real cost (2026-09-28)

Both reviews blamed the 3M-iteration loop's slowness (28x/4-5x slower than CPython) on `strcmp`-based identifier lookup down the `Env` scope chain, and named "resolve identifiers to slots" as the fix. Before writing a resolver, `perf record -g` on `tests/bench/loop_bench.zm` (the exact loop, extracted as a permanent benchmark) said otherwise: `__strcmp_avx2` and `env_lookup` combined were **2.03% + 2.09% of total time -- under 5%**. The other **~70%** was `GC_build_fl`, `GC_allochblk_nth`, `GC_clear_hdr_marks`, and pthread mutex lock/unlock inside `GC_generic_malloc_aligned` -- the Boehm collector's own allocation machinery. The reviews' diagnosis was a plausible guess that turned out to be wrong; measuring first caught it before a resolver got built to fix the wrong 5%.

**The actual cost: a fresh `Env` allocated and freed every single loop iteration.** `for i in 0..n { ... }` (and `while`) created a brand-new `Env` (`env_new`, a `calloc`) plus its binding array (`env_define`'s first call `realloc`s from a NULL, capacity-0 buffer to capacity 8 -- a real heap allocation of `8 * sizeof(Binding)`, and `Binding` is not small: a `Type` and a `Value` each) plus a `strdup`'d copy of the loop binder's name, every iteration -- then freed all three on the way out, every iteration. Three million iterations meant three million each of these malloc/free pairs, funneled through a collector whose allocator locks a mutex per call even in a single-threaded program. That churn, not string comparison, was the loop's real cost.

**The fix: one `Env` per loop, not one per iteration.** A new `env_reset(env)` (`env.c`) frees each binding's own `strdup`'d name and sets `count = 0`, *without* freeing `env` itself or its `items` buffer -- so the buffer's capacity survives from one iteration to the next, and a loop body with a stable number of declarations allocates nothing at all for its own bookkeeping after the first iteration. `STMT_WHILE` and all four `STMT_FOR` variants (range, lazy `Iter`, map/set, array) now allocate their scope once before the loop starts, `env_reset` it at the top of each iteration instead of `env_new`/`env_free` around it, and `env_free` it exactly once on every exit path (natural completion, `break`, or a `return` propagating out mid-loop) -- preserving the exact defer-running and control-flow-propagation behavior each loop already had, just with the scope's *lifetime* now spanning the whole loop instead of one iteration. Verified safe to reuse: nothing outside `interpreter.c`/`env.c` ever stores a raw `Env *` -- a lambda captures by *value* at creation time into a `ClosureObj` (each captured variable's current value is copied out, not a pointer to the environment it lives in), so no iteration's scope is ever aliased past that iteration's own end.

**Result:** `loop_bench.zm` (the 3M-iteration loop): **1.4s to ~0.3s, about 4-5x**. Re-profiling afterward shows `GC_*` symbols down to ~5% combined; `strcmp`/`env_lookup` are now a *relatively* bigger 12%/9% of a much smaller total -- a real target for a follow-on slot-resolution pass, just a much smaller one (perhaps another 15-20%) than either review's diagnosis implied. `tests/bench/scalar_arrays_bench.zm` (million-element array builders, less loop-scope-churn-dominated): 3.99s to 3.06s, about 25%. `fib_bench.zm` (`fib(27)`, recursive, no loop): unchanged (~0.47-0.52s) -- expected, since `call_function` still allocates one scope per *call*, not per loop iteration, a separate cost this change doesn't touch.

**Not done, and now correctly sized:** slot resolution, still a real but smaller win; `call_function`'s per-call scope allocation (the equivalent fix for function calls, which `fib`-shaped recursive workloads would benefit from, not loops); the "does not scale with clients" concurrency half of F2 (already diagnosed separately as the collector itself, not this).

Verified: full test suite (808 fixtures) and the `health-record-backend-ziman` SQLite integration suite (all 17 Python test files) both pass unchanged; `tests/bench/loop_bench.zm` and `tests/bench/fib_bench.zm` added as permanent regression-tracking benchmarks for this and any future interpreter-speed work.


## Slot resolution, and three ways two independently-built Env trees can disagree (2026-09-28)

The follow-on to the scope-reuse fix above: resolve each identifier's `Env` lookup to a `(depth, slot)` pair once, during type-checking, so the interpreter can jump straight there (`env_at_slot`) instead of re-comparing names down the scope chain every time the expression runs -- the fix the original reviews actually asked for, now correctly sized as a smaller win on top of the bigger one already done.

**Mechanism.** `Expr`/`Stmt` each gained `resolved_depth`/`resolved_slot` (-1 by default -- see `expr_new`/`stmt_new`). `env_lookup_resolved` (`env.c`) is `env_lookup` plus reporting how many `->parent` hops and which `items` index the match was found at. The type checker's four places that look an existing name up (`EXPR_IDENT`, `call.local_name`, `STMT_ASSIGN`, `STMT_VALUE_BLOCK`'s assign-target) call it and store the result; the interpreter's same four places use `env_at_slot(env, depth, slot)` when `resolved_depth >= 0`, falling back to the original name-based `env_lookup` otherwise.

**The premise -- that the type checker's `Env` tree and the interpreter's are built in lockstep, so a slot computed by one means the same thing to the other -- turned out to have three genuine exceptions, not zero.** Each was found the same way: implement the seemingly-obvious version, run the full suite, and follow the first wrong answer to its actual cause rather than assuming the first fix was complete.

1. **A capture, or anything past it (including a global).** A lambda's *runtime* call frame is rooted directly at the global env -- a capture is a value copied into one of its own leading parameters at call time, never found by walking up to the scope the lambda was defined in (see `call_function`'s closure-calling path). But type-checking a lambda's body walks the *compile-time* nested chain, where its root is nested inside whatever scope contains the lambda literal -- a different hop count for anything not found inside the lambda's own scopes. Fixed by leaving `resolved_depth` at -1 whenever the search crosses an `is_lambda_boundary` scope to find its match, `is_global` or not.

2. **A global val itself, boundary or not.** `init_param_defaults` (interpreter.c) defines one `g_global_env` slot per omitted-`Option<T>`-default parameter, anywhere in the whole program, *before* `init_global_vals` defines the real module-level vals -- but the type checker never calls `env_define` for those particular slots at all (a reference to one is a synthetic `EXPR_IDENT` with its type pre-filled by `make_default_ref_expr`, bypassing `check_expr` -- and this whole resolution pass with it -- entirely, since "the global-env slot it names isn't defined until interpretation starts"). A global's index at check time and at run time are consequently not guaranteed to be the same number. First reproduced as `global_val_basic` printing `Some(20)` for `print(greeting)` -- not a crash, a *confidently wrong answer*, because slot indexing doesn't know it read the wrong thing the way a NULL-checking name lookup would. Fixed by also leaving `resolved_depth` at -1 for any match found in `is_global` scope, unconditionally.

3. **A lambda's own declared parameter, when the lambda captures anything at all.** `check_lambda` builds its root scope's env from the declared parameters, in order, *before* checking the body -- but by the time the body-check finishes discovering what the lambda captures, those captures get prepended to the *front* of the same `FunctionDecl`'s param list for `call_function` to bind them from at call time (see ast.h's `lambda_ncaptured` comment). So the parameter root's own env put at index 0 stays index 0 in the type checker's own bookkeeping, but `call_function` actually binds it at index `ncaptured` once any capture exists -- a shift with no way to predict while still walking the very body that determines whether there will be one. Found via `lambda_basic` (`add(5)` -- capturing `base` -- printing `20` instead of `15`, then segfaulting a few lines later). Fixed by also leaving `resolved_depth` at -1 for a match found directly in an `is_lambda_boundary` scope, no crossing required.

4. **`defer`'s own hidden variables -- fixed the opposite way from the other three.** `check_defer` synthesizes `$deferN$i` identifier references for a deferred call's arguments (evaluated once, at `defer`-statement time, into hidden variables the replayed call reads later) -- but never called `env_define` for them during type-checking, exactly the same bypass shape as case 2's default-parameter keys. Unlike a global, though, this happens inside an *ordinary function's own local scope* -- excluding the whole scope from the fast path (case 2's fix) would have meant losing the benefit for every other local in any function that happens to use `defer`, an unacceptably broad cost for a narrow problem. Fixed the other way instead: made `check_defer` call `env_define` for each hidden variable too, at type-check time, in the same order `interpreter.c`'s own `STMT_DEFER` handling already does at run time -- closing the gap by making the two trees agree, rather than by declining to trust either. Found via `migrate_basic` (`run_transaction`'s `val result` reading `$defer1$0`'s value instead of its own).

**Why four bugs in one pass, and why that's not a reason to distrust the fix now.** All four are the same underlying shape: something creates a binding, or a reference to one, *outside* the ordinary `env_define`-during-`check_stmt` / `env_define`-during-`exec_stmt` pairing this whole resolution scheme assumes is symmetric. Three (captures, globals, capturing-lambda-parameters) are structural properties of *where* a name lives, cheap to check per-lookup and safe to exclude permanently. The fourth (defer's hidden variables) was cheaper to fix at the source than to carve out. A grep for every other `expr_new(EXPR_IDENT, ...)` in `typecheck.c` (`mk_ident_expr`, used by the `switch` rewrite) confirmed no fifth instance: that one's synthetic references point at real, ordinarily-`env_define`d bindings from the rewritten statement tree both phases execute identically, so it needed no special case.

**A real false alarm along the way, worth recording so it isn't rediscovered:** `fib_bench.zm` appeared to regress from ~0.5s to ~0.9s between measurements taken minutes apart with no relevant code change in between. The machine is a hybrid Intel Core Ultra (P-cores and E-cores); an unpinned process can land on either from run to run, a 2x swing on its own. `taskset -c 0` pinning both the pre-slot-resolution and post-slot-resolution binaries to the same core, six runs each, showed them statistically identical (4.951s vs 4.990s for 6 runs) -- correctly so, since `fib` never references more than one locally-scoped parameter per call, where a `strcmp` against an immediate first-scope match was already nearly free; slot resolution's win is specific to `loop_bench.zm`-shaped code with many lookups per unit of work, confirmed on the same pinned-core methodology (baseline 12.964s / slot-resolution 3.385s for 6 runs each, folding in the scope-reuse fix already committed).

Verified: full test suite (808 fixtures, including the three fixtures above whose exact failures diagnosed each bug) and the `health-record-backend-ziman` suite both pass; `loop_bench.zm`/`fib_bench.zm` re-measured pinned to a single core for a noise-free comparison.


## Call dispatch: cached, not re-scanned, and a per-call Env pool (2026-09-28)

Profiling `fib_bench.zm` after slot resolution (above) showed it hadn't gotten meaningfully faster, for a good reason: `fib` never crosses the pattern slot resolution speeds up (one locally-scoped parameter, found immediately). Two other costs dominated instead, both specific to *calling* a function rather than reading a variable inside one.

**`find_function` scanned every loaded function, by name, on every single call.** `eval_expr`'s `EXPR_CALL` case calls `find_function(module, e->as.call.callee)` to get the `FunctionDecl*` to run -- a linear `strcmp` scan over `module->functions`, which (same as `g_global_env`, see the bits-module and interpreter-speed entries above) holds every function from every loaded file, prelude and corelib included. `check_call` (typecheck.c) already runs this exact same scan once, at type-check time, to validate the call -- the result was simply never kept. Fixed by adding `call_fn` to `Expr` (ast.h), set once by `check_call` right after its own `find_function` succeeds, and read directly by the interpreter instead of re-scanning. Always non-NULL by the time interpretation reaches that branch (type-checking already required it to resolve for the program to compile), unlike `resolved_depth`/`resolved_slot`, which has a real "not resolved, fall back" state -- this doesn't need one.

**A fresh `Env` (plus its items buffer) was allocated for every function call, same as the per-iteration allocation the loop fix above already closed -- just for calls instead of iterations.** Fixed with a per-thread free-list pool (`env_pool_acquire`/`env_pool_release`, mirroring `t_defer_envs`'s own existing structure immediately above it in the file): `call_function` takes a pooled `Env` if one is available instead of `env_new`, and gives it back (via `env_reset`, not `env_free`) instead of discarding it. Safe for recursion specifically because call/return is strictly LIFO per thread -- a call's own `Env` stays alive as a local variable on the C call stack for exactly as long as it's in use, and is only released after every call *it* made has already returned its own borrowed `Env`, so the same object is never handed to two live calls at once.

**The GC-safety subtlety this reused, not reinvented:** the collector does not reliably scan thread-local (`__thread`) storage, so a pool array holding the only references to otherwise-unrooted `Env` structs risks the collector treating them as garbage while they sit in the pool between one call's release and a later call's reuse -- exactly the failure mode `t_defer_envs`'s own comment already documents and already solves, by allocating that array `GC_MALLOC_UNCOLLECTABLE` (a root the collector always scans) rather than through the ordinary `GC_MALLOC` a `ZIMAN_GC` build's `malloc`/`calloc` are redirected to (`zgc.h`). The new pool's array uses the identical allocation, and releases it at the identical point (`spawn_thread_entry`, right where `defer_envs_release()` already runs) so a long-running program spawning many short-lived threads doesn't accumulate one abandoned array per thread that ever ran. Verified with `valgrind --leak-check=summary` on the `nogc` build (real `malloc`/`free`, so a use-after-free or double-free would actually show up): zero errors, both for a plain recursive `fib` and for a `spawn`-heavy fixture (`array_push_threads`) that exercises the thread-exit cleanup path -- leaked-byte counts statistically unchanged from the pre-pooling baseline, the small increase that does show up fully explained by pooled `Env`s legitimately surviving until process/thread exit instead of being freed immediately after each call, bounded by the deepest recursion a thread ever reaches (itself already bounded by the existing stack-depth guard), not by total call count.

**A third, smaller find along the way: the ~48-branch builtin-name `strcmp` chain (`"print"`, `"str"`, `"format"`, ...) still ran in full for every ordinary call, `call_fn` or not.** `check_call`'s own matching chain only ever reaches its `find_function` fallback (setting `call_fn`) after every one of those branches has already failed to match at type-check time -- so `call_fn != NULL` is exactly as reliable a "definitely not a builtin" signal as it is a "definitely this function" one. Added a new branch immediately after `call.through_value`, checked first, that uses `call_fn` directly and skips the whole chain; the original chain (including its own old fallback) is left completely in place, unreached for this case rather than removed, as a zero-cost defensive fallback.

**A methodological note worth recording, not just the fix:** partway through, `loop_bench.zm` (which calls no user function in its hot path at all) appeared to speed up alongside `fib_bench.zm` after the pooling change, then *stayed* fast even with pooling and the dispatch bypass both temporarily disabled for an isolation test -- a result that made no causal sense for either fix. Comparing the incremental, one-fix-at-a-time measurements taken over the course of this session turned out to be comparing across real system drift (a long session of sustained heavy compilation and several `valgrind` runs on a hybrid P-core/E-core chip, the same machine the earlier `fib_bench` false-alarm regression came from), not across code changes. The fix was to stop trusting incremental deltas measured minutes apart and instead rebuild the true pre-session baseline and the final combined state side by side, then benchmark both back-to-back in the same short window: **`loop_bench.zm` 7.212s to 1.513s (about 4.8x), `fib_bench.zm` 2.650s to 0.660s (about 4.0x)**, six pinned runs each, immediately adjacent in time. These are the numbers to trust; the individual per-fix percentages quoted earlier in this session's investigation are not, and aren't repeated here for that reason.

Verified: full test suite (808 fixtures) on both the `ziman` (GC) and `ziman-nogc` builds, and the `health-record-backend-ziman` suite, all pass.


## `internal` visibility, a soft keyword, and a package boundary designed to be replaced later (2026-09-28, F3/P2-5)

The language-design review named a real gap (§4.2): `net.idle_put`/`idle_take`/`idle_clear`, `db.RunRequest`/`Page`/`OpenRequest`/`FetchRequest`/`EndRequest`/`Request`/`run_request`, and `datasource.PoolState`/`IdleConnection` are all `pub`, purely because Ziman's visibility was binary (private to one file, or exported to the whole world) and these are shared *between* a handful of the library's own files (`client.zm` calls `net`'s idle functions; `mysql.zm`/`pg.zm` call `db`'s request plumbing) with no way to say "shared among us, not exported beyond us." The review's own suggested fix was `pub(package)` or moving things into `_internal` modules by convention.

**Chose neither exactly as proposed, after the user asked for a C#-style three-tier model instead: `pub` / `internal` / private, in ascending order of reach.** `pub(package)`-as-proposed turned out to have a real problem once checked against the actual motivating case: `net.zm` lives in `lib/core/`, `client.zm` in `lib/http/` -- a directory-based "package" boundary would leave them in *different* packages and break the exact call it needs to allow. A bare `internal` keyword sidesteps the question of what a directory-based boundary should be entirely, by not being directory-based at all (see below).

**What "package" means today, chosen to be simple now and not wrong later.** Every declaration already carried a `source_file` (NULL for a bundled corelib module, a real path otherwise -- set in `load_module` from the same `from_disk` check that decides whether to fall back to the corelib source table). `Module` gained one new field from the identical check, `is_corelib`, and `same_package(a, b)` (loader.c) is exactly `a->is_corelib == b->is_corelib` -- the whole standard library is one package, a project is another, regardless of which subdirectory a file happens to live in. That single boolean comparison is *also* the reason this doesn't need to be redesigned when a real package/crate/JAR-style distribution system eventually exists (ROADMAP.md now tracks this as explicit future work): `same_package` is the one function such a system would change, to compare manifest identities instead of this one flag, supporting many distinct packages loaded together rather than just "corelib vs. everything else." Nothing about the `internal` keyword, `visibility_allows`'s call sites, or any already-written `internal` declaration's meaning would need to change -- the corelib simply becomes package `"std"` by convention.

**`internal` is a soft keyword, not a reserved one -- because a real collision was found before writing a line of parser code.** `health-record-backend-ziman` already has `pub fn internal<T>(result: Result<T, string>) -> Result<T, ServiceError>` (`service.zm:67`), imported via `use service.internal` and called as `internal(...)` across `token.zm`, `admin.zm`, `testdata.zm` and more. Making `internal` a reserved word the way `pub`/`struct`/`fn` are would have broken that real application outright. Fixed the way C# itself handles the identical problem for `var`/`async`/`await`: `internal` is recognized only by identifier text (`match_ident`, parser.c), at exactly the one grammar position `pub` already occupies (immediately before `fn`/`native fn`/`struct`/`enum`/`val`, checked only after `pub` itself fails to match, so the two are mutually exclusive by construction) -- and this codebase already had the identical technique in hand for `unit` (a word, not a keyword, recognized only where a type is expected). Everywhere else -- a function's own name, a local variable, an import -- `internal` is an ordinary identifier; `use service.internal` and `internal(x)` keep compiling exactly as they did before this feature existed. Verified directly: `service.internal`'s own real usage, re-tested standalone before touching anything else, and the full backend test suite passing unchanged afterward.

**Enforcement threads through the same ~8 sites `pub`/private already used**, in `loader.c`: `resolve_function_ref`, `resolve_type_ref`, `resolve_enum_ref`, `resolve_type_or_enum_ref` (twice, struct and enum), the "bare `module.name` used as a function value" soft-check, and `resolve_named_imports`. Each now calls `visibility_allows(visibility, referencing_module, target_module)` instead of testing a bare `is_public` bit; `FunctionDecl`/`StructDecl`/`EnumDecl`/`GlobalValDecl` all traded their `int is_public` for a shared `Visibility` enum (`VIS_PRIVATE`/`VIS_INTERNAL`/`VIS_PUBLIC`). `lsp.c`'s hover/signature rendering and its completion-list gating were updated the same way, deliberately less precisely for the latter: completion doesn't currently distinguish `internal`'s narrower same-package reach from `pub`'s (an internal symbol from a different package can still appear in a `module.` suggestion list), a minor imprecision in *suggestions* the compiler's own enforcement doesn't share -- teaching the LSP full same-package tracking for a suggestion list's own sake didn't seem worth it yet.

**The actual migration**, closing out the review's specific complaint: `net.idle_put`/`idle_take`/`idle_clear` (lib/core/net.zm), `db.RunRequest`/`Page`/`OpenRequest`/`FetchRequest`/`EndRequest`/`Request`/`run_request` (lib/db/db.zm), and `datasource.PoolState`/`IdleConnection` (lib/db/datasource.zm) are all `internal` now, not `pub`. `client.zm`/`mysql.zm`/`pg.zm` keep calling them exactly as before (same package); a project file referencing any of them now gets a compile-time error naming the violation.

Verified: full test suite (811 fixtures: 3 new -- `internal_visible_same_package` (a two-file project sharing an `internal` struct and function), `internal_rejected_cross_package` (a project file calling the now-`internal` `net.idle_take`, rejected), `internal_as_identifier_still_works` (the exact `service.internal` shape, imported, called, and shadowed by a local `val` of the same name)) on both builds; every `tests/integration/pg`/`tests/integration/mysql` fixture still type-checks (`--check`) against `db.zm`'s newly-internal request plumbing; the full `health-record-backend-ziman` suite passes unchanged, confirming its own real `internal` function is untouched by any of this.


## Recursive lambdas: a self-value rebuilt on every call, never captured (2026-09-29, F3/P2-8)

`val fact = fn(n: int) -> int { return if n <= 1 { 1 } else { n * fact(n - 1) } }` failed to type-check before this: `fact` isn't in scope yet while its own initializer is being checked, the same rule that already governs every other `val`. The language review named this directly (§2.2(j)): "Local named functions and recursive lambdas (a `let rec`-style name binding for lambdas)."

**The real obstacle is a bootstrapping problem, not a scoping one.** A lambda captures its free variables *by value*, copied out of the enclosing scope at the moment it's constructed. A lambda can't capture "a copy of itself" that way, because the closure value doesn't exist yet while it's still being built -- the classic `let rec` chicken-and-egg problem every ML-family language solves one way or another.

**Solved without ever trying to capture self as a value.** `FunctionDecl` gained `self_name` (the name, from `val NAME = fn(...) { ... }`, the body may call itself by) and `self_ncaptured` (how many of its own leading `params` are real captures, mirroring `lambda_ncaptured`). The name is bound *directly inside the lambda's own root scope* during type-checking (`check_lambda_expecting`, right where declared parameters are bound) -- not via an ordinary `env_lookup` that would cross back out to the enclosing scope, so referencing it is never recorded as a capture at all. At *call* time, not construction time, `call_function` (interpreter.c) already has everything it needs on hand -- the `FunctionDecl` being invoked and the actual captured values this specific invocation received (the leading `self_ncaptured` entries of its own `args`) -- so it synthesizes a fresh `value_closure` wrapping exactly those two things and binds it under `self_name`, fresh, on every single call. No mutable cells, no bootstrapping: a recursive call just reads that freshly-synthesized binding and dispatches through the *already-existing* mechanism for calling a local variable that holds a function value (`call.through_value`) -- no new call-dispatch code needed anywhere.

**Why this is safe against the exact slot-resolution bug class found earlier this session.** `self_name`'s binding lands in the lambda's own root scope (`is_lambda_boundary`), the identical shape as a declared parameter whose *runtime* index shifts once captures get prepended to `FunctionDecl.params` (case 3 of the interpreter-speed entry above). `env_lookup_resolved`'s existing exclusion for exactly that case -- "found directly in an `is_lambda_boundary` scope" -- already covers `self_name` too, for the same reason, with no new gating needed: a reference to it always falls back to ordinary name-based `env_lookup`, which doesn't care what index it landed at, only that the name matches.

**Only self-recursion, deliberately.** Two separately-declared lambdas calling each other (mutual recursion) needs both names hoisted before *either* body is checked -- a harder, genuinely different problem left out of scope rather than solved speculatively. `self_name` is set only for `val` (never `var` -- a reassignable binding would make "which function is self" ambiguous) and only when the return type is already written explicitly (an omitted one is inferred *from* the body, exactly what self-reference would need to already know) -- gating on this, rather than erroring whenever it's missing, matters: the first implementation set `self_name` unconditionally for every `val`-bound lambda and broke `lambda_basic.zm`'s `val hello = fn() { print(...) }` (an ordinary, non-recursive lambda with an inferred return type, the overwhelmingly common case) with a nonsensical "must write return type" error it never asked for. Caught immediately by the full test suite; fixed by only setting `self_name` when `!return_omitted`, so a lambda that doesn't opt into an explicit signature simply doesn't get self-reference -- exactly as before this feature existed, not a new restriction on it.

**Verified beyond the basic case**: self-recursion combined with a capture (the captured value must thread through every recursive call, not just the first); the recursive lambda used as an ordinary function value elsewhere (passed to another function, called through a completely different local name than the one it recurses by internally); a recursive lambda nested inside another function's own lambda, returned, and still recursing correctly after being reassigned outside; a parameter sharing `self_name`'s own name (compile error naming both); `var` and omitted-return-type cases confirmed to fall back to the ordinary "undefined function" error, not a new one. `valgrind --leak-check=summary` on the `nogc` build (real `malloc`/`free`): zero errors, confirming the fresh-per-call `value_closure` allocation has no use-after-free or double-free risk.

Verified: full test suite (815 fixtures: `lambda_recursive`, `lambda_recursive_var_rejected`, `lambda_recursive_no_return_type_rejected`, `lambda_recursive_self_param_collision_rejected`) on both builds; the `health-record-backend-ziman` suite passes unchanged.


## UTF-8 correctness: validate at the one real boundary, add code points as an opt-in (2026-09-29, F3/P2-3)

The language review found a real gap (§S9): `bytes_to_string` accepted *any* bytes as a string as long as they held no `0` byte -- `bytes_to_string([104b, 195b])` ("h" plus a lone, truncated UTF-8 lead byte) succeeded with `Ok("h\xc3")`, invalid UTF-8 that could then flow into JSON encoding or an HTTP response. Its own suggested fix, closely followed here: "validate at input boundaries, or offer `chars`/`substring_chars`... keep byte functions explicit."

**`bytes_to_string` is the one real boundary, so it's the one place this is checked.** Every other string function (`len`, `substring`, `char_at`, `index_of`, `to_upper`, ...) keeps counting and cutting bytes exactly as documented (`lib/prelude.zm`'s own header comment already states this design, deliberately, for speed on the common ASCII case) -- validating there too would mean re-validating on every operation instead of once, at the only point arbitrary, possibly-untrusted bytes (a socket read, a file, an HTTP body) actually become a `string` in the first place. Reused nothing from `regex.c`'s own UTF-8 decoder: that one is deliberately *lenient* (an invalid sequence falls back to one raw byte, so a regex never fails to match just because its input happens to be malformed) -- exactly backwards for a function whose whole job is to *detect* malformed input. `utf8_decode_strict` (`prelude.c`) is a new, independent, properly strict decoder: it rejects a truncated sequence, a bad continuation byte, an overlong encoding (the same code point spelled with more bytes than necessary -- a classic filter-bypass trick if a decoder accepts it silently), a surrogate half (U+D800-U+DFFF, never a real code point on its own), and anything past Unicode's own U+10FFFF ceiling. Verified specifically: `bytes_to_string([192b, 175b])` (an overlong two-byte encoding of `/`) is now rejected, naming the byte offset.

**Three new functions give the code-point-aware alternative the review's second suggestion asked for, without touching anything that already existed.** `chars(s) -> [string]` (split into individual code points), `char_count(s) -> int` (how many, cheaper than `len(chars(s))` when only the count matters), and `truncate_chars(s, max_chars) -> string` (shorten to at most `max_chars` code points without ever cutting one in half -- the review's own "no way to truncate text safely" named directly). All three are a runtime error naming the byte offset if the string isn't valid UTF-8 to begin with -- reachable only by chaining a byte-level function (`substring`, a `concat`'d slice) into one of these, since `bytes_to_string` already rejects invalid UTF-8 at the boundary where it would otherwise enter a program at all. Deliberately not a parallel API for every existing byte function (no `substring_chars`, no `char_at_chars`, no `index_of_chars`) -- `chars`/`slice`/`join` already compose for anything more elaborate than a straight truncation, and adding a whole second surface mirroring the first was judged not worth it against "keep byte functions explicit."

**Both worlds stay, on purpose.** This isn't UTF-8 replacing bytes as the default -- `len`/`substring`/`char_at` remain byte-oriented, unchanged, exactly as fast as before, for the (common) case where that's the right tool. Code-point functions are an opt-in for text a person will actually read, paying a real per-call cost (walking and decoding) that a byte-position function never has to.

> **(Reversed on 2026-10-23.)** Both worlds did not stay: `len`, `substring`, `char_at`, `index_of`, `last_index_of` and `is_char_at` all count characters now, `char_count` and `truncate_chars` are gone (their names became `len` and `truncate`), and `byte_len` is the opt-in for the byte question instead. The paragraph above is still the right account of *why* this was decided the other way, and the per-call cost it names is exactly what the reversal had to pay and then engineer away -- see "Text counts characters, and the ASCII bit that made it affordable (2026-10-23)". What it got wrong was the premise that byte offsets are "exactly right for ASCII": they are, and that is the problem, because a library written in them is silently wrong the first time its input is not.

Verified: full test suite (819 fixtures: `bytes_to_string_utf8_validation` (valid UTF-8, a truncated sequence, a bad continuation byte, an overlong encoding, a NUL byte -- one fixture, five `Result`s printed), `chars_basic`, `chars_invalid_utf8_rejected`, `truncate_chars_negative_rejected`) on both builds; `docs/lib/prelude.md` regenerated (`make corelib-reference`).


## Programmer errors are fatal (2026-09-29, F3/P2-4)

The last open piece of P2-4 (the rest done 2026-09-28: see "A unified `error_message` builtin" above). The language review found three different policies for the identical class of mistake (§4.2): `collections.sort_by_keys` returns an `Err` for mismatched array lengths, `crypto` says "a wrong argument is a runtime error," and `server.param` says asking for an undefined route parameter "is a fatal error -- it is a bug in your route function." **Decision, adopted exactly as the review proposed it: a programmer error (a bug in the calling code's own logic) is always fatal, never a `Result` a caller could forget to check.** A `Result` stays reserved for errors that come from *outside* the program -- a file that doesn't exist, a malformed date string, an HTTP body that isn't valid JSON -- where "the caller didn't do anything wrong, the world did" is genuinely possible and recoverable.

**`sort_by_keys`/`sort_by_keys_desc` were the one real violation found.** Both `items` and `keys` are always arrays the *same program* built; a length mismatch between them can never be "bad external data," only a bug in whatever assembled the two arrays -- exactly `server.param`'s own shape of mistake, not `parse_date`'s. Changed from `Result<[T], string>` to a plain `[T]`, fatal on mismatch via the same idiom `server.param` already uses (`val x: Result<T, E> = err(...); return unwrap(x)` -- there is no dedicated "fatal(message)" helper in the library, so this is written out at each of the small number of sites that need it, the same way `server.param`/`crypto` already do it, rather than introducing a new one for two more call sites).

**Simplified a real caller along the way.** `migrate.zm`'s two callers were switching on `sort_by_keys`'s `Result`, converting an `Err` into a `DbError` -- dead code in practice, since `versions` in both cases is `collections.map` applied to the exact same `items` array being sorted, so the lengths can never actually differ at either call site. Both simplified to a bare `ok(collections.sort_by_keys(...))`, removing a switch/Err-wrapping block that existed only to handle an outcome that was already structurally impossible -- the kind of defensive code this design's own "don't validate what can't happen" principle argues against, that the old `Result` signature had been quietly encouraging.

**Searched the rest of the library for the same shape of violation and found none.** Other `Result`-returning functions checked (`json`'s field accessors, `csv`'s delimiter check, `time`'s component validators) all parse genuinely external, untrusted text (a JSON value, a CSV delimiter, a date string) -- correctly recoverable, not programmer errors, and left unchanged.

Verified: full test suite (821 fixtures: `collections_sort`, `collections_sort_desc`, `collections_extras`, `ord_option_result_array`, `map_set_helpers` updated for the new signature; `sort_by_keys_length_mismatch_rejected` and `sort_by_keys_desc_length_mismatch_rejected` new, covering the now-fatal path) on both builds; `docs/lib/collections.md`/`docs/CORELIB.md` regenerated.


## Runtime stack traces, the last piece of C7 (2026-09-29, C7)

Part 1 of C7 (source excerpt/caret, always-named file, sorted by position, some cascades closed) was already done. What was left, per the review (L P1-12): "no stack traces -- when a runtime error fires 10 calls deep, you get the crash site, not the path that led there." A fatal error already names the exact line and column it happened at; it said nothing about how execution got there.

**New machinery: a per-thread call-frame stack, living in error.c next to `ThreadBoundary` rather than in interpreter.c.** `call_function` (interpreter.c) is the one place every Ziman-level call goes through -- native or not, named or through a captured closure value -- so it's the one place that pushes a frame (`ziman_push_frame(fn->name, fn->source_file, call_line, call_col)`, right after `ZIMAN_STACK_CHECK()`) and pops it before every return. `call_line`/`call_col` is the position *in the caller* that made this call -- already a parameter `call_function` had for other reasons -- so a frame reads as "this function, called from here," the same information a caller's own stack slot holds in any native debugger. The array itself is `__thread`, reachable only through that pointer, so it needs the identical `GC_MALLOC_UNCOLLECTABLE` treatment this session's `t_defer_envs`/`t_env_pool` (interpreter.c) already established for exactly this reason: the collector does not reliably scan thread-local storage, and a plain `GC_MALLOC`'d buffer held only by a `__thread` pointer can be collected out from under a running thread.

**Why this lives in error.c, not interpreter.c.** `ziman_error` is the single choke point for every runtime error, on both its exit paths (unwind via `longjmp` to a `ThreadBoundary`, or print-and-`exit(1)` directly on the main thread with none active) -- reading the frame stack has to happen exactly there, before either path is taken, since the trace describes the call chain *at the moment of the error*, which the `longjmp` path is about to discard by unwinding past every pending `call_function` return (and its pop) in one jump. Keeping the frames next to `ThreadBoundary` (which error.c already owned) avoided a backwards dependency from error.c into interpreter.c.

**Entering a `ThreadBoundary` resets the frame count to zero.** A spawned thread's frames, at the instant its error fires, describe a call chain that the `longjmp` is about to abandon -- once control reaches the boundary's own catch, that dynamic extent is over. Without a reset, those stale frames would still be sitting in the array the next time *anything* pushes onto it on this thread -- an `on_error` handler call, one of the thread's own deferred calls -- silently prepending an unrelated, already-finished call chain onto a fresh one's trace. Resetting inside `ziman_thread_boundary_enter` (rather than at every individual `longjmp`-catch site, of which `thread_failed` alone has three) covers all of them with one change, since every one of those sites already arms a fresh boundary before running its own guarded code.

**The trace is deliberately *not* folded into `ThreadBoundary.message`.** That string isn't only ever shown to a person at a terminal -- it's also handed to a Ziman program's own `on_error` handler as an ordinary `string` argument, and read back out by the library's own `test`-running machinery (built on `spawn`/`on_error`) to report which assertion failed. The first implementation embedded the trace there unconditionally and broke four fixtures outright (`test_basic_fail`, `test_cases_val`, `test_cases_builder_fails`, `spawn_on_error_handler`) plus the `--json` error format's exact-match fixture -- caught immediately by the full test suite, before this was anywhere near committed. Fixed by leaving `b->message` exactly as before, and adding a separate accessor, `ziman_trace_string()`, called only from the two places a trace is genuinely meant for a terminal: `ziman_error`'s own direct-print path (an uncaught error with no active boundary -- always the main thread), and `thread_failed`'s no-`on_error`-handler branch (interpreter.c) -- a spawned thread that fails uncaught, printed straight to stderr, the program going on. JSON-mode errors don't get a trace at all: inventing a schema for one (a `"stack"` array, say) is a separate, larger decision than this task's scope, and the existing JSON contract (locked in by `cli_json_runtime_error`) stays exactly as it was.

**Native calls get frames too, natively.** `call_function`'s `is_native` branch pushes and pops exactly like the interpreted-body path, so a native that raises its own `ziman_error` (an index out of bounds, a wrong argument) shows up in the trace by its own name -- consistent, and free, since it's the same push/pop the ordinary path already needed.

Verified: full test suite (825 fixtures: `error_stack_trace` (three ordinary nested calls), `error_stack_trace_recursive` (the same function appearing four times at different depths, confirming frames aren't deduplicated or confused with each other), `error_stack_trace_multifile` (a cross-module call showing each frame's own file, not the caller's), `error_stack_trace_spawned_thread` (the no-`on_error`-handler path, relying on the harness's timeout the same way `stack_depth_spawned_thread` already does, since main's own `receive` never wakes) new) on both builds; `valgrind --leak-check=full` on the `nogc` build shows the new frame buffer leaking only the same way `env_pool`'s own buffer already does for the main thread (never released, since the process is about to exit) and zero actual errors; the full `health-record-backend-ziman` suite passes unchanged.

## A mechanical check against one specific doc-drift shape, not doc drift in general (2026-09-29, F5)

F5's last remaining piece, P1-9: "a CI check that greps docs for the 'not yet' list against `pub` signatures." The motivating case was concrete and already found once by hand: `SYNTAX.md` said "Not yet: server-side TLS (`listen_tls`)" after `lib/core/net.zm` had already grown a real `pub fn listen_tls` -- the doc was written before the feature landed and never revisited once it did.

**Extended to DESIGN.md and declined for ROADMAP.md (2026-10-07, F11 and after).** Adding docs/DESIGN.md
to its sources found two genuinely stale claims immediately, and needed two refinements: a *quoted* "Not
yet" is a citation rather than a claim (this very entry quotes the stale sentence three times, so the
check reported the entry documenting itself), and a `**Superseded ...**` note ends the claim it corrects,
since everything such a note names is what *has* landed.

docs/ROADMAP.md was tried the same way, with "not started" as a second marker, and **produced 40 findings
of which nearly all were wrong** -- so it was reverted. The reason is the shape of the prose, not the
rule: "HTTP/2 -- not started" is followed by a paragraph mentioning `listen_tls`, `net.connect_tls`,
`byte_and` and more, none of which the entry claims are missing, and the continuation-pulling that makes
the check work on a terse `Not yet: a, b, c` list is exactly what drags those in. A narrower variant --
flag a "not started" entry that cites a tasks.md id which is now closed -- is precise but matches three

Not yet: client certificates, ALPN, ..." -- `listen_tls` and "Not yet" share a line, but `listen_tls` names the feature that *does* exist, appearing *before* the marker. Splitting the line at "Not yet" and only scanning what comes after it is what keeps this from flagging `listen_tls` against itself on every run.

**Verified the check actually catches what it's for**, not just that it runs clean today: temporarily rewrote the `listen_tls` line back to its old, genuinely-stale wording ("Not yet: server-side TLS (`listen_tls`), client certificates, ..."), confirmed `make not-yet-check` fails naming both the doc line and the declaration site, then reverted. ## `concat` becomes variadic, and a real bug found testing it (2026-09-29)

`concat(a: string, b: string) -> string` only ever took exactly two strings; joining three or more meant nesting (`concat(concat(a, b), c)`), which 18 real call sites in the backend were already doing rather than reach for `join`'s more awkward three-leading-`Option<string>` signature for the common "just glue these together" case. Changed to `concat(pieces: string...) -> string` -- `native_concat` now sums every piece's length and copies them all into one allocation instead of exactly two -- backward compatible with every existing two-argument call.

**Testing the new zero-argument case (`concat()` should be `""`) surfaced a real, pre-existing type-checker bug, unrelated to this change.** `sum()` against `docs/SYNTAX.md`'s own `fn sum(nums: int...) -> int { ... }` example -- which explicitly documents `print(sum())  // 0` as legal -- failed to type-check at all: "function 'sum' is missing required argument 'nums'". Root cause in `canonicalize_named_args` (typecheck.c): a syntactically-positional call with *zero* arguments (`f()`) is deliberately routed through the named-argument-filling machinery (see that function's own long-standing comment -- this is what makes `sb_new()` callable, since every one of its parameters is `Option<T>`), and the "was this parameter actually given?" loop had no exception for a trailing variadic parameter -- it isn't `Option<T>`, so it was treated as unconditionally required, even though a variadic parameter's own well-defined "nothing given" reading (zero elements) needs no `Option` wrapper to express at all. `check_call`'s own downstream arity check and `collapse_variadic_args` (interpreter.c) were already completely fine with a zero-length variadic tail -- confirmed by tracing both before writing the fix -- so the bug was entirely contained to this one function manufacturing a fake error for an argument that was never actually required.

**Fix**: the "is this required?" loop now also skips a trailing variadic parameter left unfilled, and the final reordered-arguments array is trimmed to exclude it (`fixed_count` entries instead of `fn->params.count`) rather than leaving a `NULL` in that slot -- so a zero-argument call reaches `check_call`'s ordinary variadic-tail handling exactly as if the trailing parameter had never been declared, not a new code path grafted on. This applies uniformly to every shape that can leave a variadic parameter unfilled: a bare `f()` (`sum()`), a named call that never names it (`labeled_sum(label: "total")` when `labeled_sum(label: string, nums: int...)`), and, unchanged from before, a named call that does supply it (`join(pieces: parts)`) or a positional call with one or more trailing values.

Verified: full test suite (827 fixtures: `concat_variadic`, `variadic_zero_args` new -- the latter covering `sum()`, a positional call with values, `concat()`/`concat("a")`/`concat("a","b","c")`, `join()`, and the named-call-omits-the-variadic-parameter case specifically) on both builds; `valgrind --leak-check=full` on the `nogc` build finds zero actual memory errors (only the same "process exits without freeing" leak category every other run this session already has); `make fmt-check` shows only the pre-existing unrelated backend failures; the full `health-record-backend-ziman` suite passes unchanged.


## Deep-copy at the two thread-crossing points, landed ahead of the allocator it's for (2026-09-29, F2)

Phase 1 of docs/MEMORY.md's thread-owned-heap design: `spawn`'s own `args`/`handler` and `send`/`try_send` on a `Channel` no longer hand the new thread (or the channel's queue) a bare pointer into the calling thread's own values -- each now gets `value_deep_copy(v)` (new, `value_copy.c`/`.h`), a value with nothing heap-allocated shared with the original.

**Why land this now, before any of the allocator work it's actually for.** Under today's allocators (the collector, or plain `malloc` in `ziman-nogc`), nothing is ever reclaimed out from under a value another thread still holds, so a deep copy instead of a pointer alias cannot change any program's observable output -- only what crossing costs. That made it possible to verify with the existing test suite alone (827 fixtures, unchanged output on both builds) rather than needing the harder allocator machinery to exist first, and it removes a real prerequisite from the critical path of the bigger change: once thread-owned heaps exist, a pointer handed across without this fix becomes a live use-after-free the moment the source thread's heap collects.

**Recursive, one function, every `Value` kind.** `value_deep_copy` (value_copy.c) switches on `Type.kind`: scalars (`int`/`float`/`bool`/`byte`/`unit`) are embedded in the `Value` itself, nothing to copy; `string` gets a fresh `value_string_copy`; `bigint`/`decimal` get their underlying `BigNum` digit array actually duplicated (`value_bigint`/`value_decimal` themselves only do a shallow struct copy -- confirmed by reading their implementation before assuming otherwise -- so the digits still needed a real `memcpy`); `array`/`struct`/`result`/`enum`/a closure's captured values all recurse into their own payload; `Map`/`Set` are rebuilt by walking `mapobj_entries` and re-inserting through the ordinary `mapobj_set` API rather than hand-copying trie nodes, which also reproduces the original insertion order for free (the trie's own ordering rule). A packed array (`[int]`/`[float]`/`[byte]`/`[bool]`) comes back boxed rather than packed -- deliberate: packed-vs-boxed is purely an internal storage optimization with no visible effect on any program (SYNTAX.md's own Builtins section says so), so this is a missed optimization for the rare thread-crossing case, not a correctness change; a packed fast path can be added later if it ever matters against a real workload.

**One deliberate, load-bearing exception: `Channel` values are never deep-copied, even nested inside something that is.** A channel is the language's one identity-based, intentionally-shared-across-threads handle -- deep-copying one reachable through a struct field or array element (ROADMAP.md's own `struct Node { peers: Channel<Node> }` cycle example shows this is a real, reachable shape) would silently disconnect two ends of what the program meant to be a single conduit. `array_push`'s spare-capacity `store` is dropped on copy for a related but distinct reason: it is tied to one thread's own compare-and-swap sequence of pushes, and letting a copy on another thread share it would mean two independently-collected heaps racing a CAS over memory only one of them will end up owning -- correctly unreachable today (nothing collects yet), but wrong the moment thread-owned heaps exist, so fixed now rather than left as a landmine for whoever builds that part.

**A question this surfaced that MEMORY.md didn't have yet, added to its open questions**: a value sitting inside a `Channel`'s own queue, between `send` and `receive`, doesn't belong to either thread's heap the way this document originally framed it -- it's live in a genuinely shared structure for an indeterminate time. Under thread-owned heaps, either the channel's buffered contents need to live outside any single thread's collected region (similar to how the channel object itself would need to), or the sending thread's collector needs to treat its own channel sends as roots until delivery. Not resolved here; flagged for the Phase 3 design work once collection itself exists.

Verified: full test suite (828 fixtures: `thread_crossing_deep_copy` new, exercising every `Value` kind -- array, `Map`, `Set`, `bigint`, `decimal`, a nested struct-carrying enum, a string array, a `Map<string, [Point]>`, and a closure captured into an `on_error` handler -- crossing both a `spawn` and a `Channel`, output identical to a hand-run reference before writing the fixture) on both builds; `valgrind --leak-check=full` on `nogc` finds zero memory-safety errors (only the same already-expected "nothing frees before exit" leak category); `make fmt-check` shows only the pre-existing unrelated backend failures; the full `health-record-backend-ziman` suite (including its multi-connection, channel-heavy `db_pool_sqlite` example) passes unchanged.


## A standalone arena allocator, landed inert before anything calls it (2026-09-29, F2)

Phase 2 of docs/MEMORY.md's thread-owned-heap design, first increment: `src/arena.c`/`.h`, a bump-allocated, `mmap`-backed region -- `arena_alloc` never frees anything individually, only forward-allocates into growable blocks; `arena_destroy` releases every block in one shot. This is the per-thread heap itself, before any collection exists on top of it (that's Phase 3). Nothing in the interpreter calls it yet -- landed standalone, with its own test (`tests/c/arena_test.c`, `make test-arena`), rather than combined with the much larger and riskier step of routing the interpreter's actual allocation sites through it, which deserves its own dedicated pass with this piece already proven correct underneath it.

**Built on `mmap`/`munmap`, never `malloc`/`free` -- a real constraint, not a style choice.** `src/zgc.h` is force-included into every translation unit of a `make`/`make gc` build (the Makefile's own `-include`), which *textually* redefines `malloc`/`calloc`/`realloc`/`strdup`/`free` to route through Boehm's collector -- including inside `arena.c` itself, the moment it compiles as one of the wildcarded `src/*.c` files. An arena's entire purpose is to be memory the collector never touches, so it cannot call anything zgc.h would intercept; `mmap`/`munmap` are the one allocation primitive that isn't, and are also the idiomatic choice for a region allocator's own block storage regardless.

**A genuinely free correctness property, not just documented as a nicety**: every byte `arena_alloc` hands out is already zero-filled. Not a general arena-allocator guarantee -- specific to this one, because a fresh `mmap`'d anonymous page is zero-filled by the kernel, and pure bump allocation never reuses a byte range within a live block until the whole block is released at `arena_destroy` (nothing is ever "freed and reused" mid-block the way a free-list allocator would). So every returned range is either fresh from the kernel or has simply never been handed out before -- `calloc`'s own guarantee, at no extra cost.

**Two real bugs found by the test before this ever compiled into anything larger**, exactly why this was worth its own standalone pass: (1) alignment -- `ArenaBlock`'s own header (`next`/`size`/`used`, 24 bytes on a 64-bit build) isn't itself a multiple of the 16-byte alignment every allocation is supposed to get, so the block's `used` counter had to start at `round_up(header size, 16)`, not the header's own raw size, or every allocation in a fresh block would land 8 bytes short of aligned; (2) `arena_alloc(a, 0)` handed out the *same* pointer twice in a row, since `round_up(0, 16)` is `0` and nothing advanced the bump pointer -- fixed by treating a zero-size request as needing at least one alignment unit, honoring this module's own documented "a zero-size allocation returns a valid, distinct pointer" contract (stronger than plain `malloc(0)`'s looser one) instead of quietly weakening it to match the bug.

**Header offset computed with `offsetof`, not assumed equal to `sizeof(ArenaBlock)`** -- the C standard doesn't promise a trailing flexible array member's offset matches the struct's own `sizeof` (they agree on every platform this runs on today, but `offsetof` is what actually guarantees it, at zero cost, so there was no reason to rely on an assumption instead).

Verified: `make test-arena` (10 checks: creation, zero-fill, three allocations staying distinct, 16-byte alignment, an oversized allocation getting its own dedicated block without disturbing earlier ones, `arena_reserved` growing correctly, 100,000 small allocations across many blocks all reading back correctly, the zero-size-allocation contract, and two destroy-lifecycle shapes) passes with zero failures; `valgrind` on the standalone test binary finds zero errors and zero leaks (every `mmap` is paired with a `munmap`); the full interpreter test suite (828 fixtures) is unchanged on both builds, confirming `arena.c` compiling into the wildcarded source tree has no effect on anything yet, as intended -- it is currently dead code, wired into nothing.


## `value_deep_copy` gets a real, safe destination: a per-thread outbound arena, never shared, never destroyed (2026-09-29, F2)

Closes the correction found while scoping Phase 2 (docs/MEMORY.md): Phase 1's `value_deep_copy` was allocating through the ordinary allocator (`malloc`/`GC_MALLOC`, whatever `value.c`'s own constructors use) -- fine under a single shared heap, but a real bug waiting to happen once per-thread arenas exist for everything else, since a copy landing in the *sending* thread's own arena would become a use-after-free the moment that thread exits (its arena freed at exit) while the receiving thread -- unboundedly, if it's a long-lived actor -- still holds it.

**Every thread gets a second arena, used only by `value_deep_copy`, created lazily and never destroyed.** `src/value_copy.c`'s `outbound_arena()` is a `__thread Arena *`, mirroring the established lazy-`__thread`-state pattern (`t_defer_envs`, `t_env_pool`) exactly, with one deliberate difference: nothing ever calls `arena_destroy` on it, matching `arena.c`'s own reusable design being put to a second use it wasn't originally scoped for (Phase 2's plan was one arena per thread, freed at exit; this is a second one per thread, on purpose never freed). **This needs no lock, despite outliving its own thread, for the same reason sharing an ordinary `Value` across a channel already needed none**: only the thread that calls `value_deep_copy` ever writes into its own outbound arena; every other thread only ever *reads* an already-fully-built, immutable value out of it afterward. `Arena` itself stays single-writer, exactly as documented -- this doesn't add concurrent access to one arena, it just chooses not to reclaim this particular one.

**Every `Value` kind got its own arena-aware constructor** (`src/value_copy.c`: `arena_string_copy`, `arena_bigint`/`arena_decimal`, `arena_array_copy`, `arena_struct_copy`, `arena_result_copy`, `arena_enum_copy`, `arena_closure_copy`) rather than reusing `value.c`'s own constructors, which allocate through the ordinary path with no way to redirect them -- giving every constructor in `value.c` an allocator parameter for this one caller was judged a much larger, more invasive change than duplicating the (small) construction logic here, where it's scoped to exactly the one place that needs it.

**One honest, explicitly-flagged gap, not swept under the rug: `Map`/`Set` are not yet arena-routed.** Rebuilding a persistent hash trie with a caller-supplied allocator needs `mapobj.c`'s own cooperation (it has no arena-aware variant yet), a separate piece of work. Left on the ordinary allocator for now -- exactly how every value crossing a thread was allocated before this file existed, so not a regression, just unfinished coverage, recorded as such rather than silently handled the old way and left undocumented.

**A real, serious bug the interpreter's own unit tests couldn't have caught, found only by running the actual backend suite: routing `value_deep_copy` through an `mmap`'d arena silently breaks native resource handles.** `admin_test.py` (`health-record-backend-ziman`) hung, then failed migration startup outright with "invalid or closed connection handle," on the very first version of this change -- not from a memory-safety bug (`valgrind` was clean throughout), but from a genuine design gap only a real workload with a real database pool surfaces. This codebase represents a native handle (a database connection) as the handle object's own heap address, cast to a plain `int64_t` and carried inside an ordinary `Value` -- `src/native_sqlite.c`'s own comment on `DbConn`/`g_live` already says why: "being in the set does not keep it alive... a Connection value nobody holds any more is collected." Boehm keeps that object alive *only* because its address, in bit-pattern form, sits somewhere its conservative scanner looks -- normally the C stack or another `GC_MALLOC`'d block. `arena_alloc`'s whole design point is that its memory is invisible to that scanner (`mmap`, not `GC_MALLOC` -- see `arena.h`'s own comment); copying a `Connection` struct into the outbound arena moved the disguised pointer into memory Boehm no longer looks at, so once the *original*, `GC_MALLOC`'d copy became unreachable, the collector saw nothing left pointing at the underlying `DbConn` and finalized it -- closing the connection out from under a program that, through the arena copy, still believed it was open.

**Root-caused by first ruling out the newer work, not assuming it**: reverted to the commit before *any* of this session's F2 memory changes and reproduced the identical hang, which said the cause predated today entirely -- until a stale server process from the investigation's own earlier interrupted runs turned out to be squatting on the test's fixed port, a self-inflicted red herring. Killing it and retrying from a clean state reproduced the *real* failure cleanly (a clean startup error, not a hang), which is what led to the actual root cause above. Worth recording as its own small lesson: a hang during iterative debugging is not automatically the bug under investigation -- check for leftover state from the debugging itself before trusting a reproduction.

**Fixed with `arena_create_scanned`** (`src/arena.c`/`.h`): every block of a "scanned" arena is also registered with the collector (`GC_add_roots`) as an additional conservatively-scanned range, and un-registered (`GC_remove_roots`) before being `munmap`'d in `arena_destroy` -- a no-op in a build without the collector, since nothing is ever collected there to threaten. `outbound_arena()` now calls this instead of the plain `arena_create`. Scanning the whole arena is broader than strictly necessary (most values crossing a thread are never a disguised pointer), but a value's shape isn't known until after it's copied, and treating harmless integers as potential pointers is exactly what conservative scanning of the ordinary C stack already does everywhere else in this interpreter -- not a new kind of imprecision, the same one applied to one more region.

**Verified the fix directly, not just that the suite went green again**: wrote a minimal reproduction (`tests/lang/thread_crossing_native_handle.zm` -- a connection opened on a spawned thread, sent over a `Channel`, with `os.collect_garbage()` forced explicitly between the send and its use) and confirmed it fails with the exact "invalid or closed connection handle" error when `outbound_arena()` is temporarily reverted to plain `arena_create`, then passes once reverted back -- a real before/after, not an assumption that fixing the symptom fixed the cause.

Verified: full test suite (829 fixtures: `thread_crossing_native_handle` new) on both builds; `arena_test.c` extended (`arena_create_scanned` behaves like the plain one for ordinary allocation -- its actual root-registration is untestable from that standalone, non-`ZIMAN_GC` binary, hence the interpreter-level fixture above); two manual stress tests (5,000 sequential sends of a struct from one thread; 8 concurrently `spawn`ed workers sending 16,000 messages total, 5 repeated runs) clean under `valgrind` on `nogc`; `db_pool_sqlite.zm` (the suite's own multi-connection pool example) run 8 times back to back with identical output each time; the full `health-record-backend-ziman` suite passes, including `admin_test.py`'s account-deletion-with-medications case, which is what originally caught this.


## Object headers, the foundation Phase 3's mark/copy phases will need (2026-09-30, F2)

Phase 3's first concrete implementation increment: `src/gc_object.c`/`.h`, a thin layer on top of `arena.c` giving every allocation a small header -- `{kind, size, marked}` -- prepended by `gc_alloc(Arena*, GcKind, size_t) -> void*`, which hands back a pointer to the payload itself, exactly like a plain `arena_alloc` result (same 16-byte alignment guarantee, achieved the same way `arena.c` achieves it for its own header -- round the header's own size up to the alignment first, so it never shifts the payload off it). `gc_kind_of`/`gc_size_of`/`gc_is_marked`/`gc_set_marked` read it back given the same pointer `gc_alloc` returned.

**Why this exists at all, restated from MEMORY.md's own design section**: a conservative stack scan finds a pointer-sized word that looks like a valid arena address; it has no way to know what's actually *at* that address. `Value.type` can't help, because it lives wherever the `Value` itself is stored (a C local, an `Env` slot, another object's own field), not at the target address a pointer inside it refers to. A header at the target address is the only way the eventual mark phase can know "this is an `ArrayObj`" vs. "this is a plain string buffer" once it's found a bare pointer and nothing else.

**`GcKind` has seven values, not one per `Value.type.kind`**: most Ziman types need no tracing at all (scalars are embedded in the `Value` itself), and several distinct `Value` payload shapes collapse to the same tracing behavior -- every leaf allocation (string bytes, `BigNum`/`Decimal` digits, a packed array buffer) is `GC_ATOMIC` regardless of which Ziman type it backs, since none of them hold a pointer that needs following. `GC_VALUES` is its own kind, not folded into `GC_ARRAY`, because it's the shape three different structures share (`ArrayObj.boxed_items`, `StructObj.fields`, `ClosureObj.captured` are all just "a `Value[]` of some count"), traced by walking each element by its own `type.kind`, not by this tag.

**Deliberately inert and standalone, same discipline as `arena.c` itself**: nothing in the interpreter calls this yet. `gc_alloc` doesn't know how to build a real `ArrayObj`/`StructObj`/etc. -- that's the mark/copy phase's own job, still ahead, and deliberately not conflated with "does the header layer itself work." `gc_kind_of`/`gc_size_of` only work on a pointer `gc_alloc` itself returned, never an arbitrary interior address -- consistent with the interior-pointer resolution already recorded in MEMORY.md (a copying collector re-copies a view's own bytes rather than needing to find an enclosing header from the middle of a shared buffer, so this layer never needs to support that case at all).

Verified: `make test-gc-object` (11 checks: each kind/size round-trips correctly, two adjacent objects of different kinds/sizes don't corrupt each other's headers or payloads, the whole declared payload of an atomic allocation is writable end to end, alignment holds, the mark bit is independently settable/clearable per object, a zero-size payload is valid) passes with zero failures; `valgrind` on the standalone test binary finds zero errors and zero leaks; the full interpreter test suite (829 fixtures) is unchanged on both builds, confirming `gc_object.c` compiling into the wildcarded source tree has no effect on anything yet, as intended.


## The copy/relocate primitive: `value_copy.c`'s own logic, generalised onto object headers, with sharing preserved (2026-09-30, F2)

Phase 3's second implementation increment: `src/gc_copy.c`/`.h`. A real collection cycle needs a way to walk a `Value` graph from a set of roots and rebuild it, live objects only, in a fresh arena -- and `src/value_copy.c` already *is* almost exactly that recursive walk, just built for a different caller (a one-off copy at a thread crossing, into a plain `arena_alloc`'d, unheaded destination). Rather than design a separate tracing algorithm from scratch, this reuses that same per-kind structure (one static function per `Value` payload shape, switching on `Type.kind`) with two things added: every structural allocation goes through `gc_alloc` (so the result carries the header the eventual sweep/relocate phase needs), and a dedup map preserves sharing across the copy.

**Why sharing preservation matters here but not in `value_copy.c`.** A one-off thread crossing pays the cost of a duplicated shared substructure exactly once. A value that survives many collection cycles over a long-running thread's lifetime would pay it *every cycle*, compounding -- a struct referenced from ten places in a long-lived data structure would grow into ten independent copies after one collection, and worse after the next. `GcDedup` (a plain open-addressing pointer-to-pointer table, same hash and probe scheme as `src/handles.c`'s `HandleSet`, but insert-only and unlocked since a single thread owns one for the span of a single copy pass) tracks "this source pointer has already been copied to this destination pointer," so two different paths through the graph that reach the same `ArrayObj`/`StructObj`/`ResultObj`/`EnumObj`/`ClosureObj`/boxed `BigNum`/`Decimal` still reach the same object after the copy, exactly as before it.

**A second instance of the interior-pointer problem, found while designing this, not while debugging it.** `array_obj_view` (`src/value.c`) hands back a *view* -- a fresh `ArrayObj` wrapper, but sharing its parent's `boxed_items`/packed buffers at a byte offset, not its own allocation's start address -- the exact same shape as a string's `substring`/`trim`/`split` sharing a parent buffer, which MEMORY.md's Phase 3 design section already flagged and resolved (a copying collector re-copies a view's own bytes rather than tracking interior pointers). This module extends that same resolution uniformly to every buffer capable of being a view: string bytes, a packed array's own buffers, and any `Value[]` array (`ArrayObj.boxed_items`/`StructObj.fields`/`ClosureObj.captured`, even though only the first of these three is ever actually sliced in practice -- one rule for the whole shape is simpler to reason about than tracking which call sites happen to be safe) are never deduplicated, always copied fresh from wherever their pointer currently points for exactly their own declared length/count. Deduplicating one of these by raw address would risk conflating two genuinely different values that happen to start at the same byte -- a string and a zero-offset prefix slice of it share `ptr` but not `len`, for instance. Dedup is used only for whole-object pointers that are never sliced by anything in this language.

**Packed arrays don't actually need the interior-pointer treatment they were first assumed to need.** `gc_copy_array` reads every element through `array_get` (which already resolves a view's own offset internally) rather than ever touching `bytes`/`bools`/`ints`/`floats` directly, and always rebuilds the copy boxed -- the same "packed-vs-boxed is purely an internal optimisation, invisible to any program" tradeoff `value_copy.c` already made, for the same reason. That sidesteps the packed-buffer view case entirely rather than solving it: there is no code path in this module that ever reads a packed buffer's raw bytes.

**`Map`/`Set` inherit the same known gap `value_copy.c` already had, not a new one**: not yet `gc_alloc`-routed, rebuilt through the ordinary `mapobj_set`/`mapobj_empty` API in insertion order, same as before. `Channel` is shared by identity, never copied, same rule and same reason as `value_copy.c`.

**Tested standalone, but not dependency-free like `arena.c`/`gc_object.c`** -- exercising the real `Value` representation (not a synthetic stand-in) means linking `value.c` and everything it itself needs (`ast.c` for `Type`, `error.c`/`stack.c` for the runtime-error and recursion-depth paths `value.c` can hit, `bignum.c`/`decimal.c`, `mapobj.c`). `value_hash` (normally `src/interpreter.c`, not linked here) is stubbed in the test itself, harmless since nothing in it constructs a `TY_MAP`/`TY_SET` value -- there is nothing of this module's own to verify in that branch anyway, given the gap above.

Verified: `make test-gc-copy` (35 checks -- every `Value` kind copies with correct content; a plain string and bigint each get a genuinely new, `GC_ATOMIC`-headed buffer; the interior-pointer ambiguity is exercised directly, a 5-byte string and a 3-byte, same-start-address view of it both copy to their own correct, independent 3/5-byte content; an `ArrayObj` reachable from two array elements and a `StructObj` reachable from two array elements both dedup to the same copied object, not two; an array view's sliced content survives the copy correctly; every structural copy's header reports the right `GcKind`; a `Channel` is returned unchanged) passes with zero failures; `valgrind --leak-check=full` on the standalone test binary reports zero self-introduced leaks (the only remaining reports are `ast.c`'s `type_array`/`type_struct`/`type_result`/`type_enum`/`type_channel`/`type_func` allocations, the same permanent-AST, never-freed-by-design memory every `Type` the real interpreter ever builds also leaves in place); the full interpreter test suite (829 fixtures) is unchanged on both builds, confirming `gc_copy.c` compiling into the wildcarded source tree has no effect on anything yet -- nothing calls it outside its own test.


## Resolving a bare stack word back to an object: `gc_lookup.c`, and a gap in the design found while scoping it (2026-09-30, F2)

Phase 3's third implementation increment, and the piece root-finding actually needs: `src/gc_lookup.c`/`.h`, `const void *gc_lookup(const Arena *a, const void *candidate)` -- given an arbitrary address, resolves it to the `gc_alloc`'d object it falls within (exact match) or inside (interior match), or `NULL` if it isn't one of `a`'s objects at all.

**A gap found while scoping the *next* increment (the actual conservative stack scan), before writing any of it.** `gc_copy.h`'s own design (previous entry) established that string/packed-array/`Value[]` interior pointers never need resolving during ordinary graph tracing, because tracing always starts from an already-typed `Value` with its own `len`/`count` already in hand. A stack scan is different: it finds bare, untyped words on the C stack with *no* such context attached. Working through what a scan would actually find turned up a real, previously unaddressed case: `Value.as.str.ptr` (a string view sharing a parent buffer at an offset -- `value.c`'s `value_string_view`/`substring`/`trim`/`split`) is embedded directly in the `Value` union with no wrapper object around it, unlike every other heap-referencing field (`arr`/`st`/`res`/`en`/`clo`/`bi`/`dec`/`map`/`ch`, which are all pointers to their own wrapper's own exact `gc_alloc`'d start -- see `gc_copy.h`'s own comment on why those never need interior-pointer handling). A transient `Value` holding such a view, sitting only as a C-stack local mid-evaluation with nothing else pointing at it yet, would present its scanner with exactly the bare interior pointer `gc_copy.c` never has to deal with. Without a way to resolve it, a stack scan finding only that word would fail to recognize the underlying buffer as reachable at all -- a real, silent memory-safety bug (the collector discarding memory a live view still points into), not a missed optimization.

**Resolved without reproducing Boehm's own interior-pointer machinery.** The full generality Boehm's `ALL_INTERIOR_POINTERS` needs (resolving an interior pointer into *any* object kind, including structured ones, via per-block size-class bookkeeping) isn't needed here: every other heap-referencing `Value` field already resolves by exact match once its wrapper is found (ordinary graph tracing from there does the rest by dereferencing), so this module only has to make exact matches *and* the one interior-pointer shape above both work, for whatever kind of object it happens to land on.

**No separate index, built or maintained.** `gc_alloc`'s own bump allocation already lays every object out contiguously and self-describingly (each header says exactly how far to the next one) -- `gc_next_object` (new, `gc_object.c`/`.h`) is the one place besides `gc_alloc` itself that knows the private header layout, walking a raw byte range one object at a time; `gc_lookup` uses it to scan every block of an arena (`arena_first_block`/`arena_next_block`/`arena_block_content`, new, `arena.h`/`.c`) until it finds an object whose declared `[start, start + gc_size_of(obj))` span contains the candidate, or runs out of objects. This is `O(objects currently in the arena)` per call -- fine for the handful of stack words a conservative scan checks once per collection, deliberately not something built for per-allocation-frequency use.

**`arena_block_content` has to account for the one block that isn't purely gc_alloc content.** The block that embeds the `Arena` struct itself (`arena_create_impl`) reserves some of its own bytes before any real allocation happens; walking from a block's raw `data` as if every byte were a `gc_alloc` header would misparse the `Arena` struct's own bytes as one. Identified which block that is by a property already true of the existing code, not a new invariant added for this: exactly one block ever has `next == NULL` (the original one `arena_create_impl` makes; every later block's `next` is set the instant it's created, in the "current is full" branch of `arena_alloc`, and nothing ever touches the original block's `next` again) -- `arena_block_content` skips past the `Arena` struct's own reserved bytes on that one block only, nothing on every other.

**A precondition worth stating plainly for whoever wires a real per-thread heap on top of this later**: walking an arena this way is only meaningful when *every* allocation into it went through `gc_alloc`, never a bare `arena_alloc` call directly -- `value_copy.c`'s own outbound arena mixes bare `arena_alloc` today and is not walkable this way, which is fine (nothing needs to walk it), but a future arena that mixed the two for some incidental bookkeeping need would silently misparse. Documented on `arena_block_content` itself, not just here.

Verified: `make test-gc-lookup` (18 checks -- exact match on the first object allocated into a fresh arena, interior match at several offsets, the boundary case of one byte past a payload's declared end correctly *not* matching, several objects of different kinds/sizes walked correctly in sequence, addresses that must resolve to nothing at all -- before any real content, `NULL`, an unrelated stack address, a small integer masquerading as a pointer -- alignment padding between two objects not being misattributed to either neighbour, and the walk correctly crossing from one `mmap`'d block into a second and third one, forced by a dedicated oversized allocation) passes with zero failures on the first run; `valgrind --leak-check=full` on the standalone test binary finds zero errors and zero leaks; the full interpreter test suite (829 fixtures) is unchanged on both builds, confirming `gc_lookup.c` and `arena.c`/`gc_object.c`'s new exposed accessors have no effect on anything yet -- nothing outside `gc_lookup.c`'s own test calls any of it. The actual conservative stack scan (walking a thread's real C stack, using `stack.c`'s existing bounds computation, feeding each candidate word through this function) is the next increment, still ahead.


## The actual conservative stack scan, and the one test in this whole effort that can't be fully valgrind-clean (2026-09-30, F2)

Phase 3's fourth implementation increment: `src/gc_scan.c`/`.h`, `int gc_scan_stack_roots(const Arena *a, void (*visit)(const void *, void *), void *ctx)` -- the piece the previous three increments built toward. Scans the *calling* thread's own C stack, word by word, from (approximately) the current stack pointer up to the thread's own measured upper bound, feeding every word through `gc_lookup`; whatever resolves to a real object gets reported to `visit`, once per matching stack word (deliberately not deduplicated to one call per distinct object -- a mark phase built on top of this already needs an idempotent "already marked, skip" check for ordinary graph tracing, so there is no reason to deduplicate twice).

**Always the calling thread's own stack, never another thread's -- not a limitation to lift later, but this design's entire premise.** A stop-the-world collector has to pause and inspect every thread's stack, since any of them might hold a root into the one shared heap. This design's whole point (docs/MEMORY.md, "one heap per thread") is that a thread's garbage is its own problem to collect, on its own time -- so there is never a reason to touch another thread's stack, and no locking, suspension, or signal machinery is needed here at all. Confirmed by the API shape itself: nothing about `gc_scan_stack_roots` takes a thread handle.

**Reused this codebase's own existing idiom for "the current stack pointer," rather than a different technique.** `src/stack.h`'s `ZIMAN_STACK_CHECK` macro and `ziman_stack_remaining` already compute an approximate stack pointer as `&` of a local variable ("the address of a local is (near enough) the stack pointer," in that macro's own words) -- `gc_scan_stack_roots` does exactly the same thing, not `__builtin_frame_address` or anything new, so this stays consistent with how the rest of the interpreter already reasons about its own stack. The upper bound comes from a new `stack.c` accessor, `ziman_stack_bounds` -- deliberately not `ziman_stack_limit` (the recursion-depth guard's own margin-adjusted limit): this needed the real bounds `measure_this_thread` already computes internally but had never exposed, so `measure_this_thread` now also records the raw low address (`t_stack_low`, new) alongside what it already tracked.

**Reads raw stack bytes with `memcpy`, not a pointer cast and dereference**, avoiding any strict-aliasing question about reinterpreting arbitrary bytes (an `int`, a `double`, a real pointer -- whatever actually happens to live at that stack address) as a `void *` through a typed lvalue.

**The one module in this whole effort that cannot be made fully `valgrind --leak-check=full` clean, and why that is not a regression in rigor.** Every earlier piece (`arena.c`, `gc_object.c`, `gc_copy.c`, `gc_lookup.c`) was verified with a completely clean `valgrind` run -- zero errors of any kind. `gc_scan_test` cannot clear that bar, and trying to force it to would mean testing something other than what this module actually does: conservative scanning's whole technique is to read stack memory the compiler may never have written in this call chain (a slot left over from an earlier, unrelated, already-returned call) and treat it as a *possible* pointer -- `valgrind`'s memcheck flags exactly this as "Conditional jump or move depends on uninitialised value(s)," which is real, expected, and the same interaction Boehm's own collector has with valgrind, not a defect in `gc_lookup`'s or `gc_scan`'s own logic. Confirmed this is the *only* thing valgrind finds, not a cover for something worse: `valgrind --leak-check=full --undef-value-errors=no` (every other memcheck category -- invalid reads, invalid writes, leaks -- left fully enabled, only the "uninitialised value used" class turned off) reports zero errors and zero leaks on the same binary that shows 8 "uninitialised value" warnings under the default settings.

Verified: `make test-gc-scan` (6 checks, using `volatile` locals to guarantee a real object's pointer is actually written to stack memory rather than kept only in a register at this codebase's own `-O2` build setting -- an object referenced by an ordinary exact-start local is found; one referenced *only* by an interior-pointer local, the scenario `gc_lookup.c` exists for, is found; the same object referenced by two different locals is still found; the scan reports success) passes with zero failures across five repeated runs (stack contents vary run to run, so this was rerun deliberately rather than trusted once); `valgrind --leak-check=full --undef-value-errors=no` finds zero errors and zero leaks, confirmed distinct from the default run's expected uninitialised-value noise as described above; the full interpreter test suite (829 fixtures) is unchanged on both builds, confirming `gc_scan.c` and `stack.c`'s new `ziman_stack_bounds` accessor have no effect on anything yet -- nothing outside `gc_scan.c`'s own test calls either. Still ahead: the collection trigger and wiring a full end-to-end cycle (deciding when to run, walking from real interpreter roots rather than a test's own synthetic ones, actually relocating survivors with `gc_copy.c` and discarding the old arena).


## Phase 3 switches from copying to mark-sweep: conservative roots can't be relocated, and neither can precise ones in this evaluator (2026-09-30, F2)

While scoping "wire up the collection trigger" (the next item the previous entry left open), working through what actually happens when a live root is found turned up a real, disqualifying problem with the copying design docs/MEMORY.md committed to: **a conservative stack scan's own roots can never safely be relocated.** `gc_scan_stack_roots` cannot tell a real pointer from an ordinary integer that happens to look like one -- that is fine for keeping something alive a little longer than strictly needed, but not fine for *moving* it: rewriting a stack slot to point at a relocated copy, when that slot was actually just an unrelated integer, would silently corrupt real data. Boehm hits this identical wall and resolves it the same way every mature conservative collector does -- never move anything. A copying collector fundamentally needs every root it might act on to be reliably a real pointer; conservative scanning cannot promise that.

**A cheaper-looking alternative was considered and ruled out, not just skipped.** Before accepting mark-sweep's cost (a new, non-bump allocator), a precise alternative was worked through: since this interpreter already tracks its own call chain explicitly for stack traces (`ziman_push_frame`/`ziman_pop_frame`, `error.c`), could root-finding walk that instead of scanning the raw stack, if collection only ran at statement boundaries (never mid-expression)? Tracing a concrete case killed this: in `f(x) + g(y)`, while `g(y)` is executing (itself recursing into `call_function`, itself hitting its own safe points), `f(x)`'s already-computed result sits *only* as a transient C local in the outer expression evaluator -- not in any `Env`, not on any frame's root list, since the `+` hasn't finished evaluating both operands. A precise, `Env`-chain-only root walk would not see it; if a collection ran during `g`'s own execution, `f(x)`'s value could be discarded out from under the still-running expression. This is not a rare shape -- any multi-argument call or multi-operand expression has it -- and fixing it properly would mean compiling to an explicit operand-stack VM instead of tree-walking recursion, an incomparably larger rewrite than anything else in this effort. Surfaced to, and confirmed with, the project owner via two rounds of discussion before committing to mark-sweep -- this is a large enough fork in the remaining work to warrant that, not a unilateral call.

**What carries over unchanged, and what doesn't.** `gc_object.c`'s header -- kind, size, and critically the `marked` bit, which was clearly sized for exactly this scheme even before the pivot -- needs no change at all. `gc_scan.c`'s `visit(obj, ctx)` callback shape (report the object found; no way to rewrite the stack slot it came from) already fits a non-moving collector perfectly -- it was never going to relocate anything in the first place, so nothing about it was actually built for the wrong design. `gc_lookup.c` is unaffected. `gc_copy.c`'s own logic does not carry over as *Phase 3's collector* -- mark-sweep never relocates anything, so there is no more "copy into a fresh destination" step for it to perform in that role -- but it remains a correct, tested, still-useful "deep copy with sharing preserved" primitive; whether it eventually replaces `value_copy.c`'s own thread-crossing copy logic is a separate, undecided question, not resolved by this pivot either way.

**`src/gc_heap.c`/`.h`: the one genuinely new mechanism mark-sweep needs.** `arena.c` only bump-allocates and mass-frees an entire arena at once -- it cannot reclaim one dead object's space for individual reuse without discarding everything else in it too, which a non-moving collector needs constantly (an object dies; its space should be available to the *next* allocation of a similar size, not just at the next full-arena reclaim, which for a long-lived thread might be never). `GcHeap` adds a free-list layer on top of an internal `arena_create_scanned` arena (native-handle safety, same reasoning as every other arena this design has created): `gc_heap_alloc` hands out memory, reusing a same-size-class chunk if one is free; `gc_heap_sweep` -- run after a mark phase (still ahead) has already marked every reachable object -- walks every object the heap holds (via `arena_block_content` + `gc_next_object`, the exact same walk `gc_lookup.c` already established) and reclaims anything left unmarked, clearing survivors' mark bits for the next cycle.

**Segregated free lists by power-of-two size class**, the standard resolution to "how do I know a freed chunk is big enough to satisfy a later request without tracking exact sizes": `gc_heap_alloc` rounds a request's *total* footprint (header included, via a new `gc_header_span` accessor -- `gc_object.c` stays the one place that knows the header's actual size) up to the next power of two, and always allocates exactly that many bytes, fresh or reused, never the caller's minimal size. A freed object's own recorded size is therefore always already an exact class size, so `gc_heap_sweep` can bucket it onto the right free list with no size recomputation or comparison. `gc_size_of` on a `GcHeap`-allocated object therefore reports its class size, not necessarily the caller's exact requested payload -- a real, deliberate difference from `gc_alloc`'s own exact-size contract, but a safe one: nothing anywhere (`gc_copy.c`, `gc_lookup.c`) relies on `gc_size_of` being exact; a string's real length always comes from the `Value`'s own `len` field.

**A genuine bug caught by working through the minimum size class before writing the sweep code, not by testing it afterward**: a freed chunk's own free-list "next" link has to live somewhere, and the natural place -- the chunk's own now-unused payload bytes, the same trick every free-list allocator uses -- doesn't exist at all for a payload smaller than a pointer (a zero- or near-zero-byte request, which `GC_VALUES`'s own empty-array case already makes a real, not hypothetical, shape). `gc_heap_alloc` now enforces a minimum effective payload of `sizeof(void *)` before computing a size class, so every class, including the smallest, always has room for its own free-list link once something in it is freed. Exercised directly in the test (a genuinely zero-payload allocation, freed and confirmed safe to relink).

**A new `GcKind` value, `GC_FREE`**, marks a chunk currently on a free list -- not a live `Value`-backing object at all, so `gc_lookup` resolving a stray stack word to one (a real, if rare, possibility -- the same class of harmless false positive conservative scanning always risks) must never be mistaken for something worth tracing. `gc_heap_sweep` is careful to skip any object it finds already `GC_FREE` rather than re-link it -- an already-free chunk is already correctly on some class's free list, and touching its link again without unlinking it first would corrupt that list, not just waste work.

**A precondition worth stating as plainly as `arena_block_content`'s own**: every allocation into a `GcHeap`'s arena must go through `gc_heap_alloc`, never bare `gc_alloc` or `arena_alloc` directly -- `gc_heap_sweep`'s walk assumes every object's recorded size is already an exact power-of-two class size, which only `gc_heap_alloc` guarantees.

Verified: `make test-gc-heap` (17 checks -- ordinary allocation is fully usable and correctly headered; a zero-payload allocation is safe to free and relink; a full sweep with nothing marked reclaims everything, and a later allocation of a matching size reuses the freed slot with its kind correctly overwritten and its mark bit clear; marking one of two same-class objects before a sweep reclaims exactly the other, leaves the survivor's content and kind untouched while clearing its mark bit, and a later allocation reuses the reclaimed slot; a freed object reads back as `GC_FREE` while sitting on its free list; a payload bigger than one arena block still works) passes with zero failures on the first run after fixing the minimum-payload bug above; `valgrind --leak-check=full` finds zero errors and zero leaks; the full interpreter test suite (829 fixtures) is unchanged on both builds, confirming `gc_heap.c` and `gc_object.c`'s new `GC_FREE`/`gc_set_kind`/`gc_header_span` additions have no effect on anything yet -- nothing outside `gc_heap.c`'s own test calls any of it. Still ahead: the real mark phase (reusing `gc_copy.c`'s own per-`Value`-kind traversal structure, calling `gc_set_marked` instead of copying), the collection trigger, and wiring `gc_scan_stack_roots` + the mark phase + `gc_heap_sweep` into one real end-to-end cycle.
