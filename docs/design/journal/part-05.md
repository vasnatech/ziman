## A real interpreter crash found mid-style-sweep, isolated to Boehm's own `GC_gcollect()` -- root cause still open (2026-10-04)

Surfaced as a side effect of unrelated work: a mechanical sweep converting `is_Variant(x)`-guard-then-`unwrap_Variant(x)` idioms in `lib/` to `if`-let/`switch` form. Converting `pg.zm`'s/`mysql.zm`'s `serve()` actor loop -- specifically the `FetchCursor` request's `deferred` guard, `if cursor_open && r.cursor == cursor_id && Option.is_Some(deferred) { ... Option.unwrap_Some(deferred) ... }` rewritten as an equivalent `if`-let binding `Some(x) = deferred` -- crashed the interpreter intermittently (roughly half of repeated runs) with no code-shape difference that should matter semantically. The crash vanished running under plain `gdb` with its default signal handling, which in hindsight was a red herring explained below, not evidence the race was gone. Reverted the conversion at both call sites (left as `is_Some`/`unwrap_Some`, each now commented explaining why) and moved on with the rest of the sweep rather than block it on an unrelated interpreter bug -- documenting it here instead, as asked.

**A second, independent, fully deterministic failure turned out to be the far more tractable way in.** `make test-pg`'s `pg_rows` fixture hangs -- confirmed on a clean checkout, nothing to do with any change this session made -- partway through a deliberate "two statements contending for one cursor" sequence. Direct run under a 20s `timeout` confirms it: five lines print, then nothing, `exit 124`.

**Built a minimal, 100%-reliable repro from there** (no fixture, no `gdb` yet): open a cursor against a real, throwaway `postgres:17` container, drain it fully (a natural full exhaustion, the connection's cursor state correctly clearing itself), call `os.collect_garbage()` explicitly, then open and drain a second cursor. Every single run (confirmed across repeated trials) segfaults partway through the second cursor's own request/reply exchange -- removing the explicit `os.collect_garbage()` call makes it disappear entirely, so this is the same underlying race as the style-sweep's original ~50%-of-runs crash, just pinned to a reliable trigger instead of left to natural allocation-threshold timing.

**The `gdb`-vanishes effect is Boehm, not the bug disappearing.** Boehm's own thread-suspend mechanism uses `SIGPWR` (and `SIGXCPU`/`SIGUSR1`/`SIGUSR2` depending on configuration) to pause other threads during a collection -- entirely routine, happens on every collection, every run. `gdb`'s *default* signal handling stops and reports on every one of these as if it were a real fault, which looks exactly like "the crash is gone" to anyone who hasn't told it otherwise. `handle SIGPWR nostop noprint pass` (and the same for the other three) before `run` is what actually lets a real fault surface through `gdb` at all; without it, every attempt to debug this under `gdb` was debugging Boehm's own bookkeeping, not this bug.

**The real backtrace, once `gdb` was told to ignore Boehm's own signals**: `SIGSEGV` inside `__strcmp_avx2`, called from `eval_enum_access` (`interpreter.c:1117`, the `is_<Variant>`/`unwrap_<Variant>` consumption path -- see that function's own header comment) at `pg.zm:746`, column 13 -- the `Run(r)` arm of `serve()`'s own `switch req { ... }`. `req` is the value just returned from `val req = receive(requests)`, the statement immediately before. Its `EnumObj`'s `variant_name` field reads back `NULL`, `enum_name` reads back bytes that look like unrelated stack garbage rather than a valid string pointer -- the signature of a dangling pointer into memory that something else has since reused, not a null/uninitialized value. `req` crosses from the sending thread to `serve()`'s own thread through the ordinary cross-thread channel path (`channel_send`/`channel_receive`, `value_copy_send` into a dedicated per-message scanned arena, `value_copy_receive` copying back out into the receiving thread's own allocators, `arena_destroy` once done -- see the "`value_deep_copy` gets a real, safe destination" and "Closing the temporary-buffer gap for real" entries above for this machinery's own history).

**Ruled out, each by a direct, repeatable experiment, not by inspection alone:**
- *Ziman's own Phase 3 `GcHeap` collector* (`maybe_collect`/`ziman_force_collect`, `t_gc_unsafe_depth`). Wrapped `value_copy_receive`'s own recursive construction (`ordinary_struct_copy`/`ordinary_array_copy`/`ordinary_enum_copy`/`ordinary_closure_copy`, and the inline `TY_MAP`/`TY_SET` loop next to them) in the exact `gc_unsafe_enter`/`gc_unsafe_leave` guard every `EXPR_STRUCT_LIT`/`EXPR_CALL`/`EXPR_ARRAY_LIT`/`EXPR_WITH` site already uses for the identical "plain buffer filled one element at a time, through further allocating recursion" shape (see "Closing the temporary-buffer gap for real," above) -- a real, independently-justified gap in its own right (nothing had audited `value_copy.c`'s receive side against this exact hazard before), but it did not stop the crash. It also broke the standalone build: `gc_unsafe_enter`/`leave` are `interpreter.c`-private, and several `test-gc-*` unit targets link `value_copy.c` without `interpreter.c` at all, so exposing them needs either a shared translation unit both sides can link or a different seam -- not attempted further once the fix was already shown not to address the actual bug. Reverted in full (`interpreter.c`/`.h`, `value_copy.c`) rather than leave a non-fix sitting in the tree breaking five unit tests.
- *The `Guard` finalizer* (`prelude.c`'s `guard_finalizer`, the mechanism a dropped `Connection` uses to tell its owning thread to close). Commenting out `GC_invoke_finalizers()` in `os.collect_garbage()`'s native implementation (`native_os.c`), leaving `ziman_force_collect()` and `GC_gcollect()` both active, did not stop the crash -- rules out a premature `Request.Close` finalizer firing as the mechanism, which an earlier, less precise trace of this same investigation had looked like it might be.
- *The optimizer hiding a live pointer from Boehm's conservative stack scan* (a classic false lead with `-O2`). A full `-O0` rebuild (every `.c` file, same `vendor/bdwgc/libgc.a`) crashes identically, every run -- rules out optimization-dependent register/stack-slot reuse as the cause.
- *A spawned thread not properly registered with Boehm for suspend/scan.* `src/zgc.h` is force-included project-wide specifically so `<gc.h>`'s own `GC_THREADS`-gated `pthread_create` redirect (to `GC_pthread_create`) takes effect before anything else can declare the unwrapped symbol (`zgc.h`'s own comment says so directly) -- and both `ziman_run_on_big_stack` (`main`'s own thread) and `ziman_spawn_thread` (every `spawn`) call what reads as plain `pthread_create`, confirmed via this redirect to actually be the wrapped one (the crash's own backtrace shows `GC_pthread_start_inner`/`GC_call_with_stack_base` in the spawned thread's frame, which only appears for a properly-registered thread). Thread registration itself is not the gap.

**Isolated to one specific call, by direct removal**: commenting out *only* the explicit `GC_gcollect()` line in `os.collect_garbage()` (keeping `ziman_force_collect()` before it and `GC_invoke_finalizers()` after, both otherwise unchanged) makes the crash disappear -- confirmed clean across repeated runs with it removed, and crashing across the same number of runs with it restored. Boehm's own *automatic*, allocation-threshold-triggered collections clearly also carry the same bug (the original style-sweep crash, and the independently-discovered `pg_rows` hang, both happen with no explicit `os.collect_garbage()` call anywhere in the program) -- the explicit call is only a reliable way to force the identical race on demand, not a separate cause.

**Continued past the point above -- a second, distinct failure mode found, with the mechanism pinned far more precisely.** Tried to build a minimal, Postgres-free repro to make iterating faster: a synthetic two-thread `spawn`/`Channel` worker with the identical shape (a long-lived actor loop, persistent `var` state mutated across iterations, struct-carrying messages, `os.collect_garbage()` between rounds). Over a dozen variations -- heavier struct payloads, thousands of rounds, a real local TCP loopback with an echo server standing in for Postgres's own socket -- none reproduced either failure, even at far higher message volume and GC frequency than the real driver ever sees for a 10-row cursor. One of these loopback variants looked like it reproduced a hang (`exit 124` under a 20s `timeout`), which very nearly got reported as a second confirmed repro before being checked properly.

**That apparent hang was a false alarm, and the way it was caught is worth recording as its own lesson.** `strace -f` attached to the "stuck" process mid-run showed `recvfrom`/`sendto` calls succeeding continuously throughout the whole trace window -- real, ongoing work, not a frozen thread. `ps -o pid,time,%cpu` confirmed it directly: accumulated CPU time was climbing, not flat. The program was simply slow -- consistent with the already-documented "close to half of all CPU time is garbage-collection-related under load" finding several entries up, not a new bug. **"still running after N seconds" does not distinguish a hang from a slow program; accumulated CPU time does** -- near-zero and flat means genuinely blocked, climbing means real progress. Applying that same check to `pg_rows.zm`'s own hang settles the question properly: `time timeout 180 ./ziman tests/integration/pg/pg_rows.zm` reports `user 0m0.131s`, `sys 0m0.045s` against **3 minutes of wall-clock time** -- a real, hard deadlock, not slowness, and the loopback experiments' non-reproduction is itself informative (whatever this needs, high message volume and GC pressure alone are not it).

**Caught live with `strace -f -p <pid>` on the genuinely deadlocked `pg_rows.zm` process** (started separately, polled with `ps`/CPU-time until confirmed stuck, then straced directly -- no `gdb`, no signal-handling gotcha to work around this time): all three threads sit in `futex` waits, none in a socket syscall. The outer process thread is in `pthread_join` on the "big stack" thread (`ziman_run_on_big_stack`, routine, not evidence of anything), the big-stack thread (Ziman's own `main()`) is blocked in what reads as a condition-variable wait, and `serve()`'s own thread is *also* blocked in a condition-variable wait -- on `receive(requests)`, waiting for the next message, having apparently already replied to whatever it processed last.

**Confirmed directly, not inferred, with one more round of temporary instrumentation** (`fprintf(stderr, ...)` in `channel_send`/`channel_receive`, `value.c`, dumping each call's raw `ChannelObj*` and thread id -- reverted immediately after, see below): the exact sequence at the hang is `serve()` reaches `receive(requests)` and blocks; `main()` then calls `send(requests, Request.Run(...))` -- the identical `requests` pointer `serve()` is already blocked on, confirmed byte-for-byte from the trace -- followed immediately by `receive(reply_to)` on a freshly-created reply channel; and that is the last line in the entire trace. Grepping the full trace for that exact reply-channel address finds exactly one occurrence -- `main()`'s own wait -- and *zero* sends to it from anywhere, including `serve()`'s thread, which shows no activity at all after the point `main()`'s send should have woken it.

**This rules out the `eval_enum_access`/corrupted-`EnumObj` mechanism as the explanation for *this* failure specifically.** A `switch req { Run(r) { ... } ... }` crash would show `serve()` active (inside `eval_enum_access`, mid-dispatch) with garbage field contents, the same shape as the SIGSEGV above; instead `serve()` is cleanly parked in `pthread_cond_wait`, never having been woken at all. `channel_push_locked` (the send side) calls `pthread_cond_signal` while holding `ch->mutex`; `channel_receive` (the wait side) checks its predicate and calls `pthread_cond_wait` also while holding `ch->mutex` -- textbook-correct, and under ordinary POSIX semantics a signal sent this way *cannot* be lost regardless of what else happens on either thread, including a signal-based suspend landing at an inconvenient moment, which is exactly why this is worth flagging precisely rather than hand-waved as "probably the same bug as the crash above." It may or may not share a root cause with that crash (both need genuinely concurrent threads, both correlate with Boehm's collector running near the failure, and both were found investigating the identical style-sweep conversion) -- not yet established which, and this entry does not assume they are the same bug just because they were found together.

**The deadlock's mechanism, found for real this time -- disproving the "lost wakeup" theory along the way.** First tried the obvious practical mitigation without fully understanding the cause: changed `channel_receive`'s unbounded `pthread_cond_wait` into a loop of short (100ms) `pthread_cond_timedwait` calls, re-checking the predicate on every wake, timeout or not. If a signal were merely *lost*, this self-heals within 100ms regardless -- the predicate check only needs the mutex re-acquired, never the signal itself. Fifteen straight runs of `pg_rows.zm` with this in place: fifteen deadlocks, unchanged. This disproves "lost wakeup" outright: `serve()`'s thread was never actually failing to notice `ch->count` had changed:

**It was never coming back to check at all, because something else told it to stop.** Re-instrumented with `fprintf` at every `pthread_mutex_lock`/`channel_push_locked`/`pthread_cond_wait` boundary in both `channel_send` and `channel_receive`, and separately in `guard_finalizer` (`prelude.c`) itself. The trace is unambiguous: partway through `serve()` handling an entirely ordinary, legitimate request -- *while still replying to it correctly* -- `guard_finalizer` fires, on `serve()`'s own thread, targeting the exact `requests` channel `serve()` reads from. `serve()` sends its real reply, loops back to `receive(requests)`, and immediately dequeues the `Request.Close` the finalizer just pushed -- not `main()`'s next real request, which hasn't been sent yet. `serve()`'s own code does exactly what `Request.Close` tells it to: says goodbye to the server, closes the socket, sets `open = false`, and the function returns -- the thread ends, cleanly and silently, by design, for a connection that `main()` is still actively using. Every request `main()` sends afterward queues forever behind a reader that no longer exists.

**Why the finalizer fires at all was proposed as a two-collector theory in an earlier revision of this entry, and that theory does not survive the next check -- corrected here rather than left standing.** The original idea: `GuardBuf` (the object `guard_finalizer` is registered on) is a plain `malloc`'d (Boehm-`GC_malloc`'d) block, so only Boehm's own collector ever reclaims *it* directly -- but the *only* thing pointing to it is a disguised-pointer-as-`int` inside a Ziman-level `Guard` struct, itself nested inside `pg.Connection`, itself the payload of `main()`'s own `conn`. That struct lives in `ziman_thread_heap()`, this interpreter's own separate, precise (not conservative) Phase 3 collector -- the one with its own history of "root chain doesn't reach this deep" bugs several entries up. The theory was: if *that* collector's own mark pass fails to find the `Guard` struct reachable from `conn`, `gc_heap_sweep` zeroes it, erasing the disguised pointer before Boehm ever gets a chance to see it; Boehm's later, correct-by-its-own-lights conclusion that nothing points to `g` would then just be downstream of damage Ziman's own sweep already did.

**Tried to confirm it directly, and the evidence point the other way.** Added logging to `gc_mark_interpreter_roots`/`gc_mark_env_chain` (`gc_interp_roots.c`/`gc_env_roots.c`) printing every frame's `Env` address on every Phase 3 collection cycle, plus a direct check for a binding literally named `conn`, and separately tagged each thread's identity unambiguously (`fn=%s` off `SpawnArgs.fn->name` in `spawn_thread_entry`, a one-line marker in `run_program`) rather than inferring roles from call volume, which had already caused one mix-up earlier in this same session (misreading which of two threads was `serve()`). Run against the real, unmodified `pg_rows.zm`: `main()`'s own Phase 3 collector fires exactly twice in the entire run before the hang, both at `main()`'s *own top level* (one frame deep, no nested call active), both correctly finding `conn`. It never fires again -- not once -- while `main()` is nested inside `sum_rows`/`datasource.rows`/`pg.rows`/`open_rows`, which is the only place the proposed gap could matter. `pg_rows.zm` never calls `os.collect_garbage()` anywhere, so nothing *forces* `main()`'s own collector to run there either. **If `main()`'s own Phase 3 sweep never runs during the only window where it could erase the pointer, it cannot be what erases the pointer** -- the theory's own mechanism isn't exercised in the run where the bug happens.

**A second candidate -- a race between `arena_alloc`'s block growth and a concurrent Boehm collection on another thread -- was considered and ruled out by inspection, not by testing.** `ziman_thread_heap()`'s arena is `GC_add_roots`-registered per block (`arena_create_scanned`), and a thread growing its own arena (`arena_alloc`, `src/arena.c`) calls `GC_add_roots` (via `maybe_scan`) on a freshly `mmap`'d block *before* returning a pointer into it -- registration happens strictly before the caller writes anything real into the new memory, every time, with no window in between where a just-written, not-yet-registered pointer could exist for a concurrent Boehm collection (triggered by `serve()`'s own busier allocation, on its own thread) to miss. Ruled out without needing to reproduce it: the code's own ordering makes the mechanism impossible as described.

**A richer synthetic repro -- diverse `Row`/`Page`-shaped structs instead of one repeated shape, a fresh per-"cursor" `Guard` created and legitimately dropped on every iteration (mirroring `CursorHandle`'s own, not just the connection's), real allocation volume per round -- still did not reproduce it,** three thousand iterations, explicit `os.collect_garbage()` every ten. Every attempt at a Postgres-free repro in this whole investigation has now failed, regardless of how closely it was shaped after the real code.

**Settled the "what erases it" question directly, with a `gdb` hardware watchpoint on the real `pg_rows.zm` failure, rather than guessing at a fourth theory.** Broke at the exact line in `native_guard_new` (`prelude.c`) right after `fields[0] = value_int((int64_t)(intptr_t)g)` runs, captured the *absolute address* of that one `int64_t` into a `gdb` convenience variable (`set $addr = &fields[0].as.i` -- not a symbolic watch on `fields` itself, which `gdb` reported as "optimized out" moments later once the compiler no longer needed to keep that local alive), set a hardware watchpoint on `*(long*)$addr` for writes, deleted the breakpoint, and let the program run uninterrupted (the four `SIGPWR`-family signals still set to `nostop`/`pass`, as established earlier). Result: the watchpoint **never fires**. The program runs to its usual failure -- `serve()`'s own thread exits (`gdb`'s own `[Thread ... exited]` notification confirms it, matching the connection's `serve()` thread id established earlier, not the other two) -- and then hangs, exactly as every unmodified run does, all without that one `int64_t` ever being written to a second time after its original, correct initialization.

**This changes the finding materially, not just rhetorically: nothing ever overwrites, zeroes, or otherwise erases the disguised pointer.** It sits there, byte-for-byte correct, for the entire run. `serve()`'s thread still ends -- meaning `guard_finalizer` still ran, meaning Boehm still concluded `g` was unreachable -- while the one and only pointer to it remains perfectly intact in memory the whole time. Every "something erases the pointer, then Boehm correctly notices later" theory this entry has proposed (Ziman's own sweep, the arena-registration race) was already short of direct confirmation; this rules out the entire *category*, not just those two specific mechanisms. **The real question was never "what erases the pointer" -- there is nothing to erase.** It is: why does Boehm's own conservative scan, which by its documented contract should find *any* bit pattern matching a live heap address sitting in memory it scans (a thread's own stack and registers at suspension, plus every `GC_add_roots`-registered range, which includes the entire arena the `Guard` wrapper struct and its nested `fields` pointer live in), fail to recognize this one, specific, unchanging, valid pointer as a reason to keep `g` alive. The earlier retraction of "this is Ziman's own bug, not Boehm's" stands, now on firmer ground than when it was written -- not just "unproven," but actively counter-evidenced.

**Pursued the second angle -- whether a plain disguised-int pointer is even safe under this compiler's own optimizer -- with a minimal, Ziman-free C program against the vendored `libgc` directly, and it found something real, but not this.** A ~60-line standalone program (`GC_INIT`, one `Outer -> Wrapper -> GuardValue(int64_t handle)` chain identical in shape to `native_guard_new`'s own, a `GC_register_finalizer`, a tight loop calling `GC_gcollect()`/`GC_invoke_finalizers()` every 1000 rounds) fired the finalizer **at round 0**, every single run, same binary -- a 100%-deterministic, compile-time artifact, not a timing race (five repeated runs of the identical binary, five identical `PREMATURE FIRE at round=0`). `objdump -d` on that binary's own `main` found why immediately: the compiler (whole-program-visible, single translation unit, `-O2`) proved every store building the chain (`fields->handle = ...`, `wrapper->fields = ...`, `outer->guard = ...`) was a dead store -- nothing in that tiny program ever *read* any of those fields back in a way that affected observable behavior, so the optimizer deleted the writes outright. `GC_base()` on each pointer confirmed it afterward: in a *working* variant of the same program (one that added an `fprintf` actually reading the fields before the loop, forcing the compiler to materialize the writes), the chain survived every time -- a real, general, well-known conservative-GC-vs-optimizer hazard, reproduced and confirmed in isolation.

**Checked whether the real interpreter has the identical exposure before concluding anything, and it does not.** `objdump -d ./ziman --disassemble=native_guard_new` shows `fields[0] = value_int(...)` (the `movups XMMWORD PTR [rbp+0x0],xmm0` storing `value_int`'s own return value directly into `fields`) present and intact in the compiled binary, not eliminated -- because, unlike the single-file toy program, `fields` escapes `native_guard_new` across a translation-unit boundary (returned, wrapped, read by `interpreter.c` and everything downstream of it, none of which GCC can see while compiling `prelude.c` without LTO, which this build does not use) -- the exact property that lets a whole-program-visible toy prove a store dead can never apply here. Disproven by direct disassembly, not by re-reasoning about why it *should* be fine: the general hazard is real, reproducible, and worth knowing about for this codebase's own handle/builder pattern in the abstract, but it is not, itself, this bug.

**Took that one remaining angle and walked it two levels further out, with the same `gdb` watchpoint technique, now against temporary `fprintf` instrumentation (in `struct_obj_new` and `enum_obj_new`, `value.c`) rather than a breakpoint *condition* -- `gdb`'s own handling of optimized-code parameter values (`count@entry` disagreeing with plain `count`, a `DW_TAG_call_site` lookup failing outright for one inlined call site) made conditional breakpoints too unreliable to trust here, so the filtering moved into the C source instead, as a one-line `if` guarding an `fprintf` that only fires for the exact struct/enum shape being watched; the breakpoint then sits on that `fprintf`'s own line, unconditional, and only reachable when the guard already matched.** First watched `&fields[1].as.st` -- the *ordinary*, non-disguised pointer field inside `pg.Connection`'s own struct that points at the `Guard` wrapper (one level out from the disguised `int64_t` the first watchpoint covered). Captured it the same way (absolute address into a `gdb` convenience variable, breakpoint deleted immediately after), let the program run uninterrupted: **this watchpoint never fires either.** `serve()`'s thread still ends, the program still hangs, and this second, entirely ordinary pointer -- the kind conservative scanning has no excuse to miss -- sits in memory unchanged the whole time, same as the first.

**Went one level further still: watched `&e->payload.as.st` on `conn`'s own `EnumObj` -- the pointer, inside `main()`'s own `conn` variable, to the `pg.Connection` struct itself** (found via `enum_obj_new`, condition narrowed with `strstr(enum_name, "Connection")` once the first attempt's exact-match `"Connection"` never hit at all -- the real `enum_name` turned out to be the module-qualified `"datasource::Connection"`, the same qualification style as `"db::Request"` from the `SIGSEGV` investigation above). Same result: **never fires.** Three separate watchpoints now, at three successive distances from `g`, covering the entire pointer chain from the disguised handle up through the one value `main()` itself holds -- and not one byte of any of them is ever rewritten.

**This changes where the mystery sits, concretely.** Nothing downstream of `conn`'s own `EnumObj` is ever modified, reused, or reclaimed for anything else -- confirmed three times over, not inferred. Whatever Boehm's mark phase is failing to do, it is failing *at or above* `conn`'s own `EnumObj`: either that `EnumObj` itself is never found reachable (its own header never gets marked, even though nothing yet overwrites its contents -- Boehm's reclaim is lazy, a block marked dead does not have its bytes touched until something else actually needs that space), or `main()`'s own `Env` -- the structure holding the `conn` binding itself, a plain, ordinary `GC_MALLOC`'d/`calloc`'d block (`env_new`, `src/env.c`) with **no `GC_add_roots` registration and no explicit Boehm-visible root of any kind** -- is the one Boehm's conservative scan never finds a path to. `Env`'s only *existing* root sources (`gc_mark_env_chain`, `t_frames`/`ziman_frame_env_at`) are Ziman's own Phase 3 machinery, invisible to Boehm by construction; Boehm finding an `Env` at all depends entirely on conservative stack/register scanning turning up a live C-level pointer to it on *some* thread's stack at the moment a collection runs -- exactly the category of dependency the previous entry's standalone `libgc` test proved *can* break under the right (compiler-optimization-shaped) conditions, even though that specific toy turned out not to describe `native_guard_new`'s own exposure. The question this entry opened with -- is it this, applied to `Env` and the real interpreter's own, much deeper call graph, rather than to a single-file toy -- is now the leading, not merely plausible, explanation, though still not confirmed down to a specific disassembled call site the way the toy program's own dead store was.

**Took the direct route instead of disassembling `exec_stmt`/`call_function`/`eval_expr` by hand: caught two consecutive real collections on `main()`'s own thread and searched its live stack for `mainenv` directly with `gdb`'s `find`, rather than inferring from static code.** Broke on `GC_stopped_mark` (the actual stop-the-world-and-mark entry point used by *every* collection, explicit or automatic -- `GC_gcollect` itself, tried first, is only the explicit, user-facing entry and was never called even once in this entire run, confirming the real `pg_rows.zm` failure runs entirely on Boehm's *automatic*, allocation-threshold-triggered path). Getting this right took two false starts worth recording: a fixed `$rsp`-relative search window first reported the pattern "not found" at a point that turned out to be a red herring -- `info proc mappings` on `main()`'s own huge, custom-sized stack (`ziman_run_on_big_stack`, a ~536 MB anonymous mapping) showed a consistently inaccessible patch roughly 16 KB above whatever the current `$rsp` happens to be, present on *every* hit regardless of call depth, that `find` halts at and that has nothing to do with running out of real stack (the mapping's own top is tens of megabytes further up) -- worth knowing about if anyone else probes this stack with `gdb`, but a tooling quirk, not a finding. Once the search was split into a near window (`$rsp` to `$rsp+0x3000`, short enough to clear that patch) and a separate far window well past it (`$rsp+0x40000` to `$rsp+0x900000`), the real result came through clean.

**And it is conclusive, not merely suggestive.** Two consecutive `GC_stopped_mark` hits, same process, same `mainenv` value, same search code: the first hit finds `mainenv` sitting on `main()`'s own stack, in a caller's frame above the then-current `$rsp` (`0x7ffff4c0a2d8`, `1 pattern found`). The very next `GC_stopped_mark` hit -- one allocation-threshold cycle later, `$rsp` only ~8 KB deeper into the same call graph -- finds it **nowhere**: not in the near window, not in the far window, not (per the per-thread register dump taken at the first two `GC_stopped_mark` hits earlier in this same investigation) in any register on any thread either. The identical 8-byte value that was unambiguously present on the stack a moment before is, a moment later, in the same run, gone from everywhere Boehm's conservative scan looks.

**This is the root cause, confirmed by direct observation rather than inference: `main()`'s own `Env*` local -- the only thing standing between Boehm's conservative scan and `conn`, and transitively the `Guard`'s own handle -- gets dropped from the stack, and is never placed in any register either, once execution is far enough into the real interpreter's own call graph, even though the `Env` (and everything reachable through it) is still fully live from the Ziman program's own perspective.** `Env` has no other Boehm-visible root: `gc_mark_env_chain`/`t_frames` (`ziman_frame_env_at`) are Ziman's own, separate Phase 3 mark pass, walked only by `gc_heap_collect`, never consulted by Boehm's own `GC_stopped_mark`. The two collectors have two different, disjoint notions of what is reachable, and only one of them -- Ziman's own, confirmed correct throughout this investigation, right up to `conn`'s own `EnumObj` -- actually gets it right.

**A concrete, well-supported fix shape falls out of this directly, though not implemented here.** Boehm exposes exactly the hook this needs: `GC_set_push_other_roots` (`gc_mark.h`, vendored, not yet used anywhere in this codebase) registers a callback Boehm's own mark phase calls on every cycle to push *additional* roots beyond its own conservative stack/register scan -- precisely the seam that would let Ziman teach Boehm about the same root set `mark_this_threads_roots` already walks for its own Phase 3 collector (`g_global_env`, every thread's own `t_frames`, `t_defer_envs`, `t_env_pool`), unifying the two collectors' reachability instead of leaving Boehm to guess via conservative scanning alone. Not attempted in this session: it is a real, if narrowly-scoped, architectural change (a new cross-thread iteration need, since `GC_set_push_other_roots`'s callback runs on whichever thread is doing the collecting and would need to visit *every* thread's own frame stack, not just its own -- `t_frames` and friends are `__thread`-scoped today, written assuming each thread only ever marks itself) and belongs in its own entry once attempted, not folded into this one.

All diagnostic changes from this investigation (temporary `print` instrumentation in `lib/db/pg.zm`/`lib/db/db.zm`, the reverted `value_copy.c`/`interpreter.c`/`.h` hardening attempt, the temporary `native_os.c` edits used to isolate `GC_gcollect()`, the `-O0` build, the loopback-socket repro attempts, the bounded-retry `channel_receive` experiment, the `fprintf` instrumentation in `value.c`/`prelude.c` used to trace the lost-wakeup sequence and catch `guard_finalizer` firing live, the thread-identity markers in `interpreter.c`/`main.c`, and the frame/env logging in `gc_interp_roots.c`/`gc_env_roots.c`) were reverted or discarded; nothing from this entry is reflected in any other file. The `is_Some`/`unwrap_Some` style left in place at `pg.zm`'s and `mysql.zm`'s own `FetchCursor` guards, each with a comment pointing back to this finding, is the only trace of it in `lib/`.

**The `GC_set_push_other_roots` fix from the previous entry was implemented, verified safe, and -- directly tested against the real `pg_rows.zm` repro -- found not to close the deadlock on its own.** `src/gc_boehm_roots.c` (new), plus small additions to `error.h`/`.c` (`ziman_frames_root_addrs`/`ziman_frames_root_ranges`, exposing a thread's own `t_frames` as a `ZimanMemRange`) and `interpreter.h`/`.c` (the equivalent for `t_defer_envs`/`t_env_pool`/`t_active_iters`/`t_pending_handler`, plus `ziman_global_env_addr`): a global, mutex-protected registry mirroring `native_thread.c`'s own `ThreadInfo`/`g_threads` shape (ordinary, non-`__thread` memory, so it stays Boehm-visible and cross-thread-readable), one record per thread holding just the *addresses* of its own root sources, re-read fresh on every collection. `ziman_gc_register_thread_roots()`/`ziman_gc_unregister_thread_roots()` are called at the start/end of `spawn_thread_entry` and at the equivalent points for `main`'s own logical thread (`run_program`/`run_tests_program`, `main.c`); `ziman_gc_install_boehm_root_hook()` runs once, at process startup, before either.

**Caught one real near-miss before it reached a real repro.** `GC_set_push_other_roots` *replaces* `GC_push_other_roots`, which defaults to `GC_default_push_other_roots` -- i.e. `GC_push_all_stacks()`, the actual mechanism that pushes *every* thread's own stack and registers in a `GC_THREADS` build (`vendor/bdwgc/os_dep.c`). Installing a callback without first saving the previous one (`GC_get_push_other_roots()`) and chaining to it stops Boehm from scanning any thread's stack at all -- not a subtle effect: `make fmt-check`'s very first real multi-file run (enough allocation to trigger one real automatic collection) immediately segfaulted deep inside `GC_realloc`/`GC_free_internal`, a far worse, far more general breakage than the one narrow bug this module exists to close. Fixed by capturing `GC_get_push_other_roots()` before installing, and calling it first inside the new callback. Worth flagging precisely because it is exactly the kind of mistake this hook's own name invites: "set" reads like "add," and the vendored header's own doc comment does not warn otherwise.

**With that fixed, the full suite is clean.** `make`/`make nogc` both build with no warnings; `./tests/run_tests.sh` passes 834/834 (repeated runs, no flakiness) under the real `ZIMAN_GC` build; `make fmt-check` fails only on the same pre-existing unformatted files in the sibling `health-record-backend-ziman` repo this entry's very first paragraph already found unrelated to any of this. (`ziman-nogc`'s own run showed 1-3 unrelated flaky failures across repeated runs, a different failure each time -- expected and unrelated: `ziman_gc_register_thread_roots`/`ziman_gc_unregister_thread_roots`/`ziman_gc_install_boehm_root_hook` are all `#ifdef ZIMAN_GC`-gated no-ops in a `nogc` build, so this fix cannot be the cause; a build that frees nothing at all growing an unbounded heap under a fixed per-test `timeout` is a pre-existing, orthogonal source of noise in that build specifically, not investigated further here.)

**Then re-ran the actual acceptance test: a throwaway `postgres:17` container, the real driver, the real `pg_rows.zm` fixture.** The deadlock still reproduces, byte-identical to every earlier capture in this entry: five lines print, then nothing, `exit 124` under a 60s `timeout`, `user`/`sys` CPU time near zero against the full wall-clock wait -- a genuine deadlock, unchanged by the fix. `make test-pg`'s own full run: 10 passed, 1 failed (`pg_rows`), same shape.

**One more round of temporary instrumentation (reverted after use, same as every other diagnostic pass in this entry) pinned the discrepancy to a single, concrete, still-unresolved contradiction.** Dumped, from inside the new `push_other_roots` callback itself (i.e. *during* the real collection, on the real failing run), each registered thread's own `frame_count`/`frame[0].env`, confirmed via `GC_base()` to be a real, intact, correctly-tracked Boehm block every single time, right up through the collection immediately preceding the finalizer firing -- the fix's own root-pushing is doing exactly what it is supposed to. Then walked `env_lookup(frame0.env, "conn")` by hand from that same callback, down through `conn`'s own `EnumObj`, `Connection`'s own `StructObj`, `Guard`'s own `StructObj`, its `fields` array, to the disguised handle -- checking `GC_base()` at every hop. Result: `GC_base()` is `NULL` for the `EnumObj` and both `StructObj`s (expected -- `struct_obj_new`/`enum_obj_new` allocate their own wrapper headers via `gc_heap_alloc(ziman_thread_heap(), ...)`, Ziman's own Phase-3 arena, not a plain Boehm `GC_MALLOC`/`calloc` block, so there is no Boehm block header to find), but resolves correctly (to itself) for `Guard`'s own `fields` array *and* the disguised handle itself -- both ordinary, un-migrated, plain `malloc` (Boehm-tracked) blocks, exactly as `struct_obj_new`'s own comment says. Every byte in the whole chain is still correct at the moment of failure, same as the three gdb watchpoints several paragraphs up already established.

**Cross-referencing against `arena.c`'s own `GC_add_roots` calls deepens the contradiction rather than resolving it.** Every arena block this thread ever created is logged at creation; the one containing all three arena-resident objects above (`conn`'s `EnumObj`, `Connection`'s `StructObj`, `Guard`'s own `StructObj`) was registered once, early in the run (`conn` is the very first thing `main()` creates), and -- confirmed by reading `arena.c` itself, not just by absence of a log line -- can only ever be unregistered by `arena_destroy`, called exclusively at thread exit, which has not happened; blocks are added to an arena's list as it grows, never individually retired. That block should therefore be an unconditional Boehm root, rescanned in full on *every* collection regardless of reachability from anywhere, for as long as the owning thread is alive -- which, by every fact checked above (nothing overwritten, the block still registered, `Guard`'s own `fields` pointer sitting right there in that unconditionally-scanned memory, itself resolving to a real tracked block), should keep `g` alive with no dependency on `Env` rooting at all. And yet the finalizer still fires.

**This entry now ends on an open, sharpened contradiction rather than a confirmed mechanism.** Every structural fact this investigation can check independently -- `Env` now correctly rooted and confirmed intact at the moment of failure; the arena block holding the whole `conn`/`Guard` chain confirmed still `GC_add_roots`-registered and never removed; every pointer in the chain confirmed byte-for-byte unmodified by three prior gdb watchpoints plus this fresh runtime chase -- individually says the finalizer should not fire. It fires anyway, unchanged by a fix that closes the one gap this investigation had concretely identified. The next step is almost certainly inside Boehm's own mark implementation itself (`vendor/bdwgc/mark_rts.c`/`mark.c`): whether a `GC_add_roots`-registered range outside Boehm's own `GC_INIT`-managed heap (this arena is raw `mmap`, never `GC_malloc`) is actually rescanned, in full, on every single collection the way `GC_push_all`-pushed stacks are, or whether something about its `ALL_INTERIOR_POINTERS`/multi-threaded handling treats it differently in a way none of this investigation's own reasoning about the public API has surfaced yet -- not confirmed either way in this entry, left for whoever picks this up next.

**The fix itself is being kept, not reverted.** It closes a real, independently-documented gap (`Env` had no Boehm-visible root at all before this), is verified not to regress the full test suite, the `nogc` build, or `fmt-check`, and is a legitimate, necessary piece of the eventual real fix even though it is not, by itself, sufficient. All temporary diagnostics added to find the above (the `fprintf`s in `gc_boehm_roots.c`'s `push_other_roots`, the `env_lookup("conn")` chase function, `arena.c`'s `GC_add_roots` logging, a matching debug accessor briefly added to `error.h`/`.c`) were reverted after use, same discipline as every other diagnostic pass in this entry; only the fix itself (`src/gc_boehm_roots.{c,h}`, the `error.h`/`.c` and `interpreter.h`/`.c` root-address accessors, and the three call sites in `interpreter.c`/`main.c`) remains.

**Took the next step the previous paragraph proposed -- a minimal, Ziman-free C program against the vendored `libgc` directly, this time purpose-built to test the specific open question (does a `GC_add_roots` range outside Boehm's own heap actually get rescanned, in full, on every collection) -- and it did not reproduce the bug, across five successively closer variants, all kept in the session's scratchpad, not this repo.** Re-confirmed first (`debug_chase_conn`'s own trace, above) that `conn`'s `EnumObj`, `Connection`'s `StructObj`, and `Guard`'s own `StructObj` all three sit inside the *one same* registered arena block (cross-referenced against a temporary log of every `GC_add_roots` call `arena.c` made for the whole run) -- meaning Boehm's unconditional, whole-block scan of that single range should find `Guard`'s own `fields` pointer directly, by raw byte-scanning, with no dependency on chasing through `Env` or any Ziman-level object graph at all, as long as the block is still registered and actually rescanned. Built that exact shape standalone: one `mmap`'d, `GC_add_roots`-registered block (never `GC_malloc`'d), holding the *only* pointer to an otherwise-unreferenced, finalizable `GC_MALLOC`'d object nested one level deeper (mirroring the arena-header/ordinary-array alternation the real chain has) -- single-threaded, this survives millions of iterations and repeated explicit `GC_gcollect()` calls without ever finalizing early. Added, one at a time, confirmed-present but previously untested ingredients: two concurrent `pthread`s doing ordinary `GC_MALLOC` churn, forcing real cross-thread stop-the-world collections (still survives, 3/3 runs); this session's own `GC_set_push_other_roots` hook installed and chained exactly as the real fix does, pushing one harmless dummy range (still survives, 3/3 runs); roughly a thousand *additional* `GC_add_roots` registrations accumulating from both threads over the run, well under Boehm's hard `MAX_ROOT_SETS` abort threshold but far more than a trivial test usually exercises, matching a true "not-thousands-but-not-just-one" middle ground this session had not actually measured before writing this paragraph (deliberately overshooting on the first attempt hit that exact abort, `"Too many root sets"` -- the same, already-known, already-partially-fixed limit the 2026-09-30 entry above found; recalibrated down by roughly 2000x to a volume representative of what `pg_rows.zm` itself could plausibly produce, not what a stress test would) (still survives, 4/4 runs).

**This is itself a real, useful negative result, not a dead end to shrug off.** It directly recapitulates, one level more minimal than before (no Ziman at all, not even a parser or interpreter loop), this same investigation's own earlier finding ("every attempt at a Postgres-free repro in this whole investigation has now failed, regardless of how closely it was shaped after the real code") -- now true even of a C program built solely to exercise Boehm's own public root-registration API in exactly the shape this bug seems to need. Whatever is actually happening is not a simple, structural flaw in how `GC_add_roots` interacts with multi-threading, finalizers, or a second installed `push_other_roots` hook in isolation -- those were each tested directly here and each came back clean.

**Took the one remaining lever the previous paragraph named -- a thread genuinely blocked on real socket I/O, not a tight allocation loop or a condition-variable wait -- and it also came back clean.** A sixth variant: a connected loopback socket pair (`socketpair(AF_UNIX, SOCK_STREAM, ...)`, not a full TCP listen/accept, but a real blocking syscall either way), one thread parked in `recv()` for the entire test (given nothing to read, same as `serve()` genuinely waiting on `receive(requests)` with nothing queued), the other doing the usual `GC_MALLOC` churn, explicit `GC_gcollect()`, and finalizer check against the same target shape as every earlier variant. Four runs, four survivals -- the target is never finalized early even with one thread parked in a real blocking syscall the whole time collections run on the other.

**Six variants in, all clean, named a real fork rather than guessing at a seventh: asked, and the answer was to build the combined toy** -- every ingredient together rather than one at a time, on the theory that the bug might need more than one of them simultaneously. **It also survived.** A seventh variant, closer to `pg_rows.zm`'s own shape than anything before it: the *two-level* arena-wrapper/ordinary-array chain (`"Connection".fields` -> an ordinary array -> `"Guard"`'s own header, in the *same* registered block -> `"Guard".fields` -> a second ordinary array -> the finalizable target -- not just one hop, matching `Connection`/`Guard`'s own real alternation exactly), a genuine two-socket request/reply exchange between `main`-like and `serve`-like threads repeated across 5000 rounds (both ends demonstrably, repeatedly blocked waiting on each other mid-run, not just once at the start), this session's own `GC_set_push_other_roots` hook installed and chained throughout, and roughly 580 additional `GC_add_roots` registrations accumulating from both threads as the rounds ran (recalibrated down from an initial overshoot that hit the same, already-known `MAX_ROOT_SETS` abort as before -- the realistic volume this time, matched to toy5's own earlier calibration, not a stress test). Checked after every 50th round, not just once at the end. Five full runs, five clean survivals -- the target is never finalized early even with every previously-isolated ingredient present and interacting at once.

**Seven variants, every one of them clean, is a strong result on its own terms.** Every ingredient this investigation could name -- multi-threading, a second `push_other_roots` hook, a realistic volume of additional root registrations, a thread blocked on genuine socket I/O, and now all of them together plus a real two-level wrapper/array chain and a repeated, genuine blocking request/reply exchange -- has now been tested, alone and in combination, against Boehm's own public API directly, with none of them reproducing the bug. This does not just fail to find the mechanism; it actively narrows where it can be. Whatever this needs is either (a) something in the real interpreter's own code that a hand-built analogue of the *data shapes* and *threading pattern* cannot capture no matter how faithful -- the real `receive`/`send`/`channel_send` implementations themselves, the real `gc_heap_alloc`/`gc_heap_sweep` bookkeeping interleaved with Boehm's own collector in ways this toy's plain `mmap`+`GC_add_roots` doesn't replicate, or something specific to the real `struct_obj_new`/`enum_obj_new` `Type`-carrying `Value` shape this toy simplified away -- or (b) something specific to real Postgres network I/O (actual `recv()` returning actual bytes from an actual remote process, not a same-host `socketpair` loop) that this investigation has still never tried to isolate away from. Left for whoever continues this, with the toy-based line of attack now reasonably exhausted rather than abandoned mid-stream: either instrument the real interpreter more (as the entries above already did extensively) rather than keep building analogues of it, or try a real-but-minimal `net.listen`/`net.connect` Ziman repro (not Postgres, but still the real driver's own socket/channel code) as the next rung between "pure C toy" and "the full Postgres-backed fixture."

**Took exactly that next rung, and it found the real mechanism at last -- not in Boehm at all.** Built a minimal, non-Postgres wire-protocol responder (a Python script, kept in the session's scratchpad, not this repo: handles the startup handshake with trust-equivalent `AuthenticationOk`, then answers every simple-query and extended-protocol/cursor exchange with a small, fixed, fake row set regardless of the SQL actually sent) and pointed the *real* `pg.zm` driver's own `connect`/`serve`/`Guard`/`spawn`/`Channel` code at it, from a Ziman script that opens one connection and loops `datasource.rows(conn, sql)` to completion thousands of times in a row -- real allocation pressure and real request/reply blocking on both ends, through the real interpreter, with no Postgres container and no hand-built C analogue of its data shapes. It hung, every run, at the exact same round (192) -- the deterministic, near-zero-CPU-over-wall-clock signature this whole investigation already knows by heart, now reproduced in under two seconds locally with no network variance at all.

**Re-adding the `guard_finalizer` trace (the same instrumentation several earlier paragraphs in this entry used and reverted) over *this* repro, then cross-checking against `GC_base`, found it directly.** `message_variant` -- which should only ever be `"Close"` (the connection's own `Guard`) or `"EndCursor"` (a per-cursor `Guard`, `db.zm`'s `CursorHandle`, created fresh by *every* `datasource.rows()` call and legitimately finalized once each one's iterator is drained -- a normal, expected firing, not a bug, confirmed harmless by inspection: `serve()`'s own `EndCursor` handler is a no-op against an already-closed cursor id) -- instead read back `"Some"`, `"Int"`, and outright binary garbage across repeated firings, with `GC_base()` returning `NULL` for every one of those `EnumObj` pointers. Re-running the *real*, Postgres-backed `pg_rows.zm` repro with the identical trace confirmed the same signature there too, at the exact point it has always hung: `enum_name=Option variant=Some GC_base(en)=(nil)`, right where `[Int(7), Text(x), Bool(true), Float(1.5), Null]` prints and everything has always stopped.

**The mechanism, once seen, is simple and entirely independent of every Boehm-side theory this whole entry spent exploring.** `GuardBuf` (`prelude.c`) is a plain `malloc`/`GC_MALLOC`'d block -- Boehm-visible, which is what every earlier paragraph in this entry was about -- but its own `message` field (the `Request.Close`/`Request.EndCursor(...)` value the finalizer sends) is a `Value` whose backing `EnumObj`/`StructObj` wrapper, like every such wrapper in this interpreter, was allocated through `enum_obj_new`/`struct_obj_new` -- `gc_heap_alloc(ziman_thread_heap(), ...)`, Ziman's *own*, entirely separate, per-thread Phase 3 precise collector, not Boehm's heap at all. Nothing in Phase 3's own root-walking (`mark_this_threads_roots`, `gc_mark_interpreter_roots`, `gc_mark_env_chain`) has ever visited a `GuardBuf`, because a `GuardBuf` is not itself a Ziman `Value` or `Env` -- it is a bare native handle, invisible to every mechanism this interpreter already has for protecting *Ziman-visible* state. The instant the Ziman-level `Guard`/`Connection` value that would otherwise have protected `message` becomes unreachable -- which, for a per-round `CursorHandle`, is completely routine, every single round -- Phase 3's own next sweep on that same thread is free to reclaim and reuse whatever arena slot `message`'s `EnumObj` happens to occupy, for something entirely unrelated (`Option.Some`, `SqlValue.Int`, anything else that thread allocates next). Whenever Boehm's *own*, independently-timed collector eventually decides the `GuardBuf` itself is unreachable and runs the finalizer -- arbitrarily later, on whichever thread happens to be collecting -- `message` is already garbage, and `channel_send` queues *that* garbage into `requests`. `serve()` dequeues it expecting a `Request`, and whatever happens next depends entirely on what the reused bytes happen to spell: this entry's own very first finding, months of `DESIGN.md` entries ago -- a `SIGSEGV` inside `eval_enum_access`'s `strcmp` dispatch on a `receive`d value's garbage `enum_name`/`variant_name` -- is almost certainly the *same* mechanism with unluckier garbage; this entry's own long-hunted deadlock is the same mechanism with garbage that (for reasons not further chased down, and not needed to be) lands `serve()` somewhere it silently stops reading `requests` instead of crashing outright. **The two-collector framing this entry floated and retracted early on was closer to right than given credit for -- it just had the wrong two objects in mind.** It is not `Env` that falls between Boehm and Phase 3; it is `Guard.message`.

**Fixed the same way every other root-source gap in this whole project's history has been closed: a new, explicitly-scoped root source, not a change to either collector's own general policy.** `src/gc_guard_roots.{c,h}` (new): a global (not `__thread`) registry -- mirroring `native_thread.c`'s own `ThreadInfo`/`g_threads` shape, for the identical reason `gc_boehm_roots.c` earlier in this entry needed one -- of every currently-live guard's own `message` field address plus which thread's `ziman_thread_heap()` created it. `ziman_guard_register` is called once, from `native_guard_new`, right after `message` is set; `ziman_guard_unregister` once, from `guard_finalizer`, *after* it has read `message` for the last time, not before. `gc_mark_live_guards(heap, a)` is called from `mark_this_threads_roots` (`interpreter.c`) on every Phase 3 collection, marking every registered guard's own `message` whose owner matches the calling thread's own heap into that thread's own arena `a` -- protecting it for the guard's *entire* lifetime, independent of whether the Ziman-level value that used to point at it is still reachable at all, which is exactly the window the existing `gc_mark_register_struct_content_marker` seam (`ArrayBuilder`/`MapBuilder`/`SetBuilder`'s own fix for the identical "disguised handle, invisible payload" shape) cannot cover -- that seam only runs while the struct *value* itself is still marked reachable from some other root, but a guard's entire purpose is to act *after* the value holding it is already gone. Unlike `gc_mark_live_guards`'s own Boehm-side cousin (`push_other_roots`), this one genuinely needs its lock while walking: Phase 3 stops no other thread, so a concurrent register/unregister on another thread is a real race here, not just a formality copied from the pattern it mirrors. Not `#ifdef ZIMAN_GC`-gated at all, unlike every fix earlier in this entry -- Phase 3 is Ziman's own collector, active in both the `ZIMAN_GC` and `nogc` builds alike, and the gap applies equally to both.

**Verified against the exact repro that found it, then against everything else.** The fake-listener sustained-load script: previously hung at round 192 of 20000, every run; with this fix, it runs past round **2007** before hitting a *different*, unrelated, already-known wall (`"Too many root sets"` -- Boehm's `MAX_ROOT_SETS` abort, the 2026-09-30 entry's own finding that a long-lived thread's own `gc_heap` arena blocks, once registered via `GC_add_roots`, are never individually reclaimed within that thread's lifetime, only at thread exit -- that entry's own fix addressed the two leak sources it found, a per-connection thread's own heap and `value_copy.c`'s outbound arena, not *ordinary* sustained growth on an single, otherwise-ordinary long-lived thread; a real, separate, already-scoped architectural question, explicitly not undertaken here). The real, Postgres-backed `pg_rows.zm` fixture: previously hung after five lines, `exit 124`, every run; with this fix, it runs to completion in under three seconds and gets *eleven* lines further than ever before, failing only on that same separate `MAX_ROOT_SETS` wall -- `make test-pg`'s own full run: **10 passed, 1 failed** (`pg_rows`, now aborting instead of hanging, on an unrelated, pre-existing, already-documented limitation). The ordinary suite is unaffected: `./tests/run_tests.sh` 834/834 under the real `ZIMAN_GC` build; `make fmt-check` clean (same pre-existing unformatted sibling-repo files as every earlier check in this entry); `ziman-nogc` shows the same pre-existing, already-documented cross-run flakiness (a different handful of tests failing each run, unrelated to this fix, already attributed earlier in this entry to that build's own unbounded-heap-under-fixed-timeout character) -- not a regression, confirmed by the failing set changing shape across repeated runs with no code change in between.

**What is left, deliberately not undertaken in this entry: the `MAX_ROOT_SETS` wall for an ordinary long-lived thread's own sustained allocation.** The 2026-09-30 entry's own fix covered a thread *ending* (release its heap) and a value crossing threads (destroy its own temporary arena once copied out) -- neither applies to a thread, like `main()` here or a long-running `serve()`, that simply keeps allocating through its own single, ever-growing `gc_heap` for its whole life. Every block that heap's arena ever `mmap`s stays `GC_add_roots`-registered until that thread ends, which for `main()` is the whole program's run. A `pg_rows.zm`-scale workload (dozens of statements) is nowhere near the 2048-entry limit; the fake-listener script's own thousands of rounds is. Whether this matters for any *real* workload, and what the right fix looks like (compacting/coalescing registrations, periodically relocating long-lived survivors into a smaller, stable set of blocks, or something else) is exactly the kind of design question the 2026-09-30 entry itself flagged as needing a real decision rather than a guess -- left open, deliberately, rather than guessed at here.


## The original style-sweep crash, re-examined with the real root cause in hand: a parser bug, not a GC bug at all (2026-10-05)

With the Guard/Phase-3 fix above committed and pushed, went back to the very first thing the long GC entry above ever found: converting `pg.zm`'s/`mysql.zm`'s `FetchCursor` guard from `is_Some`/`unwrap_Some` to an `if`-let (`if cursor_open && r.cursor == cursor_id && Some(e) = deferred { ... }`) crashed the interpreter intermittently, "not yet root-caused," and was left reverted with a comment pointing at a "timing-sensitive concurrency bug." With the real GC mechanism now understood and fixed, the natural next step was to try the conversion again and see if it held.

**It didn't -- but not because of anything GC-related.** Re-converting both files and running `./ziman --check` on them crashed roughly half the time, same as the original report. Reducing to a 20-line, Postgres-free, interpreter-free (no `spawn`, no `Channel`, no runtime execution at all -- just `--check`, pure type-checking) program with the identical condition shape (two booleans and an `Option` pattern, `&&`-joined, followed by `else if`, not `else { ... }`) reproduced it at a *higher* rate, ~75% of runs, confirming it was never about `pg.zm`'s own size or Postgres at all -- just this exact syntax shape. Tried `ziman-nogc` on the same minimal file next, specifically to rule Boehm out the same way every earlier entry in this file has: it crashed at the *same* rate, with no garbage collector running at all. That single check reframes everything that follows -- whatever this is, it cannot be about collection timing, dropped roots, or anything this whole document has spent months chasing.

**`valgrind` (already used elsewhere in this project's own history for exactly this kind of question) found it directly, no guessing required.** `Invalid read of size 4` / `Address 0xb0000000a is not stack'd, malloc'd or (recently) free'd`, inside `check_stmt` (`typecheck.c:3541`, the very first line of the function: `switch (s->kind) {`) -- `s` itself is garbage by the time it's dereferenced. The full call chain (`check_switch` -> nested `STMT_IF`/`STMT_BLOCK` dispatches, matching the `if`-let's own desugared shape exactly) pointed at one specific frame: `check_stmt`'s `STMT_IF` case calling `check_block(module, env, s->as.if_stmt.then_block, ...)` unconditionally, with no kind check on what `then_block` actually holds.

**The bug: `parser.c`'s own multi-part `if`-let desugaring (`parse_if_binding`, the general case for two or more `&&`-joined parts) builds a synthetic "did every part hold" check -- `if !$flag { <the user's own else> }` -- and assigns the user's `else` directly to that synthetic `if`'s own `then_block`.** `then_block` is supposed to always be a real `STMT_BLOCK`: every other producer of one is an ordinary `{ ... }`, and `check_block`/`check_stmts_in_scope` read `block->as.block.stmts.count`/`.items` through the union with no kind check at all, unlike `else_block` (which `check_stmt`'s own `STMT_IF` case explicitly checks the kind of before deciding whether to recurse into `check_stmt` directly or wrap in `check_block`). `else_stmt = match(p, TOK_IF) ? parse_if_mode(p, allow_binding) : parse_block(p);` -- when the user writes `else { ... }`, this is always a block, and the bug never fires; when they write `else if ...` (exactly `pg.zm`'s/`mysql.zm`'s own `FetchCursor` shape, and exactly this entry's own minimal repro), `parse_if_mode`'s ordinary (non-pattern) path hands back a bare `STMT_IF`, which then gets jammed into `then_block` as-is. `check_block` reads that `STMT_IF`'s own `cond`/`then_block`/`else_block`/`line`/`col` fields as if they were a stmt list's `items`/`count`/`capacity` -- `0xb0000000a` is exactly the kind of small-integer-shaped garbage those fields produce when misread as a pointer. Not a timing bug at all: whether it crashes on a given run depends only on whatever happens to be sitting in the memory the misread "items" pointer and "count" happen to name, which is why it looked intermittent without ever actually depending on collection timing, thread scheduling, or anything else "timing-sensitive" -- the single-part-with-`else-if` case (`if Some(x) = o { ... } else if ... `) was never affected, since that path already assigns to `else_block`, which already has the kind-aware handling; only the *multi-part* (2+ `&&`-joined parts) case, naming `then_block` where nothing else in the codebase ever had, was exposed.

**Fixed with a four-line guard at the one call site that builds this, `parser.c`'s `parse_if_binding`: wrap `else_stmt` in a synthetic `STMT_BLOCK` when it isn't already one**, before assigning it to `otherwise->as.if_stmt.then_block` -- restoring the invariant every other `then_block` in the codebase already holds, rather than teaching `check_block` to tolerate a non-block (which would just be papering over the same mismatched-invariant risk at a different layer). A regression case was added to the existing `tests/lang/if_binding_patterns.zm` fixture: a multi-part condition followed by `else if` (not `else { ... }`), the one shape the existing fixture never covered -- every other multi-part case there already ends in a plain `else { ... }`, which is exactly why this went unnoticed before. (The function needed one unreachable `return` after its own `if`/`else if`/`else` to satisfy "every path returns" -- a *different*, already-documented gap, `SYNTAX.md`'s own "a multi-part chain *with* an `else` isn't seen by the 'every path returns' check," unrelated to this bug and not attempted here; it does not affect `serve()`'s own real use, which returns nothing.)

**Verified**: the minimal repro and both real files pass `--check` cleanly across 20-30 repeated runs each, on both the `ZIMAN_GC` and `nogc` builds (0 crashes, versus roughly half before); `./tests/run_tests.sh` 834/834; `make fmt-check` clean; `make test-pg` and `make test-mysql` both land on the *same* `MAX_ROOT_SETS` wall the entry above already found and deliberately left open, not a new regression, and *not* the deadlock -- the re-converted `FetchCursor` itself holds. The `is_Some`/`unwrap_Some` style this project's own mechanical sweep left behind at both call sites, the one remaining trace of "not yet root-caused" anywhere in `lib/`, is gone.


## Closing the `MAX_ROOT_SETS` gap for an ordinary long-lived thread: block-level reclaim, and a second, separate leak found verifying it (2026-10-05)

Picked up the one deliberately-deferred question from the long GC entry above: an ordinary long-lived thread (`main()`, or a long-running `serve()`) just keeps allocating through its own single, ever-growing `gc_heap` arena for its whole life, and nothing ever reclaimed a *block*, only individual *objects* within one -- every 256KB block, once `GC_add_roots`-registered, stayed registered until the whole arena was destroyed at thread exit. Compaction/relocation was never on the table (`docs/MEMORY.md`'s own "Phase 3 switches from copying to mark-sweep" entry, confirmed with the project owner across two rounds of discussion: a conservative stack scan can never safely tell a real pointer from one that merely looks like one, so nothing reachable can ever move).

**The fix needs no relocation at all, just a coarser-grained version of the reclaim `gc_heap_sweep` already does per object.** `arena_reclaim_block(a, prev, b)` (`arena.c`/`.h`, new): unlinks `b` from `a`'s own block list and releases it -- `GC_remove_roots` then `munmap` -- exactly like one iteration of `arena_destroy`'s own loop, just for one block instead of every one. `gc_heap_sweep` (`gc_heap.c`) now tracks, per block, whether anything in it survived this cycle's mark pass (`any_live`, set alongside the existing per-object dead/alive check it already walks every object through); if nothing did, and the block isn't the one still being bump-allocated into (`prev == NULL` on the very first block visited, `arena_first_block`'s own result) or the one block that embeds the `Arena` struct itself (`next == NULL`), the whole block is reclaimed rather than just adding its dead objects' slots to the free lists. One real correctness wrinkle, found by reasoning through it before writing the sweep code (the same discipline this effort has used throughout): an object swept dead in an *earlier* cycle is already linked into `h->free_lists[]` from back then, and reclaiming the block out from under that link would dangle it the moment something later walks that class's list looking for a chunk to reuse -- `remove_block_from_free_lists` (new) splices out every free-list node whose address falls in the block's own range, across every size class, before the block is ever unmapped.

**No new unsafety category, just the existing one applied more coarsely.** Both the per-object and per-block reclaim depend on exactly the same thing: that the mark pass just completed is a complete, correct account of what's still reachable. If it weren't, the *existing* per-object reclaim (already trusted, already shipping) would already be unsafe, with or without this change.

**Verified against the one tool built for exactly this since the previous entry: the fake-listener sustained-load script, now also run against the clean, already-pushed state for a proper before/after.** Direct instrumentation (a per-sweep block count, reverted after use) confirmed the fix does exactly what it was built to do: the thread it's watching settles at a small, stable 4-13 blocks for the *entire* run, never growing with round count, regardless of how far the test gets. `./tests/run_tests.sh` 834/834 on both builds; `make fmt-check` clean; `test-arena`/`test-gc-heap` (and every other standalone `gc_*` unit test) pass.

**And yet the same fake-listener script still hits `"Too many root sets"` at almost the same round count as before the fix (clean baseline: round 2007, twice, exactly, confirmed by rebuilding from the pushed commit and rerunning; with this fix: round 2021) -- because the real growth isn't coming from `gc_heap`'s own arena at all.** A second counter (also reverted after use), this time on `arena_create_impl`/`arena_destroy` directly, counting every currently-live *scanned* arena process-wide, found it: the count climbs to ~2021-2025, right where the abort fires -- not from `gc_heap`'s per-thread arena (confirmed small and stable by the first counter), but from `value_copy.c`'s own per-crossing "outbound" arena, the one `value_copy_send`/`value_copy_receive` use to deep-copy a value across a `Channel`/`spawn` boundary and which `arena_destroy`s itself the moment the receiving side has its own independent copy (the 2026-09-30 entry's own fix, confirmed working correctly for the cases it covered).

**Traced to a specific, previously-unknown leak: `db.zm`'s `next_item`, "putting back" a value into a channel that isn't actually crossing threads at all.** `buffer_page`/`next_item` (`lib/db/db.zm`) use an ordinary `Channel<Option<Row>>` purely as a same-thread FIFO -- never shared, never received from any other thread -- to buffer a cursor page's rows one at a time. Its own `send()` calls go through the *exact same* `value_copy_send` machinery a genuine cross-thread send does (`EXPR_CALL`'s own native `send`, `interpreter.c`, has no way to tell "this channel never actually leaves this thread" from "this one does," and doesn't try to), creating a fresh scanned arena for `enum_obj_new`'s own copy of the value's wrapper header -- *even for a payload-less variant like `Option.None`*, which carries nothing that genuinely needs copying at all. `next_item`'s own comment says why it puts one back: "a `None` in the buffer marks the end and is put back, so asking again after the end is safe" -- but the *first* caller to see that `None` (an ordinary `for` loop, which stops iterating the moment it sees one) never asks again, so the value this `send(buffer, item)` just created sits in the now-abandoned buffer channel, received by nobody, its own arena never destroyed, forever. One leaked, permanently `GC_add_roots`-registered arena per cursor fully drained the ordinary way -- confirmed to reproduce identically on the clean, already-pushed commit (`c7e2292`), with no relation to this entry's own block-reclaim work at all; the two were simply discovered together while verifying the fix above, because both manifest as the same `"Too many root sets"` abort under enough sustained cursor traffic.

**Deliberately not fixed in this entry.** A plausible fix exists (`value_copy.c`'s own enum-copying could skip `lazy_arena` entirely for a payload-less variant, copying only `enum_name`/`variant_name` into an ordinary, non-arena `malloc`'d wrapper instead -- safe under Boehm's own conservative scan the same way any other plain `GC_MALLOC`'d block already is, and a strictly more general fix than patching `db.zm`'s own call site, since *any* payload-less-enum `send()` anywhere in the interpreter would benefit identically) but touches `value_copy.c`'s foundational, every-crossing-in-the-interpreter copy path, which is its own, separately-scoped piece of work -- asked, and chose to land the (complete, verified, unrelated) block-reclaim fix on its own rather than fold a third investigation into the same commit. `make test-pg`/`make test-mysql`'s own `pg_rows`/`mysql_rows` cases remain the one known-failing case, now confirmed to be this leak specifically rather than the deadlock or the `gc_heap`-arena-growth question this entry set out to answer -- both already fixed.


## The `value_copy_send` leak fix, and a fourth, distinct, still-unfixed `MAX_ROOT_SETS` trigger found verifying it (2026-10-05)

Implemented exactly the fix the previous entry scoped and deliberately deferred: `arena_enum_copy` (`value_copy.c`) now only calls `lazy_arena` when `en->has_payload` is true. A payload-less variant (`Option.None`, `Request.Close`, any no-payload enum) gets an ordinary `malloc`'d (Boehm-tracked under `ZIMAN_GC`) copy of its wrapper instead -- safe for the identical reason `gc_guard_roots.h`'s own `GuardBuf` already is: the only thing that will ever reference this copy is a `Channel`'s own queue, itself plain `malloc`'d and so already fully visible to Boehm's ordinary conservative scan, with no help from Ziman's own Phase 3 needed at all. `value_copy_receive`'s own matching `ordinary_enum_copy` needed no change -- it already reads `en->enum_name`/`variant_name`/`has_payload` generically, with no assumption about how the intermediate copy was allocated.

**Verified directly against the exact leak this closes.** Temporary counters (reverted after use, same discipline as every other diagnostic pass in this file) on `lazy_arena`'s own create and the matching `arena_destroy` call sites (`value.c`'s `channel_finalize_received`/`channel_send`/`channel_try_send_status`, `interpreter.c`'s `spawn_thread_entry`) confirmed the live count now returns to **0** repeatedly throughout the fake-listener stress script's own run, where it previously climbed in lockstep with round count. The same script's own round-reached number, as a cruder but independent check, moved from ~2021 (block-reclaim alone) to ~2814 before hitting a *different* failure -- progress, not yet a full fix, for a reason below. `./tests/run_tests.sh` 834/834 both builds, `fmt-check` clean, `test-gc-copy` (the one standalone unit test that links `value_copy.c`) passes.

**But `make test-pg`/`make test-mysql`'s own `pg_rows`/`mysql_rows` still hit `"Too many root sets"`, at the *exact same point* in each one's own output as every earlier run this entire investigation has ever captured -- unmoved by either of today's two fixes.** That byte-for-byte-identical failure point is the tell: whatever causes it cannot be the leak just fixed (confirmed returning to 0 throughout a run thousands of rounds longer than all of `pg_rows.zm`) or the `gc_heap`-arena-growth question the previous two entries already closed (confirmed bounded at a handful of blocks). `pg_rows.zm`'s own output stops exactly after the line printed by `print(is_ok(datasource.query(conn, "SELECT 1")))` right after its own `iter_close` section -- meaning the very next statement, `print(is_ok(datasource.rows(conn, "SELEC 1")))` (a deliberate SQL *syntax* error, testing that `open_rows` correctly propagates a failed `OpenCursor` without ever creating a cursor at all), is where it goes wrong. `mysql_rows` fails at the analogous spot in its own, differently-ordered script. Neither this entry's own fake-listener repro, nor either of today's two real fixes, ever exercises a SQL error at all -- the fake listener always answers success, by construction, so this specific trigger has never actually been tested by anything built so far in this whole investigation.

**Deliberately not chased further in this entry.** This needs a real Postgres (or MySQL) container to even reproduce at all (the fake listener cannot simulate a server-side parse error, by its own design), and is evidently a *fourth*, independent contributor to the same `MAX_ROOT_SETS` symptom, on top of the three already found and two already fixed across this and the previous two entries -- narrowed precisely enough to know where to start (whatever `open_rows`'s own error path, or `collect_result`/`start_cursor`'s own handling of a server-side `ErrorResponse`, does with the request/reply arena pair in that specific case) but not yet investigated at all. Landed as its own commit, on top of the already-pushed block-reclaim fix, with this finding written up rather than guessed at further.



## The fourth `MAX_ROOT_SETS` trigger, found: a cursor left early strands a whole page of rows in a channel nobody will ever receive from -- plus a separate pg driver bug the abort had been hiding (2026-10-05)

Picked up exactly the question the previous entry narrowed and then deliberately left: `pg_rows`/`mysql_rows` still aborted with `"Too many root sets"` at a byte-for-byte-identical point, unmoved by either of that entry's two fixes. The previous entry's own guess at *where* -- `print(is_ok(datasource.rows(conn, "SELEC 1")))`, the deliberate SQL syntax error, reasoned about from where the output stopped -- **turned out to be wrong, and the reasoning that produced it is worth recording as the mistake it was**: the output stops after nine lines, and counting `pg_rows.out`'s own lines back to the statements that print them puts the ninth at `print(is_ok(datasource.query(conn, "SELECT 1")))` on line 52, not line 65. The failing region is the `for round in 0..5` early-`break` loop on lines 55-60, and the SQL-error path the previous entry singled out is never reached at all. A guess about a line number, from a line count, with the real fixture in hand the whole time -- the actual abort location took one `addr2line` run to establish and should have been measured, not inferred.

**Measured, not inferred, this time.** A temporary shadow copy of Boehm's own root-set table in `arena.c` (every `GC_add_roots`/`GC_remove_roots` call mirrored into a local array, with `GC_set_abort_func` hooked to dump the counters at the abort; reverted after use, the same discipline as every other diagnostic pass in this file) answered three questions at once. The live registered-range count climbs **monotonically to 2039 and never comes back down** -- so it is a real leak, not a transient peak. `same_start_merge=0` and `remove_nomatch=0` -- so Boehm is neither silently merging a re-used `mmap` address into an existing entry nor failing to match a removal, two plausible mechanisms ruled out rather than argued about. And `backtrace()` from inside the hooked abort names the leaking allocation directly: `lazy_arena` (`value_copy.c:13`) from `value_copy_send` (`value_copy.c:216`).

**Root cause: `db.zm`'s page buffer is a channel, and a value left queued on a channel keeps its crossing copy alive for as long as the channel does.** `buffer_page` (`lib/db/db.zm`) eagerly pushes an entire cursor page -- up to `cursor_fetch_rows`, 500 rows -- into a `Channel<Option<Row>>` before the iterator pulls the first one back out, and each of those `Option<Row>.Some(row)` sends gets its own dedicated, `GC_add_roots`-registered arena from `value_copy_send`, exactly as any other send does. Drain the cursor to the end and all 500 are received and destroyed; **leave the loop early and every row still in the buffer is stranded in a channel nothing will ever receive from again, its arena registered forever.** `pg_rows`'s own five-round `break` loop strands ~499 rows a round, five times, on top of the ~500 a legitimate in-flight page already holds -- which is precisely the 2039 the shadow table measured, and precisely why the abort point never moved: it is a function of the fixture's own round count, not of anything the previous two fixes touched. This is the same shape as the leak the previous entry found and the already-landed `value_copy.c` fix closed (`next_item`'s own put-back `None`), one layer out: that one stranded a single payload-less wrapper per drained cursor, this one strands a whole page of payload-carrying rows per *abandoned* cursor.

**Fixed where the knowledge is: `end_cursor` now drains the buffer before ending the cursor.** It already runs on every way a cursor ends that isn't "dropped and collected" -- `iter_close`, and a `for` loop left early -- and it is the one place that knows the buffer will never be read again, so it takes the buffer as a second argument and `try_receive`s it empty (`channel_len` as the loop condition) before sending `Request.EndCursor`. That releases every stranded row's arena at once rather than leaving it to a collection that may never come: the arenas are `mmap`'d *outside* Boehm's own heap, so 500 of them exert almost no collection pressure on the allocator that would have to notice them. Measured after the fix: peak live registered ranges for the whole of `pg_rows` drops from **2039 to 500**, the legitimate in-flight page and nothing more.

**A separate, genuine pg driver bug the abort had been hiding the whole time.** With the leak fixed, `pg_rows` ran to the end and was still one line short: `database error: division by zero`, the row-level error from `SELECT 10 / (2 - g)`, was silently dropped. Confirmed pre-existing and unrelated by reproducing it on a three-line fixture against the clean tree (`git stash`, rebuild, same missing line) -- it had simply been unreachable behind an abort nine lines earlier, and no amount of work on the leak would ever have surfaced it. `finish_page`'s "rows arrived before the error" branch returns `open: false` (correct -- it has already run `sync_and_drain`, the server-side cursor really is finished) together with `deferred: p.failure`, the error it still owes the client on its next fetch. But `serve`'s own `FetchCursor` handler guarded the deferred-error branch on `cursor_open &&`, which that very same `CursorStep` had just set to false -- so the next fetch fell through to the `!cursor_open` branch and answered with an empty, finished page instead, discarding the error. **`mysql.zm`'s own `serve` already had the correct form** (`if r.cursor == cursor_id && Some(e) = deferred`, keyed on the cursor id alone), with the identical `open: false`-plus-`deferred` shape from its own `fetch_page` -- the two drivers were meant to be the same here and pg was the outlier. Fixed by dropping the `cursor_open &&` guard to match, with a comment saying why it is deliberately absent.

**Verified.** `pg_rows` byte-identical to its expected output; `make test-pg` **11/11** and `make test-mysql` **6/6**, both fully green for the first time in this entire investigation (they have been the one known-failing case across the previous three entries). `./tests/run_tests.sh` 834/834; `make fmt-check` clean; all nine standalone `gc_*` unit tests pass. The `ziman-nogc` build segfaults flakily on two or three fixtures per run (`csv_extended`, `regex_cache`, `yaml_basic`, `http_endpoints`, `map_set_builders`, a different subset each time) -- **confirmed to do so identically at the clean `792c3a0` commit**, none of the affected fixtures touching `lib/db` at all, so it is a separate pre-existing problem in that build and not a consequence of this change; recorded here because `docs/MEMORY.md` last recorded that build as stable across five runs, so something has regressed it since, and it is now its own open question.

**And a fifth trigger of the same symptom, demonstrated on code with no leak in it at all.** With the leak fixed, a single fully-drained cursor still holds ~500 registered ranges at its peak -- a quarter of Boehm's whole 2048-entry table -- because that is simply what a 500-row page buffered through a channel costs. Six worker threads, each on its own connection, each streaming one 4000-row cursor and draining it completely, abort at `live=2039`: correct code, nothing stranded, `rems` climbing normally the whole way. So `MAX_ROOT_SETS` is not merely where four separate leaks happened to show up; at one `GC_add_roots` slot per queued message it is a hard concurrency ceiling on the language's own `Channel`. The fix that removes the ceiling rather than the next leak is to stop using Boehm's fixed-capacity static-root table for scanned arenas at all and push them from the `GC_set_push_other_roots` hook `gc_boehm_roots.c` already installs for `Env` -- an uncapped, walk-a-list root source. Left as its own next piece of work rather than folded into this commit, which is already two independent fixes.


## `MAX_ROOT_SETS` stops being a limit at all: scanned arenas move off Boehm's static-root table onto the `push_other_roots` hook (2026-10-05)

The previous entry demonstrated the fifth trigger of `"Too many root sets"` and, unlike the four before it, this one had no leak in it: six threads each streaming *and fully draining* one 4000-row cursor abort, because one `GC_add_roots` slot per queued `Channel` message against a 2048-entry table makes roughly 2048 simultaneously-queued messages a process-wide ceiling. Four leaks had hit that ceiling first and each been mistaken for the whole problem in turn; the ceiling itself was the thing worth fixing.

**The seam already existed in this codebase.** `gc_boehm_roots.c` installs a `GC_set_push_other_roots` callback -- added two entries ago for `Env`, for the unrelated reason that Boehm cannot find an `Env` on its own -- which Boehm's mark phase calls on every cycle to push root ranges beyond its own stack/register scan. It has no capacity limit of any kind: it is a function that walks whatever it likes. So `arena_create_scanned` no longer calls `GC_add_roots` per block at all. Instead each scanned arena goes on a global list (`g_scanned`, `arena.c`) that a new `ziman_arena_push_scanned_roots` walks from that callback, `GC_push_all`-ing every block of every live scanned arena. `arena_destroy` takes the arena off the list instead of calling `GC_remove_roots`, and `arena_reclaim_block`'s existing unlink-from-the-block-list *is* now the whole of what stops a block being scanned.

**The interesting part is not the list, it's that these run constantly.** `gc_boehm_roots.c`'s own thread registry gets away with "a mutex only the add/remove needs, and those never happen during a collection" because threads start and exit rarely. A scanned arena is created and destroyed *per value crossing a `Channel`*, so a thread **will** be suspended part-way through a link or an unlink by a collection, repeatedly. Both are therefore written so that the forward chain the collector walks is whole at every instant: the link sets `next_scanned` and then publishes the new head with one release store; the unlink repairs the predecessor's `next_scanned` with one release store *before* touching any `prev_scanned` (which only the locked mutators ever read). The same reasoning applies one level down, to `arena_alloc` adding a block: `a->current` is published with a release store *after* `fresh->next` is the rest of the list, or a collector walking from the new head would stop at the `NULL` `block_new` leaves there and silently miss every older block -- a missed-roots bug, not a crash, and so exactly the kind that would have shipped quietly.

**Two performance findings, both measured rather than assumed, and the second only because the first was wrong.** Pushing from a hook rather than registering a fixed range makes one thing possible that `GC_add_roots` could not: reading each block's `used` live on every collection, so only the bytes `arena_alloc` has actually handed out get scanned, never the rest of the 256KB block. That matters because a crossing copy of one small value gets a whole block to itself. Twelve threads each streaming a cursor: **3.4-4.0s pushing whole blocks against 1.4-1.5s pushing only `used`.** Separately, the first version of the list was singly linked, which made unlinking walk to find the predecessor -- quadratic in how many arenas are live at once, and serialised under one global lock: **6.5s against 1.5s on the same twelve threads** once the links went both ways. Both numbers come from running it both ways after writing comments claiming speedups neither had actually been measured for; the claims were wrong in the same direction (each is a real 2.4x-4.3x win, neither is the "never finished against seconds" the first drafts said), which is a good argument for not writing a number down until it has been produced.

**Verified, including the thing that actually matters for a change like this: that it costs nothing when it isn't needed.** At four concurrent cursors -- under the old ceiling, so the only workload both builds can run -- the clean `1dcc852` build and this one are indistinguishable (0.62/0.81/0.71s against 0.62/0.62/0.54s). At sixteen, `1dcc852` **aborts in 4.35s** and this build completes. `tests/bench/server_concurrency.sh` against the real `health-record-backend-ziman`, run on both builds back to back, is flat within noise (c=1 661 vs 666 req/s, c=4 1315 vs 1324, c=8 1382 vs 1355, c=16 958 vs 963, zero failures either way) -- and an earlier, higher-looking set of numbers for this build turned out to be nothing but run-to-run variance, which is why it was re-run against a rebuilt baseline rather than against what `docs/MEMORY.md` recorded months of sessions ago. `./tests/run_tests.sh` 834/834; `make test-pg` 11/11; `make test-mysql` 6/6; all nine standalone `gc_*` unit tests pass; the real app's own suite passes in full (19 files, ~1000 checks); `make fmt-check` clean. `valgrind --leak-check=full` on three channel/thread fixtures: 0 bytes definitely lost, and the error contexts are byte-for-byte the same 11 `Conditional jump` reports the clean build produces on the same fixture -- the known, pre-existing Boehm conservative-scan interaction, with nothing new added.

**What this does not fix, now visible for the first time.** Above about fourteen concurrent streaming cursors the process no longer aborts -- it goes CPU-bound instead, reproducibly, in `gc_next_object`/`gc_lookup` (20.7% and 3.5% of a `perf` profile at sixteen threads, with `GC_mark_from` another 14.2% and `__strcmp_avx2`/`native_lookup` the already-known ~14%). That is Ziman's *own* Phase 3 mark phase resolving addresses by walking an arena's objects linearly, not anything this entry touched: `ziman_arena_push_scanned_roots` itself is 4.9% of the same profile. It is a pre-existing scalability wall that no workload could previously reach, because the `GC_add_roots` ceiling aborted first -- the fix removed the crash and exposed the next limit behind it, which is progress and not a regression, but it is the obvious next thing and it is not small.


## The `gc_lookup` wall: an object-start bitmap per arena block, and a mark-stack livelock found behind it (2026-10-05)

The previous entry left "above about fourteen concurrent streaming cursors the process goes CPU-bound in `gc_next_object`/`gc_lookup`" as the obvious next piece of work, on the strength of a `perf` profile taken at sixteen threads. Going after it found two separate things, and got the relationship between them backwards at first.

**What `gc_lookup` was doing, measured before changing anything.** `gc_mark.c`'s `is_gc_heap_object(a, ptr)` asks "is `ptr` an object this `gc_heap` actually allocated" of essentially every pointer the mark phase touches, because most of this interpreter's objects still aren't `gc_heap`-allocated and writing a mark bit through a pointer with no real header corrupts whatever those bytes belong to -- an incident this collector has already shipped once. `gc_lookup` answered it by walking the containing block's objects one at a time from its content start. Instrumenting it (temporary counters, reverted after use) on a six-thread cursor-streaming benchmark: **710,688 calls, 136 million object steps, 827 objects walked per in-arena answer**, max 2,152. The split is what decided the design: **138,708 of those answers were exact matches and 20 were genuine interior pointers.** All of the cost was the exact-match question -- the one that does not need a walk at all.

**A memo cache was the obvious cheap fix and the numbers talked me out of it.** Simulating a 1024-entry direct-mapped positive-only cache in the diagnostic gave a 77% hit rate -- but with 132,201 evictions against 139,952 fills, and that figure is an *upper* bound, because a real cache would have to be reset at the start of every collection to stay honest about allocation. The remaining walks still averaged 826 steps. Cheap, approximate, and needing an invariant about what may allocate during marking; rejected in favour of something exact.

**The fix: one bit per `ARENA_ALIGN` bytes of every arena block, set by `arena_alloc` for each allocation it returns, reserved inline between the block's own header and its content.** An exact match becomes a single bit test -- "did an allocation start one header-span before this address" -- and an interior address a short backwards scan for the nearest start, whose span is then checked for actually reaching that far. Inline rather than a side table on purpose: no second `mmap`, no registry mapping a block to its bitmap, and nothing to free, since it is unmapped with the block it describes by `arena_destroy` and `arena_reclaim_block` alike, neither of which needed a line of new code. It costs 1/128th of every block, 2KB of a 256KB one. Two incidental wins came with it: `ziman_arena_push_scanned_roots` now pushes from the content start rather than the block base, so the bitmap's own dense bit patterns are never handed to conservative scanning; and the bitmap makes the exact answer *exact*, where the tempting alternative -- deciding from whether the bytes before an address look like a header -- is a probabilistic guess whose rare false positive is precisely the corruption already shipped once.

**It works, and on this benchmark it buys no wall-clock time at all.** `gc_next_object` and `gc_lookup` disappear from the profile completely. The six-thread and twelve-thread runs are unchanged end to end (2.05/2.15/2.13s against 1.96/2.23/2.02s). The win is real but it is *CPU*, not latency: twelve threads go from **5.53-6.04s of user CPU to 3.33-3.66s, about 40% less**, matching almost exactly the 37% of profiled CPU the two functions held (31.2% + 5.5% in a healthy twelve-thread profile). That benchmark waits on Postgres, so the CPU it stops burning simply goes idle. `tests/bench/server_concurrency.sh` against the real app is flat within noise in both directions (614/1125/1028/694 against 676/1071/1040/713 req/s). So: a third of the interpreter's CPU under this kind of load, returned, with no throughput change on either benchmark available to show it -- worth landing on its own terms, and worth saying plainly rather than dressing up.

**And the thing the profile was actually pointing at was not this.** Replacing `gc_lookup` did not move the cliff at all: fourteen threads finish in 1.7s, fifteen never finish, reproducibly, with the bitmap exactly as without it. Boehm's own statistics name it immediately: **3,935 `"Mark stack overflow; current size: 4096 entries"` messages and only seven completed collections**, the mark stack never growing past its initial 4096 entries. `vendor/bdwgc/mark.c`'s `GC_signal_mark_stack_overflow` deliberately does *not* set `GC_mark_stack_too_small` when `GC_parallel` is on ("that will be done in `GC_return_mark_stack` if required"), and `"No room to copy back mark stack"` -- the one place that would -- appears **zero times** in the whole run. So the stack never grows, every overflow invalidates the mark state, and the collector restarts marking forever with the world stopped. `GC_MARKERS=1`, which turns `GC_parallel` off and restores the non-parallel branch, runs the same fifteen-thread case in **2.82s**.

**That livelock is the next limit behind the one the previous entry removed, and it was being hidden by it.** The trigger is the number of root ranges `push_other_roots` hands Boehm, one per queued `Channel` message: fifteen cursors buffering 500 rows each is ~7,500 ranges against a 4,096-entry mark stack. While scanned arenas were registered with `GC_add_roots`, `MAX_ROOT_SETS` capped that at 2,048 -- **below the mark stack's capacity, so the abort was accidentally protecting the process from the livelock.** Removing the cap exposed it, which is worth recording as the cost of that fix rather than filed as an unrelated discovery.

**Deliberately not fixed here, with a view on which fix is right.** Patching `GC_signal_mark_stack_overflow` to set the flag unconditionally fights an upstream comment that says the parallel path means something specific by not setting it, inside vendored third-party marking internals. Forcing `GC_MARKERS=1` gives up parallel marking process-wide to work around one pathological shape. The honest fix is to stop producing thousands of root ranges in the first place -- `value_copy_send` gives every value crossing a `Channel` its own `mmap`'d, separately-scanned arena, which is also what made each queued message cost 256KB of address space and a root-set slot in the first place, and the precedent for not doing that already exists in this file: the payload-less-enum fix allocates its copy with plain `malloc`, Boehm-visible through the channel queue, needing no arena and no root range at all. Extending that to every crossing copy would collapse the root ranges from one-per-queued-message to one-per-thread and retire most of this entry's and the previous two entries' subject matter at once. It is a change to the foundational copy path every crossing in the interpreter goes through, and it is its own piece of work.

**Verified.** `./tests/run_tests.sh` 834/834; `make test-pg` 11/11; `make test-mysql` 6/6; all nine standalone `gc_*` unit tests pass, `test-gc-lookup` among them -- it already checked exact matches, interiors, the last valid payload byte, one byte past a declared end, padding gaps between objects, and resolution across three blocks, all of which pass unchanged against the bitmap. Two cases were added for what the bitmap newly makes possible to get wrong: an address inside an object's own *header* must not resolve to that object (the bitmap records header addresses, so resolving one has to step forward and then find the address genuinely short of the payload), and no address anywhere in a block's header or bitmap region may resolve to anything (checked by sweeping 512 bytes backwards from the arena's own control block). `make fmt-check` clean; the real app's suite passes in full. `valgrind --undef-value-errors=no --leak-check=full` (the mode the Makefile's own `test-gc-scan` comment prescribes, since feeding genuinely uninitialised stack words to `gc_lookup` is what conservative scanning *is*): 0 bytes definitely lost on four channel/thread/GC fixtures, and `gc_iter_state_survives_collection`'s single remaining context is identical to the clean build's, inside Boehm's own `GC_mark_from`. Without that flag the uninitialised-value reports on `channel_bounded` move from 11 to 19-plus-9, reproducibly -- same origin, one more place for it to surface, since the exact-match path now does arithmetic on a candidate word where it used to only compare it. `csv_records`'s 4,800-byte `getline` leak is byte-identical to the clean build, as already recorded. `ziman-nogc` still fails two or three fixtures per run from the same known pool, unchanged.


## Crossing values stop getting their own arena: `value_copy_send` allocates where Boehm can simply trace it (2026-10-05)

Three entries in a row ended by pointing at the same decision, so this one changes it. `value_copy_send` gave every value crossing a `Channel` or a `spawn` its own dedicated `arena_create_scanned` arena -- `mmap`'d memory registered with the collector as a conservatively-scanned root range, destroyed the moment the receiving side had its own independent copy. That was correct and promptly reclaimed, and it produced three separate hard ceilings in turn, each discovered as a failure and each initially mistaken for the whole problem: `MAX_ROOT_SETS` filling up (plus four distinct leaks of such arenas found while chasing it), and then, once that ceiling was lifted by pushing the ranges from `GC_set_push_other_roots`, Boehm's own mark stack overflowing and livelocking the collector. Every one of those followed from root ranges scaling with *queued messages* rather than with threads.

**The requirement was never rooting.** Read where it is actually written down -- `mapobj.h`, on the `_into` pair that exists for this and nothing else -- and it is exactly one thing: a crossing copy must not live in a heap that the *sending* thread may destroy (`ziman_thread_heap_release`, at its own exit) before the receiving side has copied it out. Not "must be a root"; "must not be thread-tied". Plain `malloc` -- `GC_MALLOC` under `zgc.h`, Boehm's shared heap, belonging to no thread -- meets that directly, and meets it *better*: a copy there is **traced** rather than **rooted**, found through whatever actually holds it (a `ChannelMsg` in a channel's own `malloc`'d queue, a `SpawnArgs` a new thread is started with, both themselves `GC_MALLOC`'d) and reclaimed once nothing does. The precedent was already in this file: the payload-less-enum fix had been allocating its copy exactly this way, for exactly this reason, since the first `MAX_ROOT_SETS` leak.

**Three things were verified rather than assumed, because the arena being an unconditional root had made all three moot.** First, the `spawn` handoff: `sa->args` is reachable only through `sa` until the new thread has it, and `sa` is `GC_MALLOC`'d. Boehm's own `pthread_create` wrapper holds it in a `struct start_info` that is a *stack local of the calling thread*, and blocks on `sem_wait(&si.registered)` before returning -- with the comment "this also ensures that we hold onto the stack-allocated `si` until the child is done with it" (`vendor/bdwgc/pthread_support.c`). Parent stack is scanned; child registers before the parent returns; no window. Second, disguised native handles -- the whole reason `arena_create_scanned` exists rather than `arena_create` -- stay alive, because `GC_MALLOC` blocks are conservatively scanned, which is precisely what the *receive* side has always relied on. Third, `gc_mark.c` needed no change at all: a crossing copy has no `gc_alloc` header, so it is simply `is_gc_heap_object == false`, the existing not-yet-migrated path that walks fields without touching a mark bit -- and `gc_mark_map`/`mark_leaf` were already gated that way, their comments already anticipating a headerless MapObj/Leaf.

**What it cost to write: `Arena **slot` leaves 12 functions and 14 allocation sites in `value_copy.c`, `ChannelMsg.owner_arena` becomes an `int needs_receive`, and `SpawnArgs.crossing_arena` and all four crossing `arena_destroy` calls go away.** `value_copy_receive` is untouched: the receiving thread still wants values in its own `gc_heap`, and questioning that is separate work. `arena_create_scanned` now has exactly one caller left, `gc_heap_create` -- so scanned root ranges went from one per queued message to one per thread.

**The livelock is gone, measured where it used to be certain.** Fifteen, sixteen and twenty-four concurrent streaming cursors -- every one of which previously never finished, reproducibly, with the collector spinning in restarted mark phases -- now complete in 2.24s, 2.27s and 3.99s with parallel marking on. `GC_PRINT_STATS` on the fifteen-thread case: **0 mark stack overflows and 28 completed collections, against 3,935 overflows and 7 completed collections before.**

**And it is substantially faster, for a reason worth naming precisely.** 200,000 struct sends through a bounded channel: **1.13s to 0.36s, about 3x**, with user CPU and peak RSS both flat (0.52s/42MB against 0.50s/41.6MB) and the entire difference in *system* time, **1.26s to 0.10s**. That is the `mmap`/`munmap` syscall pair every single crossing used to pay, gone. On the twelve-thread cursor benchmark the shape is different and worth recording honestly: elapsed improves ~18% (1.9s to 1.6s) and system time drops (2.5s to 1.6s), but **user CPU rises (4.1s to 5.3s)** -- that workload keeps far more crossing data live at once, so Boehm now traces what a root range used to cover wholesale. Total CPU there is roughly flat; the win is wall-clock and the removal of the ceiling, not a free lunch. `tests/bench/server_concurrency.sh` against the real app is flat within noise in both directions (665/1139/1012/687 against 615/1129/1040/687 req/s, zero failures), as expected -- that app crosses few values per request.

**One real regression, in the build that documents it as its own behaviour.** `ziman-nogc` has no collector and, per README, "never frees anything" -- but `arena_destroy` was a genuine exception to that, actually reclaiming crossing copies. With them `malloc`'d and never freed, the same 200,000-send program's peak RSS there goes from 296MB to 455MB (+54%). The `gc` build is flat. This is the `nogc` build becoming consistent with its own documented contract rather than a new leak in the real one; recorded rather than fixed, since making `nogc` free anything at all is a different project. Its suite stays in the same flaky band it has been in for three entries (3-6 failures per run against 3-4, from the same known pool, every subset different each time).

**Verified.** `./tests/run_tests.sh` 834/834; `make test-pg` 11/11; `make test-mysql` 6/6; all nine standalone `gc_*` unit tests; the real app's own suite in full; `make fmt-check` clean. The eight fixtures that exercise crossings and channels directly -- `thread_crossing_map_set_worker_exit`, `thread_crossing_deep_copy`, `thread_crossing_native_handle`, `gc_collect_preserves_thread_crossed_value`, `channel_bounded`, `channel_close_drain`, `array_push_threads`, `enum_cross_enum_variant_reuse` -- are clean 15 runs each, which matters more than a single pass here: every bug this area has produced has been a race that a single run hides. `valgrind --undef-value-errors=no --leak-check=full` on seven of them: 0 bytes definitely lost, and every error context byte-identical to the clean build's (35/2, 86/2, 341/2 on the three that have a second one, all inside Boehm's own `GC_mark_from`).


## A freed `Env` marked through the env pool's own stale `parent`: `make test-nogc`'s coin-flip segfault, root-caused (2026-10-05)

Three entries in a row recorded `ziman-nogc` as "flakily failing two or three fixtures per run, a different subset each time" and filed it as pre-existing and separate. That characterisation was wrong, and checking it properly was worth more than the three mentions put together: **every fixture tried crashes about half the time** -- `toml_basic`, `yaml_basic`, `map_set_builders`, `http_endpoints`, `csv_extended`, `regex_cache`, each 2-3 segfaults in 6 runs. The suite only ever showed three to six failures because most fixtures are too small and short-lived to hit it. The real figure is a coin-flip crash on any non-trivial program in a shipped build configuration.

**Root cause, from `valgrind` on the `nogc` build rather than from reasoning.** An `Invalid read` inside `gc_mark_env_chain` (`gc_env_roots.c:10`, the `env->count` load), on a 72-byte block -- `sizeof(Env)` -- freed at `interpreter.c:1862`, which is `STMT_WHILE`'s own `env_free(scope)`. The reading path is `gc_heap_collect` -> `mark_this_threads_roots` -> `gc_mark_interpreter_roots`, which marks every `Env` in this thread's env pool. `env_pool_release` calls `env_reset` (clearing the bindings, freeing each `strdup`'d name) but left `env->parent` pointing at whatever scope that `Env` had last been used under, and `gc_mark_env_chain` follows `parent` chains. So a block scope borrowed from the pool, given back, and then outlived by nothing more exotic than an ordinary loop's `env_free` leaves the pool holding a pointer into freed memory for the next collection to walk. One line: `env->parent = NULL` on release. `env_pool_acquire` already re-parents on the way out, so nothing ever observes the NULL -- a pooled `Env` is now actually what the pool's own comment always described, an empty parentless scope waiting to be reused.

**Why the real build never showed it, which is the part worth keeping.** A `make gc` build's `free` is `((void)(p))` -- zgc.h makes it a no-op -- so the dead scope was never reclaimed, and the stale `parent` pointer itself kept it *reachable*, so Boehm never collected it either. The ownership was wrong the whole time and the build was correct by accident, on two independent coincidences. A `nogc` build has a real `free`, which is precisely what made it visible there and nowhere else. That is an argument for `make test-nogc` being load-bearing rather than a curiosity: it is the only configuration in which this class of mistake can fail loudly at all.

**Verified.** `ziman-nogc` is **834/834, five runs in a row** -- restored to what `docs/MEMORY.md` last recorded before the regression crept in -- against three to six failures on every single run before. The six fixtures that crashed 2-3 times in 6 now crash **0 times in 8** each. `valgrind` on `yaml_basic` under `nogc`: **0 invalid reads and 0 use-after-free**, down from a run full of them, with the only remaining reports the two expected `gc_lookup` conservative-stack-scan contexts the Makefile's own `test-gc-scan` comment documents as "what conservative scanning *is*, not a bug". On the `gc` build, which this cannot have affected: suite 834/834 three times, `make test-pg` 11/11, `make test-mysql` 6/6, all nine standalone `gc_*` unit tests, the real app's suite in full, `make fmt-check` clean, `valgrind --undef-value-errors=no` unchanged (0 bytes definitely lost, same single Boehm-internal context).

**Two honest negatives.** The retention this also removes in the `gc` build -- a stale `parent` keeping a dead scope and everything bound in it alive -- is not measurable: a loop-heavy program's peak RSS is 40.9MB with the fix and 40.9MB without, run time identical, because the pool is bounded at a couple of dozen entries and Boehm's own 32MB initial heap dwarfs the difference. It was worth checking before claiming, and the claim does not survive the check. And **no dedicated regression fixture is added, because none of the four shapes tried actually reproduces it**: a `while` body with a nested block called 400,000 times; the same with six levels of recursion; a `return` out of a `while` body (which is the exact `env_free` the valgrind trace named); and that last one scaled 33x -- none produces so much as an invalid read under `valgrind` on the buggy binary. The trigger evidently needs a pool/collection interleaving these do not create, and shipping a fixture that passes on the broken build would assert coverage that does not exist. The regression coverage is `make test-nogc` itself, which catches this on essentially every run through the six fixtures named above; that it was *read* as pre-existing flakiness for three entries is the actual lesson, not a missing test.


## Native dispatch stops being a 247-entry `strcmp` scan per call: the implementation is resolved once per declaration (2026-10-05)

The one part of F2's original profile that had never been addressed, flagged as "explicitly out of scope" in a 2026-09-30 entry and visible in every profile taken since: `__strcmp_avx2` plus `native_lookup`, consistently around a fifth of all CPU time. The cause turns out to be as plain as it gets. `native_lookup` is a linear walk over every registered native, `strcmp` per entry, and `call_function` called it **on every single native call**.

**Measured before touching it.** 247 natives are registered. One run of `tests/lang/yaml_basic.zm` makes 9,595 native calls and **1,964,293 string comparisons** doing so -- an average scan depth of 205. The table is built once, before any Ziman code runs (`native.h` says so), and a `FunctionDecl`'s `name` never changes, so every one of those comparisons after the first per declaration re-derived an answer that could not have changed.

**The fix is the same move `env_lookup_resolved` already made for ordinary variables, one layer over.** `FunctionDecl` gains a `native_impl` field, resolved from `name` on that declaration's first call and kept. Same run afterwards: **23 lookups and 4,807 comparisons**, 23 being exactly the number of distinct natives the program calls -- a 409x reduction, and the floor, since nothing can resolve fewer times than once per function used.

Two details worth recording. The field is a bare `void (*)(void)`, not a `NativeFn`, because `ast.h` cannot include `native.h` (which needs `value.h`, which needs `ast.h`) -- and specifically a *function* pointer rather than `void *`, since converting between function pointer types and back is well defined where round-tripping one through an object pointer is not; `-Wpedantic`, which this build runs with, says so out loud and caught the first attempt. And the store/load pair is `__ATOMIC_RELAXED`: two threads reaching an unresolved declaration together both do the lookup and both write the same pointer, so the atomics are there to make that race well-defined rather than to coordinate anything, there being exactly one correct answer that never changes.

**Results, and one correction to how they were nearly reported.** `__strcmp_avx2` (16.2%) and `native_lookup` (10.1%) -- **26.3% of profiled CPU between them -- disappear entirely** from a `csv_extended` profile; neither appears above a 2% floor afterwards. A native-call-heavy loop (3 million `math.sqrt`/`math.cos` calls) goes **2.12s to 0.75s, 2.8x**; `csv_extended` itself 0.85s to 0.65s, about 24%. On `tests/bench/server_concurrency.sh` the first A/B looked like a **regression** (c=4 913 against 1065 req/s), which is impossible for a change that only deletes comparisons -- and was indeed pure noise: rebuilding both binaries once and interleaving three rounds each gives c=4 **1142 against 1076 (+6%)** and c=8 **1000 against 981 (+2%)**, the new build ahead in five of six paired runs. That benchmark had already produced a misleading non-interleaved pair earlier in this investigation; the lesson did not stick the first time, so it is written down here instead. The modest real-app figure is the honest one: that app does comparatively few native calls per request, so a fifth of CPU on a native-heavy workload is a few percent on it.

`GC_mark_from` now sits at 46% of that `csv_extended` profile, up from 37.7% -- not because it got slower, but because the denominator shrank. It is the next thing in front of anyone who profiles this interpreter.

**Verified.** `./tests/run_tests.sh` 834/834 on **both** builds; `make test-pg` 11/11; `make test-mysql` 6/6; all nine standalone `gc_*` unit tests; the real app's own suite in full; `make fmt-check` clean; `valgrind --undef-value-errors=no --leak-check=full` 0 bytes definitely lost with every error count byte-identical to the previous build (205 errors from 2 contexts on `csv_extended` either way).


## Going after `GC_mark_from`, finding it irreducible, and finding the real cost somewhere else entirely (2026-10-05)

The previous entry left `GC_mark_from` at 46% of a `csv_extended` profile as "the next thing in front of anyone who profiles this interpreter." Chasing it produced one useful negative result and one large unrelated win, and the negative result is worth as much as the win.

**What Boehm is actually doing, measured.** `ziman_arena_push_scanned_roots` hands Boehm the thread's whole `gc_heap` as a conservatively-scanned root range. Instrumented on `csv_extended`: **~16 MiB pushed per collection across 63 blocks, 187 MiB of conservative scanning in a 0.65s run**, 12 collections. A census of the heap itself (temporary, reverted) shows that is not garbage: the heap sits at 0.5 MiB for most of the run and balloons to **57 MiB live across 403,336 objects** while the fixture parses its deliberately-large 20,000-row CSV into JSON -- about ten objects per cell, which is simply what a boxed, immutable JSON representation costs. The census also reports **`atomic 0 KiB`**: there are no `GC_ATOMIC` objects in the `gc_heap` at all, so there is no pointer-free data in there to exclude from scanning.

So the 46% is two collectors traversing one genuinely large live object graph. Boehm has to see inside those objects, because they can hold a native handle disguised as an `int64` (arena.h's own reason for `arena_create_scanned` existing) and pointers into kinds that are still `GC_MALLOC`'d. **Three candidate fixes were ruled out with evidence rather than argued about.** Tuning collection frequency: `GC_FREE_SPACE_DIVISOR` swept from 1 to 24 changes nothing, 13 collections at every setting, because they are driven by heap expansion rather than free-space ratio (and higher divisors are strictly slower, 0.66s at 1-2 against 1.02s at 24). Marking atomic blocks: there are none. Pushing live objects individually instead of one range per block: 140,000-400,000 `GC_push_all` calls against a 4096-entry mark stack, which is exactly the livelock two entries ago. The honest conclusion is that this cost goes away only by completing the migration -- strings, `Env`, closures, `MapNode` -- until `gc_heap` objects hold no pointers Boehm needs to follow and the arena need not be pushed at all. That is the whole remaining program, not a change.

**Correction, same day (see "The gc_heap migration, measured and abandoned" below): that last sentence is wrong.** Completing the migration cannot retire this cost, because a native handle is retained *only* by a conservative scan finding its disguised `int64` (`handles.h` keeps the live-handle table unscanned on purpose), and `struct_obj_new` is already migrated -- so the `gc_heap` arena stays a Boehm root permanently however much else moves. Migrating more into it also *enlarges* the pushed range, and measures slower: ~10% on a `format`-heavy run, ~8-10% on a closure-heavy one, ~7% on the same closure change across eight threads.

**The win came from profiling a different shape.** A decimal-heavy loop (300,000 multiply-and-divide iterations) spends **no measurable time in marking at all**: `GC_build_fl` 19.8% + `GC_malloc_kind` 14.7% + `GC_allochblk_nth` 7.4%, **about 42% in Boehm *allocation***. The cause is in `bignum.c`. `mag_divmod` finds each quotient limb by binary search over `[0, BIGNUM_BASE)` -- about thirty bisection steps -- and every step called `mag_mul` to materialise `mid_limb * divisor` into two freshly `calloc`'d arrays, read once for a comparison and dropped. That is roughly sixty allocations per dividend limb, for a single-limb-by-multi-limb product that needs no allocation whatever.

`mag_mul_limb` (new) computes that product into a caller-provided buffer and returns its trimmed limb count, with semantics matching `mag_mul(&limb, limb == 0 ? 0 : 1, b, nb, ...)` exactly including the zero case. `mag_divmod` now allocates **one** product buffer for a whole division -- on the stack when it fits -- and reuses it for every probe and for the final subtraction. Limbs above the returned count are left as they were, which is safe precisely because every reader (`mag_compare`, `mag_sub`) is bounded by the count, and that is what makes one buffer reusable. `mag_mul`'s own `uint64_t` accumulator moved to the stack too for products up to 64 limbs (576 decimal digits, past every `decimal` this language has): it is pure scratch, and since `free` is a no-op in a collector build, every multiply had been handing Boehm another block to sweep for nothing.

**A trap avoided by measuring first.** The obvious-looking fix was to allocate digit arrays with `zalloc_atomic`, since `uint32_t` limbs are never pointers. That would have been a straight bug: `zalloc_atomic` maps to `GC_MALLOC_ATOMIC`, which does **not** zero, and every one of these sites is `calloc` precisely because the algorithms depend on zeroed limbs. The profile said allocation volume, not scan volume, so the right fix was to stop allocating rather than to re-tag the allocations.

**Results.** The decimal loop goes **1.18s to 0.37s, 3.2x**, with peak RSS unchanged. Boehm allocation in its profile drops from ~42% to 4.3%, and `mag_mul_limb` at 45.8% is now the arithmetic itself -- the right thing to be at the top.

**Verified, with the differential test this kind of change deserves.** Hand-rolling a multiply inside a division algorithm is exactly where a subtle wrong answer hides, so both binaries were kept and `tests/lang/bignum_mul_divmod_wide.zm` (new) was run through each: 238 lines of `bigint` and `decimal` multiply, divide and remainder, magnitudes up to ~90 digits, growing a value past one limb and dividing it back down across forty divisor sizes -- **byte-identical output from the pre-change and post-change binaries**, which is what the recorded `.out` file now locks in. Beyond that: `./tests/run_tests.sh` **835/835 on both builds**, `make test-bignum` and `make test-decimal` clean, all nine `gc_*` unit tests, `make test-pg` 11/11, `make test-mysql` 6/6 (both drivers decode numeric columns through this code), the real app's suite in full, `make fmt-check` clean, and `valgrind --undef-value-errors=no --leak-check=full` on the new fixture and `bigint_factorial_100`: 0 bytes definitely lost, single expected context.
